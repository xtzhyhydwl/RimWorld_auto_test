# 推时间：选哪个手段、推多少、怎么证明真的走了

> 时间只按 tick 推进，每次推进都要能用返回值证明「真的走了」。
> **要「推到某个 tick」或「推到某个事件发生」：直接用 §0 的 `advance`（游戏内闭环：`dsh.gamelink` 命令通道 + tick 边界刹车）。**
> 本文件的速度数字：§2.3 与 §0 是 **2026-10-25 本机实测**（`advance` 三程自测），§0.1/§2/§4 是 2026-10-24 实测；换机器先重标定（见 §2.2），不要沿用。
> 环境类数字（帧率、激活 mod、时间速度上限、日志路径）**不要照抄本文件**——跑 `node src/cli.js env-check --profile <p>` 取本次值
> （字段含义见 [环境探针](环境探针.md)；2026-10-24 已落地并真机验过）。

## 0 推时间：照这个做（2026-10-25 晚起）

**推时间只用这一条命令**。别的推时间手段（`play_for`、`step_game_ticks`、「算时间+延时」）**一律不用**。

```powershell
node src/cli.js advance --profile <p> --ticks 3000        # 相对：推 3000 tick（首选）
node src/cli.js advance --profile <p> --to-tick 62000     # 绝对：落到某个确定的 tick
```

**步骤（照做，不要发挥）**

1. 先确认实例在局内：`node src/cli.js call rimbridge/get_bridge_status --profile <p>` 的 `state.playable=true`。不在局内就先起殖民地。
2. **给相对 tick 数（`--ticks N`）**。只有"必须落在某个确定 tick"时才用 `--to-tick` —— 自己读 tick 再算 `当前+N` 会偏（实测 3000 只走了 2992）。
3. 判过：返回 `ok=true`、`stopReason="target"`、`reached == to`（相对模式则 `ticksAdvanced == N`）、`paused=true`。
4. 失败时按 `stopReason` 处置：`stalled` / `timeout` ⇒ 处理外部暂停（关窗口、结束教学步骤）后**用同一参数再跑一次**；`E_NO_ACK`（命令行报错）⇒ 实例没在泵命令，先确认已进图、`dsh.gamelink` 已启用。
   **不要**因为失败就换回 `play_for` / `step_game_ticks`。
5. 还不行 ⇒ **停手报【缺原子】**（SKILL.md §6），把 `stopReason` / 命令原文 / 候选目录路径写进报告。

**要「推到某件事发生就停」也用它**（2026-10-25 两轮真机验过）：

```powershell
node src/cli.js advance --profile <p> --stop-when "letter"            --max-ticks 300000
node src/cli.js advance --profile <p> --stop-when "message:离开了"     --max-ticks 200000
node src/cli.js advance --profile <p> --ticks 20000 --watch "letter;message"   # 只记录、不打断
```

- 探针写法：`letter` / `letter:<defName>[:<含词>]` / `message` / `message:<含词>` / `message:def=<defName>[:<含词>]`，
  多条用 `;` 分隔、**先命中者停**。
- 判过：`stopReason="probe"`，现场在 `stopPayload`（信件 defName/label 或消息 text/defName）。
  **跑满没等到是 `stopReason="maxTicks"`** —— 这两个必须分清，别把"没等到"写成"到了"。
- 现在只有**信件 / 右上角消息**两类探针。要"小人倒地 / 左侧 alert / 地图上出现某物" ⇒ **停手报【缺原子】**，
  不要拿 `--watch` 硬凑、也不要改回 `play_for` 轮询。
- 原子清单 + 组合配方（含"分段到检查点""提前 cancel 再续跑"）：[`docs/GameLink-协议-v1.md`](../../../../../docs/GameLink-协议-v1.md) §9。

**实测量级**（1.7.4985 / `voiced`）：`Fast` ≈180 tick/s；`Ultrafast` **3677–13743 tick/s**；20000 tick 墙钟 **1.8–5.4 s**（旧逐片实现 61.5 s）。
字段级契约：[`docs/GameLink-协议-v1.md`](../../../../../docs/GameLink-协议-v1.md)。

> **历史**（2026-10-25 白天）：`advance` 曾是「上位机逐片 `play_for` + 每片回读 + 末尾 `step_game_ticks` 兜底」，
> 那版的分段参数（`--chunk-ms` / `--landing` / `--slow-*`）已随实现删除。
> 下面 §0.1 与 §2.3 的数字是那一版测的，作为**手段本身的速率参考**仍然成立。

## 0.1 三种底层手段

| 手段 | 调用形状 | 速度（实测） | 什么时候用 |
| --- | --- | --- | --- |
| `step_game_ticks` | `{ticks, pauseFirst:true, timeoutMs}` | **精确但慢**：**每帧 1 tick**（`advancedFrames == advancedTicks`）⇒ 吞吐 = 帧率。**600 tick = 6010 ms ≈ 100 tick/s**（另三段 6007 / 6024 ms） | 要**精确 tick**、要把 `advancedTicks` 当断言 |
| `play_for` | `{durationMs, speed:'Fast'}` | **按墙钟，tick 不精确**：Fast `durationMs:1000` → **182 tick**（≈182 tick/s）；600 ms → 112 tick、800 ms → 144 tick | **长跑**、需要真实跑帧（刷渲染） |
| `set_time_speed` | `{speed:'Paused'|'Normal'|'Fast'|…}` | 只改速度，不推进 | 只调倍速；推时间仍靠上面两种 |

- `play_for` 的 `speed` 接受 `Normal|Fast|Superfast|Ultrafast`（`runs/tools.json` schema 原文）。
  **实测速率表见 §2.3**（`Fast` / `Superfast` / `Ultrafast` 都有数字了）；**「请求档位 ≠ 实际档位」是本条最重要的一句话**。
- 【实测】`play_for` 返回里的 `previousUltraSpeedBoost` / `restoredUltraSpeedBoost` 在**没传 boost 参数**时是 `null`（不是 `false`），而 `finalUltraSpeedBoost` 可能是 `true` —— **这三个字段拼不出"调用前后是不是同一个值"**。要举证"没开 boost"，看 `forceRequestedSpeed:false` + 自己没传 `ultraSpeedBoost`，**别用 `final` 单独下结论**。
- 仓库策略：推时间速度**上限仍是 `Fast`**（取向是宁可慢、不拿漏事件换时间）。
  `Superfast` / `Ultrafast` / `ultraSpeedBoost` / `forceRequestedSpeed` **要用户当次同意**。
  （2026-10-25：用户嫌 `Fast` 慢，当次同意用 `Superfast` 跑完最后一程 —— 这类同意是**按次**的，不构成新默认值。）
- `rimworld/play_until_letter` 也在工具表里，但它默认 `speed:4`（= `Ultrafast`）且默认带 boost ⇒ **不在默认可用范围**，本轮未实测。

## 1 推之前：三个前置

1. `get_ui_state.windowsForcePause === false`。为 true 时 `play_for` 会静默 0 tick（报文里只有一句 `Game was paused externally`，`success` 有时还是 true）。
   常见强制暂停窗口之一是主菜单：`close_main_tab{tabId:'main-tab:Menu'}`。注意两个工具的参数名不同——`close_main_tab` 收 `tabId`，`open_main_tab` 收 `mainTabId`。
   究竟当前有哪些窗口、窗口类型是什么，读 `get_ui_state` / `get_screen_targets` 本次返回，别背清单。
   【未验证】`step_game_ticks` 能不能穿过强制暂停：本轮**没有造出**强制暂停窗口，旧文档里「step 能穿透」这句话没有实测支撑，当**未知**处理（真遇到就先关窗口）。
2. 地图就绪。刚开完殖民地时 `step_game_ticks` 可能 `status=failed` 且 0 tick（`readiness=mapData` 只保证数据就绪）：
   推之前挂一次 `rimbridge/wait_for_game_loaded{readiness:'currentMap', pauseIfNeeded:true}`，失败就重试（`src/smoke.js` 就是这个模式）。
3. 推完要回读什么，先想好（见 §5）。

## 2 推的时候：四条纪律

1. **`step_game_ticks` 一律显式给全三个参数**：`{ticks, pauseFirst:true, timeoutMs}`。
   - `pauseFirst:false` 不是"先不暂停"，而是把"游戏得先暂停"的责任交给调用方；缺省时实测三次全 failed、0 tick。
   - 工具级 `timeoutMs` 默认 10 000：实测 `{2000,pauseFirst:true}` 不传 `timeoutMs` ⇒ 10017 ms 后 `status:timedout`、只走 **999/2000**。
   - **`timeoutMs` 是硬顶**：3000 tick 在 `timeoutMs:30000` 下仍 `status:timedout`、只走 **2996**。这是实现硬顶，不是估算问题——请求越多，越必须留足。
2. **预算按实测 ≈100 tick/s 算，留 100% 余量**：`timeoutMs ≈ ticks / 100 × 1000 × 2`。

   | 请求 tick | 纯推进（≈100 tick/s） | 建议 `timeoutMs` |
   | --- | --- | --- |
   | 600 | ≈6 s（实测 6.0–6.1 s） | 12 000 |
   | 1 200 | ≈12 s | 24 000 |
   | 3 000 | ≈30 s（实测 30 s 内跑不完） | 60 000 |
   | 6 000 | ≈60 s | 120 000 |

   慢帧机器上 100 tick/s 会更低 ⇒ **每段都看实际耗时**，出现「耗时接近 `timeoutMs`」就把余量加大、把段切短。
3. **判据是 `advancedTicks`，不是 `success` / `status`**：跨游戏天边界可能 `status=failed` 但推进有效；实测 `step_game_ticks` 请求 3000 得 `success:false` + `advancedTicks=2996`。按 `advancedTicks` 累计。
4. **分段**：每段显式 tick 数，段间回读业务字段 + 查新事件；不要一次推一大段再回读。

### 2.1 段长怎么定（最要紧）

- **段长不由"速度"决定，由被测事件可能的最小间隔决定。** 速度只决定「这段要花多久」。
- **`advance` 也一样：目标是"边界"，不是"最终时间点"。** `advance` 只保证"精确到点"，它**不知道这一程跨过了什么**。所以只要这趟可能跨过状态变化，就必须把它拆成多个 `--to-tick`（每个边界一次调用、到了先暂停采样再继续），而不是一口气推到最远处。
  必须当成边界的东西：**从中立转敌对/开打**、索粮期限到期、buff 到期移除、档位阈值（mal 0.40 / 0.75）、信件出现、任务阶段切换。
  实测教训（2026-10-25）：一次 `advance` 用 `Ultrafast`+boost（8800–12000 tick/s）推进，**几十毫秒就盖过了「中立→敌对」的窗口** —— 存档里只剩"已经敌对"的结果，那个时刻发生了什么全丢了。**宁可多停十次，也不要冲过一个窗口。**
- 现在的"停下来"**不是硬件触发**：靠 agent 轮询读到（`live --until` / `wait`）再下 `rimworld/pause_game`。
  ⇒ 从"事件发生"到"游戏真的暂停"之间有一段**盲窗**：一次工具往返 + 轮询间隔 + 人/agent 决策。
  段越长，盲窗覆盖到的 tick 越多，越可能**整段吞掉事件窗口**（事件发生了、后续 tick 把状态又推过去了，回读看不到）。
- 默认 **600 tick/段（≈6 s）**：本轮 5 段全部 600/600，成本 ≈6 s/段，可控。
- **窗口敏感用例 100–300 tick/段**：跨天边界、信件/事件刚触发、短 job（搬运、进食、开门）、任何"只在几十 tick 内可见"的状态。
- **宁可多分几段**：多一段只多一次工具往返（秒级），漏一次事件要整轮重跑。
- 分段不等于安全：段内事件仍可能被吞。真正要卡时间点，用**事件驱动**（`live --until` 挂后台 job）而不是"推完再看"；见 `日志与事件取证.md`。

### 2.2 换机器先标定

跑一段 `step_game_ticks{600,pauseFirst:true,timeoutMs:12000}`，取返回值里的 `advancedTicks` / `advancedFrames` / `DurationMs`（`19-step600-ce.json` 就是这三个字段）：

- `advancedFrames == advancedTicks` ⇒ 1 tick/帧，吞吐 = 帧率；
- `600 ÷ (DurationMs/1000)` = 本机 tick/s，用这个数重算 §2 的预算表。

### 2.3 速率与预算口径（2026-10-25 真机实测，`advance` 逐段回读出来的）

环境：1.7.4985 / profile `rhah`（16 mod；`activeMods` 一律以当次 `env-check` 为准）。量法：`速率 = tick 增量 / 墙钟`，每段都回读 `ticksGame`。

| 手段 / 档位 | 实测速率 | 证据 |
| --- | --- | --- |
| `step_game_ticks`（2000 tick/段） | **100 tick/s**（1 tick/帧） | `runs\2026-10-25-0002-v5\10-advance-selftest-3000.txt`：3000 tick / 30.1 s |
| `play_for` `Fast`（5000 ms 段，27 段） | **169–177 tick/s**（首段 169，其余 174–177；段越短这数越低 —— 400 ms 段只剩 ≈130，因为往返开销占比上去了） | 同目录 `12-advance-selftest-30000.txt` |
| `play_for` `Superfast`（15 s 段） | **320–652 tick/s**，但**有 29 段只有 59 tick/s** | 同目录 `13-advance-t22-superfast.txt` |
| `play_for` `Ultrafast` | 30 s 段 891–903 tick（**30 tick/s**）与 12 s 冲出 120000（**10000 tick/s**）并存 | V4 `runs\2026-10-25-0002-v4\push-ultra3.log` |

三条结论：

1. **事件之前：请求多少就是多少。** 新开的档、没事件的时候，`play_for` 就是按档位跑（`Fast` 实测 169–177、`Superfast` 320–652）。**不要因为"可能被强制慢速"就预先降档**。
2. **事件之后：游戏会钉回 1×。** `ForceNormalSpeed` 一生效，请求 15× 也只有 ≈59 tick/s（V5 实测连续 29 段如此）。这时候唯一的解法是 `forceRequestedSpeed:true`（`--force-speed`，`advance` 长跑档默认开）。⇒ 判进度只能看回读的 `ticksGame`。
3. **"冲出去"是片长的函数，不是档位的函数。** 裸调 `play_for{speed:'Ultrafast', durationMs:12000}` 当然会一次冲出 120000 tick（V4 就是这么丢的）；但 `advance` 是 1 秒一片、每片回读、接近就缩到 200 ms、最后交 `step` —— 一片最多走掉预算的 60%，**结构上越不过目标**。

**预算公式**（`advance` 内部已实现；调用方只需要估"这一程大概多久"）：

```
墙钟 ≈ (目标增量 − landing) / 有效速率 + landing / 100 + 段数 × 0.1 s
```

| 目标增量 | `Fast`（177 tick/s） | `Superfast`（320–650，但会被强制慢速段拉低） | 说明 |
| --- | --- | --- | --- |
| ≤ 3 000 | — | — | 全在 landing 内 ⇒ 走纯 step，**≈30 s**（2026-10-25 实测 30.1 s / 2 段） |
| 6 000 | ≈34 s + 落点 ≈20 s | ≈17 s + 落点 | 【估算】按上表速率外推 |
| 30 000 | **184 s**（实测 39 段） | ≈86 s + 落点 | `Fast` 那格是实测 |
| 46 200 | ≈261 s【估算】 | **255 s（实测 54 段，含 29 段被拉回 59 tick/s）** | 两档实际只差几秒 —— 见 §2.3 结论 3 |
| 79 200（22 游戏小时） | ≈450 s（≈7.5 min） | ≈420 s【估算】 | 都以"中途被强制慢速约 2 小时游戏时间"为代价 |

- **时间 ↔ tick**：1 小时 = 2 500 tick，1 天 = 60 000 tick ⇒ 6h=15000、12h=30000、18h=45000、22h=79200、24h=86400、33h=119700、48h=172800。
- **每段开销** ≈100–130 ms（5 s 段的墙钟是 5100–5131 ms）。⇒ 段不是越短越好，但**岸点（要采样的 tick）之前必须切小段**（§2.1）。
- **（历史）`--landing` 默认 3000 tick ≈ 30 s** 是旧逐片实现给"最后一段的不确定性"留的缓冲；现在落点由游戏内 tick 刹车保证，没有 landing 参数。
  只推几百 tick 仍然别用 `advance` 更省事的话——现在 `advance` 一趟往返就够，直接用它（几百 tick 也就几十毫秒）。
- 速率是**机器相关**的：换机器 / 换 profile（mod 数变多）先按 §2.2 标定一次，别照抄上表。

## 3 推多少

| 目的 | 量 | 依据（实测优先） |
| --- | --- | --- |
| **推到某个确定的 tick（检查点 / 取样点）** | `advance --to-tick <绝对tick>` | §0；绝对 tick = 事件当刻 tick + 增量（先 `call rimworld/get_game_info` 取当前 `ticksGame`） |
| 看 pawn 走几个格 / 做完一个动作 | 600 tick 起，逐段加 | 本轮 5 段 600/600，≈6 s/段 |
| 等游戏内一天（60 000 tick） | `advance`：Fast **≈340 s**【估算】；分段 `step`：**≈600 s**（≈100 tick/s） | 60 000 ÷ 177 / ÷ 100 |
| 只为了让渲染跟上、准备截图 | `play_for` 400–1000 ms（≈73–182 tick） | 实测 600/800/1000 ms → 112/144/182 tick；**必须做，不是可选**，机理见 §4 |
| 跨天/跨季节事件 | 分段 + 段间查事件（`live --until` / `runs/live/<p>.ndjson`） | 事件比 tick 更早给出信号 |

> 旧数字一律作废：`≈541–592 tick/s`、预算公式 `请求tick ÷ 400 × 1000`、"一天 60 000 tick ≈ 100 s"
> 都是按别的机型/别的口径写的，与本轮实测差 4–6 倍。

## 4 画面 vs 速度：step 不出帧

**机理（一句话）**：暂停态下硬推 tick，逻辑照跑、坐标是对的，但引擎**不连续出帧**，pawn 的**绘制位置不刷新** ⇒ 画面停在你推之前的样子。

【实测 2026-10-25，本机 1.7】

- 暂停态 `step_game_ticks` 推进后：`Avila` `(104,110)→(110,111)`、`Ren (110,115)→(114,113)`，坐标回读已变；
  但截图里两人**名字标签像素位移 = 0**；按格裁剪（`screenshot_cell_rect`）看，人仍在**旧格**。雪牛（Muffalo）同样冻结。
- 接着 `play_for` 真跑帧 400 ms（≈74 tick）⇒ 画面立刻追平；之后再 `step` 又冻。
- **人现场验证**：同一实例里手动放开时间，画面完全连续正常 ⇒ **游戏和引擎没问题**，纯粹是「暂停态硬推 tick」的观感问题。
- 环境侧不背锅：1.7 是 Waylith + Vulkan，Unity 图形参数无解析者；`-monitor` 被忽略、`-screen-width` 生效；
  桥接读到的 813×486 是 DPI=192 的虚拟化值，**与冻结无关**。

### 4.1 选型表

| 方式 | 适用场景 | 速度量级 | 画面是否会动 | 风险 |
| --- | --- | --- | --- | --- |
| **纯 step**（`step_game_ticks`） | 只推进**数值**：HP、计时器、`spawned`、库存计数、`advancedTicks` 类断言 | **最快**：≈100 tick/s（实测 600 tick ≈6 s） | **冻结**，pawn 停在旧格 | 期间的截图/人眼观察**一律不可用作证据**（画面是推之前的） |
| **纯 play_for**（`speed:'Fast'`） | 需要连续画面、要看动画/穿门/过程、要人眼观察 | ≈真实时间：按实测 182 tick/s，600 tick ≈3.3 s（**量级估计**，未单独实测 600 tick 整段） | **连续** | 慢于 step；tick 数不精确（墙钟驱动），不能当精确 tick 断言 |
| **混合**（step 分段 + 每段 `play_for`） | 既想快、又要画面基本连续（**推荐默认**） | 接近纯 step（每段多花 ≈100 ms） | **基本连续**（像快进） | 多一次工具往返/段；段长仍受 §2.1 约束 |

混合的固定手法：`step_game_ticks{300–600, pauseFirst:true, timeoutMs:12000}` → `play_for{durationMs:100, speed:'Fast'}` → 回读 → 下一段。

### 4.2 可复现判据：画面到底追平了没

1. **推进前**回读一次坐标（`rimworld/list_colonists` 之类），记下 pawn 的**旧格**。
2. `step_game_ticks` 推进后再回读坐标，算出**新格**（逻辑位置一定已经变了，这是"推到了"的判据）。
3. 用 `screenshot_cell_rect` **按格裁剪**：旧格矩形、新格矩形各裁一张（同一 `clipRect` 参数、前后可对照）。
4. 判读：
   - **新格裁剪里能看到人/名字标签、旧格里没人** ⇒ 画面已追平，可以截图取证；
   - **旧格里还有人** ⇒ 冻结帧，这次截图**作废**；先 `play_for` 400–1000 ms 再裁一次。
5. 不要用整图 diff 代替第 3、4 步：草会飘，120 tick 内整图可差 20 万像素，整图 diff 分辨不出「冻结」和「刷新」。

判据的强度分档见 `截图取证.md` §2.1；截图本身的坑见同文件 §3。

### 4.3 不要为了画面提速

**不要**为了"让画面动起来/看清楚"而擅自启用 `Superfast` / `Ultrafast`（含 `ultraSpeedBoost` / `forceRequestedSpeed`）——**需用户当次同意**。
要更快，就按 §4.1 的混合方式加段，而不是换速度档。

## 长推进先清场（2026-10-25 用户当场提出，硬要求）

推得越远，**原版/别的模组往图里塞的东西越多**，样本就不再干净。

- 实测代价：验「围攻儿童不参战」时推 75000 tick，图里混进 `Faction_14` 的 4 只虫子（(47–53,35–38)），
  同时殖民者被打到 2 倒地 1 乱窜 ⇒ **"谁去吃地上的食物""谁先倒地"这类地图级结论直接失真**。
- 判据：**被测事件之外**的敌对 pawn = 不带该事件的来源标记（如 RHAH 的 `RHAH_HungerMark`）/ 不在该 Lord 里。
  这类单位**直接杀掉**，不要留着当噪声；杀不掉就换一条更短的推进路线，别带着它们下结论。
- 做法：① 事件触发后立刻扫一遍全图 pawn（读存档一次即可）并清场；② 长期推进**分段**，每段之后复查"图里还有谁"；
  ③ 要验"吃东西/取物"这类结论，**食物自己放、放在被测 pawn 旁边**，不要指望战场自然产物。
- 单只 pawn 的自有字段（role / attitude / duty / curJob / 需求）不受旁边有别人影响 ⇒ 这类结论不必清场也能用；
  **地图级 / 归属级**结论必须清场。
- **更省的办法：不要重推，复用存档。** 把需要的阶段（进攻开始 / 战斗结束 / 某人倒地…）存一次档，之后每次都 `load_game` 回到同一个起点
  ⇒ **零推进、零新增干扰、起点逐字节一致**。实测：tick 78026 的围攻现场存成 `r10-assault.rws`，第二轮做投食对照时直接载入，没有再推 75000 tick。
  ⚠ `load_game`/`load_game_ready` 返回 `success:true` 之后，`spawn_thing` / `get_cell_info` 仍可能报 `No current map is active`
  ⇒ **载入后必须再过一道 `wait --scenario 进图且可玩`**，再发后续命令。
