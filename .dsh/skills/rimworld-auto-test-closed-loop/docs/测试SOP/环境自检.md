# 环境自检（每次开测前跑，不过就停手）

> 目的：确认这套环境**能摆条件、能读状态、能推时间**。缺一件，后面测出来的结论都不可信。
> 判据全部是可回读的字段或文件，不靠"看起来没问题"。

## 0 检查项

**硬性（不过就停手）**

| # | 检查 | 判据 | 不过怎么办 |
| --- | --- | --- | --- |
| 1 | 桥接与归属 | `status --profile <p>` 的 `bridgeResolution.ok = true` | 重启实例，再按「等桥接就绪」（硬性表下方）重新等 |
| 2 | 底座 mod 已加载 | `call rimworld/list_mods`：**按 `packageId` 判**：`base-mods.json` 里每个 `packageId` 都在返回里，且 **`enabled = true` 并且 `loadedInSession = true`**（桥接不可达时 `loadedInSession` 是 `unknown` —— **不确定就停手，不当作 true**）。`enabled` 只说明"写在 ModsConfig 里"，`loadedInSession` 才说明"这次真加载进去了"，两者差一个就会假通过。被测 mod 同样；`unsatisfiedDependencies` 为空 | 停手报；按 §3 补 |
| 3 | 加载顺序健康 | `get_mod_configuration_status` 无 ordering issue、`restartRequired = false` | 按提示调序；调完必须重启实例 |

等桥接就绪（按可靠性排序）：
1. `node src/cli.js call rimbridge/ping --profile <p>` 反复采样到 exit 0 —— **推荐**。注意：桥接还没监听时 `wait` 会**立刻 exit 1**（`ECONNREFUSED`），不会按 `--interval` 轮询，所以"等桥接"不能用 `wait`，只能这样外层重试。
2. `node src/cli.js wait --profile <p> --scenario 桥接可连` —— **只在桥接已监听之后**当一次性校验用（场景 = `rimbridge/ping` 且 `message=="pong"`）。
3. `node src/cli.js wait --profile <p> --source bridge-ready --condition-file ready.json`（`ready.json` = `{"path":"result.ready","equals":true}`）—— 语义最强（四道校验"这个桥接是不是我的"），但 **`result.ready` 的真实字段形状本轮没在真机上核过**，属【推测】可跑。

**必需（每次测试都要有；缺了停手，不降级）**

| # | 为什么要 | 必须有什么 | 判据 |
| --- | --- | --- | --- |
| 4 | **推时间**（`advance`）+ 事件跟读（`live --until`） | `dsh.gamelink` 在 profile 里且已加载 | `node src/cli.js link --profile <p> --cmd time.status` 返回 `ok:true`（**这就是"通道通了"的唯一判据**；没有它 = 不能推时间，别再想桥接退路） |
| 4b | 事件通道 | 同上 | `runs/live/<p>.ndjson` 在写 |

> `dsh.gamelink` **不是按需项**：推时间的命令通道走它（`runs\live\<p>.link\`），跟自动化测试已经绑死。
> 缺了就 `node src/cli.js mods add --profile <p> --package-id dsh.gamelink --apply` 然后重启实例。

**按需（这次测试用到才必须；缺了同样停手，不降级）**

| # | 这次要用 | 必须有什么 | 判据 |
| --- | --- | --- | --- |
| 5 | 摆/读小人状态 | `void.charactereditor` 在 profile 里 | `list_mods` 里它 `loadedInSession = true` |
| 6 | `ce/*` 反射工具 | 游戏侧 `BridgeTools\DSH.CEBridge\` 有 DLL | `call ce/probe` 有返回 |

```powershell
node src/cli.js status --profile <p>
node src/cli.js call rimworld/list_mods --profile <p>                 # 看 packageId / enabled / loadedInSession / unsatisfiedDependencies
node src/cli.js call rimworld/get_mod_configuration_status --profile <p>
node src/cli.js call ce/probe --profile <p>
node src/cli.js tools ce --profile <p>                                # 有没有 ce/* 工具
```

**`npm` 脚本要透传 `--profile`**：`npm run start -- --profile voiced`（`npm run <s> -- <args>` 才会把参数转给 `cli.js`；写成 `npm run start --profile voiced` 会被 npm 自己吃掉）。
`start` / `stop` / `smoke` **不给 `--profile` 现在会被拒绝**（有意：默认值 `vanilla` 是满配那一档，猜错就是一次满配置启动）。

**`list_mods` 的判法按 `packageId`，不要按名字**：返回条数随本机安装量变、`enabled=true` 的条数随 profile 变 —— **本次激活的 mod 数以 `node src/cli.js env-check --profile <p>` 的 `mods.activeModsCount` 为准；底座清单见仓库根 `base-mods.json`（11 项）。这里不写数字。** 而且名字被本地化成「核心」「副官语音 / Voice Deputy」——按名字查必错。能照抄的核对法：

```powershell
node src/cli.js base-mods --profile <p>                                          # ① 要哪几个 packageId（唯一真源）
node src/cli.js call rimworld/list_mods --args-file c-listemods.json --profile <p>   # ② 只列已启用（c-listemods.json 内容：{"includeInactive":false}）：断言 ① 里每个 packageId 都在这份已启用列表里，且 enabled=true **且 loadedInSession=true**（unknown 不当作 true；列表可以比 ① 多，比如被测 mod）
```

**JSON 落文件，不要内联**（PS 5.1 会吞引号）：`--args '{"includeInactive":false}'` 到 node 手上会变成 `{includeInactive:false}` ⇒ `JSON 解析失败`。用 `write` 工具把 JSON 落成小文件再 `--args-file` / `--condition-file`；**不要用 `Set-Content` 写 JSON**（PS 5.1 会把中文写成 GBK）。报错里带「Windows PowerShell 5.1 吞掉了双引号」就是这件事。

返回里每条 mod 都带 `packageId` / `enabled` / `loadedInSession` ⇒ 逐个对 ① 的列表即可；`includeInactive` 默认 `true`，不给参数就会拿到**全部已安装 mod**（条数随订阅与安装量变，没有固定值，别背数字）。

## 1 mod 清单

**不在这里抄清单**：底座 mod 的唯一真源是仓库根 `base-mods.json`（每条带 `packageId` + `why`；抄第二份必漂）。
`start` 之前会自动把缺的补进 `profiles/<p>/Config/ModsConfig.xml`——**幂等、只加不删**，补了什么会打印一行。
要加一个底座 mod = 在 `base-mods.json` 里加一行数据，**不改脚本**。只读对账：

```powershell
node src/cli.js base-mods                    # 清单本身（packageId + 为什么 + 补齐顺序）
node src/cli.js base-mods --profile <p>      # 这个 profile 还缺哪几个（不写文件）
```

被测 mod 的清单是另一份数据文件 `profiles\<p>\tested-mods.json`，由 `mods` 子命令读写 —— **不要手改 `ModsConfig.xml`**（怎么补见 §3）。

**实例没起也能查**（2026-10-24 实测）：`node src/cli.js mods list --profile <p>` 一次给出「底座 11 项（√=已在 ModsConfig）/ 被测 mod（含本机装没装）/ 人工加进来的条目 / 漂移与下一步」。

运行中的 `list_mods` 更权威：它反映**实际加载**结果，能抓到"ModsConfig 写了但加载失败"——`mods list` 在活桥接下会把被测 mod 的 `enabled` / `loadedInSession` / `unsatisfiedDependencies` 一起标出来。

## 2 现有 profile 现状

**不在这里写死数字**（profile 一变、机器一换，写下的"现状"就成了最大的坑）。以探针输出为准：

```powershell
node src/cli.js env-check --profile <p>     # 一次输出：进程 / 桥接归属 / 激活 mod / 加载顺序 / 能力 / 路径
node src/cli.js base-mods --profile <p>     # 只读对账：底座还缺哪几个
```

把 `env-check` 的输出当**本次实测事实**贴进报告；要挑轻档还是满配，按它输出的激活 mod 数决定。

## 3 缺 mod 怎么补

**用 `mods` 子命令，不要手改 `ModsConfig.xml`**：手改没有校验（写坏一个 `<` 就少几条 mod）、不幂等（重复加会多一行）、也不告诉你这个 `packageId` 本机装没装。

1. 确认 mod 已在游戏侧：工坊 `294100\<id>\About\About.xml` 或 `游戏目录\Mods\<目录>\About\About.xml` 里有这个 `packageId`。
   `mods add` 会自动扫这两处并告诉你**装没装**（扫不到只警告、不拒绝 —— 你可能还没订阅，或游戏装在别的路径）。
2. 登记被测 mod 并排进 ModsConfig（`--package-id` 是 `About.xml` 里的 `packageId`，不是显示名）：

```powershell
node src/cli.js mods add --profile <p> --package-id <packageId> --name <显示名> --why <一句话> --apply
```

3. 想先只登记、稍后再排：省掉 `--apply`，之后跑 `node src/cli.js mods apply --profile <p>`。
   顺序永远是「底座（`base-mods.json` 顺序）→ 被测 mod（`tested-mods.json` 顺序）→ 其余条目（保持原相对顺序）」；幂等，没变化不写文件。
4. `stop --profile <p>` → `start --profile <p>`，再跑 §0 第 2、3 项复核（改了 ModsConfig 必须重启才生效，`restartRequired` 会告诉你）。
5. 撤掉一个被测 mod：`node src/cli.js mods remove --profile <p> --package-id <id> --apply`。
   这是**唯一**会从 `activeMods` 删行的命令（底座只加不删；手加进 ModsConfig 的条目会被 `mods list` 单列成「人工加入」，不会被动）。

对账/查看随时可以跑（只读，不写文件）：`node src/cli.js mods list --profile <p> [--json]`。

不动用户正在玩的那一局；不为了补 mod 用 `--force`。

### 3.1 新建一个只有底座的 profile

要一个干净环境（底座 + 被测 mod，不掺人工条目），**不要手改 `ModsConfig.xml`**，照这四步做（本轮 C 代理实测跑过）：

1. 复制现成 profile 的 `Config\ModsConfig.xml` 与 `prefs.json` 到新 profile 目录（`profiles\<新p>\Config\`）。
   没有现成 profile 可复制时：先 `node src/cli.js start --profile <新p>` 让它生成，再 `node src/cli.js stop --profile <新p>`。
2. 逐条减掉多出来的条目，直到条数 = 底座 11 项（要减几个就跑几次；`mods list` 随时对账）：

```powershell
node src/cli.js mods remove --profile <新p> --package-id <要减掉的> --apply
node src/cli.js mods list --profile <新p>                  # 只读对账：还差几个、多了哪个
```

3. 加被测 mod：

```powershell
node src/cli.js mods add --profile <新p> --package-id <被测mod> --apply
```

4. 核对激活数是否等于期望（底座 11 + 被测）：

```powershell
node src/cli.js env-check --profile <新p>                  # 看 mods.activeModsCount
```

**代码行为（本轮读码确认，标【推测】未真跑）**：对一个**从没启动过**的 profile，`mods add --apply` 与 `start` 都会**静默跳过底座补齐**（提示「这个 profile 还没启动过」）⇒ 先有 `ModsConfig.xml`（第 1 步），再谈补 mod。

## 4 缺 CE 桥接（`ce/*` 工具不存在）

`node src/cli.js tools ce` 没有任何 `ce/*` ⇒ 反射路线没部署。

**部署现状（2026-10-24 实测）**：游戏侧 `BridgeTools\DSH.CEBridge\` 是指向仓库 `bridge\DSH.CEBridge` 的 **junction**，DLL 已就位；
`ce/probe` 在 1.7 上通过。注意 `Get-ChildItem -Recurse` **不穿过 junction**，看起来像空目录是误判。

缺了就重建 junction（或直接拷 DLL 到 `BridgeTools\DSH.CEBridge\`），重启实例，再跑 `ce/probe`。
CE 升级后 `ce/probe` 失败 ⇒ 反射用的类型/成员字符串对不上，重编（源码 `bridge\DSH.CEBridge\DSH.CEBridge.cs`）。
