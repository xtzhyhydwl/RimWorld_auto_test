# 阶段详法

**按需读**：只用读你当前阶段那一节。方法，不含任何具体项目案例。

---

## 阶段 0：意图澄清

**方法：设计树 + 轮次拷打**（不要自由聊天）。细则用 `grilling` skill。

前沿上**至少**要有这几个问题：

1. **要"效果"还是"这个东西"？**
   - **效果** = "玩家/单位获得某个结果"（更快、更多、更强）
   - **这个东西** = "世界里真实存在某个实体，它的状态由使用过程长出来"
   - **效果几乎总能更简单地实现**（改数值、加特性、加装备、加建筑）。
     **只有"这个东西"才要求实体、才值得付复杂度。**
2. **一句话说清用户会看到什么**（用户视角，不是实现视角）
3. **不可替代性**：同样的效果有没有更简单的实现？如果有，**为什么还做这个？**
4. **平衡支点**：它凭什么不会太强？（稀缺性？位置成本？时间成本？代价？）
   **答不出来 ⇒ 这个设计大概率会破坏平衡**
5. **明确"不做"**：划出范围之外的东西（防范围蔓延）

**产出**：`docs/<名>-设计意图.md`，≤1 页，**不含实现细节**。

**失败形态**：用闲聊代替拷打 ⇒ 关键分叉没被问到。
注意：**"要效果还是要这个东西"这一问必须在前沿的第一轮**——它是所有其他问题的前提。

## 阶段 1：约束与许可

| 项 | 查什么 |
| --- | --- |
| **依赖** | 要依赖别人的作品吗？**先查许可**：能不能改、能不能再分发。`CC BY-NC-ND` 类 ⇒ **只能依赖，不能修改或再分发** |
| **自己的许可** | 用什么许可？它决定你能不能借用别人的代码/素材 |
| **发布渠道** | 渠道要求的"依赖声明"与作品清单文件里的依赖声明**是两回事，都要写** |
| **目标版本** | 当前稳定版？跨大版本（引擎换代）怎么留位？ |
| **素材来源** | 美术从哪来？有没有披露义务？ |

**Gate**：没有一条约束能一票否决当前设计。

**失败形态**：设计做完才发现许可不允许 / 依赖不可分发。

---

## 阶段 2：机制侦察（静态取证）

**做什么**：列出这个功能要用到的**每一个**机制，逐个取证：

- 类型 / 方法 / 字段：**存在吗？全名？签名？**
- 配置/数据的**字段名**与取值域（写错通常只报运行期错误、不报编译错）
- **有没有官方先例**（有先例 = 风险低；没有 = 高风险信号）
- **挂载点性质**：是公共虚方法（可覆写、零补丁）还是必须打补丁？

**产出**：**符号台账**（append-only）。每条至少：

```
符号（全名）| 签名 | 确认级别（实测 / 反编译确证 / 转述 / 未确证） | 来源 | 反例（若曾被误写）
```

**另立一份"不存在"清单** —— 它和"存在"一样重要：
**"某类型在 A 命名空间不存在、在 B 命名空间才对"这类知识，猜是猜不出来的。**

**铁律**：

1. **关键结论必须用第二个独立工具复算。** 用错工具会得到**看起来完全合法**的假结论。
2. **先知道工具的失效模式，再信它的输出**（见 `环境陷阱.md`）。
3. **追不到证据的，只进"待确证"，不许进正式节。**
4. **反例要留着**——它防止下一个人（或下一个你）写出同一个错。

**失败形态**：单一工具的假阴性被当成事实（"这个类型不存在"其实是被工具静默丢弃了）。

## 阶段 3：可行性裁决

**这一步最容易漏、代价最大。**
作用：把"我知道很多"变成"**我明确知道自己哪几件事没把握**"。

**做法**：读台账，把每个**还不确定**的点列出来，逐条判定：

```
未知量 | 现在是"猜"还是"确证" | 猜错的后果 | 怎么才能确证（读代码? 跑一次?）
```

按后果分档，**这是排序依据**：

| 档 | 含义 |
| --- | --- |
| 🔴 **重构级** | 猜错 ⇒ 架构要改、核心要重写 |
| 🟡 **返工级** | 猜错 ⇒ 某模块重写，架构不动 |
| 🟢 **改名级** | 猜错 ⇒ 改名字 / 改数值 |

**Gate**：**没有任何 🔴**。有 🔴 ⇒ 二选一：**先解决它**，或**改设计绕开它**。**绝不允许带着 🔴 进阶段 4。**

**怎么做这一步（有效方法）**：
找一个**完全不知情**的读者（人或代理），**只给它文档**，让它回答：

- 「照这些文档，你能写出实施方案吗？」
- 「**哪里你必须猜？猜错会怎样？**」
- 「哪里你读到了两个不同说法？」

> **作者本人做不了这件事**——缺口在读者脑子里，而作者不缺任何东西。

**失败形态**：把"读了很多文档"误当成"没有未知量"。

## 阶段 4：设计（施工图）

**要求**：

1. **决策与证据分层**
   - 施工图 = **只放当前结论 + 指向台账的引用**
   - 证据、反例、更正历史 = **放台账**（append-only）
   - 混在一起时，读者分不清"这是当前结论还是历史反例"
2. **假设必须标"假设"**；**每个数字标来源**：`实测` / `取自 <文件:行>` / `假设`
   （**没标来源的数字会被当成实测传下去**）
3. **代码片段标"未执行"**，跑过之后才改成"已执行 + 证据"
   （未执行的示例代码会以"已验证"的姿态被抄进产品）
4. **跨文档引用只用「文件名 §节号」，不用行号**
   （行号在并发修改下不稳定；不同读取器对同一文件还可能给出不同行号）
5. **每个挂载点标注**：公共虚方法（零补丁）还是必须打补丁
6. **明确列出所有要打补丁的位置** —— 补丁数量直接决定跨版本升级的崩溃风险

**Gate**：阶段 3 那套"不知情读者"**能照它写出方案**，且它"必须猜的"里**没有 🔴**。

---

## 阶段 5：地基探针

> **它不是"验收"，是"刺探"。**
> 阶段 3 负责**列出**你不知道的事，阶段 5 负责**把它们变成事实**——**同一件事的两端。**
> 所以产出**不是"通过 / 不通过"，而是"设计需要改什么"。**

**做什么**：写一个**用完即弃**的最小实作，把阶段 3 的 🔴🟡 变成事实。

**承担三类任务，反馈去处不同——不要混**：

| 任务 | 例子 | 答案是"不能"时 |
| --- | --- | --- |
| **(a) 能不能** | 这个机制到底支不支持 | **先改设计**；设计改不动 ⇒ 才回退阶段 0 改需求 |
| **(b) 是多少** | 某个耗时 / 阈值 / 容量 | 填进设计，**不影响可行性** |
| **(c) 怎么样** | 观感、手感、平衡感受 | 回写设计 |

**要求**：

1. **每项一个可观测判据**（看哪个字段、哪行日志、哪张截图）
2. **尽量给每项配"阴性对照"**：把该实现**旁通掉**，重跑同一场景
   > **这是把"它工作了"变成"它因为 X 才工作"的唯一手段。**
3. **自检本身也要有对照**：故意验一个**不存在**的东西，确认自检会报错
   （否则"自检通过"毫无意义）
4. **探针代码不得被产品代码引用**；跑完销毁，**把销毁清单写进状态文件**
5. 结论**回写台账**并标【实测】

**Gate**：所有 🔴 已变成事实（结论可以是"能"/"不能"/"能但代价是 X"），**且设计已按事实更新**。

**环路：4 → 5 → 4。** 探针几乎总会改设计，这是正常的。
只有当 **(a) 的答案是"不能"且设计改不动**时，才回退阶段 0。

**什么时候可以省**：阶段 3 没有 🔴、且所有未知量都是 🟢。

**失败形态**：探针范围失控 ⇒ 变成"写了个迷你版产品"而没测到关键点。

## 阶段 6：产品代码

**顺序（接口先行，不要一次写完）**：

| 步 | 做什么 | Gate |
| --- | --- | --- |
| 6.1 | **骨架 + 配置/数据**（清单、依赖、能加载） | 游戏里能加载，能生成出这个物体 |
| 6.2 | **承重行为**（这个 mod 的核心那一件事） | 核心场景**无人干预**能自动跑通一次 |
| 6.3 | **边界与解绑**（死亡 / 离图 / 被俘 / 地图卸载 / 读档 / 传送…） | 逐条走完触发点清单，**每条之后回读状态** |
| 6.4 | **存档往返** | 存档 → 退出 → 读档，状态与存档前一致 |
| 6.5 | **贴图**（可并行、可后置） | 见下 |
| 6.6 | **发布准备** | 见阶段 7.3 |

**贴图的工作方式**：

**先留占位图 + 冻结「像素尺寸 / 锚点 / 方向数」**，让逻辑线先跑通；美术后补图。
**关键契约**：后补的图必须**同尺寸、同锚点、同方向数** ⇒ **替换 = 纯文件替换，不改任何配置**。

⚠️ 两条硬要求：
- **占位清单必须登记**，发布前"归零"是硬 Gate
- **像素密度一旦冻结就不要中途改**（上游一改，下游已出的图全废）

**每步的铁律**：

1. **回读状态确认，不要相信"调用成功"。** 接口返回成功只说明调用返回了。
2. **变化驱动，不是时间驱动。** 等一个**可观测条件**成立，不要定时等待。
3. **改了就立刻验证。** 数据/配置类改动常可热重载，代码类一般要重启——按这个决定批次。
4. **边界清单要穷举着走**，不要只测"正常路径"。

## 阶段 7：验收与发布

> **验收的主体是自动化测试，不是人。**
> 需求分析绕不开、编码现在也快，**所以最大的卡点是"验收能不能提效"**。
> **自动化测试设计得越好，需要人工补的部分越少——这是最该优化的方向。**

### 7.1 自动化验收（**先做，覆盖面尽量大**）

- 每条判据必须**可观测 + 可重复**（看字段 / 看日志 / 看结构化返回 / 看截图）
- **判据要在写代码之前定下来**（预注册）——否则会不自觉地照着结果调判据
- **等条件成立，不等时间**；**每步回读**，不信"调用成功"
- **每遇到一条"人要去看一眼"的判据，追问一次：「这个能不能变成可观测字段？」**
  —— 每变一条，人工验收就少一条

### 7.2 人工验收（**只做自动化做不到的**）

- 范围：观感、手感、平衡感受
- **把人工部分当成"自动化测试的缺口清单"**：每发现一处"这个本该自动测出来"，
  **回头把它补成自动化判据** ⇒ 下一次的人工部分就更小

### 7.3 发布准备

- 许可文件齐备
- **依赖声明**（作品清单文件 + 渠道要求的依赖声明 —— **两回事，都要写**）
- **占位资源归零**（占位贴图、占位配置、调试开关）
- **探针 / 实验代码零残留**（源码、配置、链接、构建产物）
- 跨版本留位

**Gate**：自动化判据全过 + 人工部分无遗留 + 无占位资源 + 无实验残留。
