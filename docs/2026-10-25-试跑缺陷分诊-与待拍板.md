## 3 我对你两个方案的评估

### 3.1 「指针 → 纯净 MD 列 mod 清单，agent 运行时自己配」——机制已经存在，别新造
- **已经就是这个形状**：仓库根 `base-mods.json` 是底座 mod 的唯一真源（6 项：Harmony/Core/RimBridgeServer/GameLink/CharacterEditor/AutoTest）；`start` 前会自动把它补进 `profiles/<p>/Config/ModsConfig.xml`，**只加不删、幂等**；`node src/cli.js base-mods --profile <p>` 可对账、只读。
- 因此**不需要改脚本结构**，也不存在「模组配置写死」问题：加一个底座 mod = 在 json 里加一行数据（符合你「加一条数据、不改三处」的原则）。
- 真正的缺口是**文档没把这件事写给 agent**：`SKILL.md` §2 只写了 `status` 和 `list_mods`，没写「底座从哪来 / start 会自动补 / 怎么加减」。所以修法是补文档（C 类），不是改架构。
- 结论：**可重复**（清单是数据文件、幂等补齐、可对账），你这套想法不用改，只需要让文档说清它已经存在。

### 3.2 「环境事实改成探针」——可行，而且比现状好
- 现状的坏处正如你说：`docs\` 里写死的「桥接就绪 7.6 s」「8 个 mod」明天就可能是错的，而 agent 会当真。
- 方案：`docs\测试SOP\环境探针.md` 只写**要测什么 + 怎么判**（不写答案），配 `node src/cli.js env-check`（一条命令跑完：进程/桥接归属/激活 mod/加载顺序/CE 可用/时间速度上限/日志路径），输出「本次实测事实」。
- 这样事实每次由探针重新生成，写进 agent 自己的上下文；文档只保留机制说明（哪些字段、什么算合格），不会过期。
- 代价：多一个命令 + 一份薄文档；收益是「环境事实」这一整类缺陷以后不再复发。
