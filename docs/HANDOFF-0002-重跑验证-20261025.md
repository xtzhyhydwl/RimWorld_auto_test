## 0. 先做这一步：把「推时间」做成 CLI 能力（推荐，再跑验证）

**为什么**：上一轮的推时间循环是**代理自己算的**（读 tick → 算剩余 → 自己决定下一段推多久），V4 里就是因为 `Ultrafast` 突发冲刺把检查点冲过头、C 断言直接丢掉。这类确定性计算不该由模型心算，应该固化成一条子命令。

**要加的能力**（加在 `src/cli.js`，符合「长期能力进统一入口」，不要写一次性脚本）：

**对外只暴露一个参数**——目标 tick。速度、分段、落点、暂停全部内部决定，代理不需要算、也不该算：

```
node src/cli.js advance --profile rhah --to-tick 79200
# 成功：exit 0，stdout 打印 {"from":..., "to":79200, "reached":79200, "segments":n, "paused":true}
# 失败：非零退出 + 最后几段数据（推不动 / 超时）
```

（`--speed`、`--chunk-ms`、`--landing` 只作为调试用的可选覆盖，默认值写死在实现里：`Ultrafast`（不带 boost）、`chunk-ms 5000`、`landing 3000`。）

行为（内部循环，一次调用完成）：

1. `get_game_info` 读当前 `ticksGame`；若已 ≥ 目标，直接进第 4 步。
2. 剩余 > `landing`（建议 3000 tick）时：按 `chunk-ms` 调 `play_for {durationMs, speed}`，**每次调用后回读 `ticksGame`**，用「墙钟 / tick 增量」估算速率，动态调下一段时长，保证**不越过目标**（剩余 < 2×预计步长时自动缩短）。
3. 剩余 ≤ `landing` 时改用 `step_game_ticks`（精确 N tick）逐段补齐，直到 `ticksGame == 目标` 或差 ≤ 1 tick。
4. 暂停（`play_for` 的 `durationMs:1` 或专用 pause 工具，二选一，实现时定），**停住后返回最终 `ticksGame`**。
5. 任一步出现「连续两段 tick 增量为 0」⇒ exit 非零，并把最后几段数据打到 stderr/`--out`（不要静默重试）。

**边界要求**：速度白名单 `Normal|Fast|Superfast|Ultrafast`，**拒绝** `ultraSpeedBoost` / `forceRequestedSpeed`；单次 `play_for` ≤ 40 秒（CLI 60 秒 GABP 超时会掐断）；`--to-tick` 必须大于当前 tick；全程可 `--out` 落盘。

**做完自测**：起一次实例，`advance` 从一个 tick 推到 +3000、再推到 +30000，核对返回的 `ticksGame` 与存档里的 tick 一致，然后才拿它跑 §5 的断言。

> 如果时间不够做这个能力，退化方案：本轮仍用 `Fast`（180 tick/s）+ `step_game_ticks` 落点，**禁用 Ultrafast**，并接受验证慢 8–10 分钟。

## 4. 推时间的正确姿势（上一轮的教训）

- **巡航用 `Fast`**（3 倍，实测 ≈180 tick/s）：`call rimworld/play_for` 参数 `{"durationMs":40000,"speed":"Fast"}`，单次**不要超过 40 秒**（60 秒会撞 CLI 的 GABP 超时）。
- **`play_for` 必须显式传 `speed`**，不传会按当前档跑（实测退成 1 倍 ≈60 tick/s）。
- **落点用 `step_game_ticks` 精确补**到目标 tick（`play_for` 只负责大段）。
- **采样前先暂停**：暂停后状态冻结，`save_game` 再解析，采样不会丢。
- 进度按 **`ticksGame`**（`call rimworld/get_game_info` 的字段）判，不按墙钟。
