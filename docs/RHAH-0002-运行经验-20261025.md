# RHAH 0002 运行经验（2026-10-25）

> 来源：`docs\RHAH-0002-验证-1.7-V4-20261025.md` 与 `runs\2026-10-25-0002-v4\`（总墙钟 39m45s、CLI ≈95 次）。
> 这些是**下一次验证一定会再踩**的坑，按发生顺序记。

## 1. 只换 DLL + Api 不够，工坊的 Defs 树也要整树同步

- 现象：换了 `HungerAndHavoc.dll` + `HungerAndHavoc.Api.dll` 后，buff **完全不出现**，日志报缺 `RHAH_ArmedDemandEndurance`。
- 原因：工坊里那份 `1.7\Defs` 是作者 1.1.4 的旧版，没有新 hediff 与 3 条 `RHAH_Thought_SiegeFury*`。
- 做法：把仓库 `1.7\Defs` **整树**同步进工坊（先备份），再起实例；测完整树还原。
- 教训：`Def` 类改动 = 二进制 + Defs **两件套**，只换一件就是空转。

## 2. 杀掉持有桥接连接的后台 job → 游戏 CRASH

- 现象：`CRASH: Connection is not active`，丢档重开一轮。
- 原因：后台 job 持有 GABP 连接；被 kill 时连接被强断，游戏侧判定为异常。
- 做法：要么让它自然结束，要么用 `stop --profile <p>` 正常关；**不要 kill 正在跑 `call`/`wait`/`live` 的 job**。

## 3. `Ultrafast` 不可靠，不能用来「精确落到某个 tick」

- 现象：同一批 30 秒段，有的只走 **891–903 tick**，有的**一次冲出 38k–59k tick**；+86400 / +129600 两个检查点被直接冲过，C 因此没测到。
- 结论：`Ultrafast` 只能用来「大段逼近」，**落点必须用 `step_game_ticks` 补**（精确到 tick），采样前先暂停。
- 另：`play_for` **不传 `speed`** 会按当前档跑（实测退成 1 倍、≈60 tick/s）；推时间一律显式传 `speed`。

## 4. 断言要分家

- 「无人因**饥饿**倒地/死亡」和「无人死亡」不是同一条。V4 里的 2 例死亡带着 `Gunshot`/`Crack`/`Bruise`、营养不良只有 0.556/0.641，是**战斗伤亡**，不应算作 buff 失败。
- 下一轮只推到 **+22 小时（开打之前）** 验饥饿曲线与三档，战斗伤亡另立断言。

## 5. 关键实测数字（可复用）

- 营养不良增速 ≈ **2.08%/h**；`mal=1.0` 致死；原版 `extreme`（≥0.8）对意识 `setMax 0.1`。
- 到场营养不良实测 **0.500**（10/10），而设置面写 0.25——`RHAH_FamineArrival` 只把它当**下限**，来源未查明。
- `play_for` 参数名 `durationMs`；单次 ≤40 秒（60 秒会撞 CLI 的 GABP 超时）。
