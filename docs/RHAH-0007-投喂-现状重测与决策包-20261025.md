## 4 四个待决（**这一节就是要用户回答的东西**）

每个都给了推荐答案。「推荐」= 我按代码现状与代价选的，不是票的原话；与票不一致处已标出。

### D1 允许「先给一部分、之后还能再给、还能换种类」吗？
- **推荐：允许，但用「按 def 记账」实现，不改成营养累计。**
- 理由：票认为必须改成「营养累计」（牵动 `RHAH_ArmedDemand.ArmedFoodNutritionDelivered`，而那份字段**实跑二进制里没有**，会与 0006 重建绑定）。实际上 `FoodStillNeeded:396-407` 只想知道「这个人收够 N 份没有」——把单个 `foodDef` 换成 `foodDef → 已收数` 的小表就能同时支持混给与计数，语义与现在完全一致（现在也是数「份」，不是数营养）。
- 代价：`LordJob_RHAH_Visitor` + `RHAH_FoodHandoff.Received` + 菜单过滤，约 60 行；存档加一个 `foodReceived` 节点。
- 若答「不允许」：只做「该 def 已不可得时清锁」（`RequestedFood` 返回 null 即可），10 行，但玩家仍会被「一次只能一种」困扰。

### D2「可给食物」的范围
- **推荐：玩家携带 + 仓库内 + 地上散落都算，但按「在有效仓储里 / 是玩家派系」排序在前；`IsInValidStorage` 只做排序权重，不做硬过滤。**
- 硬条件只留两个：**点击的殖民者可达可预留**（否则点了也走不到，`JobDefOf.GiveToPawn` 由他执行）、**接收者吃得下**（见 D4）。
- 代价：`CollectFood` 排序键改写，约 30 行。副作用：菜单变长；「远处虫胶」仍可选但排到后面。
- 若答「只要仓库」：`IsInValidStorage` 硬过滤 + 玩家背包，≈ 15 行，但玩家「我就想用地上那堆」会被砍。

### D3 老存档能接受到什么程度？
- **推荐：写一次读档迁移，旧 `foodDef` 转成「该 def 已收数」一条；不让正在等的老档重新计数。**
- 理由：迁移成本很低（`LoadingVars` 里读旧键建表，5–10 行），而「白给过的饭不算」是玩家能立刻看见的倒退。
- 若答「不写迁移」：`ExposeData` 里旧键读出来直接丢弃，老档等待者重新计数（等于白吃）。

### D4 婴儿食物走「投喂」还是走「照护」？
- **推荐：走照护——菜单对「不能自食」的接收者改派原版 `BottleFeedBaby`（有 Biotech 时），不再走 `GiveToPawn`；同时把 `preferability >= MealAwful` 从过滤降级为排序，让 `BabyFood` 能进菜单。**
- 理由：`GiveToPawn` 对婴儿是死路（食物进背包也不会被吃，`RHAH_ReliefFood.Reject:103-106`），无论菜单怎么改都不会让他吃饱；原版瓶喂才是「喂进去就算」的那条路，且本模组已在 `RHAH_BabyCarePatch` 上动过同一处。
- 代价：改 `GiveFood` 的 job 选择（≈20 行）+ 食物过滤（≈10 行）+ 一次真机验证；**新增一条未验证依赖**（§3.2 的 ⚠）。
- 备选（若不愿碰原版照护）：投喂菜单对婴儿继续灰掉，但 tooltip 改成「请让照护者喂」，并让 `WorkGiver_BottleFeedBaby` 能真的对来客婴儿生效——这是另一张票的体量。
