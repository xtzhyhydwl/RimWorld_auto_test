## 问题

默认设置下，该离场的来客永远走不出殖民地的建筑。小人一旦进入 `Leaving`——停留到期、请求被拒、或倒地后被救起——殖民地的门就一直锁着他：不敲门，也不凿墙，只在屋里来回游荡。报告玩家原话：

> 小人已经变回中立了，不是殖民者，也不是囚犯。按逻辑他早该走了，但他没走。他想走，却出不了殖民地的门；他不砸墙也不敲门，什么都不做，只在那个房间里打转。

复现：把任意来客关进玩家建的带门房间，再把他推进 `Leaving`（用 `RestoreDeparture` 让停留到期、拒绝一次请求，或 `RHAH_Api.SetLifecycle(pawn, Leaving)`）。他会去找出口，失败，最后干脆没有任何 job。

这个修复的早期版本失败在反面：门对所有人锁死，而凿墙的 giver 是 DutyDef 里的并列节点，于是离场来客身边明明有能用的门，却去砸墙。

## 原因

两处互不相关的成因，都得修：

1. **门对错的人关上了。** `Source/Pawn/RHAH_DoorPatch.cs` 对 `Building_Door.PawnCanOpen` 做 Postfix，只要该小人属于本 mod 五个态度派系中的活跃来客，就强制 `__result = false`，除非玩家开了 `famineVisitorsOpenDoors`（默认关）。`Leaving` 不在豁免之列，于是本该走出去的小人被锁在里面。
2. **没有出口可走时没有兜底。** 离场车道依赖 `RCellFinder.TryFindBestExitSpot`，用默认的 `TraverseMode.ByPawn`。门一关，region graph 就不让小人穿过门（`Verse.Region.Allows`），搜索返回 false，`JobGiver_RHAH_Leave.TryCreate` 返回 `null`，`JobGiver_RHAH_Visitor` 把它继续往上抛，小人最终没有 job。原版对“走不出去”的兜底就是随便游荡，玩家看到的就是这个。

## 改动

16 files, +171/−27。**没有动任何 Def**：`1.6` 与 `1.7` 两份 `RHAH_Duties.xml` 都与 `fbca6ca` 逐字节相同（blob `ccd5669`），所以 XML 里没有任何一处引用旧二进制解析不到的类。

### 1) 离场来客可以开门

`RHAH_DoorPatch` 现在没有设置、也没有猜测，只有一条固定级联：

````
pawn irrelevant (!__result, no faction, player faction, not an attitude faction)  -> keep vanilla
no RHAH comp / not an active visitor                                              -> keep vanilla
hostile threat on the map                                                         -> false
lifecycle == Leaving                                                              -> keep vanilla (door opens)
everything else (Arriving / SeekingFood / Fed)                                    -> false
````

敌情仍然优先，而且是**故意**排在离场分支之前：离场分支是个 `return`，会把原版结果原样留下，如果它先跑，地图上有敌人时门就白开了。围城期间，离场来客照样待在屋里。

### 2) 没有出口时凿墙出去

`JobGiver_RHAH_Leave.TryCreate` 现在负责整条离场车道：出口搜索失败时，它换上离场 duty（`RHAH_VisitorRules.CreateLeaveDuty()`，`canDig = true`），再调用 `JobGiver_RHAH_DigOutWhenNoExit`——一个 25 行的子类，只转发到原版 `JobGiver_ExitMapBest`。原版只在 `duty.canDig && !pawn.CanReachMapEdge()` 时凿墙，所以有可达出口时仍然只产生一个普通 `Goto`；只有真正被困住的小人才动手砸东西。

为什么不做成 Def 节点，分两步说。第一，原版 `JobGiver_ExitMapBest.TryGiveJob` 是 `protected`，没法当作普通子节点塞进 DutyDef——想复用就必须有子类，而写进 XML 的子类就是 XML 新增的依赖。第二，把这个子类当作**并列**子节点，会把两个不同层次的东西摆在一起：`RHAH_VisitorLeave` 现在已经有一个子节点 `JobGiver_RHAH_Visitor`，它就是整张分发表（战斗 → 离场 → 乞讨 → 偷窃 → 等待），而凿墙 giver 只是其中一条车道里的一个分支。并列会让“他凿不凿墙”取决于两行 XML 的先后顺序，还会重新造出上面那种加载期耦合。所以兜底放在 `JobGiver_RHAH_Leave.TryCreate` 里、出口搜索返回空的时候调用：一个地方负责“这个小人的离场怎么做”，`RHAH_VisitorLeave` 与 `RHAH_VisitorSeek` 保持对称（都是单一身份节点），`defName`——也就存档契约——不受影响。

### 3) 删掉 `famineVisitorsOpenDoors` 设置

删除项：字段、它的 `Scribe` 行、两处 UI（`ModEntry` 与 Iris 菜单页）、三份语言文件，以及 `docs/references/save-ownership.md` 里那一行。

这个开关的两个位置都站不住。**关**（默认）就是上面这个 bug：必须走的小人永远卡住。**开**是反面失败：还在找吃的来客会走进仓库自己拿，而“你得喂他们”这条设计正建立在不能自取之上。改成“离场来客可以开门”也一样不行——一个关掉就会重现本 bug 的选项不叫选项，而它开着时，地图上有敌人，离场来客照样能开门。它本来也不是授权开关：Postfix 只能把 `true` 改成 `false`，玩家从来没有真正决定过谁能开门。真正的区分维度是生命周期，现在硬编码了。

### 4) 冷却、零分配与旧存档

出口搜索失败（原版的 spot 搜索和凿墙 giver 都算）会给小人挂 1 游戏小时（2500 tick）冷却，并发一个原地等待 job（120 tick）；冷却判断在任何 `RHAH_PawnSnapshot` 构造**之前**，所以冷却期间既不搜索也不分配。冷却表是 `ConditionalWeakTable`，不落盘：读档最多多搜一次。

旧存档故意不重建。落盘的离场 duty 可能还带着 `canDig = false`，但那不再是死路，因为离场车道在兜底之前会自己换上 `CreateLeaveDuty()`（早期草稿是从 `LordToilTick` 重建 duty，现在去掉了——代码更少、结果一样、不碰任何存档路径）。保留了一处相关修复：进入 `Leaving` 时清掉该小人的可达性缓存（`RHAH_ApiHost.ClearPawnReachabilityCache`），否则门还关着时算出的那行“到不了”，会在门开了之后仍把小人留在凿墙车道上。

## 行为变化与兼容性

玩家可见：

1. **离场来客现在会开殖民地的门。** 之前：默认设置下永远不开。
2. **`Arriving` / `SeekingFood` / `Fed` 的来客，门照样关着**——不变；“仓库不许自取”这条意图完好。
3. **地图上有敌对威胁时，所有来客的门都关，包括正在离场的小人。** 比这个修复的上一个版本更严，那个版本不管敌情都放离场者过。
4. **走不到地图边缘的来客会砸墙或砸门出去**，留下一个永久的洞。这是有意的（原版“被困来客凿墙出图”的行为，商队也用它），只在人真的走不出去时发生。
5. **“饥荒时来客可以开门”复选框没了**，原生设置窗口和 Iris 菜单页都没有了。
6. **旧存档里残留的键被忽略。** `Scribe` 调用已删除，值既不读也不迁移；没有新增存档键。
7. **没有人被传送。** 出口仍然靠走到出口格、由原版 `JobDriver_Goto` 触发 `ExitMap`。
8. **`RHAH_VisitorLeave` 的 `defName` 不变**，现有存档不受影响。

二进制：**本 PR 只含源码，不含任何程序集**（工作区里的 DLL 是构建产物，不是交付物）。两个目标都能用这些源码在本机构建出来：`1.7` 对着 Steam 安装构建，`1.6` 用 `dotnet build -p:RimWorldVersion=1.6 -p:RimWorldDir=<1.6 安装目录> -p:IrisMenusDll=<1.6 IrisMenus> -p:OxygenDslBuildDir=<1.6 OxygenDSL>` 构建 ⇒ **0 警告、0 错误**。**`1.6` 与 `1.7` 两个版本仍需维护者用各自版本的参照程序集重建后再发版**，因为本 PR 不发布任何程序集。

原来的阻塞点是通过构造消掉的，不是靠发二进制：因为**本 PR 完全没改 Def**，XML 不会引用现有程序集解析不到的类，所以拿当前 DLL 检出构建后能正常加载——只是还没有这个修复。这个修复的早期草稿确实加过一个 Def 节点，*那才是*让旧二进制在加载期致命的做法。
