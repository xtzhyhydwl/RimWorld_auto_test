### 1.2 冷却是怎么来的、空窗在哪（`f1e97c0` 行号）

`JobGiver_RHAH_Departure.cs`（`f1e97c0`）在两种情况下返回 null：

| 旧行号 | 情形 | 后果 |
|-|-|-|
| `:47-50`（`:49` 返回 null） | `SearchDue` 为假 ⇒ 处于 2500 tick 冷却 | duty 给不出 job |
| `:74-76`（`:76` 返回 null） | 当次 `base.TryGiveJob` 搜不到 ⇒ 写入冷却 | **同一趟思考里**就给不出 job |

冷却常量 `:14` = `GenDate.TicksPerHour` = 2500 tick；缓存 `:18-19`（`ConditionalWeakTable`，不落盘）；`base.TryGiveJob` 是 `JobGiver_ExitMapBest`（区域 BFS + 最多 30 次边缘采样），冷却只为了压掉它的重复成本。

### 1.3 为什么"返回 null"就等于"绕过模组闸门"（[IL]，1.7 反编译）

1. **同一趟思考就会落到求食**：`Verse.AI.ThinkNode_Priority.TryIssueJobPackage` 对子节点逐个调用，`result.IsValid` 为假就继续下一个；`RHAH_Duties.xml:17-22` 两个节点都给不出时，duty 的 `ThinkNode_Priority` 返回 `NoJob`。上一层 `Data\Core\Defs\ThinkTreeDefs\SubTrees_Duty.xml:11-38` 的 `LordDuty` 是 `ThinkNode_Duty`（`:13`）→ **`JobGiver_GetFood`（`:22-24`，`minCategory = UrgentlyHungry`）** → 游荡（`:26-36`）。也就是说：**不是"下一 tick"，是同一次 `TryIssueJobPackage` 里**。
   - 这一条同时否掉了候选 (b)"缩短冷却"：只要某一趟返回 null，那一趟就会被 GetFood 接走；把冷却改成 0 也只会让"返回 null 的那一趟"变成每 tick 都有，问题不减反增。
2. **原版求食不认本模组的闸门**：`RimWorld.JobGiver_GetFood.TryGiveJob`（反编译 `:51-129`）走 `FoodUtility.TryFindBestFoodSourceFor(..., allowForbidden: false, ...)` → `Ingest` / `TakeFromOtherInventory` / `PredatorHunt`。模组在 `JobGiver_GetFood` 上确有两个 Postfix，但都**不构成闸门**：
   - `Source\Pawn\RHAH_ReliefFoodPatch.cs:14-46`：只处理"已 `HasBeenFed` 且玩家开了 `ignoreReliefAfterFed` 且目标是赈灾区食物"这一窄情形，其余一律放行；
   - `Source\Pawn\RHAH_StayWorkPatch.cs:13-25`：`__result == null` 时才补一个"啃树皮/墙皮"（那条有自己的闸门）。
   - ⇒ `Leaving` 的来客只要能开门、饿到 `UrgentlyHungry`，就会拿到原版 `Ingest`，**不经过** `RHAH_BehaviorGate.FeedFromRelief`（`Source\Pawn\JobGiver_RHAH_Visitor.cs:98-105`）、`Steal`（`:125-132`）与 `RHAH_FoodHandoff` 的接收者记账。这正是 S1。
3. **门放行让这条路变可达**：`f1e97c0` 的 `RHAH_DoorPatch` 对 `Lifecycle == Leaving` 提前返回，不再把 `__result` 置 false（复审 §2 表第 4 行）。改动前门是关的，这条路径理论存在但走不通；现在走通了。

### 1.4 本轮没有改的东西（S1 之外）

- `CanWalkOut` 为假（`:58-61`）与 `CanDepartAlone` 为假（`:64-67`）仍然返回 null。它们**不在冷却窗口内**（是身份/携带状态判定），不在 S1 范围；改动它们会牵动幼童/抱持者协议。
- `CanOrderLeave` / `Allows(ExitMap)` 为假仍然返回 null，同上。
- 冷却长度、`ConditionalWeakTable` 结构、Scribe 键：一律未动。

## 二、修法详解（新行号，`6a2cbb4`）

### 2.1 三处改动

| 位置 | 代码意图 |
|-|-|
| `Source\Pawn\JobGiver_RHAH_Departure.cs:16-19` | 新增常量 `CooldownWaitTicks = 120`，注释写明三件事：原版回退链是 GetFood→游荡、门放行后求食那条路走得通且不认闸门与记账、因此"搜不到"也必须发 job；取 120 与原版回退游荡节点同频（见 2.3） |
| `:52-55` | 冷却分支：`!SearchDue` ⇒ `return CooldownWait();`（原来 `return null;`） |
| `:79-81` | "搜不到"当次：写完 `nextSearchTick` 后同样 `return CooldownWait();`（原来 `return null;`）——**这一处和冷却是两件事**：不修它，冷却起点那一 tick 仍然会被 GetFood 接走 |
| `:84-91` | 新私有方法 `CooldownWait()`：`JobMaker.MakeJob(JobDefOf.Wait)` + `expiryInterval = CooldownWaitTicks`，返回。没有目标格、没有寻路、没有状态写入、没有闭包/分配（job 来自池） |

不变量（改完后本 giver 的契约）：**只要 `CanOrderLeave` 与 `Allows(ExitMap)` 通过，本 giver 一定返回一个 job**——要么是基类的凿墙/离场 job，要么是 120 tick 的原地等待。

### 2.2 等待 job 是怎么结束的（[IL]，决定了上限数字）

- `Verse.AI.JobDriver_Wait`：`defaultCompleteMode = ToilCompleteMode.Never`（反编译 `:54`），它自己不会结束；initAction 会 `Reserve(pawn, job, pawn.Position)` 并 `pather?.StopDead()`（`:28-33`），每 4 tick 做一次 `CheckForAutoAttack`（`:34-52`）。
- 结束靠到期：`Verse.AI.Pawn_JobTracker.JobTrackerTickInterval`（反编译 `:166-193`）判定 `curJob.startTick + curJob.expiryInterval <= TicksGame && pawn.IsHashIntervalTick(curJob.expiryInterval, delta)`。
- `IsHashIntervalTick(interval, delta)` = `|TicksGame + thingIDNumber.HashOffset()| % interval < delta`（`Assembly-CSharp.decompiled.cs:13900-13908`），即每个 interval **只有一个相位 tick** 命中。
  ⇒ 实际 job 长度落在 `[120, 239]`：`start+120` 之后最近的那个相位 tick 最多再晚 119。
- 到期后 `checkOverrideOnExpire == false` ⇒ `EndCurrentJob(Succeeded)`（`:178-181`）⇒ 若 pather 没在动，原版会先起一个 1 tick 的 `Wait_MaintainPosture(1)`（`:461-471`）⇒ 下一 tick 走 `TryFindAndStartJob()`（`:472`）⇒ 主思考树 ⇒ 本 giver 再次被问。

### 2.3 为什么是 120 tick，以及为什么不学 `WaitFood` 的写法

- **120 的来源**：原版 fallback 的那个游荡节点 `JobGiver_WanderNearFallbackLocation` 就是 `<expiryInterval>120</expiryInterval>`（`SubTrees_Duty.xml:30`）；仓库自己的 `JobGiver_RHAH_Visitor.cs:68` 也用 `MakeJob(JobDefOf.Wait_Combat, 120, true)`。取同一个数，意味着"被我们顶掉的是一条 120 tick 量级的闲置 job"，重新思考的频率、以及对"门突然能走了"的反应延迟都不比原版差。
- **为什么不开 `checkOverrideOnExpire`**（`JobGiver_RHAH_WaitFood.cs:85-86` 那种写法在这里不适用）：`ShouldStartJobFromThinkTree`（`Pawn_JobTracker:833-848`）对"同一 giver 连发的同 def job"返回 false（`IsContinuation` 默认 `true`，`Verse.AI.JobDriver:690-693`），于是 `CheckForJobOverride`（`:571-590`）会把新等待 job `ReturnToPool` 掉、**旧 job 也不结束**——等待状态再也刷新不了。默认的 `false` 走 `EndCurrentJob`→`TryFindAndStartJob` 这条路，等待能一轮一轮干净地续上。
- **为什么不用 `Wait_MaintainPosture`**：`JobDriver_WaitMaintainPosture` 只是重写 `SetInitialPosture()`（反编译整文件 8 行），行为与 `Wait` 一致但会保留坐/躺姿势；离场者用 `Wait` 更贴近"站在这里等"，也与仓库既有用法一致。

## 三、四个必答问题

### 3.1 选哪种、为什么

**选"冷却期内发廉价原地等待 job"（候选 a）。**

- **(b) 缩短冷却不成立**（决定性理由，见 §1.3-1）：回退发生在**返回 null 的同一趟思考**里，`ThinkNode_Priority` 会当趟继续走 `JobGiver_GetFood`。冷却再短，只要那一趟是 null，就有一趟会被接走；把它缩到 0 等于让每一趟都露出这条缝。而且冷却存在的意义是压掉"区域 BFS + 30 次边缘采样"，缩短会把复审点名要避免的成本又加回来。
- **(c) 给 `JobGiver_GetFood` 打 Prefix 拦截 `Leaving`**（复审的另一个选项）比本方案大：要新增一处跨模组 Harmony 补丁（`Source\AGENTS.md:11` 要求写明缺口理由）、要判 `Leaving` 与各类 fallback 的边界、还会连带掐掉 `JobGiver_GetFood` 上的两个既有 Postfix（赈灾区、啃食）的语义；而 S1 的**触发条件就在本 giver 里**，在本 giver 里消掉 null 是最小闭环。
- 选 **(a) 的代价**是"离场者可能在原地站最多一个游戏小时"，可见但无害；它比"回屋吃玩家的饭并绕过记账"更符合模组目标。等待 job 不寻路、不写状态、不占缓存。

### 3.2 会不会让"本来该凿墙的人"被等待 job 拖慢

**会拖慢，但有硬上限，且不累积。**

| 项 | 数字 | 依据 |
|-|-|-|
| 冷却本身 | 2500 tick（未改） | `:14`、`:80` |
| 等待 job 实际长度 | `[120, 239]` tick | `JobTrackerTickInterval:166-169` + `IsHashIntervalTick` 的相位量化（§2.2） |
| **冷却到期后最坏再等多久才重试凿墙** | **≤ 239 tick ≈ 4 现实秒（1× 速度），占冷却的 9.6%** | 冷却到期那一刻若刚好是一条新等待的开始，最多等这条等待走完；等待到期即重新询问，基类搜索当趟执行 |
| 是否累积/漂移 | 否 | `nextSearchTick` 只写一次（`:80`），等待 job 不改它；一次失败只吃一次冷却，成功即清表项（`:73`） |
| 正常能走出去的人 | 不受影响 | 前一个 `JobGiver_RHAH_Leave`（`JobGiver_RHAH_Leave.cs:59-85`）不节流、不等待，任何一趟都可以当 tick 接走；本 giver 的等待只在"它也没给 job"之后才发 |
| 凿墙中的节奏 | 不受影响 | 基类给得出 job 时走 `:69-75`（清表项、直接返回），冷却与等待都不参与；job 到期就重新搜索 |

补充：改动**不会**让"本该凿墙的人"错过任何一次成功搜索——冷却到期后的第一次询问仍然是完整的 `base.TryGiveJob`，等待只推迟"第一次询问何时到来"，上限如上。

### 3.3 会不会引入每 tick 开销

**不会。** 评审的硬约束是"不能每 tick 跑 `CanReachMapEdge`/`TryFindBestExitSpot`"，本轮之后：

| 路径 | 每 tick | 每次"被问到" |
|-|-|-|
| 冷却窗口内 | 0（本 giver 不被调用） | 1 次 `ConditionalWeakTable.TryGetValue` + 1 次池化 `JobMaker.MakeJob`（§2.1 `:52-55`）+ 进入冷却分支前既有的 `CanOrderLeave`/`Allows`（与 `3c0595d` 完全一致，无寻路） |
| 冷却到期/首次询问 | 0 | 原有守卫 + 1 次 `base.TryGiveJob`（`CanReachMapEdge` + ≤30 次边缘采样），每 2500 tick 至多一次 |
| 拿到 job 后 | 0 | 0（等待 job 由 JobTracker 的到期检查驱动，原版逻辑） |
| LINQ/闭包/临时集合/拼串 | 无 | 无 |

"被问到"的频率：等待把询问间隔稳定在 120–241 tick，与原版被顶掉的那个 fallback 节点（`expiryInterval=120`）同量级；一个冷却窗口内至多 `2500/120 ≈ 21` 次询问/人。**没有任何新增的逐 tick 路径**，也没有新增寻路。

### 3.4 等待期间 pawn 会不会被别的 thinkNode 抢走

分四类，结论是"会被原版常量树抢，但抢不走求食这条路，不需要额外处理"。

1. **主思考树 / duty 树（含 `JobGiver_GetFood`）——抢不走**。原版只在 `curJob == null` 时才走 `TryFindAndStartJob`（`Pawn_JobTracker:197-204`）；等待 job 在手，duty 子树连评估都不会发生。这就是本修法的全部要点。
2. **常量思考树——会抢，但抢不到"吃"**。`Pawn_JobTracker:140-155` 每 30 tick 评估一次 `HumanlikeConstant`（`Humanlike.xml:484-536`），可能给出 `JobGiver_FleePotentialExplosion`、`JobGiver_FindOxygen`、`JobGiver_BoardOrLeaveGravship`、加入远行队、`JobGiver_ConfigurableHostilityResponse`（逃跑/反击）、`LordDutyConstant`。这些**都不产生 `Ingest`**（常量树里没有 `JobGiver_GetFood`），所以绕过闸门的风险仍为 0；被抢走是原版对所有 job 一视同仁的行为，**不需要处理**。
3. **`JobDriver_Wait` 自己的行为——不换 job**。它每 4 tick 做一次 `CheckForAutoAttack`（`JobDriver_Wait:34-52`）：邻近敌对会 `TryMeleeAttack`（起的是 stance，不是新 job；`collideWithPawns = true`），玩家派系还会顺手打火——**来客不是玩家派系，打火分支不生效**。所以最坏表现是"站着的离场者顺手拍了身边一巴掌"，与原版任何等待一致。
4. **健康/身份/结构化转变——会换 job，但都是原有语义**。倒地、死亡、精神崩溃、着火、被抓/被囚/被招募/被喂食，都是原版 `Pawn_JobTracker`/Lord/身份层强制结束或换 job 的路径，不是 thinkNode；`CanOrderLeave`/`CanWalkOut` 守卫会在下一次询问时把它们挡掉（行为与改动前相同）。冷却表是纯计时缓存、不携带玩法状态（`:21-22`），所以"被抢走"不会留下脏状态——最坏只是多搜一次。

**一个必须写明的副作用（[推断]，未进游戏验证）**：`JobGiver_GetFood` 上的 `RHAH_GnawFoodPatch`（`Source\Pawn\RHAH_StayWorkPatch.cs:13-25`）本来能让"原版求食也找不到东西"的饥饿来客去啃树皮；`JobGiver_RHAH_Gnaw.cs:56-60` 还把 `Wait`/`GotoWander` 当成"不忙"（`PrefersGnaw` 时）。本修法把这个入口在冷却窗口内一并关掉了（因为根本走不到 GetFood）。按 S1 的要求这是对的（离开的来客不该碰殖民地资源），但如果确实希望"濒临饿死的离场者能啃墙皮"，正确的做法是在 `RHAH_VisitorLeave` duty 里加一个带闸门的 giver，而**不是**依赖原版回退；本轮按"只修 S1"未做。
