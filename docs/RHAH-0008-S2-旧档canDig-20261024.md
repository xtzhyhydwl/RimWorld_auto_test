## 二、修法（改后）

`Source\Pawn\LordJob_RHAH_Visitor.cs:742-769`：

```csharp
internal sealed class LordToil_RHAH_VisitorLeave : LordToil
{
    bool dutiesReady;

    public override void UpdateAllDuties()
    {
        dutiesReady = true;
        for (int i = 0; i < lord.ownedPawns.Count; i++)
        {
            ...
            RHAH_Api.SetLifecycle(pawn, RHAH_Lifecycle.Leaving);
            pawn.mindState.duty = RHAH_VisitorRules.DepartureDuty();
        }
    }

    public override void LordToilTick()
    {
        // 原版读档只恢复当前 toil 不重发职责 旧档存下的离场 duty 带着 canDig=false
        // 首次 tick 按现有成员重建一次 否则无门可走的老困客拿不到凿墙兜底
        if (!dutiesReady)
        {
            UpdateAllDuties();
        }
    }
}
```

改动内容：1 个字段 + 1 行置真 + 1 个覆写方法。**没有**新存档键、**没有**改 `PawnDuty` 字段语义、**没有**新增必须落盘的字段（`dutiesReady` 是运行期标记，`Scribe` 不写它 —— 写进去反而会让载入后跳过重建）。

### 2.1 为什么这是幂等的

1. **重复调 `UpdateAllDuties` 本来就在既有设计里**：`GotoToil`（每次进入该 toil）已经调一次；`AddPawn(s)`、`LordJob.Notify_PawnDowned`/`Notify_PawnUndowned` 也会再调。所以这个函数必须、且已经是「按当前成员重算」的幂等函数，本轮只是多一个调用时机。
2. **`SetLifecycle(pawn, Leaving)` 对已是 `Leaving` 的人是空操作**：`RHAH_PawnState.TrySetLifecycle`（`Source\Identity\RHAH_PawnState.cs:79-82`）在 `next == lifecycle` 时返回 `false`，`RHAH_ApiHost.ChangeLifecycle`（`Source\Identity\RHAH_ApiHost.cs:103-106`）随即 return ⇒ **不会**重复发 `LifecycleChanged`、**不会**再清一次可达性缓存（S3 那一步只在真正 `Living→Leaving` 时执行）。
3. **duty 赋值是纯覆盖**：新对象由工厂产生，`def` 不变（`RHAH_VisitorLeave`）、`canDig = true`；不累加、不追加集合、不消费次数。
4. **只跑一次**：`dutiesReady` 在载入后的对象上是 `false`（字段不落盘），第一 tick 置真后不再进。代价 = 每 tick 一次 bool 判断，无 LINQ/闭包/分配。

### 2.2 为什么挂点必须晚于载入（而不是在 `Lord.ExposeData` 里做）

- `CanOrderLeave`（`Source\Pawn\RHAH_BatchAttitude.cs:207-218`）要求 `pawn.MapHeld != null`。lord 的 PostLoadInit 与 pawn 的 spawn 是 Scribe 里两棵独立的树，先后不保证；挂在 tick 上则**整图载入完成之后**才跑，条件天然成立。
- 反过来，挂在 `LordToil.Init` 无效（载入不走 `GotoToil`，IL 已证）。

## 三、副作用与反例检查

### 3.1 玩家/其它状态手动改掉了 duty

- **会覆盖**：载入后第一 tick，leave toil 里每个 `CanOrderLeave` 的成员都会被打回 `DepartureDuty()`。这与「进入该 toil 时」的行为完全一致，也与兄弟 toil（Travel/Seek 早已如此）一致；原版自己也把 duties 当归 toil 派生（`LordJob.Notify_PawnDowned`/`Notify_PawnUndowned` 直接调 `UpdateAllDuties`；多个原版 toil 每 300 tick 重建）。⇒ 不是本轮新引入的语义，是「lord duty 由 toil 拥有」这一既有约定的延伸。
- **两处真实反例，都不受影响**：
  - `RHAH_Envoy.Hold`（`Source\Storyteller\Suiyin\RHAH_Envoy.cs:255-267`）在把 duty 改成 `RHAH_VisitorSeek` 之前，**先把 lord 切出 leave toil**（`GotoToil(lord.Graph.lordToils[1])`），所以本 toil 的载入重建不会碰它。
  - `RHAH_MouseSwarm`（`Source\Pawn\RHAH_MouseSwarm.cs:130-144`）把 lord 切到 `LordToil_RHAH_ArmedAssault` 之后才改 duty，同样不在本 toil 内。
- 仍然保留的唯一「覆盖」场景：`lifecycle` 被外部直接写回非 `Leaving`（`RHAH_MouseSwarm.cs:109` 那种绕过状态机的直写）但人还停在 leave toil 的存档 —— 重建会把他再置回 `Leaving` 并发离场 duty。与「进入 toil 时」一致；且 `MouseSwarm` 会同时切 toil，实际到不了这一格。

### 3.2 多个 lord / 别的 lord 管着的人

- 只遍历 `lord.ownedPawns`，`lord` 是本 toil 所属的 RHAH 访客 lord。
- 且 `CanOrderLeave` 要求 `pawn.GetLord() == null || pawn.GetLord().LordJob is LordJob_RHAH_Visitor`；原版 `Lord.AddPawnInternal`（`Lord.decompiled.cs:425-429`）本身就禁止一个 pawn 同属两个 lord ⇒ 碰不到原版袭击/偷窃/绑架 lord 的人。
- 被囚/为奴/玩家派系/收留中（`IsColonyStay`）的成员照样被 `CanOrderLeave` 挡在 `continue` 外，保留原 duty（这些人本来也不该凿墙）。

### 3.3 `ArmedDemand` 分支

- 武装索粮的离场走 `RHAH_ArmedDemand.cs:159` → `RHAH_BatchAttitude.OrderVisitorLeave` → `OrderLeave` → `:265 DepartureDuty()`：**就是 7 处之一**，`9b00cbd` 起已带 `canDig`。
- 若某个军索成员此后仍停在 leave toil 并被存档，本轮的载入重建同样覆盖他（同 §3.1 的判据）。
- `ArmedDemand` 另有一条 `:284` 的记录（`completeLord && !(CurLordToil is LordToil_RHAH_VisitorLeave)` 才发 memo），本轮没动它 —— 本 toil 的重建**不切 toil**，不改变 memo 行为。

### 3.4 残留窗口：`LordToil_RHAH_WaitFood` 没有载入重建（**本轮不扩**，说明理由）

- 事实：`LordToil_RHAH_WaitFood`（`LordJob_RHAH_Visitor.cs:772-842`）的 `UpdateAllDuties` 也会给 `Leaving` 成员发 `DepartureDuty()`，但它没有 `dutiesReady`；它的 `LordToilTick` 里对 `snapshot.Lifecycle == Leaving` 的成员是 `continue`（`:805`），不会重发。
- ⇒ 旧档里「`Leaving` 且当前 toil 是 WaitFood」的人，会在下一次 `GotoToil` 之前保持旧 duty。**但是**：WaitFood 的两条出口（`foodDone` → Seek、`toLeave` → Leave）都是 `Transition`，`Lord.GotoToil:585` 必然调 `UpdateAllDuties` ⇒ 最迟在切 toil 那一刻自愈；而且这类人本来就在「等投喂」的流程里，不在「困在死屋」的场上（S2 的受害场景是停在 leave toil 的人）。
- 不扩的理由：本条属于「按需再开一格」，会把 diff 从 1 个 toil 扩到 2 个；S2 的验收判据是「已在离场状态（leave toil）的旧档 pawn 拿得到 canDig」。若日后确认 WaitFood 那格真会长期滞留，再按同一模式补 3 行即可（模式已在本文件三处存在，属加数据不是改结构）。

### 3.5 存档/兼容

- 不读不写新键；旧档 `canDig=false` 照原样读回，随后被本 toil 的重建**覆盖成新对象**（`canDig=true`），下次存档写回 `true` —— 仍是 `PawnDuty.canDig` 这一个字段，语义没变。
- 新代码不需要存档迁移；也不需要回退兼容（回退到 `6ab44c7` 的 Def 引用问题与 S2 无关）。
- 运行时状态（`dutiesReady`、`PendingRetries`）都不落盘。
