### 1.6 票面写错的两处（必须更正，否则会去修错东西）

1. **「仍被判为不可达地图边缘 ⇒ 继续凿墙」不成立。** 凿墙门槛是 `JobGiver_ExitMap` 的 `flag = … (duty.canDig && !pawn.CanReachMapEdge()) …`（`runs\tmp\ilspy17\Verse.AI.JobGiver_ExitMap.decompiled.cs:61`），而 `pawn.CanReachMapEdge()` → `Map.reachability.CanReachMapEdge(pos, TraverseParms.For(p))`（`:87790-87797`）→ 每次现做 `RegionTraverser.BreadthFirstTraverse`（`:87666-87705`），**全程不碰 `cache`**。所以门一放行，凿墙那条分支自己就关了，缓存爱怎么写都影响不到它。
2. **「干脆不朝门走」不必然成立。** 见 §1.5 第四行：duty 的第二个 giver 是 `JobGiver_RHAH_Departure`（Def：`1.7\Defs\DutyDefs\RHAH_Duties.xml` 的 `RHAH_VisitorLeave` 第二个 subNode），它的 `canBash` 默认 false，键不同 ⇒ 重算 ⇒ 门已是可通行 ⇒ 一般能发 `Goto`。
3. 所以**真实危害**是「本模组自己的离场 giver 被饿着」＋「`canBash=false` 那一族键同样可能被污染」，而不是票面写的「凿穿玩家的墙」。S3 仍然值得修：它是原版自己守着的不变量（§1.4），修它 12 行、一次性成本，能把「走门那条 giver 永远是第一顺位」这件事恢复。

### 1.7 顺带核实：寻路本身不吃这张缓存

`PathFinder` 类区间 `:101567-102710` 内搜 `reachability|CanReach` **0 命中** ⇒ 寻路是自走的区域/A*，读的是实时的 `Region.Allows`。缓存只影响 `CanReach` 家族的**判断**，不影响已经发出去的路径。

## 二、修法详解

### 2.1 改动

`Source\Identity\RHAH_ApiHost.cs`（改后行号）：

| 行 | 内容 |
|-|-|
| `:95-106` | `ChangeLifecycle` 原有部分不变（拿 comp、`TrySetLifecycle` 失败即返回） |
| `:108-113` | **新增**：`TrySetLifecycle` 成功后，`lifecycle == RHAH_Lifecycle.Leaving` 就 `ClearReachabilityCache(pawn)` |
| `:115-121` | 原有的 `Released`/`Dead` 清理与 `RaiseLifecycleChanged` 不变（清缓存放在**通知之前**，听众第一次问可达性就已经是新的） |
| `:124-135` | **新增** `static void ClearReachabilityCache(Verse.Pawn pawn)`：`pawn?.Map` 为空即返回；否则 `map.reachability.ClearCacheFor(pawn)` |

### 2.2 为什么挂在这里

- **它是唯一的汇合点。** 生命周期只有一条写路径：`RHAH_Api.SetLifecycle`（`Source\Api\RHAH_Api.cs:78-86`）→ `RHAH_ApiHost.SetLifecycle`（`:90-93`）→ `ChangeLifecycle`（`:95`）。把清缓存放这里，`Leaving` 的 8 个具名写入点（`JobGiver_RHAH_Leave.cs:33`、`:129`；`RHAH_VisitorStay.cs:131`；`LordJob_RHAH_Visitor.cs:254/687/753/797`；`RHAH_BatchAttitude.cs:262`；`RHAH_LongFollowRuntime.cs:558/822`）**一个都不用改**，将来新增写入点也自动覆盖——符合「改一个东西只改一处」。
- **不挂在门那边。** `RHAH_DoorPatch` 是每个门判定都被问到的读路径，它根本不知道「刚刚发生了什么状态变化」（Postfix 只看到 `__result` 与 pawn），在那里推断「是不是刚翻的」只会更贵更脆。
- **不清 `Released`/`Dead`。** 那两种状态下 `IsActiveVisitor` 为 false，门 patch 早就走原版结果；vanilla 自己也已在自己的释放路径里清（§1.4）。
- **不挂 `JobGiver_RHAH_Leave` 里 `SetLifecycle` 之后。** 那样只覆盖一条写入点，且把身份层的事写进行为层。

### 2.3 范围与代价（为什么是「这个 pawn + 这张图」）

| 候选 | 影响面 | 判断 |
|-|-|-|
| **`pawn.Map.reachability.ClearCacheFor(pawn)`（选中）** | 只删 `TraverseParms.pawn == pawn` 的行（`ReachabilityCache.ClearFor`，`:87183-87198`：一次 `cacheDict` 遍历 + 静态 `tmpCachedEntries` 收集后删除，**不分配、不重算 BFS**） | 最小范围；别人的结论仍然有效 |
| `ReachabilityUtility.ClearCacheFor(pawn)` | 同一次清理，但遍历 `Find.Maps` **每张图**都扫一遍（`:87808-87815`） | 多图时白扫；本 pawn 只可能在他自己那张图上被缓存（`CanReach` 会先校验 `pawn.Map != map` 并报错返回，`:87326-87330`） |
| `map.reachability.ClearCache()` | 整图作废，**所有 pawn** 下次查询全部重跑区域 BFS | 这是原版每次开关门都在付的钱（`:579657-579660`），我们没必要替它加一次 |

频率：`Leaving` 在状态机里是终态（`Leaving → {Released, Dead}`，`Source\Identity\RHAH_PawnState.cs:276-278`），`TrySetLifecycle` 对同值/非法转换返回 false（`:77-96`），所以**每 pawn 每次来访最多清一次**。空跑开销也只有一次字典扫描。

### 2.4 还需要配合什么（结论：不需要）

- **不用动 `Pawn_PathFollower`。** 过期结论卡住的是 `RCellFinder.TryFindBestExitSpot` 里的 `CanReach`（`：687913`），不是路径；寻路不读这张缓存（§1.7）。一旦新的 `Goto` job 发出，`Pawn_PathFollower.StartPath` 自会替换旧路径，不需要 `StopDead` 之类的前置。
- **不用清孩子的缓存。** 抱持者那条路（`JobGiver_RHAH_Leave.cs:129`）也是走 `RHAH_Api.SetLifecycle`，孩子切 `Leaving` 时同样被这次改动覆盖。
- **没有扩大改动**：`RHAH_DoorPatch`、duty Def、`duty.canDig`、S1 的 `RaiseLifecycleChanged` 之后的一切、`famineVisitorsOpenDoors` 默认值、Scribe 键都没碰。
