### 1.1 两个需要明说的取舍

**(a) `HostileThreat` 对离场者也不再拦。** 人类的方向是「离场肯定先走门；没有路才凿墙」，没有给敌情留例外；而「敌情时锁门」这条一旦对离场者成立，副作用是**逼他去把墙凿一个永久缺口**——比「门开一下」对玩家更糟。所以离场分支放在 `HostileThreat` 判断**之前**。这是本轮的推断性取舍，若作者更看重「有敌人时一律不开门」，把 `:28-32` 整段下移到 `:38` 之后即可（一行位置，不改语义其它部分）。

**(b) 用局部快照替代 `RHAH_Api.IsVisitor(p)`，避免多一次快照分配。** `RHAH_Api.IsVisitor`（`Source\Api\RHAH_Api.cs:36-40`）本身就是 `Get(p) != null && snapshot.IsActiveVisitor`；本轮要同时读 `Lifecycle`，若先调 `IsVisitor` 再调 `Get` 会**每个门判定分配两个快照对象**。所以取一次快照、用它的 `IsActiveVisitor` + `Lifecycle`——语义与原来完全等价（`RHAH_PawnSnapshot.cs:84`：`IsActiveVisitor => Lifecycle != Released && Lifecycle != Dead`）。门判定不是每 tick 路径（只在 `PawnCanOpen` 被问到时），但仍按 `Source\AGENTS.md` 的「Tick 路径避免分配」处理。

## 二、「只放 `Leaving`」的论证

### 2.1 为什么选 `Lifecycle == Leaving`，而不是 `duty` 或 `ReadyToLeave`

| 候选判据 | 语义 | 为什么不选 |
|-|-|-|
| **`snapshot.Lifecycle == RHAH_Lifecycle.Leaving`（选中）** | 「**已经承诺要走**」——写入点全在「决定离场」那一刻之后 | 最贴近「他确实要走」，且与行为闸门 `ExitMap` 用同一字段（`RHAH_PawnDefaults.cs:62-63`），一个概念一个判据 |
| `pawn.mindState.duty?.def == RHAH_VisitorLeave` | 「当前挂的是离场 duty」 | ① `RHAH_VisitorLeave` 这个 duty **在 `Fed`/`SeekingFood` 状态下也会被发给全部 `ownedPawns`**（`LordJob_RHAH_Visitor.cs:644/728/754/778/798` 都是 `UpdateAllDuties` 里的赋值，含 `LordToil_RHAH_WaitFood`），用它等于**把等待投喂的人也放开门**——正好是防偷吃要拦的那批；② 从 `mindState.duty` 被赋值到下一 tick 思考树重建之间有窗口，判据本身不稳定 |
| `LordJob_RHAH_Visitor.ReadyToLeave(pawn, snapshot)` | 「**是否允许/到点离场**」 | 它是 `JobGiver_RHAH_Leave` 的**准入闸门**，包含「投喂等待是否到期」「`FedLeaveDue`」「`RHAH_ArmedDemand.Holds`」等一堆前置（`LordJob_RHAH_Visitor.cs:561-589`）。它是 `Leaving` 的**超集**：为真时人会**立刻**被 `JobGiver_RHAH_Leave.cs:33` 写成 `Leaving`，所以用它不会多放人**但会多算一遍**开销大得多的判定（含 Lord/Toil 查询），并且把「要不要走」的策略耦合进门禁。用 `Leaving` 更小、更稳 |
| `comp.State.stayKind` | 「是否在收留/雇佣/招募中」 | 那三项本来就在玩家派系（`RHAH_VisitorStay.Begin:45-52`），第 `:16-17` 行已经早退；与门禁无关 |

### 2.3 反例检查（逐个排除「误放」）

1. **刚被驱逐的敌对批次成员**（`RHAH_BatchAttitude.cs:262` 把 `RHAH_Faction_Hostile` 的人设成 `Leaving`）：本轮确实也放开了他的门。**判断：正确且必要**——他已经在离场 duty 上，锁门的结果是「用玩家的墙换一条路」，而他要走的方向就是地图边缘。票 0008「风险与待答问题」里把这条列为「需要额外判敌意」，本轮**不判**，理由是：`ExitMap` 是 `Leaving` 唯一放行的行为闸门，敌方身份在 `Leaving` 下**没有**别的可用行为（见第 3 条）。
2. **`Fed`（刚吃完、还没到离场 tick）**：`leaving` 未成立 ⇒ 仍禁门。这是防止「吃饱了趁门开去仓库再拿一次」的关键一格，**保住**。
3. **离场途中会不会顺路拿食物**：门只影响「能不能穿过门」，不产生新 Job。`JobGiver_RHAH_Visitor.cs:84` 在 `lifecycle == Leaving` 时**直接返回离场结果（或 null）**，不再往下走投喂/乞讨/偷窃分支；`Steal`/`Gnaw` 闸门也不因门开而放开。⇒ 机理上不会「顺手拿」，但**路径可能穿过冷库**（观感问题）属于运行时观察项，**未验证**。
4. **还在收留/雇佣/招募里的来客**（玩家故意让他们住下）：派系是玩家 ⇒ `:16-17` 早退，本轮改动碰不到；他们到期后才由 `RestoreDeparture` 变成「非玩家派系 + `Leaving`」，**这正好是本轮要救的那一格**。
5. **`Released`（被招募/入狱/为奴/入伙）/ `Dead`**：不是活跃访客 ⇒ 与改前一样走原版结果。
6. **倒地 / 被眩晕 / 被抱持的 `Leaving` 者**：门许可对他没有意义（`PawnCanOpen` 不是移动能力的来源），`JobGiver_RHAH_Leave.cs:34` 与 `JobGiver_RHAH_Departure.cs:53-62` 的 `Downed`/`CanWalkOut`/`CanDepartAlone` 守卫一行未动。
7. **不可逆性**：`RHAH_PawnState.cs:262-281` 的状态机里 `Leaving → {Released, Dead}` 是**唯一**出口（`Leaving → Fed/SeekingFood` 均非法，`RHAH_PawnStateTests.cs:26-29` 有对应用例）⇒ 不存在「先离场骗开门、再回去偷吃」的回路。唯一绕过 `TrySetLifecycle` 的直接赋值 `RHAH_LongFollowRuntime.cs:543` 是**写回 `SeekingFood`**，方向相反、不会制造上述回路。

### 2.4 仍被禁门的状态（明确列出）

设置 `famineVisitorsOpenDoors = false`（默认）时，下列**非玩家派系 + 态度派系**来客**照旧** `__result = false`：

- `Arriving`（刚刷出、正走向殖民地）
- `SeekingFood`（**乞讨/等投喂/正在找吃**——禁门的本意）
- `Fed`（已吃、还没到离场 tick）
- 上述任一状态 + 地图有敌情时（`HostileThreat`）

不在此列（走原版，改前改后一致）：玩家派系（含收留/雇佣/招募中）、`Released`、`Dead`、非态度派系、无派系。
