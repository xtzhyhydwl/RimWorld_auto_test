## 七、根因定位（**推断**，未做插桩验证）

实测事实（可直接引用）：

1. 工坊 Def 已含 `JobGiver_RHAH_Departure` 节点（706 B，`620A4D…`），DLL 里也有该类型（`JobGiver_RHAH_Departure` / `RetryIntervalTicks` / `CanDepartAlone` / `CanWalkOut` / `IsHashIntervalTick` 五个名字在 DLL 字节里都在）。
2. 存档里 `duty=RHAH_VisitorLeave` 且 **`canDig=True`** —— `canDig` 这条开关是通的。
3. 受测体健康可走（走 48.1 格、`downed=false`、`Moving.minForCapable=0.15`）。
4. `carryTracker.innerList` 为空 ⇒ `CarriedThing=null`、`CarriedBy=null` ⇒ 修复 4.2 的 `CanDepartAlone` **不可能**是拦路者。
5. 换成原版 `JobGiver_ExitMapBest`（同基类、无三道闸门）后立刻凿墙离图 ⇒ 底座能力、路径、`canDig`、出口搜索都正常。
6. 全程 0 异常 ⇒ 不是抛错被吞。

由 1–6 推断：**卡点在 `JobGiver_RHAH_Departure.TryGiveJob` 的前置闸门里**，而三个新闸门中：
- `CanDepartAlone`（4.2）被第 4 条排除；
- `CanWalkOut`（4.1）被第 3 条强烈反证（`CapableOf(Moving)` 只要求 ≥0.15，而他在正常走路，`LearningToWalk` hediff 也不存在）；
- 剩下 **`IsHashIntervalTick(60)` 节流（4.3）**最可疑。

节流为什么会「系统性永不命中」（推断）：`IsHashIntervalTick(60)` 每 60 tick 只有**一个 tick** 为真；而这个 pawn 的闲置窗口极窄——`Wait_Wander` / `GotoWander` 一给就是几百 tick，**真正「无 job、会被问思考树」的 tick 大约每 300–600 tick 才 1 个**。两者要对上，命中率 ≈ 1/60 × (1/400) ≈ 4e-5/tick；15090 tick 里期望命中 **<1 次**，与实测「0 次」一致。评审当时的前提「job 到期后重想一次、最多多等 1 游戏秒」只在 pawn **持续闲置**时成立；对「一直有短 job」的游荡型 pawn，单 tick 哈希窗口会被无限错过。

**下一步建议（未做，属实现决策）**：把节流从「单 tick 哈希命中」改成「按 pawn 缓存上次搜索 tick，`ticksGame - lastTry >= 60` 才重试」（有状态但只存内存、不进存档），或把窗口改成 `IsHashIntervalTick` 之外的区间判定；也可以先在 giver 里加一条 `[RHAH]` 诊断日志把「闸门 null / 节流 null / base null」分开，再删。**注意：这条推断没有插桩证据，`CanWalkOut`/`Allows(ExitMap)` 也没有百分百排除。**

## 十、环境风险与口径（本轮踩到，供后人避坑）

1. **`status` / `readBridgeInfo` 会串台（实测到具体代码路径）**：`src\launcher.js:185 readBridgeInfo()` 在共用 `Player.log` 里找不到 GABP 行时，会走 `findRecordByLogFile()` 兜底并「取最新启动」的记录。目录里有一条别人的假记录 `runs\game-process.dshwait-check.json`（`pid:0`、`port:5288`、`token:fake-token-for-offline-check`、`logFile` 与 1.7 共用日志同路径、`startedAt` 18:53:53 比我晚），于是 18:53:5x 之后我的 4 次调用（`Do incident` / `list_letters` / `list_messages` / `ping`）**打到了 5288 的 FakeBridge**，返回 `success:false, message:"No current map"`。**假桥没有 Game，游戏状态零改变**，这 4 次调用无效仅重跑。
2. **本轮固定的目标身份校验**（每次动作批次前）：`Get-NetTCPConnection -LocalPort 5175` → `OwningProcess=23688`；`Win32_Process 23688` 命令行含 `-savedatafolder=…\profiles\rhah`；`runs\game-process.rhah.json` 的 pid/port/token 三者一致 → 才发命令。记录见 `00-identity-checks.jsonl`。此后所有调用**显式**用 5175 + `f6fd7a36…`，不再走 `readBridgeInfo`。
3. **1.7 的 `Player.log` 全机共用**：两个实例都写同一路径，后启动者会截断它（本轮记录 `logStartOffset:320607`，收尾时文件仅 127 KB）。因此「异常=0」的结论我用了两条路：共用日志快照（首行时间戳 = 本实例启动时间）+ per-profile 事件流 `runs\live\rhah.ndjson`（本次 `game_loaded` 之后的 202 条事件里 `kind=error` 0 条）。
4. **文档缺口（按派单要求记录）**：`node src/cli.js wait --source bridge` 这个新原语在本轮没被用上——**不是不想用**，而是它和 `call` 一样走 `readBridgeInfo`，串台期间会连到假桥；等身份问题绕开后，本轮需要等的状态（门 HP / `curJob` / `spawned`）都是**随 `step_game_ticks` 同步推进后立刻回读**的一次性读数，没有「等某个异步状态自己出现」的场合（真正需要等的是 `Leaving→离图`，而它压根没发生）。另外 skill `rimworld-auto-test` 里引用的 `scripts\diag.mjs`、`src\smoke.js` 等脚本**在当前仓库里不存在**（`scripts\` 目录为空），需要更新。
