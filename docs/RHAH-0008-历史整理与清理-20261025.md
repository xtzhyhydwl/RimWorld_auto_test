### #2 `SearchDue`/`RetryFor` 合并成一次 `GetValue` —— **做了**

`JobGiver_RHAH_DigOut.cs:52-57 / 82-87 / 101-103`：

- 改前：`SearchDue(pawn, now)` 一次 `TryGetValue`（到期还要 `Remove`），失败后 `RetryFor(pawn)` 第二次 `TryGetValue` + `Add` → 同一次 `TryGiveJob` 对同一张 `ConditionalWeakTable` 取两次。

| 情况 | 改前终态 | 改后终态 |

### #4 抽带 `dutiesReady` 的 `LordToil` 基类 —— **不做**

三处同构（`LordJob_RHAH_Visitor.cs` 的 `LordToil_RHAH_VisitorTravel`/`VisitorSeek`/`VisitorLeave`）确实都是「字段 `dutiesReady` + 在 `LordToilTick` 里首次重建」。但抽出来会更绕，理由三条：

1. **置位时机三处不同，且不同是故意的**：`VisitorTravel.UpdateAllDuties` 先 `SetDestination(...)` 再置位；`VisitorSeek.UpdateAllDuties` 在 `TryRedirectLegacyPasserby()` 为真时**提前 return 且不置位**（要保留下个 tick 重试）；`VisitorLeave` 在循环前就置位。基类若想包住「调用 `UpdateAllDuties` 之后置位」，就会把 `VisitorSeek` 那条早退变成「已就绪」，直接改掉读档重建语义。
2. **`VisitorTravel.LordToilTick` 重建之后还有整段到达判定**，基类只能给 `virtual LordToilTick` + 子类 `base.LordToilTick()`，或再加 `protected virtual void OnDutiesRebuilt()` 钩子——这正是任务里说的「引入虚方法 / 改多个 toil 的签名」。
3. **净收益只有每处 3 行**（`bool` 字段 + 2 行 `if`），代价是把「何时算 duties 就绪」这条语义从三个具体 toil 挪进基类，读者要多跳一层才能确认 `VisitorSeek` 的早退语义。按仓库「Code as Documentation / 名字写清它是什么」的偏好，保留 3 份同构代码更可读。

结论：**不抽**。若将来第 4 个 toil 也需要同一模式，再按那时三处已稳定的写法统一抽。
