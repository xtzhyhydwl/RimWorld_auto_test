## 3. 按验收标准逐条判定

### 1. 离场时能走门离图（有门可走时不拆门拆墙）——**通过（有保留）**

- 玩家造的门在原版对**中立来客本来是可开的**：门无派系时走 `RaceProps.canOpenFactionlessDoors`（默认 true），门有派系时走 `GenAI.MachinesLike(Faction, p)`，中立派系不敌对 → true（`[IL]` `Building_Door.PawnCanOpen`、`Verse.AI.GenAI.MachinesLike`）。所以 `RHAH_DoorPatch` 的 Postfix 是"否决者"，它一放行，门就真的能开。**不是**"Postfix 把 false 改成 true"那种做不到的事。
- 门能不能过是**逐 pawn** 判定的：`Building_Door.CanPhysicallyPass` → `Region.CanTraverse` → `IsForbiddenToPass`（`[IL]`）。
- `JobGiver_RHAH_Leave.TryCreate` 的出口搜索是 `RCellFinder.TryFindBestExitSpot(pawn, out spot)`（`Source/Pawn/JobGiver_RHAH_Leave.cs:60`），默认 `TraverseMode.ByPawn`，所以门放行后这条老路径自己就能成功，不必等新 giver。

保留：`[推测]` `Reachability` 的 District 对缓存（`ReachabilityCache`）不会因为"pawn 从被禁变成放行"而失效，封闭基地里可能仍按旧的"不可达"判定（§4-应修#3）。

### 2. 无路时才凿墙（兜底仍在）——**通过（有保留）**

- `[IL]` `JobGiver_ExitMap.TryGiveJob`：`flag = forceCanDig || (duty != null && duty.canDig && !pawn.CanReachMapEdge()) || ...`；`CanReachMapEdge` 是**实时** region BFS（`Reachability.CanReachMapEdge`，不走 District 缓存），所以"走得到就不凿"是原版保证的，不是模组自说自话。
- `JobGiver_ExitMapBest` 在 `flag` 为真时用 `TraverseMode.PassAllDestroyableThings` 找路，再 `DigUtility.PassBlockerJob(... canMineMineables: true, canMineNonMineables: true)`（`[IL]`）。
- 守卫生效路径：`RHAH_VisitorLeave` duty 的第一个 giver 是 `JobGiver_RHAH_Visitor`，它对 `Leaving` 的 pawn 直接返回 null（`Source/Pawn/JobGiver_RHAH_Visitor.cs:83-87`），于是落到新 giver。

保留一：旧档里 duty 已经是 `RHAH_VisitorLeave` 的 pawn，`canDig` 仍是 false，兜底不生效（§4-应修#2）。
保留二：`[IL]` 玩家**禁止通行**的门（`IsForbiddenToPass`）会被算成"无路"，于是会去凿墙（§5）。

### 3. 等待/求食阶段的禁门语义不变——**存疑**

- 判定本身没变：`Lifecycle != Leaving` 时仍走 `settings.famineVisitorsOpenDoors` + `HostileThreat`（`Source/Pawn/RHAH_DoorPatch.cs:34-38`）。
- 但"不能借此放他们进屋偷吃"这半句有缺口：`RHAH_VisitorLeave` duty 在冷却/守卫返回 null 时给不出 job，而 `LordJob_RHAH_Visitor : LordJob`（`Source/Pawn/LordJob_RHAH_Visitor.cs:15`）**不是** `LordJob_VoluntarilyJoinable`，所以原版 `SubTrees_Duty.xml` 的 lord-duty 回退会先给 `JobGiver_GetFood`（`minCategory = UrgentlyHungry`），再给 wander（`[IL]` `Data/Core/Defs/ThinkTreeDefs/SubTrees_Duty.xml:11-38`）。改动前门是关的，这条吃食路径走不通；现在走通了，而且它不认本模组的 `FeedFromRelief`/`Steal` 闸门，也不进 `RHAH_FoodHandoff` 的记账。详见 §4-应修#1。

### 4. 不引入异常/崩溃——**通过（静态判断）**

新增路径的解引用都有前置守卫：`CanOrderLeave` 保证 `MapHeld != null`（`Source/Pawn/RHAH_BatchAttitude.cs:209`），基类直接解引用 `MapHeld`；`CanWalkOut` 守卫 `health`/`capacities`；`CanDepartAlone` 空安全；CWT 键非空、`RetryFor` 先 `TryGetValue` 再 `Add`，单线程无竞态。`ConditionalWeakTable` 在 net48 也可用（未编译验证）。

### 5. 1.6 与 1.7 的 Def 一致——**通过（Def）/ 不通过（二进制，见 §4-阻塞#1）**

`1.6/Defs/DutyDefs/RHAH_Duties.xml` 与 `1.7/...` 两个文件 MD5 相同，第 20 行都是新增的 `HungerAndHavoc.Pawn.JobGiver_RHAH_Departure`；1.6/1.7 的 `Defs` 树逐文件比对，只有 `WorldObjectDefs/RHAH_KingdomSite.xml` 不同，且本分支没碰它，属既有差异。

### 6. 符合仓库编码约定——**通过（含 4 个 nit）**

### 7. 不破坏既有行为（正常离场/被囚/被招募/倒地/幼童/抱持者）——**存疑**

守卫都在，逐项推演见 §5；存疑点是"能走的幼童会不会自己挖墙"与"旧档凿墙兜底缺失"，都不是阻塞级，但验收时不能算干净通过。

### 应修

#### S1. 冷却空窗把离场者交给原版 `JobGiver_GetFood`，等于绕过求食/偷食闸门

- 位置：`Source/Pawn/JobGiver_RHAH_Departure.cs:45-50`、`:72-76`（失败后 1 小时冷却）；行为落点在原版 `SubTrees_Duty.xml:22-24`。

#### S2. 旧档里已在离场 duty 的 pawn 拿不到 `canDig`，兜底不生效

- 位置：`Source/Pawn/RHAH_VisitorRules.cs:899-904`（工厂）、`Source/Pawn/LordJob_RHAH_Visitor.cs:742-757`（`LordToil_RHAH_VisitorLeave` 只在 `UpdateAllDuties` 里发新 duty，没有 `dutiesReady` 式的读档重建；对比 `LordJob_RHAH_Visitor.cs:654-658` 的 Travel toil 有）。
- 为什么：`PawnDuty.canDig` 是 Scribe 字段（`[IL]` `Verse.AI.PawnDuty.ExposeData` 的 `"canDig"`，默认 false），旧档读回来仍是 false；`LordJob_RHAH_Visitor` 恢复 lord 后不会重发 duty，于是"无门可走的房间 + 旧档"＝仍然困住（门那条路仍然能走，凿墙那条不行）。
- 建议：`JobGiver_RHAH_Departure.TryGiveJob` 调基类前补一句 `pawn.mindState.duty.canDig = true;`（一行、幂等、不依赖 toil 重建）；或给该 toil 补 `dutiesReady`。

#### S3. 从"禁门"翻到"放行"时没有清该 pawn 的可达性缓存（推测，需实测）

- 位置：`Source/Pawn/RHAH_DoorPatch.cs:29-32`（豁免只有判定，没有任何缓存失效）；`Source/Pawn/JobGiver_RHAH_Leave.cs:33`（先置 `Leaving` 再搜索，顺序是对的）。
- 为什么：`ReachabilityCache` 是按 `(DistrictA, DistrictB, TraverseParms)` 缓存的，`TraverseParms` 里带 pawn，所以同一个 pawn 的"室内→室外不可达"会被记住；`AddCachedResult` 只加不改，只有门 `FreePassage` 变化、`Pawn_GuestTracker.Released`、`ClearCacheFor` 等才会清（`[IL]` `ReachabilityCache.cs:67-93`、`Building_Door.cs:331-337`）。正常殖民地总是有人开门，缓存会被冲掉，问题不明显；**封闭/无人走动的基地**里可能一直按旧的"不可达"判定 → 表现就是"改了还是不出门"，甚至反过来直接走凿墙路线。
- 建议：在 `Living → Leaving` 的转换处（`Source/Identity/RHAH_ApiHost.cs:95-115` 的 `ChangeLifecycle`）或 `RHAH_VisitorStay.RestoreDeparture`（`Source/Pawn/RHAH_VisitorStay.cs:120-137`）里加一次 `ReachabilityUtility.ClearCacheFor(pawn)`；一次性成本，换来的是"门真的会被重新评估"。

## 5. 边界与风险

### 有敌情时离场者也能开门——会不会让袭击者跟着进来？

分三层，结论是"增量很窄，但不是零"：

1. **敌对的 pawn 本来就被原版挡住**。`Building_Door.PawnCanOpen` 对敌对派系走 `GenAI.MachinesLike` → `p.Faction.HostileTo(machineFaction)` 为真 → false（`[IL]`）。门 Postfix 的入口是 `if (!__result) return;`，原版 false 时它什么也不做 —— 所以"武装索粮结束后仍在离场、且仍敌对"的那批人**不会**因为这次改动获得开门能力（我一度怀疑这条，查完 IL 推翻）。
2. **中立离场者在袭击期间开门**是这次新增的实际行为（原设计用 `HostileThreat` 一刀切）。真正值得说的是**物理开门的连带效应**：`Notify_PawnApproaching` 会把门顶开 `DoorOpen(max(300, moveCost+1))`；门开且未将关时 `FreePassage` 为真，`CanPhysicallyPass` 对所有 pawn 返回 true，于是**本来开不了门的敌对动物（manhunter/掠食者，`canOpenDoors=false`）**在约 300 tick 的窗口里可以从那道门进来（`[IL]` `Building_Door.cs:426-437`、`FreePassage` 定义在 `:75-89`）。对 raid 人类袭击者几乎没有增量（他们靠砸门）。
3. 同格/相邻的通行：门格本身永远可走，"能不能穿"逐 pawn 判；同行离场者之间没有互相阻塞。

结论：不是"开了一条普适通道"，是"多了一个 5 秒的窗口期"。若在意，可把豁免收紧成"当地图上没有敌对威胁，或该 pawn 已经贴在门边"，代价是重新引入被困风险。

### 离场途中会不会顺手拿殖民地食物/物品？

- 走本模组偷取/求食 giver 的路径**不会**：`JobGiver_RHAH_Visitor` 对 `Leaving` 在 `:84` 就返回了，`JobGiver_RHAH_Steal`/`Feed` 到不了。
- 会的是原版：见 §4-应修#1。它不吃"模组闸门"，但吃原版食物规则（`FoodUtility.TryFindBestFoodSourceFor(..., allowForbidden: false, ...)`）。`[推测]` 真实表现需要进游戏看（"中立访客会不会真的去吃玩家库存"取决于原版访客的食物许可，我无法在读代码阶段定论），但**路径是这次改动新开的**，这点是确定的。

### 幼童、抱持者、倒地者、被囚/被招募者分别怎样

- **幼童**：`CanWalkOut` 会排掉 `IsVanillaImmobileBaby`、Moving 能力不足、`CanOpenDoors` 为假的（`Source/Pawn/Compat/RHAH_ChildMovement.cs:83-102`），新 giver 直接返回 null → 由抱持者带走。`[推测]` 弱风险：**能自己走的幼童**会像成人一样走门/凿墙，可能和"抱持者统一带走"的既有协议不一致（`LordToil_RHAH_VisitorTravel` 的到位判定会跳过 `Leaving` 的 pawn，`LordJob_RHAH_Visitor.cs:668-673`）。
- **抱持者**：`CanDepartAlone` 挡住（`JobGiver_RHAH_Departure.cs:59`）。我原本担心"原版 post-duty 的 `JobGiver_ExitMapBest` 备份会绕过 `JobDriver_RHAH_CarryYoung` 的双方就绪检查"，查完 1.7 think tree 后**判定不成立**：`LordJob_RHAH_Visitor` 不是 `LordJob_VoluntarilyJoinable`，lord-duty 给不出 job 时先落 `JobGiver_GetFood`/wander（wander 基本总会给 job），外层那条原版备份到不了。
- **倒地者**：`CanOrderLeave` 不排除倒地，但 `CanWalkOut` 排除；原版基类还有 `pawn.Downed && !pawn.Crawling` 短路。行为不变。
- **被囚/被招募/奴隶**：`CanOrderLeave` 直接排除（`Source/Pawn/RHAH_BatchAttitude.cs:207-218`：玩家派系/囚犯/奴隶/`IsColonyStay`）；被囚时走 `Released`（`Source/Identity/RHAH_ApiHost.cs:83-88`），`IsActiveVisitor` 为 false，门 patch 本来就提前返回 → 与改动前完全一致。这一项干净。

### 多个离场者同时抢一道门

门没有预约机制，多人共享，`RCellFinder` 的 `CanReserve`（`[IL]` `RCellFinder.cs:121`）只影响选点。没发现新的死锁，最坏是排队 + 个别人多搜几次。真正会连续失败的是"30 次边缘采样全落空"（`RCellFinder.cs:153-157`：危险、被别人占位、预约失败都会命中），此时会吃 1 小时冷却（§4-应修#1）。

### 凿墙兜底会不会在"门其实能走"时误触发？冷却/缓存会不会饿死或过度触发？

- 不会因为"门能走"误触发：`duty.canDig` 只在 `!CanReachMapEdge()` 时生效，而 `CanReachMapEdge` 是实时 BFS（`[IL]`）。**会**误触发的是"物理上能过但原版判定不可过"：玩家 **forbid** 了门（`Region.CanTraverse` 对非敌对 pawn 要求 `!IsForbiddenToPass`），或门属于某个派系且 `MachinesLike` 不放行 —— 这两种情况下新 giver 会去砸玩家的墙。这是玩家可见的变化（"我把门锁了，他挖墙进来"），见 §6。
- 饿死：不会饿死门那条路（`JobGiver_RHAH_Leave` 不节流）；只会让凿墙那条最多晚 1 游戏小时。过度触发：不会（一次失败只设一次冷却），`PendingRetries` 随 pawn 回收，成功即清（`JobGiver_RHAH_Departure.cs:68`）。
