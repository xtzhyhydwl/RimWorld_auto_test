## 1. 结论

**有条件通过** —— 机制选得对、落点很小（一个 duty 节点 + 一个带闸门的 JobGiver），核心链路（门被锁 → `CanReachMapEdge` 为假 → `canDig` 生效 → 路径穿过被锁门 → 产出凿/砸 job）我按原版 IL 逐段核对成立；

## 3. 按验收标准逐条判定

### 3.1 正常情况（没有围墙）离场行为不改变 —— **存疑**

- 主路径确实不变：成人来客离场时 `JobGiver_RHAH_Visitor` 先跑，`Lifecycle == Leaving` 时它直接返回 `JobGiver_RHAH_Leave.TryCreate` 的结果（`JobGiver_RHAH_Visitor.cs:83-87`）；能走到出口时 `TryCreate` 一定给出 `Goto + exitMapOnArrival`（`JobGiver_RHAH_Leave.cs:59-85`），第二个节点根本不会被问到。所以“无阻碍时照旧”成立。
- 但 `TryCreate` 还有两个**与墙无关**的 null 分支，现在会掉到新节点上：
  1. `RHAH_ChildMovement.CanWalkOut(pawn)` 为假（`JobGiver_RHAH_Leave.cs:46,54-57`）——不能自走的幼童以前没有 job，现在会拿到原版 job（通常是 `Mine`/`AttackMelee`，因为 `Goto` 那份带 `exitMapOnArrival` 会被 `RHAH_StayWorkPatch.cs:32-42` + `RHAH_VisitorRules.cs:947-950` 拦掉，而凿门 job 不带这个标记，拦不住）。
  2. `HasUnreadyCarriedChild(pawn)` 为真（`JobGiver_RHAH_Leave.cs:65-68`）——抱着“尚未就绪”孩子的成人以前会停在原地等，现在会带着孩子直接出图（原版 `Pawn.ExitMap` 对被抱的同派系 pawn 会连带 `ExitMap`，见 5.④）。
- 结论：成人、无阻碍场景不变；这两类边界场景行为改变，且都在“没有围墙”的前提下就会发生。

### 3.2 被困时能离图 —— **通过（机制层，未做运行时验证）**

按原版 IL 逐段核对，整条链路是通的：

1. 本模组的“禁门”是 `Building_Door.PawnCanOpen` 的 Postfix（`RHAH_DoorPatch.cs:11-27`），默认关。
2. `Region.Allows(TraverseParms, bool)` 在 `TraverseMode.ByPawn` 分支返回 `door.CanPhysicallyPass(pawn) && !ForbiddenToPass(door, pawn)`；`Building_Door.CanPhysicallyPass` 调 `PawnCanOpen`。所以被本模组锁掉的门在**区域可达性**里就是不可通行 → `ReachabilityUtility.CanReachMapEdge(pawn)` 返回 false。
3. `JobGiver_ExitMap.TryGiveJob` 的 `canDig` 计算式为：`forceCanDig || (duty != null && duty.canDig && !CanReachMapEdge(pawn)) || (forceCanDigIfCantReachMapEdge && !CanReachMapEdge) || (forceCanDigIfAnyHostileActiveThreat && …)`。`JobGiver_ExitMapBest` 自己的 ctor 只设 `jobMaxDuration`、`canFlyOutOfMap`，不设 `forceCanDig`；所以这里唯一的开关就是 duty 的 `canDig` —— 与本改动注释写的“原版只在走不到地图边缘时才砸门墙”完全一致。
4. `canDig` 为真时 `JobGiver_ExitMapBest.TryFindGoodExitDest` 用 `TraverseMode.PassAllDestroyableThings`（枚举值 3）找出口；该模式下 `PathUtility.GetDoorCost` 对被锁的门返回“可破坏物代价”而不是 65535（不可通行），所以路径会穿过这扇门。
5. 随后 `PathFinder.FindPathNow` + `PawnPathUtility.FirstBlockingBuilding` 取出挡路建筑，交 `DigUtility.PassBlockerJob(pawn, blocker, cell, canMineMineables:true, canMineNonMineables:true)`，按顺序可能产出 `Mine`、`AttackMelee` 或 `UseVerbOnThing`（带 `ai_IsBuildingDestroyer` 的武器）。
6. `Mine`/`AttackMelee` 的 job 带随机 `expiryInterval`，到期后思考树重跑 → 继续凿 → 门破 → 正常 `Goto` 出图。

`PawnDuty.canDig` 在原版里的读者只有 `Verse.AI.JobGiver_ExitMap.TryGiveJob`（另见 `PawnDuty.ExposeData` 的存档和其它 LordToil 写 duty），没有别的行为被这行赋值牵连。

### 3.3 不引入异常/崩溃 —— **通过（静态）**

- 基类 `TryGiveJob` 一上来就解引用 `pawn.MapHeld.CanEverExit`（无空检查），而新 giver 的第一个判断 `CanOrderLeave` 里已经要求 `pawn.MapHeld != null`（`RHAH_BatchAttitude.cs:209-214`），这个顺序正好把空引用挡住了 —— 但这是个不显然的依赖（见 4.9）。
- 倒地被原版 `pawn.Downed || pawn.Crawling` 直接挡掉；昏迷/被抱的 pawn 不会 tick 到思考树。
- `RHAH_Api.Allows` 与 `CanOrderLeave` 都做了 null / Dead / Destroyed 判断。
- 唯一会“报错但不崩”的路：永久受困且原版也找不到出口时每 tick 重复搜索（性能，不是异常）。未编译、未跑游戏，见第 6 节。

### 3.4 不破坏“默认禁门”的设计意图 —— **存疑**

- 字面目标是保住的：没有改 `RHAH_DoorPatch`，没有设 `canBash`（`JobGiver_ExitMap.canBash` 是 protected 字段，本改动没碰，默认 false），所以 job 的 `canBashDoors` 仍是 false，“开门”权限一点没放开；`RHAH_Api.Allows(ExitMap)` 闸门也照查。
- 但语义上，“打不开门”被换成了“把门砸了”：被锁的门会在 `PassAllDestroyableThings` 路径里被当成可破坏障碍，来客会对它下 `Mine`/`AttackMelee`（或带拆建筑武器时下 `UseVerbOnThing`，可能顺带点火）。玩家看到的是访客在自己的基地里拆门/拆墙、门破之后屋顶可能塌 —— 这是比“开不了门”更重的可见后果，而改动没有任何玩家侧提示或开关。
- 所以“禁门”的**机制**没破，**体验合同**被扩写了。这一点需要产品判断，不该由代码默默决定。

### 3.5 1.6 与 1.7 的 Def 保持一致 —— **通过**

`Get-FileHash` 两个文件同为 `620A4D68752626668682667A30B6BFBEE3993B2737931DF4075C4C690A47E135`；`git show 9b00cbd:ratkin_hunger_and_havoc/1.7/Defs/DutyDefs/RHAH_Duties.xml` 确认节点确实在 1.7 文件里（1.7 通过 `LoadFolders.xml` 装载，两个版本都吃得到）。

### 3.6 符合仓库编码约定 —— **通过（有 3 条建议）**

- `internal` 默认：新类型 `public` 有明确理由（XML `<li Class=…>` 反射实例化），文件头注释也写了理由，符合 `Source/AGENTS.md:3`。
- `RHAH_` 前缀、文件名与主类型一致、Allman/块命名空间、短中文注释只写原因：均符合。
- Tick 路径：`TryGiveJob` 里没有 LINQ、没有临时集合、没有拼串；`DepartureDuty()` 只在赋值 duty 时分配一次，不在 tick 上。
  **但**基类调用会在每个闲置 tick 上做 `CanReachMapEdge` + 最多 30 次随机边缘采样的 `TryFindBestExitSpot`，与 `Source/AGENTS.md:10`（“不用高频扫图或寻路代替”）冲突 —— 见 4.3。
- “同一个概念只有一个名字”（根 `AGENTS.md` 的 DRY 条款）：已经有了 `JobGiver_RHAH_Leave` / `RHAH_VisitorLeave`，这次又引入 `JobGiver_RHAH_Departure` / `DepartureDuty` —— 见 4.6。

## 4. 我发现的问题

### 阻塞

无。

### 应修

**4.1 新 giver 没有“能不能自己走”的前置判断，非倒地但不能走的幼童会拿到凿门/砸墙 job**

- 位置：`Source/Pawn/JobGiver_RHAH_Departure.cs:17-30`
- 问题：只查了 `CanOrderLeave` 和 `ExitMap` 闸门，没有 `RHAH_ChildMovement.CanWalkOut(pawn)`。`JobGiver_RHAH_Leave.cs:46` 和 `RHAH_VisitorRules.cs:947-950` 都认为“不能自走的来客不该被塞离图 job”，但后者只挡 `exitMapOnArrival`；`PassBlockerJob` 给出的 `Mine`/`AttackMelee` **不带**这个标记，于是绕过了这道既有规则（`RHAH_StayWorkPatch.cs:32-42` 拦不住）。
- 为什么是问题：这个 mod 明确有幼年鼠族分支（`RHAH_ChildMovement.cs:29-54` 用 `LearningToWalk` 阶段判断能否自己走），这类 pawn 不是 `Downed`（原版只挡 `Downed || Crawling`），会真的被发到 “去凿门” 的 job；同时它会每 tick 重新找出口（`Mine` job 路径失败 → job 结束 → 再问）。表现是幼童对着殖民地的门做凿墙动作 + 无效寻路。
- 建议：在 `TryGiveJob` 里 `RHAH_Api.Allows` 之后加一句 `if (!Compat.RHAH_ChildMovement.CanWalkOut(pawn)) { return null; }`（与 `JobGiver_RHAH_Leave` 同一判据，别另造一套），并在注释里写明“不能自走的成员由抱持者带走，这里不接管”。

**4.2 绕过了“抱着未就绪孩子”的判断，可能带着未标记离场的孩子出图**

- 位置：`Source/Pawn/JobGiver_RHAH_Departure.cs:29`（直接 `base.TryGiveJob`），对照 `Source/Pawn/JobGiver_RHAH_Leave.cs:65-68`
- 问题：`JobGiver_RHAH_Leave` 在 `HasUnreadyCarriedChild(pawn)` 时故意返回 null（等放下/等孩子就绪），新 giver 在这个 null 之后接管，会让抱持者直接走原版 `Goto + exitMapOnArrival`。
- 为什么是问题：原版 `Pawn.ExitMap` 对被抱的 pawn 有两种处理——不同派系走 `kidnapped.Kidnap`，同派系则把它从 carry 容器里取出并一起 `ExitMap`。也就是说孩子不会留在图上，但它的 mod 状态可能还停在 `Arriving/SeekingFood` 而不是 `Leaving`，与 `JobDriver_RHAH_CarryYoung.LeaveIfExit`（该文件 `:118-136`）刻意保证的“先确认双方都允许离图再一起出图”不一致，批次/账目上会留下一个“已离图但仍算活跃来客”的记录。
- 建议：把 `JobGiver_RHAH_Leave` 里的“抱持/放下”判据抽成一个可复用的 `internal static bool CanDepartAlone(Verse.Pawn pawn)`（包含 `CarriedBy`、`carryTracker.CarriedThing`、`HasUnreadyCarriedChild`），新 giver 也调它；这样“谁能单独离场”只有一处定义。

**4.3 永久受困时每个 tick 跑一次出口搜索，且没有节流**

- 位置：`Source/Pawn/JobGiver_RHAH_Departure.cs:29`；触发条件是没有可破坏的阻挡物 / 找不到出口（例如全封闭的不可破坏地形、`CanEverExit == false` 的图）
- 问题：原版 `Pawn_JobTracker.JobTrackerTickInterval` 在 `curJob == null && mindState.Active` 时每 tick 调 `TryFindAndStartJob`（`IsHashIntervalTick(30)` 只挡常量思考树那一段，不挡主思考树）。所以这条路径上每个闲置 tick 都会：`CanReachMapEdge`（区域 BFS）+ `TryFindBestExitSpot`（最多 30 次边缘随机采样，每次一次 `CanReach`）。而且 `JobGiver_RHAH_Leave.TryCreate` 在同一个 tick 里**已经**跑过一次 `TryFindBestExitSpot`（`JobGiver_RHAH_Leave.cs:60`），等于翻倍。
- 为什么是问题：`Source/AGENTS.md:10` 明确禁止“用高频扫图或寻路代替”；原来只有一次搜索，现在受困者变成两次，且第二个更贵。多个受困来客同图时会明显掉帧。
- 建议：在 `TryGiveJob` 最前面加 `if (!pawn.IsHashIntervalTick(60)) { return null; }`（或一个 per-pawn 的重试 tick），让“每 60 tick 试一次”而不是“每 tick 试一次”；空返回不会卡住思考树，只是把重试变稀。

### 建议

**4.4 玩家可见后果没有任何提示或开关**

- 位置：`Source/Pawn/JobGiver_RHAH_Departure.cs`（行为）+ `RHAH_Settings`（缺）
- 问题：默认设置下（`famineVisitorsOpenDoors` 关）来客会拆殖民地的门/墙，玩家侧零提示。
- 建议：`RHAH_Settings` 加一个 `visitorsMayDigOut`（默认开），关掉时新 giver 直接返回 null（回到“开门或卡住”）；或在首次给某个来客发出“凿”job 时发一条 `Messages.Message`（“来客正在凿开你的门”）。本 mod 其它地方都遵守“玩家必须知道发生了什么”，这里不该例外。

**4.5 旧存档迁移：读档后 `duty.canDig` 可能仍是 false**

**4.6 “离场”这个概念现在有两个名字**

## 5. 边界情况

1. **正常离场（无阻碍）**：不变。成人来客由第一个 giver 发出 `Goto + exitMapOnArrival`（`JobGiver_RHAH_Leave.cs:82-85`），新节点不被问到。两处例外见 3.1。
2. **被囚禁/被招募的 pawn**：安全。`CanOrderLeave` 排除 `Faction.OfPlayer`、囚犯、奴隶、非来客，并要求 Lord 为空或 `LordJob_RHAH_Visitor`（`RHAH_BatchAttitude.cs:207-218`）；不会接管原版袭击/绑架 Lord。
3. **倒地/昏迷**：安全。原版 `Downed || Crawling` 直接返回 null；即使有 job 漏过来，`RHAH_StayWorkPatch.cs:32-42` + `RHAH_VisitorRules.cs:947-950` 还会再挡一次 `exitMapOnArrival`。
4. **幼童 / 抱孩子的**：有问题。不能自走的幼童见 4.1；抱持者见 4.2。补充一条已验证事实：原版 `Pawn.ExitMap` 对被抱 pawn 是同派系就一起带出图、跨派系则 `kidnapped.Kidnap`，所以“孩子被留在图上”不会发生，风险在状态不一致与跨派系绑架语义。
5. **多个来客同时被困（抢同一扇门）**：不会崩，但会排队。`MineOrWaitJob` / `MeleeOrWaitJob` 先 `CanReserve(pawn, blocker, 1, -1, null, false)`，抢不到的人拿 `WaitNearJob` 在门口等；门破后依次出图。观察项：先抢到的人 job 到期/被打断时可能换目标，出现“轮流凿同一面墙”的观感。
6. **玩家自己的门/墙被凿**：会真的被凿掉（`Mine` 作业对非 `Mineable` 建筑同样走 `DoDamage`，`isinst Mineable` 只用于矿脉 designation 分支）。玩家可见后果：门消失、屋顶可能塌、若来客带 `ai_IsBuildingDestroyer` 武器还可能放火。好感/敌对链路我没有验证（见第 6 节）。这是本改动最主要的“误伤面”，建议按 4.4 给开关与提示。
7. **与既有“Gnaw/啃墙”是否冲突**：同 tick 不冲突。`JobGiver_RHAH_Visitor.cs:83-87` 在 `Lifecycle == Leaving` 时已经提前返回，啃墙（`:107-114`）不会在离场后再被问到；新 giver 在同一 duty 里排第二，两者不会同时产出 job。潜在交叉在“同一面墙”：Gnaw 的 job 会预留目标，Mine 抢不到预留时会改 `WaitNearJob`，表现为“啃到一半改去凿/或干等”。属观察项，不构成阻塞。

## 6. 我没能验证的东西

- **运行时行为**：没有启动游戏，没有实测“门被锁 → 来客凿门 → 出图”，也没有实测凿门耗时、玩家可见提示、屋顶塌陷/火焰等后果。3.2 的结论是原版 IL 推断，不是实测。
- **1.6 的 API**：本机只装了 1.7（`1.7.4985 rev1269`），没有 1.6 的 `Assembly-CSharp.dll`，所以 `JobGiver_ExitMap.defaultLocomotion` 在 1.6 是否同为 `protected`、`PawnDuty.canDig` 在 1.6 是否存在，**没有核对**。1.7 上这两处都成立（前者 `Family`，后者 public 字段）。若 CI/本地只编 1.7，1.6 的编译风险没有被任何东西覆盖。
- **没有编译、没有跑测试**：评审是只读的，`dotnet build` / `dotnet test` 都没执行；`RHAH_JobGiverTests` 的现状（不会因为新文件失败，但也没覆盖它）是读源码得出的。
- **原版对非 `Mineable` 建筑的 `Mine` 作业在运行时是否真能把玩家的门打掉**：IL 层面 `DoDamage` 不要求 `Mineable`，但 `Toils_Mining` 的具体 toil 我未逐条展开，实际破坏速率/是否会被 `FailOnCannotTouch` 提前终止未验证。
- **好感/敌对/袭击判定**：来客破坏玩家建筑是否会触发派系好感变化、殖民地反击、`GenHostility` 状态改变，未查证。
- **其它 mod 兼容**：与 Toddlers（`LearningToWalk`）、牵引类 mod（`RHAH_LeashBridge`：新路径不调 `ClearDeparture`，正常靠 toil 切换时的 `LordJob_RHAH_Visitor.cs:281` 兜底，但“无 Lord + 直连 StartJob”的情形我没有确认是否一定清）、以及任何改写 `JobGiver_ExitMap`/`PawnDuty` 的 mod 的相互作用，均未验证。
- **性能数字**：4.3 的“每 tick 一次搜索”是按 IL 结构推断（`JobTrackerTickInterval` 未对 `TryFindAndStartJob` 加 hash 间隔门），没有 profiler 数据。

## 7. 如果退回，最小修复建议

结论不是退回；若评审方选择退回，最小集合就是 4.1–4.3，改动都很小、且都在同一个文件里：

1. `JobGiver_RHAH_Departure.TryGiveJob` 开头加节流：`if (!pawn.IsHashIntervalTick(60)) return null;`（4.3）。
2. 闸门之后加 `if (!RHAH_ChildMovement.CanWalkOut(pawn)) return null;`（4.1）。
3. 把 `JobGiver_RHAH_Leave` 的“抱持/放下”判断抽成可复用的 `CanDepartAlone`，两个 giver 共用（4.2）。
4. （顺带、不阻塞）把判断体抽成 `internal static TryCreate`，补 `RHAH_JobGiverTests` 的 XML 契约断言，删掉未使用的 `using RimWorld;`。
