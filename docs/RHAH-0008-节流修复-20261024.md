## 结论（5 行）

1. **节流改成什么**：把 `pawn.IsHashIntervalTick(60)`（按 tick 取模的"单 tick 窗口"）换成 **结果缓存 + 冷却**——`ConditionalWeakTable<Pawn, Retry>` 只记"下次可再搜的 tick"，**只有基类 `TryGiveJob` 返回 null（搜不到）才写入**，冷却 `GenDate.TicksPerHour`（2500 tick = 1 游戏小时）；拿到 job 就清表项。
2. **首检是否立即生效**：**是**。表里没有该 pawn 的表项 ⇒ `SearchDue` 直接为真，第一次闲置询问就一路走到 `base.TryGiveJob`；冷却到期也是"下一次询问立刻重判"，不看是否刚好落在某个 tick 上（`JobGiver_RHAH_Departure.cs:78-94`）。
3. **编译结果**：1.7 目标 `-t:Rebuild` **0 个警告 0 个错误**（`EXIT=0`，`runs\tmp\rhah-rebuild-1.7-0008-throttle.log`）；反射探针（`dotnet run`）589 类型 0 加载错误，`FailedSearchCooldownTicks=2500` / `PendingRetries=ConditionalWeakTable<Verse.Pawn,Retry>` / `SearchDue` / `RetryFor` 全部 PRESENT，DLL 字节里 `IsHashIntervalTick` = **False**。
4. **是否改 Def**：**否**。两份 `RHAH_Duties.xml` 仍是 706 B / `620A4D6875…`（SHA256 实测逐字节相同）；也没动 `RHAH_DoorPatch`、`famineVisitorsOpenDoors` 默认值、Lord 结构、设置项、存档键。
5. **是否有每 tick 昂贵调用**：**没有**。`CanReachMapEdge` / `TryFindBestExitSpot` 只在 `base.TryGiveJob` 里，冷却期内**一次也不进基类**（连两道守卫都跳过，`JobGiver_RHAH_Departure.cs:45-50`）；冷却外的每次询问至多一次基类搜索，与 `9b00cbd` 基线、与原版 giver 同频。

## 一、根因分析：`IsHashIntervalTick` 为什么会饿死触发

### 1.1 事实（引自复验报告，均为实测）

| # | 事实 | 出处 |

| 2 | `Leaving` 起点 tick 9634，到末次采样 tick 24724 共 **15090 tick ≈ 6.04 游戏小时**仍 `spawned=true`、人在封闭房内 | 复验 §3.1、§结论② |
| 3 | 全程 **0 异常**（含 `TryIssueJobPackage` / `JobGiver` 相关 0 条）⇒ giver 是**静默返回 null**，不是抛错被吞 | 复验 §五 |
| 4 | 单变量对照：同一 duty 换成原版 `JobGiver_ExitMapBest`（同基类、无三道闸门/节流、不节流），同一 pawn 在 tick 25324 拿到 `Mine`，tick 27124 `spawned=false` ⇒ 底座/路径/`canDig`/出口搜索都正常 | 复验 §3.2 |
| 5 | `carryTracker.innerList` 为空；`downed=false`；自己走了 48.1 格；`ageBiologicalTicks` ≈ 31.5 岁 | 复验 §2.2、§2.1 |

### 1.2 机制（推断，与上面 5 条一致）

- 思考树只在 pawn **闲下来**时才问 giver：原版 `Pawn_JobTracker` 在 `curJob == null && mindState.Active` 时调 `TryFindAndStartJob`（评审 §4.3 引的 IL 结构）。`Wait_Wander` / `GotoWander` 一给就是几百 tick，所以"可被询问的 tick"是**稀疏且随机**的（~1/300–1/600）。
- `Thing.IsHashIntervalTick(60)` 对某个 pawn 而言每 60 tick **只有一个** tick 为真，且这个相位由 `thingIDNumber` 固定。于是"能问"与"窗口开"两个事件必须**恰好同一 tick** 才可能触发，概率 ≈ `1/60 × 1/(300…600)` ≈ **3e-5–6e-5 / tick**；15090 tick 内的期望命中 **≈ 0.5–0.9 次**，实测 0 次，与观测一致（复验 §七 给的是同一量级：`<1 次`）。
- 关键点不是"重试变稀"，而是**窗口是单 tick 的**：只要 pawn 始终有短 job，节流窗口就**可以被无限错过**；而"到期后多等最多 1 秒"这个前提只在 pawn **持续闲置**时成立（评审 §4.3 的量化隐含了这个前提），对游荡型来客不成立。
- 另一个放大器：`IsHashIntervalTick` 的位置在 `base.TryGiveJob` **之前**（`95fc93c` 的 `JobGiver_RHAH_Departure.cs:33-37`），所以它挡的是"整个 giver"，连**本来能给出 job 的那一次**也一起挡掉——它挡的不是"重复搜索"，而是"第一次搜索"。这与评审 4.3 的原意（省掉重复的昂贵搜索，不是降低触发概率）方向相反。

### 1.3 本轮没有做的事（口径）

- **没有插桩**证明红臂就是这条节流造成的。排除法在复验报告里已经走到"`CanDepartAlone` 被存档数据排除、`CanWalkOut` 被实际行走反证、只剩 `IsHashIntervalTick`"，本轮**沿用**这个结论，没有再加日志。
- 因此本报告**不声称**"绿臂会回来"。本轮只保证一件事：**首问不被吞、且首问就是一次完整判定**。如果下一臂仍红，那原因必在 `CanWalkOut` / `RHAH_Api.Allows(ExitMap)` / `CanOrderLeave` / 基类，而不可能是节流——这一点现在是可以从代码结构直接判定的（节流分支只在基类**返回 null 之后**才写状态）。

### 2.2 为什么**不会饿死**（首检与到期首问都立刻生效）

1. **首检**：新 pawn / 新存档 / 表里没有键 ⇒ `TryGetValue` 失败 ⇒ `SearchDue` 返回 `true` ⇒ 同一 tick 内做完两道守卫 + 一次完整基类搜索。**没有任何"必须落在某个 tick"的条件**，因为它比对的是"上次搜不到的 tick + 2500"与当前 tick 的大小关系，而不是取模。
2. **到期**：`now >= nextSearchTick` ⇒ 立刻重判（并从表里移除，保持"表里只有正在冷却的人"）。冷却长度对"下一次询问什么时候来"没有要求，只要求"来了就允许"。
3. **拿到 job 不设冷却**：连续凿门时每次询问都会真正搜索一次，`Mine` 到期→重想→再搜索→继续凿，节奏完全由 job 自己的 `expiryInterval` 决定，**节流不参与**。这正是 95fc93c 丢掉的东西。
4. **守卫不缓存**：`CanWalkOut` / `CanDepartAlone` 的结论从不落表，成员状态一变（放下孩子、受伤、成长）下一次真正判定就会反映出来。

### 2.3 为什么冷却取 **1 游戏小时（2500 tick）** 而不是 60

- 本 giver 是 duty 树里的**第二个**节点，只有在**前一个 giver 已经返回 null（走不到地图边缘）**时才会被问到（评审 §2 表第 1 行的顺序论证、复验 §3.2 的对照）。所以：
  - 任何"让人能正常走出图"的变化（玩家开门、墙被别的东西打穿、人被挪到可达区域）都在**同一 tick** 被**不节流的** `JobGiver_RHAH_Leave.TryCreate` 接走（`JobGiver_RHAH_Leave.cs:59-85`），**与这里的冷却无关**；
  - 冷却期内真正会"晚一点"的，只有"几何变成可凿但仍不可走"这种极窄情形，代价是已判过失败的人**最多晚 1 游戏小时**再试一次——而这个人在此之前本来就是干站着。
- 反过来，取 60 tick（1 现实秒）意味着 31 次寻路/秒/受困人（`CanReachMapEdge` 1 次 + 至多 30 次边缘采样各一次 `CanReach`），5 个受困来客就是 ~150 次/秒，评审 4.3 要压的正是这个。1 小时把"搜不到"的代价压到 **1/2500**，同时**不影响任何一次能成功的搜索**。
- 数值上也沿用仓库既有口径：`RHAH_ReliefFood.RetryBaseTicks = GenDate.TicksPerHour`（`Source\Pawn\RHAH_ReliefFood.cs:32`，`JobGiver_RHAH_Gnaw.cs:79-85` 用它做"搜不到 target 就歇一小时"），即"一次昂贵搜索无果 → 冷却一游戏小时"是本仓库已有的模式；本轮没有直接引用那个常量，因为食物搜索的冷却是有玩法含义的节奏，而这里是纯性能保险，两者不该共用一个名字。

### 2.4 为什么缓存**不落盘**是安全的

- 表里只有一个 `int nextSearchTick`，语义是"下次可以再花 2500 tick 里的那一次昂贵搜索"，**不携带任何玩法状态**：不决定谁该离场、不影响 `duty` / `lifecycle` / 闸门 / 账目，也没有任何别处读它。
- **丢表项的后果 = 多搜一次**（多一次 BFS + 至多 30 次边缘采样），最坏是性能，不是行为。因此：读档/换图/重进游戏（pawn 是新实例，`ConditionalWeakTable` 自然空）⇒ 首问立即全量判定；`ConditionalWeakTable` 的键是弱引用，pawn 被回收/销毁后表项随之消失，不会随游戏进程无限增长。
- 唯一"内存缓存跨存档存活"的路径是**同一进程内读一个更早的档**（`TicksGame` 被回拨），那时旧值可能落在很远的未来。`SearchDue:86-90` 用 `nextSearchTick - now <= FailedSearchCooldownTicks` 兜底：**差值超过一个冷却长度的表项一律按到期处理**。正常单调时间下差值恒 ≤ 2500，这条分支永远不触发；时间被回拨时它把"可能几小时不再检查"压回一小时以内。
- 反过来，如果写成存档字段：要给旧档加键、要考虑卸载残留、还要在 `ExposeData` 里维护集合补齐（`Source\AGENTS.md` 的存档键条款），收益为零。

## 三、另两处守卫没有误杀成年健康来客

### 3.1 `CanWalkOut`：与 `JobGiver_RHAH_Leave` **同一个函数**，不是"另造一套"

- 我们的调用：`JobGiver_RHAH_Departure.cs:53` → `Compat.RHAH_ChildMovement.CanWalkOut(pawn)`。
- 前一个 giver 的调用：`JobGiver_RHAH_Leave.cs:46` → **同一个** `RHAH_ChildMovement.CanWalkOut`；为假时 `:54-57` 直接 `return null`。
- 判据（`Source\Pawn\Compat\RHAH_ChildMovement.cs:83-102`）：`Dead / Downed / CarriedBy != null` 否决；原版 `Baby` 且 `CurLifeStage.alwaysDowned` 否决；`Moving` 容量 `CapableOf` 为假否决；`LearningToWalk` hediff 阶段 ≤ 0 否决。**没有一项比前一个 giver 更严**（就是同一份代码）。
- 复验存档对受测体的实测（`docs\RHAH-0008-修复后复验-20261024.md` §2.2）：`downed=false`（每次采样）、`ageBiologicalTicks=113529284` ≈ 31.5 岁（成年，非 `Baby`）、`hediffSet` 只有 `RHAH_HungerMark` + `Malnutrition`（**没有** `LearningToWalk`）、实际自己走了 48.1 格（`Moving` 只要求 ≥ 0.15，`PawnCapacityDefs.minForCapable`）。⇒ 五条否决分支**全都不成立**，`CanWalkOut` 对该 pawn 返回真。`Malnutrition` severity 0.52 不影响 `Moving` 容量判定（原版只按容量算），且他确实在走路。

### 3.2 `CanDepartAlone`：只挡住"前一个 giver 本来也不会发 job"的人

- 定义：`JobGiver_RHAH_Leave.cs:162-166` → `pawn != null && pawn.CarriedBy == null && pawn.carryTracker?.CarriedThing == null`。
- 逐支对照"`JobGiver_RHAH_Leave.TryCreate` 会怎么处理这个人"：

| 状态 | `Leave.TryCreate` 的结果 | 新 giver 的守卫 | 是否比 Leave 更严 |
|-|-|-|-|
| 空手、`CarriedBy == null`（**成年健康来客的常态**） | 走到 `:59-63`，找出口成功就发 `Goto`；失败则 null → 轮到我们 | `CanDepartAlone` 为真，放行 | 否 |
| `CarriedBy != null`（正被抱着） | 这类 pawn 不 tick 自己的思考树；即便 tick，`:46` 的 `CanWalkOut` 已否决（`RHAH_ChildMovement.cs:85`） | 否决 | 否（更早的一层已经否决） |
| 怀里有**未就绪**孩子 | `:65-68` `HasUnreadyCarriedChild` ⇒ **null**（故意等放下/等孩子就绪） | 否决 | 否（两者都拒绝） |
| 怀里有**已就绪**孩子 | `:69-80` 发 `RHAH_CarryYoung`（**非 null**）⇒ 根本轮不到我们 | 否决 | 不适用：轮不到 |
| 怀里有已就绪孩子**且** `:60` 找不到出口 | **null**（`:59-63` 在抱孩子分支之前）⇒ 轮到我们 → 被否决 | 否决 | **是**，但这是"Leave 已经先失败了"的残留（评审修复报告 §五.4 已记录为有意保留），不是本轮引入 |

- 受测体实测：`carryTracker.innerList` 为空（⇒ `CarriedThing == null`、`CarriedBy == null`，复验 §2.2 第 8 行） ⇒ `CanDepartAlone` 对该 pawn 返回**真**。
- 结论：对"成年、健康、空手"的来客，两道守卫都是**真**，**不会**成为红转绿的阻挡项；能挡住他们的仍然只有"走不到边缘"这一件事（也正是本该发凿门 job 的条件）。

### 3.3 守卫在冷却期的位置（本轮唯一的行为取舍，明说）

冷却期内我们**不评估**这两道守卫（`:45-50` 在它们之前返回 null）。这不改变结果（冷却期无论如何返回 null），只是省掉重复判断。守卫的**结论**从不进缓存，所以"成员变成不能走"这件事不会被缓存掩盖——冷却期内本来也发不出 job，冷却到期后的第一问就重新判。
