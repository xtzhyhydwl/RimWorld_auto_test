## 一、逐条修复说明

行号均为改后文件的实际行号（commit `95fc93c`）。

### 4.1 「能不能自己走」的守卫

- **位置**：`Source/Pawn/JobGiver_RHAH_Departure.cs:39-43`

```csharp
// 不能自走的成员由抱持者带走 给他们凿门 job 只会原地无效寻路
if (!Compat.RHAH_ChildMovement.CanWalkOut(pawn))
{
    return null;
}
```

- **做法**：在 `Allows(ExitMap)` 之后、`base.TryGiveJob` 之前，用本模组既有的 `RHAH_ChildMovement.CanWalkOut`（`Source/Pawn/Compat/RHAH_ChildMovement.cs:83-102`：排除 `Dead/Downed/CarriedBy`、原版 `Baby` 且 `alwaysDowned`、`Moving` 容量不足、`LearningToWalk` 阶段 0）直接否决。没有另造判据，也没有新增 helper。
- **为什么**：`JobGiver_RHAH_Leave.TryCreate` 在 `CanWalkOut` 为假时返回 null（`JobGiver_RHAH_Leave.cs:46,54-57`），新 giver 正好接在这个 null 后面；而 `RHAH_StayWorkPatch.cs:32-42` + `RHAH_VisitorRules.cs:947-950` 只拦带 `exitMapOnArrival` 的 job，凿门 job（`Mine`/`AttackMelee`）不带这个标记，拦不住 —— 所以必须在**发 job 之前**用同一个判据挡掉。挡掉后这类 pawn 的行为回到改动前（拿不到 job，由抱持者带走/等照顾），不会再出现「幼童对着门凿 + 每 tick 无效寻路」。
- **顺带的一致性**：`CanWalkOut` 内含 `CarriedBy != null`，所以「正被别人抱着的人」在这里也一并挡掉（这类 pawn 本来也不 tick 思考树，属冗余保险）。

### 4.2 「抱着未就绪孩子」的检查

- **位置**：`Source/Pawn/JobGiver_RHAH_Leave.cs:162-166`（新增）+ `Source/Pawn/JobGiver_RHAH_Departure.cs:45-49`（调用）

```csharp
// 抱持者由 JobDriver_RHAH_CarryYoung 保证双方都允许离图后一起走 其它 giver 不许单独带走
internal static bool CanDepartAlone(Verse.Pawn pawn)
{
    return pawn != null && pawn.CarriedBy == null && pawn.carryTracker?.CarriedThing == null;
}
```

- **做法**：把评审 4.2 建议的「谁能单独离场」收成一处定义 —— 被抱（`CarriedBy`）或怀里有东西（`carryTracker.CarriedThing`，未就绪孩子必然落在这一支）就不能单独离图；新 giver 调它，为真才允许走原版 `Goto + exitMapOnArrival`。**没有改** `JobGiver_RHAH_Leave.TryCreate` 里原有的 `HasUnreadyCarriedChild`（`JobGiver_RHAH_Leave.cs:65-68`）与「抱着已就绪孩子 → 发 `RHAH_CarryYoung`」分支（`:69-80`），那条路径的语义原样保留。
- **为什么**：`JobGiver_RHAH_Leave` 在抱持时是故意返回 null 的（等放下或等孩子就绪，由 `JobDriver_RHAH_CarryYoung.LeaveIfExit` 保证双方就绪后一起出图）。新 giver 若在这个 null 之后接管，就会让抱持者直接吃原版出图 job：原版 `Pawn.ExitMap` 会把被抱的同派系 pawn 一起带出图、跨派系则 `kidnapped.Kidnap`（评审 §5.④），孩子的 mod 状态可能还停在 `Arriving/SeekingFood`，批次账目上留下「已离图但仍算活跃来客」。
- **口径选择（比评审更保守一处）**：`CanDepartAlone` 挡的是**任何**怀里有东西的 pawn，不只「未就绪孩子」。理由：抱持者的正确出口是 `RHAH_CarryYoung`，不是「自己走 + 顺带把孩子拖出图」；这一支在 `9b00cbd` 之前本来就是「拿不到 job」，所以不算新退步（残留限制见第五节第 3 条）。

### 4.3 出口搜索节流

- **位置**：`Source/Pawn/JobGiver_RHAH_Departure.cs:10-12`（常量）与 `:33-37`（判断）

```csharp
// 受困者每闲置 tick 都会问到这里 原版出口搜索是区域 BFS 加最多 30 次边缘采样
// 与上一个 giver 的同类搜索叠加即每 tick 两次 故按 60 tick 重试
const int RetryIntervalTicks = 60;

// 上一个 giver 不节流 一旦能走到边缘当 tick 就接手 这里稀疏重试不拖慢能走掉的人
if (!pawn.IsHashIntervalTick(RetryIntervalTicks))
{
    return null;
}
```

- **做法**：用原版 `Thing.IsHashIntervalTick(int)`（按 `thingIDNumber` 错开、常量时间取模、无分配、无新状态、无存档键）把新 giver 的重试频率压到 60 tick 一次；节流点放在两道廉价闸门之后、`base.TryGiveJob`（真正做 `CanReachMapEdge` + `TryFindBestExitSpot`）之前。
- **为什么安全（不会让能走掉的人卡住）**：新 giver 是 duty 树里的**第二个**子节点。`JobGiver_RHAH_Visitor` 在 `Lifecycle == Leaving` 时直接把 `JobGiver_RHAH_Leave.TryCreate` 的结果返回（`JobGiver_RHAH_Visitor.cs:83-87`），而这个 giver **不节流**；门被玩家打开、墙被别的东西打穿、或人走到另一个可达区域的那一刻，`TryCreate` 当 tick 就给出 `Goto + exitMapOnArrival`，根本不会问到新节点。所以节流只影响「第一个 giver 也返回 null（走不到地图边缘）」的人。
- **为什么不拖慢凿门**：`Mine`/`AttackMelee` job 本身持续若干秒，job 到期后重想一次、最多多等 1 游戏秒（60 tick）才重试，门破的总时长没有可感知变化；反过来用「游戏内小时级」（2500 tick）会让一次凿门拖成几十游戏小时，所以没选小时级，选「缓存结论 N tick」里的 N = 60（评审 4.3 的建议值）。
- **量化**（按评审 §4.3 引的 IL 结构：`curJob == null && mindState.Active` 时每 tick 调 `TryFindAndStartJob`）：节流前每个闲置 tick ＝ 既有 giver 1 次出口搜索（`JobGiver_RHAH_Leave.cs:60`，未改动）+ 新 giver 1 次（含区域 BFS 与最多 30 次边缘采样）；节流后＝每 tick 1 次（与基线同）+ 每 60 tick 多 1 次。**新增路网的频率降为 1/60，且没有任何新的每 tick 工作**（`IsHashIntervalTick` 只在两个廉价判断之后执行）。

### 一并按「建议」做掉的两处（同文件，零行为影响）
