围攻里的儿童为什么只会闲逛
以及那三处必须先改的地方

改动方向对、落点小，可以合；但有一条判据放错了层、一处名字与语义打架、还有一个在原版下恒真的死条件——而那个死条件在装了 Toddlers 时会把儿童重新推回"闲逛 + 饿死"。

评审对象 未提交的 2 个源文件 基准 d699404 评审方式 只读（read / grep / git） 未做 未编译、未跑单测、未起游戏

结论：先做 3 条必修（1 条分层 + 2 条命名/语义）。RHAH_FamineWeapons 的两个判据不一致判为加注释、不改行为；Pawn → Compat 不算越界（既有约定，有 3 处先例），别顺手去改它。

后续（21:3x，用户口径覆盖了 B-1）：本模组不该对"能不能打"加任何条件。所以最终不是"把判据搬到规则层"，而是把年龄判据整个删掉、不加替代—— 原版婴儿天然执行不了暴力，玩家装了让婴儿能打的模组也不归我们管。

一、症状是怎么一步步发生的

这是整份评审的前提。每一次"为什么错"的判断，最终都挂在这条链的某一环上。

  1. 围攻开始，来客全员拿到 role = Siege
    到这里成人和儿童没有任何差别——Fight 闸门（role == Siege）对他们一律放行。
  2. CanFight 里的 Adult() 把儿童拦下
    成人过，儿童不过。这是本票要改的那一行。
    JobGiver_RHAH_Visitor.cs:52
  3. 派 duty 的地方按 CanFight 分流
    成人 → AssaultColony；儿童 → RHAH_VisitorSeek，而它的焦点是儿童自己站的那一格。
    LordToil_RHAH_ArmedAssault.cs:19-21
  4. 这条 giver 在武装进攻期间直接返回 null
    于是"去吃东西"那一段一次都走不到——不是被闸门挡住，是根本没轮到。
    JobGiver_RHAH_Visitor.cs:88
  5. 只剩原地闲逛，最后饿倒
    行为上看起来就是"这孩子什么都不会干"。
  6. 修法：把"能不能打"从"是不是成人"改成"是不是婴儿"
    一处判据同时决定"派 duty"和"派战斗 job"，所以两处一起好；吃饭那一半也跟着好，不用单独改取食逻辑。
    CanFight → RHAH_VisitorRules.AllowsCombat

二、三条必修

点开看"现状 / 为什么错 / 怎么改 / 影响面"。三条都不改行为（第三条只在装了 Toddlers 时才可能改行为）。

必修 · 分层 B-1 年龄规则留在了 JobGiver 层，与紧邻先例相反
位置
JobGiver_RHAH_Visitor.cs:59-64，调用点 :52
现状
新方法把"年龄 + 身体"两条判断自己捂着：!= Baby && ManipulationStage > 0
为什么错
① RHAH_VisitorRules 自述职责就含"年龄"，文件里已有一整族年龄规则（KeepsAge / YoungAge / WalkingAgeFloor…），新规则却落在 JobGiver； ② ManipulationStage 的 0/1/2 是 Compat 的内部约定，Pawn 层裸写 > 0 等于把阈值知识复制到第三处； ③ 同一个目录里的先例正好相反：JobGiver_RHAH_Feed 把原始 stage 交给 RHAH_VisitorRules.BlocksReliefFeed 去判阈值。
建议
下沉成 RHAH_VisitorRules.AllowsCombat(stage, manipulationStage)，JobGiver 只负责取数。
影响面
2 个文件约 6 行 + 一条纯函数单测；不动行为。
处置：不适用。这条判据最终被整个删掉了（见顶部口径与 C-2），所以不存在"该放哪一层"——规则层不加这个函数。
必修 · 命名 C-1 AbleToFight 与 CanFight 是同义词
现状
同一件事在代码里有四个带 fight 的名字：闸门 Fight、查询 Allows(pawn, Fight)、合成判据 CanFight、子条件 AbleToFight。前三个各自名副其实，第四个是纯同义重复——Can 和 Able 在英文里都是"能"。
为什么错
违反"同一个概念在代码里只有一个名字"；更实际的问题是名字隐去了真正的判据（年龄 + 动手阶段）—— 下一个想知道"这人算不算能打"的地方（RHAH_FamineWeapons）无名字可复用，只能再写一遍 Adult()，于是有了 D-1。
建议
并进规则层；若坚持留原层，改名 CombatCapable（Can* = 判据，Capable = 身体条件）。
影响面
纯改名 2 行，零行为变化。
处置：采纳前者——名字直接消失，CanFight 保持唯一入口名。
必修 · 语义 C-2 ManipulationStage > 0 在原版下恒真，只在 Toddlers 下生效——而生效时方向是反的
为什么说它是死条件：ManipulationStage 返回 0 只有两条路，其中第一条就要求 == Baby。
场景ManipulationStage>0!= Baby结果
原版 · 成人真真等价
原版 · 儿童真（无 hediff ⇒ 恒返回 2）真等价
原版 · 婴儿假（第一条就返回 0）假等价
Toddlers · 能走但动手阶段 0假真分歧：被挡在战斗外
为什么错
① 死条件 + 只在第三方模组下才活的分支，没有注释、没有测试； ② 它生效的方向正好与口径相反：Toddlers 下"能走、但动手阶段还是 0"的儿童会被判成不能打 ⇒ 又落回 RHAH_VisitorSeek ⇒ 还是闲逛、还是不吃——正是本票要修的那个症状； ③ 注释写的"能动手"也不准：stage 0 的另一半含义是"原版不能动的婴儿"，"能动"和"动手"不是同一个轴。
建议
判据只留 != Baby（倒地/昏迷 CanFight 已判）；若确实要"不能动手就不许打"，改用与"能动"同源的命名判据，并补 stage 0 的用例。
影响面
判据 1 行 + 1 条测试；行为变化只在 Toddlers 场景（推测，未在游戏内验证）。
处置：比"删掉"更彻底。不只是删 ManipulationStage > 0，而是把整条年龄判据删掉、不加任何替代—— 婴儿本来就被原版的 !pawn.Downed 挡住（原版婴儿恒为 alwaysDowned）；装了"让婴儿能走 / 能打"的模组，那是玩家的选择，不由本模组阻塞。

三、七条建议

不阻塞合并。其中 D-3 直接贴着改动的判据，是"语义变了名字没跟上"的典型。

建议 D-1 两套"能打"判据不一致 → 只加注释
现状
RHAH_FamineWeapons 仍用 Adult() 决定发不发武器 ⇒ 改动后合成结论是"儿童会徒手参战、永远拿不到武器"。
为什么只加注释
本票非目标明写"不新增儿童专属武器"；给儿童发武器会直接改变围攻里儿童存活率，是设计决定，不该由一次修 bug 顺带做；adult 这个形参名在"发放武器"语境里是准确的，不构成命名债。
处置
加一行注释说明"两个判据不同是刻意的"，行为不变。
建议 · 口径 D-2 实际作用域是「所有被玩家打成敌对的来客」，不止围攻
链路
RHAH_BatchAttitude 会把批次成员态度置 Hostile → Fight 闸门对 Hostile 一律放行 → 乞讨 / 偷窃等事件被下令开打后，儿童这次也会跟着打（以前不会）。
性质
不是 bug，是口径问题：票面原写"其它事件类型的儿童不被顺带改掉"。
处置
未决，需拍板：① 一视同仁；② 只在围攻 lord 里放行儿童。
注意：这条不建议默默过去——它决定这个改动对外的影响面有多大。
建议 · 命名 D-3 LordToil 里的 fights 名不副实，还带一个死项
原式 fights = (swarm || Enabled) && CanFight，却只在 fights && !swarm 时给突击 duty ⇒ swarm 那一支永远被丢弃。
swarmEnabledCanFight改前 duty改后 duty
真任意任意VisitorSeekVisitorSeek
假假任意VisitorSeekVisitorSeek
假真假VisitorSeekVisitorSeek
假真真AssaultColonyAssaultColony
另一个错
蜂群单位其实照样打（走 RHAH_MouseSwarm / Wait_Combat），所以叫 fights 也不对——它表示的是"拿 AssaultColony duty"。
处置
改名 assaults、去掉死项；八格真值表逐格等价。同时给 VisitorSeek 那行加注释（借它的 think tree，站位就是原地）。
建议 · 语义 D-4 != Baby 与仓里既有的 flags 惯用法不一致
现状
被替换掉的是扩展方法 Adult()（按位测试），新代码用不等号。
为什么错
DevelopmentalStage 是 [Flags]，Baby|Child 这种组合在 lifestage XML 里合法 ⇒ != Baby 会把它判成"不是婴儿"。
处置
随年龄判据一起作废——判据整个删掉了，已经没有"是不是婴儿"要判。
建议 · 测试 D-5 / D-6 用例名超出断言、辅助方法名偏轻
D-5
用例名原本声称"Siege 让成人与儿童行为等价"，但它只断言 CanFight 为真 ⇒ 改名 VisitorCombatAcceptsChild，行为等价的证据留在票面文档（那里有真机取证）。
D-6
SetLifeStage 其实是"替换整张寿命表"（重写 lifeStageAges + 重建 ageTracker），不是"设一个值"⇒ 名字保留、加一行注释说明适用范围。
附带确认
不存在跨用例污染：每个 Visitor() 都新建 RaceProperties 与 ThingDef。
建议 · 验证缺口 D-7 新用例是 CanFight 第一次被断言为 true——绿不绿没人验过
风险点
CanFight 末条要过 pawn.WorkTagIsDisabled(WorkTags.Violent)，而测试替身 Visitor() 的 story / workSettings 都是 null——这条路径以前从没被走到 true。
处置
下次开会话先跑一次 Tests 工程确认。若在替身上抛异常，需要给 Visitor() 补 workSettings / story 替身（推测，评审没跑）。
本机限制
dotnet test 的 testhost 被 OpenProcess 拒绝（Win32Exception 5）⇒ 只能构建、不能跑。
