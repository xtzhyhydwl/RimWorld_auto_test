# RHAH E12 乞食围攻：信件永远关不掉 —— 根因

> 只读分析，未改任何文件，未编译、未运行游戏。路径相对 `RimworldMods/ratkin_hunger_and_havoc`。
> **实测**＝直接读到代码；**推测**＝未运行验证。

## 结论（先行 3 行）

1. 「选敌对」这条路径**从不写 `Settled`**，所以 `RHAH_ChoiceRecord.Open` 永远为真，信件永远 `Pending`；`Pending` 恰好同时禁掉右键、隐藏 Close、并让超时判定被 `ArmedAssault` 跳过 —— 玩家侧看到的就是「没有出口」。
2. 于是信件只剩两个出口：**交足食物**（`Deliver`），或 **`Owner(record) == null`**（整批再没有任何"活着+在地图上+未倒地+可下令"的成员）。后者不是"围攻结束"的判据，而是"批次一个合格成员都不剩"的判据。
3. 围攻里天然存在**合格但不参战**的成员（`LordToil_RHAH_ArmedAssault` 把打不了的人派成原地游荡，见 `Source/Pawn/LordToil_RHAH_ArmedAssault.cs:19-21` + `Source/Pawn/JobGiver_RHAH_Visitor.cs:43-56`）。所以他们活着时 `Owner != null`，"杀光所有在打的围攻者"也关不掉信；只有把**批次里每一个人**都弄成不可用，才会在下一个整点被静默收信。

## 2. `Refresh` / `Owner` 逐条前置条件（`Source/Pawn/RHAH_ArmedDemand.cs`）

### 2.1 `Owner(record)`（`:67-84`）—— 唯一的「围攻还在不在」判据

1. `record != null`，`RHAH_ChoiceRuntime.FindMap(record.MapId)` 非 null（`:69`）
2. `map.lordManager.lords` 里存在一个 Lord，其 `LordJob is LordJob_RHAH_Visitor job` 且 `job.ArmedChoiceId == record.Id`（`:74`）
3. 该 Lord 的 `ownedPawns` 里存在一个 pawn，**同时**满足（`:79-80`）：
   - `RHAH_Api.Get(pawn)?.SpawnBatchId == record.BatchId`
   - `record.PawnLoadIds.Contains(pawn.thingIDNumber)`
   - `pawn.Spawned`
   - `!pawn.Downed`
   - `RHAH_BatchAttitude.CanOrderLeave(pawn)`：未死、未销毁、`MapHeld != null`、非玩家派系、非囚、非奴、`IsVisitor`、`AllowsModBehavior`，且 Lord 为空或访客 Lord（`Source/Pawn/RHAH_BatchAttitude.cs:207-218`）

任一条件命中即返回该 Lord；**一个都不命中才返回 null**。

### 2.2 `Refresh(record)`（`:86-92`）

```
record == null || !record.Open  → return false      // 不再尝试删信
Owner(record) != null           → return true       // 什么都不做
否则                            → Finish(Ignore)    // Settled=Ignore + RemoveLetter
```
即：**`Refresh` 是「全批无人 → 收信」的唯一执行者**，而 `Finish` 已经是 a+c 完整实现（不是只标状态位）。

### 2.3 谁调用 `Refresh`，多频繁（实测）

| 调用者 | 频率 | 备注 |
| - | - | - |
| `Source/Core/GameComponent_RHAH_Game.cs:59-63` → `Source/Incidents/RHAH_ChoiceRuntime.cs:108-126` → `RHAH_ArmedDemand.cs:103-112` | **每游戏 tick 进一次，`:107` 用 `tick % GenDate.TicksPerHour == 0` 收敛成每游戏内小时一次** | 与 Lord 是否存活无关 |
| `RHAH_ChoiceRuntime.cs:204`（`TrySettleRequest` 武装分支） | 每次点信里的按钮 | `Refresh` 假 → 直接 `return record.Settled` |
| `RHAH_ArmedDemand.cs:184`（`PlanPayment`，被 `CanPay` 调用） | **每次打开/绘制信件、评估"交付"按钮时** | 有副作用：评估按钮本身就会尝试收信 |
| `Source/Pawn/LordJob_RHAH_Visitor.cs:166-186`（`Notify_PawnLost` / `Notify_PawnDowned` / `Notify_LordDestroyed` → `RefreshArmedRequest`） | 事件驱动 | 死亡/倒地/离图/Lord 销毁时 |

**答案（否证任务里的假设）**：兜底**不依赖 Lord 的 tick 回调**。主轮询是 `GameComponent.GameComponentTick`，Lord 被销毁也照样每 tick 跑到。所以「Lord 先被销毁 → 回调永远不来 → 信永不清」**不是**本 bug 的根因。

### 2.4 当围攻者全死时，`Owner` 会返回 null 吗？

**会，代码可证**：死者被三重排除 —— `CanOrderLeave` 首条即 `pawn.Dead`（`RHAH_BatchAttitude.cs:209`），且 `pawn.Spawned` 对尸体为假，`Lord` 也会在成员丢失时移除该 pawn。**所以"真·全死"必然导致 `Owner==null` → 下一整点 `Finish` → 删信**（`Source/Tests/RHAH_AttackChoiceTests.cs:202-227` 的单元测试也正是这么断言的，包括 `dead` 一行）。

这与你实测「全死透也不消失」**直接冲突**，因此唯一自洽的解释是：**那一局里 `Owner` 判据始终有人命中** —— 见 §6。

### 2.5 `Refresh` 会不会提前 return 导致"集合空了却没走到 Finish"？

- `:88` 是唯一提前 return：`!record.Open`。这只会发生在 `Settled` 已被写过的时候（此时 `RemoveSettledArmedLetters` 会兜删信）。
- `Owner` 里**没有**"先遍历、后判空"的分叉：它自己就是空集判定，空集必然返回 null。
- `Tick`（`:103-112`）在 `!Enabled` 时走 `Resolve(Ignore)`（也删信），其余提前 return 只影响超时判定，不影响 `Owner`。

## 3. `Finish` 到底做了什么（`:94-101`）

```
record.Settled = action;                                   // a
遍历 Find.LetterStack.LettersListForReading（倒序），
  命中 letter is ChoiceLetter_RHAH_Request && letter.choiceId == record.Id 的，
  Find.LetterStack.RemoveLetter(request);                   // c
```
- 它**同时**做 a 和 c，**不是**只标状态位。
- 匹配靠 `(类型, choiceId)`。`choiceId` 在 `Source/Incidents/RHAH_IncidentFacts.cs:348-356` 由 `record.Id` 写入；`nextChoiceId` 是有存档的（`Source/Core/GameComponent_RHAH_Game.cs:438`），所以"id 撞车导致删错信"不成立。
- `Finish` 是 `private static`，没有消息、没有日志 —— 收信是**静默**的（这也是"玩家以为没生效"的一部分）。

## 4. 信件类全文要点（`Source/Incidents/ChoiceLetter_RHAH_Request.cs`，184 行，无 `#if`）

| 成员 | 行为 |
| - | - |
| `CanDismissWithRightClick`（`:17`） | `!Pending(FindRecord(...))` → **记录还 Open 就禁右键** |
| `Choices`（`:19-90`） | `ArchivedOnly || !Pending(record)` 时**只给 `Option_Close`**（`:24-28`）；否则给 交付（`:62-76`，E12 走 `RHAH_ArmedDemand.CanPay`）+ 拒绝（`:79-81`）+ 忽视（`:82-84`）+ 原版"暂缓"（`:88`）。**待回复期间没有 Close** |
| `ExposeData`（`:92-101`） | 只存 `choiceId/mapId/kind/site/amount/expireTick`；**不存"是否已回答"** |
| `Wrapped`/`Settle`（`:104-138`） | 点按钮 → `RHAH_ChoiceRuntime.TrySettleRequest`；`:119`、`:136` 是信自己的删信点（`:136` 条件 `!record.Open`） |
| `Pending`（`:140-144`） | `record != null && record.Open && (IsRequest(record) \|\| expireTick 未到)`；E12 是 `IsRequest`，所以**只看 `Open`，与 `ExpireTick` 无关** |
| 未覆写的成员 | **没有** `Tick`、`CheckDismiss`、`AutoArchive`、`CanShowInUI`、`Timeout`（全文实测）；`1.6/1.7` 的 `RHAH_Letters.xml` 里 `RHAH_ChoiceRequest` / `RHAH_ChoiceRequestGreen` 也没有超时/自动归档字段 |

**回答第 3/4 问**：
- 信件**没有任何轮询**去盯 `Settled`。存在一个每小时轮询（`RHAH_ChoiceRuntime.cs:144` → `:148-167`），但它只删 `!record.Open` 的记录对应的信；`Settled` 一旦被写，信本来就在 `Finish` 里删了，所以它是补刀，不是主路径。
- 因此：**只要走不到「交付」或「`Owner()==null`」，信就永久存在** —— 这一条被证实。
- 「信只由交付回调移除」不是硬编码，但**在行为上等价**：把记录从 `Open` 变成 `!Open` 的玩家可触发动作只有交付（`RHAH_ArmedDemand.cs:153-162`）；拒绝/超时只置 `ArmedAssault`，不写 `Settled`。

## 5. 逐条走一遍「选敌对 → 全杀 → 信还在」

1. 玩家点「拒绝/敌对」：`ChoiceLetter_RHAH_Request.cs:79-81` → `Settle` → `TrySettleRequest` → `RHAH_ChoiceRuntime.cs:204` `Refresh`（此时有人 → true）→ `:212` `Resolve(Reject)`。
2. `Resolve`（`RHAH_ArmedDemand.cs:140-169`）：`Enabled` 为真、`action != Deliver`，走 `:164-168` —— 置 `job.ArmedAssault = true`、转敌对、下令进攻、发消息。**`Settled` 一个字节都没写**（实测）。
3. 之后 `Pending` 恒真 → 右键禁、无 Close、`:110` 的 `!job.ArmedAssault` 让它跳过超时 → `ExpireTick` 名存实亡。
4. 玩家把**在打的**围攻者全杀了：`Owner` 只要求"还有一名合格成员"，非战斗成员（`CanFight` 为假：非成年、禁暴力、`Allows(Fight)==false`、仍在 `WaitFood` toil、被 stun —— `JobGiver_RHAH_Visitor.cs:43-56`）拿到的是 `RHAH_VisitorSeek` 原地游荡（`LordToil_RHAH_ArmedAssault.cs:19-21`），**还活着、还在地图上、还能被下令**。
5. `Owner` 继续返回那个 Lord → `Refresh` 每整点返回 true → `Finish` 永远不执行 → 信永远挂着；交付按钮又因为拿不到"可达食物 + 可达成员"而常灰。

## 6. 根因判定

**根因（结构性，实测+一处推测）**：E12 把"事件是否已解决"只存在 `Settled` 一个位，而**「敌对」这条分支故意不结算**（`RHAH_ArmedDemand.cs:164-168`）；于是记录永远 `Open`、信件永远 `Pending`，而 `Pending` 正是禁掉全部人工出口（右键 `:17`、Close `:24-28`、超时 `:110`）的开关。剩下唯一的自动出口 `Owner(record)==null` 判的不是"围攻结束"，而是"**批次里一个合格成员都不剩**"；围攻中不参战却合格的成员（见 §5.4）让这个条件在实践中长期不成立。所以玩家侧的表现就是：**只有正常交食物（`Deliver` → `Finish` → `RemoveLetter`）能让信消失，杀光在打的人不行。**

**关于「我把他们全部杀死、全死透」**：若字面成立（`Owner` 判据无人命中），按代码必在下一个游戏内小时被静默删信，且打开信件评估"交付"按钮时（`RHAH_ArmedDemand.cs:184`）也会立刻触发删信。实测与之矛盾，**故推断那一局里仍有至少一个命中 `Owner` 判据的成员**（最可能是非战斗成员、卡在地图边缘没走出去的离场者、或批次里非成年的幼崽）。**此条为推测，未运行验证**；要定论只需在 `Refresh` 的 `Owner==null` 分支与 `Owner` 命中处各打一行日志（pawn 名 + 状态），或让玩家在围攻结束后用开发工具数一遍该批次（`CompRHAH_Pawn.State.spawnBatchId` 相同）还活着的成员。

## 7. 最小修改点候选（不改事件语义）

### 候选 1（推荐，1 行级）：把「敌对/超时」当作一次作答，结算并删信

位置：`Source/Pawn/RHAH_ArmedDemand.cs:164-168`（`if (!StartsAssault(...)) return;` 之后）
做法：在 `job.ArmedAssault = true;` 前后调用现成的 `Finish(record, action);`（或先 `record.Settled = action;` 再 `Finish`）。
效果：玩家一作答，记录离开 `Pending`，`Finish` 用现成逻辑删信；**围攻本身的一切都不变**（`ArmedAssault`、转敌对、Toil、`ArmedChoiceId`、Lord 全部照旧），只是把"已回答"写进状态位。附带好处：`RemoveSettledArmedLetters` 多一道补刀，重进存档也不会复活。
风险点（需注意，不改变玩法）：`Settled=Reject` 后 `Holds/FoodRequest/NoteFood` 会失效（`RHAH_ArmedDemand.cs:42-59`、`:127-139`），即"敌对后再塞食物结算"这条路会被关掉 —— 按"已回答"的语义这正是期望行为。

### 候选 2（保底，收紧 `Owner`）：让不参战的人不再钉住信件

位置：`Source/Pawn/RHAH_ArmedDemand.cs:79-80`
做法：在 `job.ArmedAssault == true` 时追加"该 pawn 仍处于敌对/可战"判据（例如 `RHAH_Api.Get(pawn).Attitude == RHAH_Attitude.Hostile` 或复用 `JobGiver_RHAH_Visitor.CanFight(pawn)`）。
效果：只剩非战斗残留时 `Owner` 变 null → `Finish(Ignore)` → 静默收信。
风险：会让"围攻结束"提前认定，`Ignore` 是静默的（`Finish` 不发消息）；`CanFight` 含 `stunner`/`Adult` 等外部条件，收紧过头可能在战斗中误判为 null（把还在打的信关掉）。**建议只作候选 1 的补充，不作主修**。

### 候选 3（最小 UI 兜底，不推荐单独使用）

位置：`Source/Incidents/ChoiceLetter_RHAH_Request.cs:24`
做法：在 `!Pending` 之外，当记录已转围攻（如 `Pawn.RHAH_ArmedDemand.Refused(任意成员)`）时也 `yield return Option_Close`。
风险：关信后玩家再没地方交付，且记录会永久留在 `openChoices`（`Settled` 仍为 `None`）—— 换了泄漏点。只应作为候选 1 之外的过渡手段。
