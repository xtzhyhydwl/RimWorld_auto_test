# RHAH E12「乞食围攻」：`Owner(record) == null` 兜底为什么在真实游戏里不生效

- 对象：`RimworldMods/ratkin_hunger_and_havoc`（下称 RHAH），事件 I-014 / I-030 / I-045。
- 方式：**只读**静态阅读 + 对**已部署 DLL** 做了一次 IL 调用点扫描（不编译、不运行游戏、不改任何文件）。除标「推测」外，结论都有代码行号。
- 路径一律相对 `ratkin_hunger_and_havoc`。

---

## 0. 结论（3 行）

1. **兜底的对象不是"名册"，是"活着的 Lord"**：`Owner(record)`（`Source/Pawn/RHAH_ArmedDemand.cs:67-84`）遍历的是 `FindMap(record.MapId).lordManager.lords`，再在这些 Lord 的 `ownedPawns` 里找**一个**同时满足 6 个条件的成员；`record.PawnLoadIds` 只当白名单用，**没有任何一处代码遍历"死人名单"**。
2. **所以「死人残留引用让 `Owner` 永不返回 null」这个假设可以直接否证**：`Owner` 没有任何"pawn 无效就跳过整个判定 / 集合非空但无效项导致既不 null 也不有效"的分支 —— 它只有两条出口：`return lord`（命中）或 `return null`。而且死者在**第一道**就被挡掉：`CanOrderLeave` 首条是 `pawn.Dead`（`Source/Pawn/RHAH_BatchAttitude.cs:209`）。
3. **于是「信关不掉」只剩一个自洽解释：`Owner` 确实命中了一个"活着 + Spawned + 未倒地 + 可下令"的同批次成员。** 关键在 `Owner` **不检查这个成员是否在 `record.MapId` 这张图上、也不检查它是否还在敌对/参战**，而调试面板/`Present`/通用兜底 `CloseUnavailable` 全都按 `MapHeld.uniqueID == record.MapId` 过滤（`Source/Incidents/RHAH_ChoiceRuntime.cs:640`）。这一处不对称能同时解释用户看到的三件事：面板里没有、地图上没看见、信却一直挂在右边。（"敌对"分支本身不写 `Settled` —— `Source/Pawn/RHAH_ArmedDemand.cs:164-168` —— 是让"唯一自动出口"变成"批次里还剩一个活人"的根）

**关于题面里那两个具体怀疑，逐条回答（实测）：**

- 「pawn 死亡时有没有代码把成员从批次/注册表里摘掉？」
  - **从 `record.PawnLoadIds` 里：没有任何摘除逻辑**（全仓只有追加点 + 读档补空集合：`Source/Core/GameComponent_RHAH_Game.cs:500-509`）。死者 ID 永久留在记录里。
  - **从 Lord 的 `ownedPawns` 里：有，而且有两道**。① 原版 `Lord.Notify_PawnLost` 会按 `LordJob.ShouldRemovePawn` 移除，RHAH 覆写对 `Killed` 返回 true（`Source/Pawn/LordJob_RHAH_Visitor.cs:160-164`，只对 `Incapped`/`PreserveForAttitudeChange` 时的 `ChangedFaction` 返回 false）；② 本模组的死亡补丁 `RHAH_DeathPatch`（`Source/Pawn/RHAH_LifecyclePatch.cs:40-67`）在 `Pawn.Kill` 后置里 `SetLifecycle(Dead)` 并调 `RHAH_VisitorGroup.NotifyDead`（`:58-59`）→ `NotifyReleased`（`Source/Pawn/RHAH_VisitorGroup.cs:37-62`）→ `lord.RemovePawn(pawn)`，空 Lord 再 `RemoveLord`。
  - 其余 `Hook_/Patch` 里也没有"批次摘人"逻辑：`Patch` 全仓只命中 `Toils_Ingest.FinalizeIngest`、`Pawn.Kill`、`Pawn.ExitMap`、`Pawn_AgeTracker.BirthdayBiological`（`Source/Pawn/RHAH_LifecyclePatch.cs:11/40/70/108`）。
- 「死引用会不会让 `Owner` 既不返回 null 也不返回有效 pawn？」
  - **不会，且与"集合里有没有死引用"无关**：死 pawn 同时被 `pawn.Dead`（`RHAH_BatchAttitude.cs:209`）与 `pawn.Spawned`（`:79`）挡掉；`pawn == null` 的条目在 `:79` 处 `snapshot?.SpawnBatchId == record.BatchId` 直接为 false 短路，不会抛异常。`Owner` 的返回值只可能是"有效 Lord"或"null"，不存在第三种状态。

### 2.3 谁会让一个"已经不参战"的成员继续合格

- `LordToil_RHAH_ArmedAssault.UpdateAllDuties`（`Source/Pawn/LordToil_RHAH_ArmedAssault.cs:13-22`）：`fights = (swarm || Enabled) && JobGiver_RHAH_Visitor.CanFight(pawn)`；打不了的人拿到 `RHAH_VisitorSeek` **原地游荡**（`:21`）。
- `CanFight`（`Source/Pawn/JobGiver_RHAH_Visitor.cs:43-57`）要求：Lord 未因关闭开关而停用、当前不在 `WaitFood` 且被列进食、`CanOrderLeave`、`Spawned`、`!Downed`、未被 stun、`DevelopmentalStage.Adult()`、态度 `Hostile`、派系敌对、`Allows(Fight)`、未禁 `WorkTags.Violent`。

- I-014 的批次数是固定 5（`Source/Incidents/RHAH_IncidentWeight.cs:154`），角色统一 `Siege`（`Source/Incidents/RHAH_IncidentRoster.cs:39-41`），但**年龄是随机的**（`Source/Incidents/RHAH_IncidentFacts.cs:41` → `GenerationAge`，区间由 `settings.minGeneratedAge/maxGeneratedAge` 决定），5 人里出现未成年人是正常的。

## 3. `Refresh` 的调用链与全部前置条件

```csharp
// Source/Pawn/RHAH_ArmedDemand.cs:86-92
internal static bool Refresh(RHAH_ChoiceRecord record)
{
    if (record == null || !record.Open) return false;   // 唯一提前 return
    if (Owner(record) != null) return true;             // 命中就什么都不做
    Finish(record, RHAH_ChoiceAction.Ignore);           // Settled=Ignore + 删信
    return false;
}
```

`Refresh` **全文只有 2 个 if**，没有 `Find.LetterStack == null` / `letterId` / `lord == null` 之类的提前 return；`Owner` 内部也没有。所以"走不到 `Owner`"只可能发生在调用方。

### 3.1 谁调用 `Refresh`

| 调用者 | 频率 | 代码点 |
| - | - | - |
| `GameComponentTick` → `RHAH_ChoiceRuntime.Tick` → `RHAH_ArmedDemand.Tick` | 每 tick 进函数，`tick % GenDate.TicksPerHour == 0`（或 `tick == record.ExpireTick`）才真正跑 | `Source/Core/GameComponent_RHAH_Game.cs:59-63`（`tick = Find.TickManager.TicksGame`）→ `Source/Incidents/RHAH_ChoiceRuntime.cs:108-146`（`:122-126` 武装分支）→ `Source/Pawn/RHAH_ArmedDemand.cs:103-112`（`:107` 闸门、`:108` Refresh） |
| `TrySettleRequest` 的武装分支（玩家点信里任何按钮） | 每次点击 | `Source/Incidents/RHAH_ChoiceRuntime.cs:202-214`（`:204`） |
| `PlanPayment`（被 `CanPay` 调用 → 信里"交付"按钮的可用性求值） | **每次枚举信的选项**（即打开信/重建按钮时） | `Source/Pawn/RHAH_ArmedDemand.cs:179-214`（`:184`） |
| `LordJob_RHAH_Visitor.Notify_PawnLost / Notify_PawnDowned / Notify_LordDestroyed` | 事件驱动 | `Source/Pawn/LordJob_RHAH_Visitor.cs:166-186`（`:183` 有 `armedChoiceId <= 0` 的提前 return） |

要点（实测）：主轮询**不依赖 Lord 的 tick 回调**；而且**玩家只要点开这封信**，`CanPay → PlanPayment → Refresh` 就会立刻判一次 —— 所以"等整点"不是用户关不掉信的解释。

### 3.2 E12 为什么走不到通用兜底

`RHAH_ChoiceRuntime.Tick` 在 `:122-126` 对"武装索粮记录"直接 `RHAH_ArmedDemand.Tick(...)` 然后 `continue`，于是 `:127-132` 的 `CloseUnavailable`（按 `Present(record).Count == 0` 收信）**永远轮不到 E12**。这条通用兜底反而是最合理的判据，被 `continue` 短路了。

## 4. 信件那一侧

- **标识一致性：没问题（实测）**。`SendLetter` 用 `record.Id` 写 `request.choiceId`（`Source/Incidents/RHAH_IncidentFacts.cs:348-356`），`Pending`/`Finish`/`RemoveSettledArmedLetters`/`CloseUnavailable` 全部按 `ChoiceLetter_RHAH_Request.choiceId == record.Id` 匹配（`Source/Incidents/ChoiceLetter_RHAH_Request.cs:147-164`、`Source/Pawn/RHAH_ArmedDemand.cs:99`、`Source/Incidents/RHAH_ChoiceRuntime.cs:159/176`）。`nextChoiceId` 是存档字段（`Source/Core/GameComponent_RHAH_Game.cs:438`），不会因读档重复发号。
- **同一记录多封信：可能，但不是本 bug 的原因**。`ChoiceLetter_RHAH_Request` 只有一个构造点（`RHAH_IncidentFacts.cs:348`），每 `Submit` 一封；`RHAH_ChoiceRuntime.Open` 命中已有 Open 记录时会复用同一 `record.Id`（`Source/Incidents/RHAH_ChoiceRuntime.cs:22-28`）并再发一封 → 同一 `choiceId` 两封信。但 `Finish`（`RHAH_ArmedDemand.cs:97-100`）和每小时补刀 `RemoveSettledArmedLetters`（`RHAH_ChoiceRuntime.cs:148-167`）都是**倒序遍历删掉所有同 `choiceId` 的信**，所以"删一封另一封还在"不成立。
- **`ChoiceLetter_RHAH_Request` 全文要点**：`CanDismissWithRightClick => !Pending(...)`（`:17`）；`Choices` 在 `ArchivedOnly || !Pending` 时只给 `Option_Close`（`:24-28`），Pending 期间给"交付（`:62-76`，E12 走 `RHAH_ArmedDemand.CanPay`）/拒绝（`:79-81`）/忽视（`:82-84`）/原版暂缓（`:88`）"；`Settle` 的删信点在 `:119`（记录已不存在）与 `:136`（`!record.Open`）；`Pending`（`:140-144`）= `record != null && record.Open && (IsRequest(record) || …)`。**它没有 `Tick/CheckDismiss/AutoArchive` 覆写**，所以信本身不会自己超时消失。
- 注意一个**反向副作用**：`Pending` 为真 ⇒ 用户看到"没有 Close、右键无效"；反过来说，如果 `Settled` 真的被写过，用户**一定能**手动关掉这封信。用户"怎么也关不掉"本身就是"`Settled` 仍是 `None`"的证据，而不是"信栈坏了"。

## 5. 已排除（否证）的假设

| 假设 | 结论 | 依据 |
| - | - | - |
| 死 pawn 的引用残留在某个集合里，导致 `Owner` 永不 null / 卡在中间态 | **否证** | `Owner` 只遍历 `lord.ownedPawns`；死者在 `RHAH_BatchAttitude.cs:209`（`pawn.Dead`）与 `RHAH_ArmedDemand.cs:79`（`pawn.Spawned`）被挡；只有 `return lord` / `return null` 两个出口 |
| `record.PawnLoadIds` 是"遍历对象"，空集合/无效项会让判定失真 | **否证** | 它只做 `Contains` 白名单（`RHAH_ArmedDemand.cs:79`）；空集合只会让 `Owner` 更容易返回 null（更快收信） |
| `Refresh` 因 `letterId` 对不上 / `Find.LetterStack == null` 提前 return | **否证** | `Refresh` 全文 2 个 if（`:88`、`:89`），不碰信栈；`Finish` 里对 `Find.LetterStack` 用了 `?.` |
| 兜底只靠 Lord 的 tick 回调，Lord 一销毁就再没人调 | **否证** | 主轮询在 `GameComponentTick`（`Source/Core/GameComponent_RHAH_Game.cs:59-63`），传的是 `TicksGame`，`GenDate.TicksPerHour` 整点必命中（`:107`） |
| 装的是旧 DLL，里面根本没有这套兜底 | **否证（实测）** | 对已部署的 `…/workshop/content/294100/3807233439/1.7/Assemblies/HungerAndHavoc.dll` 做反射+IL 调用点扫描：类型 `HungerAndHavoc.Pawn.RHAH_ArmedDemand` 有 `Owner/Refresh/Finish/Tick/Resolve`，且 `Tick` 的 IL 里调用了 `Refresh` 与 `Owner`，`Refresh` 的 IL 里调用了 `Owner` 与 `Finish` |
| 同一记录多封信，删一封剩一封 | **否证** | `Finish`/`RemoveSettledArmedLetters` 都按 `choiceId` 删全部 |

**剩下唯一自洽的解释就是：`Owner` 命中了人。** 下面按可能性排序。

## 6. 根因候选

### 候选 1（最可能）：批次里还剩一个"活着、站着、可下令、但不打仗"的成员

- **一句话机理**：`Owner` 的判据不是"围攻结束了"，而是"批次里还有没有一个 `Spawned && !Downed && CanOrderLeave` 的成员"。`LordToil_RHAH_ArmedAssault` 会把打不了的人（幼年 / 禁暴力 / 被 stun / 未转敌对）派成**原地游荡**，这些人不参战、不主动靠近，玩家"清光在打的人"之后他们仍在 `ownedPawns` 里 ⇒ 每个整点（以及每次点开信）`Refresh` 都返回 true ⇒ `Finish` 永不执行。
- **支撑证据**：`Source/Pawn/RHAH_ArmedDemand.cs:79-80`（判据只有 Spawned/未倒地/CanOrderLeave）、`:108-109`、`:86-92`；`Source/Pawn/LordToil_RHAH_ArmedAssault.cs:19-21`；`Source/Pawn/JobGiver_RHAH_Visitor.cs:43-57`（`CanFight` 的成人/暴力/stun/敌对门槛）；`Source/Incidents/RHAH_IncidentFacts.cs:41`（年龄随机）；`Source/Pawn/LordJob_RHAH_Visitor.cs:160-164`（倒地者仍留在 Lord 里）。
- **只读观测**：
  1. 存档 XML 搜 `<displayId>I-014</displayId>`（或 I-030/I-045）找到那条记录，读它的 `<batchId>`；
  2. 用这个 batchId 搜 `<spawnBatchId>` —— 每个该批次 pawn 的 `RHAH_HungerMark` hediff 上都有这个键（`Source/Identity/CompRHAH_Pawn.cs:72`）。数一共几个、各自 `<lifecycle>` 是什么（`Dead` / `Leaving` / `SeekingFood`）、是否还有 `<dead>False</dead>` 的；
  3. 再看这些活着的 pawn 的 hediff 里 `<attitude>`（`CompRHAH_Pawn.cs:85`）是不是 `Hostile`、年龄是否成人 —— 若有一个 `SeekingFood + Neutral + 未成年` 的，就是它钉住了信。
  4. 游戏内等效观察：按 `spawnBatchId` 筛（而不是按"正在打"或"在地图上"筛）。
- **怎么修**（一行级即可，二选一）：
  - **治标**：`Source/Pawn/RHAH_ArmedDemand.cs:79-80` 追加条件 —— `job.ArmedAssault == true` 时要求该成员仍在敌对/可战（例如 `RHAH_Api.Get(pawn).Attitude == RHAH_Attitude.Hostile` 或直接复用 `JobGiver_RHAH_Visitor.CanFight(pawn)`）。风险：`CanFight` 含 stun/成人等外部条件，战斗中可能过早判"没人"而静默收信。
  - **治本**：让"玩家已作答"进状态位 —— 在 `Source/Pawn/RHAH_ArmedDemand.cs:164-168`（`job.ArmedAssault = true;` 前后）调用现成的 `Finish(record, action)`（或先 `record.Settled = action`）。这会关掉"敌对后仍可在信里补交粮"这条玩法（`docs/references/incidents.md:18` 明确保留它），需产品决策。

### 候选 2：成员活着但已不在 `record.MapId` 这张图上（`Owner` 缺地图判据）

- **一句话机理**：`Owner` 只查 `pawn.Spawned`（`:79`），**任何地图上的 Spawned pawn 都算命中**；而调试面板/`Present(record)`/`CloseUnavailable` 都要求 `pawn.MapHeld.uniqueID == record.MapId`（`Source/Incidents/RHAH_ChoiceRuntime.cs:640`）。于是"这张图上没有、面板里也没有"和"`Owner` 仍命中"可以同时成立 —— 这正是用户描述的现象组合。
- **支撑证据**：`Source/Pawn/RHAH_ArmedDemand.cs:79-80`（无 `MapHeld` 判据）对比 `Source/Incidents/RHAH_ChoiceRuntime.cs:633-648`（`Present` 的 `MapHeld` 过滤）与 `:598-631`（`Pawns` 从 `PawnsFinder.AllMapsWorldAndTemporary_AliveOrDead` 取，跨所有图）；`:122-126` 的 `continue` 又让按 `Present` 收信的通用兜底轮不到 E12。
- **只读观测**：同候选 1 的第 2 步 —— 用 `<batchId>` 搜 `<spawnBatchId>`，看这些 pawn 分别落在哪个 `maps/<li>` 节点下；如果某个 pawn 在**另一张图**（多殖民地 / 临时图 / 口袋图）而记录 `<mapId>` 指向当前图，即命中本候选。
- **怎么修**：`Source/Pawn/RHAH_ArmedDemand.cs:79-80` 加 `pawn.MapHeld != null && pawn.MapHeld.uniqueID == record.MapId`（与 `Present` 对齐；若希望"跨图残留也能收信"，则反过来把 `Present` 改成跨图）。

### 候选 3（低可能）：同一事件存在第二条 Open 记录 / 第二批人

- **一句话机理**：`RHAH_ChoiceRuntime.Open` 只在 `BatchId` 与 `MapId` **都相同**时复用记录（`Source/Incidents/RHAH_ChoiceRuntime.cs:22-28`）。若 E12 被重放（Approach 二次到达、`SpawnArrived` 重试成功两次、或同一 DisplayId 排了两次队），就会生成**两条 I-014 记录 + 两封信**；杀光其中一批只结算那一封，另一批的 `Owner` 仍命中，玩家看到的就是"一封关不掉的信"。
- **支撑证据**：`Source/Incidents/RHAH_IncidentFacts.cs:111-114`（每次 `Submit` 都会 `SendLetter`）；`Source/Incidents/RHAH_ChoiceRuntime.cs:14-34`（去重键）；`Source/Core/GameComponent_RHAH_Game.cs:136-148`（Approach 启动失败会退回原地 spawn）与 `:162-229`（`SpawnArrived` 可被反复调用）；`Source/Incidents/RHAH_IncidentSchedule.cs` 队列里 `QueueIncident` 只按 DisplayId 去重（`Source/Core/GameComponent_RHAH_Game.cs:354`）。
- **只读观测**：存档 `openChoices` 里有几条 `<displayId>I-014</displayId>`，各自 `<id>`/`<batchId>`/`<settled>`；两封信则是 `letters` 里两个 `<li Class="HungerAndHavoc.Incidents.ChoiceLetter_RHAH_Request">`，看它们的 `<choiceId>` 是否不同。
- **怎么修**：如果确认是双记录，最小改法是让 `Open` 的去重键在武装索粮下只按 `DisplayId + MapId + 仍 Open`（不看 BatchId），或在 `IncidentWorker` 层对同一 DisplayId 的待处理队列做互斥；否则改 `Source/Incidents/RHAH_ChoiceRuntime.cs:22-28` 一处即可。

## 7. 存档里看什么（确切 Scribe 键名）

### 7.1 记录本体：`GameComponent_RHAH_Game.openChoices`

组件在 `<game><components>` 下的一个 `<li Class="HungerAndHavoc.Core.GameComponent_RHAH_Game">`；列表键 **`openChoices`**（`Source/Core/GameComponent_RHAH_Game.cs:437`，`LookMode.Deep`），游标 **`nextChoiceId`**（`:438`）。

每条记录（`RHAH_ChoiceRecord.ExposeData`，`Source/Incidents/RHAH_RequestRules.cs:576-631`）的键：

| 键 | 含义 | 关键性 |
| - | - | - |
| `id` | 记录号，= 信的 `choiceId`，= Lord 的 `armedChoiceId` | **对齐三处的主键** |
| `displayId` | `I-014` / `I-030` / `I-045` | 定位记录 |
| `mapId` | 事件发生的图 `uniqueID` | 候选 2 的对照项 |
| `batchId` | `RHAH_Runtime.NextBatchId`（≈ 发生时的 `TicksGame`） | 与 pawn 的 `spawnBatchId` 对照 |
| `kind` / `choice` / `site` / `amount` | E12 武装索粮下固定 `SimpleMeal` / `Aid` / `None` / 份数 | `kind=SimpleMeal` 是 `IsRequest` 为真的必要条件 |
| **`settled`** | `None`（= Open，信永 Pending）/ `Deliver` / `Reject` / `Ignore` / `Timeout`… | **一眼定生死** |
| `expireTick` | 期限；`IsRequest` 为真时 `Pending` 不看它 | 次要 |
| **`pawnLoadIds`** | 批次成员的 `thingIDNumber` 白名单（只增不减） | 与 pawn 侧对照 |
| `armedFoodDelivered` / `armedFoodNutritionDelivered` | 已交粮记账 | 交付路径用 |

（实测样例：`<id>1</id><displayId>I-007</displayId>…<settled>Feed</settled><pawnLoadIds><li>1253950</li>…`，来自 `…\LocalLow\Ludeon Studios\RimWorld by Ludeon Studios\Saves\个人主义协定.rws`。）

### 7.2 批次成员：pawn 的 hediff comp

每个本模组生成的 pawn 有一个 `RHAH_HungerMark` hediff，其 comp 键（`Source/Identity/CompRHAH_Pawn.cs:68-105`）：**`spawnBatchId`**、**`sourceIncidentDisplayId`**、**`lifecycle`**、**`attitude`**（另有 `attitudeAtArrival`、`hasBeenFed`、`foodWaitUntilTick`、`childPawnLoadIds`…）。

→ 用法：拿记录的 `batchId` 去搜 `<spawnBatchId>`，就能把整批人（无论在哪个图、是死是活）**全部**列出来；再用 `lifecycle`（`Dead`/`Leaving`/`SeekingFood`…）与 `attitude`（`Hostile`/`Neutral`…）判断"还有没有候选 1/2 里那种活人"。

### 7.3 Lord 侧

Lord 在 `maps/<li>/<lordManager>/<lords>/<li>`，其 `LordJob` 节点是 `<li Class="HungerAndHavoc.Pawn.LordJob_RHAH_Visitor">`，关键键 **`armedChoiceId`**（`Source/Pawn/LordJob_RHAH_Visitor.cs:330`）与 **`armedAssault`**（`:331`）；成员列表是原版 `ownedPawns`（对 pawn 的 `Scribe_References` 引用）。
→ 用法：`armedChoiceId` 等于记录的 `id` 的那个 Lord，就是 `Owner` 的候选 Lord；看它 `ownedPawns` 还剩几个、分别是 `pawnLoadIds` 里的哪个号。
（说明：本机现有存档里 `lords` 为空、也没有任何 `I-014` 记录，故**未能取到这种 Lord 的 XML 样本**；`ownedPawns` 条目的确切引用写法（形如 `Thing_<thingIDNumber>`）未实测，请以存档里实际字符串为准。）

### 7.4 信

`<letters>` 下 `<li Class="HungerAndHavoc.Incidents.ChoiceLetter_RHAH_Request">`，键：**`choiceId`**、`mapId`、`kind`、`site`、`amount`、`expireTick`（`Source/Incidents/ChoiceLetter_RHAH_Request.cs:92-101`），另有原版 `<ID>`（信栈 ID，与 `choiceId` 无关）。
→ 用法：`<choiceId>` 必须等于某条记录的 `<id>`；数一数有几封信指向同一个 `choiceId`（§4 的重复发信）。

**一次只读验证的最短路径**：存档搜 `I-014` → 记下 `id` / `batchId` / `mapId` / `settled` / `pawnLoadIds` → 搜 `spawnBatchId`+该 `batchId` → 看还剩几个非 `Dead`、在哪个图、`attitude` 是什么。这三步能把候选 1/2/3 全部区分开。

## 8. 未验证 / 边界

1. **没跑游戏、没编译、没跑单测**。所有"应该会收信"的断言都只来自读码；`Source/Tests/RHAH_AttackChoiceTests.cs:202-227`（`ArmedRequestClosesWhenLastEligibleVisitorIsGone`，含 `dead` 分支）只是**意图证据**，且它是用反射把 `healthState` 设成 `Dead`、pawn 仍留在 Lord 里，**恰好没有覆盖"死在真实 Kill 流程里、Lord 已被清空"以外的情形**，所以测试通过不代表实机能收信。
2. **原版语义未读源码**：`Lord.Notify_PawnLost`/`ShouldRemovePawn` 的精确调用时序、`Thing.Spawned` 对尸体/容器/销毁对象的取值，均按 RimWorld 常识推理，**未读 Assembly-CSharp**。不过 §1 的结论不依赖这些细节 —— 因为 `CanOrderLeave` 第一句就是 `pawn.Dead`。
3. **`thingIDNumber` 是否跨存档稳定未验证**：`record.PawnLoadIds` 存的是 `thingIDNumber`。若原版读档会重发 ID，这套白名单在存档往返后会全部失配（那种情况下 `Owner` 会更早返回 null、信会更早被收掉，与本次现象相反，故不作为候选）。要定论需读原版 `Thing.ExposeData`/`UniqueIDsManager`。
4. **用户那一局的存档没能拿到**：本机 `Saves\` 下最新若干存档（含 `个人主义协定.rws`、`Autosave-*.rws`）里 `openChoices` 都没有 `I-014` 记录，`lords` 为空，所以"当时到底谁活着"没有直接证据 —— §6 的排序是**推测**，观测方法已写在第 7 节。日志里能确认 E12 确实发生过：`Player.log` 有 `[RHAH] Spawned queued I-014. def=RHAH_BeggarSiege points=300 target=map:0`，`Player-prev.log` 有 `[RHAH] Approach started for I-014. points=300 map=0`（注意 `map:0`，那张图的 `uniqueID` 是 0，且与存档里记录的 `mapId=19/21/23/31/32…` 不是一回事 —— 与候选 2 的"记录 `mapId` 与成员实际所在图不一致"值得一起看）。
