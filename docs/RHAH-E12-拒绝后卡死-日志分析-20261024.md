# RHAH E12「乞食围攻」拒绝后卡死 —— 日志与运行态分析（2026-10-24）

> 本文是一次事故的取证记录，服务于「拒绝后卡住」这个现象。结论部分是**实测**；标注「推测」的部分没有直接证据，不要当结论用。
> 取证对象：测试工程 `RimWorld_auto_test` 起的隔离实例（profile `rhah`），PID 24848。
> 产出目录：`runs/freeze-20261024/`；原始测试产物：`runs/20261024-RHAH-E12/`。

## 一、结论（3 行）

1. **测试实例没有结束、也没有被杀**：PID 24848 仍在运行；冻结（17:04:07.7 → 17:05:15.6，共 **68 秒**）已自行恢复，恢复后 `Responding=True`、桥接 6ms 内应答。
2. **日志对这次卡死完全沉默**：`Player.log` 停在 17:02:38 的 109 行（8,649 字节），冻结窗口内**零输出**；桥接的内存日志 journal 也只有 2 条（最后一 条 17:02:31）。**没有任何 Exception / NullReference / StackOverflow，也没有任何重复刷屏行**（全日志最高频行只出现 3 次）。
3. **最可能的卡因（分两层）**：①**拒绝后游戏永久停在暂停态、对话框不关** —— `RHAH_ArmedDemand.Resolve` 的攻击分支不调用 `Finish`，不写 `Settled`、不摘信，于是 `Dialog_NodeTreeWithFactionInfo` 一直开着、`windowsForcePause` 一直生效，tick 冻在 3181 不再前进（这是用户看到的「卡住」）；②**一次 68 秒的真卡顿**，起始时刻与 `rimworld/search_debug_actions` 调用重合，期间主线程不处理窗口消息（`Responding=False`），CPU 稳定烧 ~2 核。

## 五、根因判定

### 5.1 有证据的部分

1. **「拒绝」这个动作本身没有卡住主线程**。`click-ui-target` 15ms 返回；其后 7 秒内 `list-letters`(0ms)、`take-screenshot`(105ms)、`get-ui-layout`(4ms) 全部正常。换而言之，卡顿**不是**发生在拒绝的那一瞬间。
2. **拒绝确实执行到了「开始攻击」分支**：截图里出现 `has begun attacking` 的提示；信件仍在、选项仍在、`Settled` 没被写。
3. **卡顿是一个 68 秒的、主线程独占的时间窗**（17:04:07.7→17:05:15.6）：期间 `Responding=False`（17:05:10 实测），CLI 30 秒超时，两条排队的桥接调用在同一瞬间放行。这个窗口的**起点与 `search-debug-actions` 的发起时刻重合**，而此前 13 秒（17:03:53→17:04:07）游戏处于暂停、桥接调用全部毫秒级。
4. **冻结窗口内日志为零**（两个独立通道互证），**没有异常**、**没有重复刷屏行**。
5. **冻结结束后游戏自愈**，没有崩、没有退出、没有重启；`Responding` 回到 True，桥接恢复毫秒级。
6. **世界时间冻在 tick 3181 的直接原因是 `windowsForcePause`**：RHAH 的信件对话框一直开着，游戏就一直暂停。这与「拒绝分支不写 `Settled`、不摘信」的已知代码背景吻合。

### 5.2 推测（无直接证据，需下一步验证）

- **推测 A（信/对话框不关 → 永久暂停）**：`RHAH_ArmedDemand.Resolve` 的攻击分支（本地源码 `Source/Pawn/RHAH_ArmedDemand.cs` 第 164–168 行：置 `job.ArmedAssault = true` → `StartArmedAssault` → `ReceiveMemo` → `Messages.Message`）**没有调用 `Finish(record, action)`**（对比第 155 行的 Deliver/Ignore 分支有调用）。`Finish` 才会写 `record.Settled` 并 `Find.LetterStack.RemoveLetter`。信不摘 → `ChoiceLetter_RHAH_Request` 的对话框不会被关 → 强制暂停不解除 → 玩家看到「世界停住」。**注意**：实例加载的是工坊旧版二进制（`workshop\content\294100\3807233439\1.6\Assemblies\HungerAndHavoc.dll`，2026-10-16），本地源码是更新版，行号只能当**行为等价**参考，不能当旧版二进制的行号。
- **推测 B（68 秒卡顿来自调试动作搜索）**：两次 `search-debug-actions` 的 `DurationMs` 分别是 67,891 和 33,078，且同时结束。最省事的解释是**第一次调用自己在主线程上跑了 ~68 秒**（枚举整棵 debug action 树 + 反射），第二次只是在它后面排队。**反向可能**：主线程在 17:04:00–17:04:07 之间被别的东西占住，两条搜索都在等它——但那个 7 秒窗口里游戏是暂停的、没有任何模拟在跑，也没有日志，我倾向前者。
- **推测 C（不是死循环、不是死锁）**：
  - 不是死锁：死锁 CPU 接近 0，而这里稳定 1.8–2.1 核。
  - 不是典型死循环刷屏：日志无重复行（最高 3 次），且两个日志通道都零输出。
  - 但「CPU 在冻结期与恢复后一样高」这条负面证据很硬：**如果 68 秒里真是纯自旋，应该看到 CPU 明显高于基线**。所以更像「主线程被一个**有限但极慢**的操作占住（每帧/每步都在算，日志无话可说）」，而不是死循环。
- **推测 D（旧版二进制缺少 `Tick/Owner/Refresh/Finish`）**：旧版没有这些方法，意味着「到点未付 → 自动开打」和「信被摘掉」两条收敛路径都不存在；E12 的未结算状态在旧版里是**没有出口**的。这与观察到的「信永远开着」一致。

## 六、下一步复现取证建议

1. **先分离变量**：在**干净的调试殖民地**（不触发任何 RHAH 事件）单独计时一次
   `node src/cli.js call rimworld/search_debug_actions '{"query":"kill"}' --profile <p>`。
   - 若单次就要 30–70 秒 → 68 秒卡顿与 RHAH **无关**，是工具/桥接的性能问题，应从 RHAH 结论里剔除。
   - 若是毫秒级 → 说明 68 秒是被别的长任务挡住，再按第 3 条抓栈。
2. **验证「拒绝后不结算」**（这才是 RHAH 的确定性问题，且**不需要**再看卡顿）：
   - 拒绝后立刻读 `rimworld/list_letters`：若信仍在、`totalCount` 仍为 1、选项仍是 4 个 → 确认没写 `Settled`；
   - 读 `GameComponent_RHAH_Game.OpenChoices`（或现有诊断工具）看 `record.Open` / `record.Settled`；
   - 再点 `Postpone`（`closesDialog: true`）看对话框能否关掉、暂停能否解除——这能证明「卡住」是 UI 层不关窗，而不是游戏逻辑死掉。
3. **下次真卡顿时抓线程栈**（这次没抓到，因为没预置工具）：
   - 卡顿期间 `procdump -ma <pid>` 生成 dump，或用 `dotnet-stack`/`dotnet-dump` 抓托管栈；
   - 或临时在 `RHAH_ArmedDemand.Resolve` 的攻击分支前后加 `Log.Message`（**只在测试用 profile 里加**），看分支是否走完、走到第几步；
   - 同时 `rimbridge/list_operations` 是**最便宜的时间线证据**：`StartedAtUtc`/`CompletedAtUtc`/`DurationMs` 能直接把冻结窗口钉到毫秒。
4. **提高可观测性的最小改动**：`Resolve` 攻击分支补一行 `Log.Message`（带 `record.Id`、`members.Count`、`job.ArmedAssault`），并在 `Finish` 里补日志。当前这个 bug 全流程**一条日志都没有**，任何后续分析都只能靠桥接状态推断。
5. **复现性**：目前**只有一次**（本次）。用户自己那局在 16:47 前后也排过 I-014 并正常退出，不能算第二次。要判定可复现，需要按第 2 条在固定调试殖民地里再点一次。

## 七、未验证 / 做不到

- **没有 dump、没有线程栈**：68 秒里主线程具体停在哪个方法**未知**；推测 A/B/C 都建立在时间线与状态推断上。
- **没有做过 A/B**：没有在「关掉 RHAH」或「不点拒绝」的对照下重跑，所以「拒绝 → 卡顿」的因果强度只到「时间相邻」这一级。
- **没有验证旧版二进制的真实行为**：本地源码（新版，有 `Owner/Refresh/Finish/Tick`）与工坊旧版 DLL 不是同一份代码；「旧版 `Resolve` 不写 `Settled`」来自任务背景描述 + 观察到的行为一致，**没有反编译核对**。
- **没有确认那 5 只 ratkin 是否真的进入了 assault 状态**（`job.ArmedAssault`、Lord/duty/toil 的实际值没读）；只看到 `Messages.Message("RHAH_ArmedDemand_Attack")` 对应的游戏内提示。
- **没有测「点 Postpone 能否解除暂停」**（怕干扰用户正在看的实例），所以「对话框不关是唯一原因」还差一步。
- **`Player.log` 为什么从 17:02:38 起彻底沉默**：结合 RimBridge journal 判定为「游戏确实没打印」，但没排除「RimBridge 的日志钩子只覆盖部分通道」这种可能；不过 `Player.log` 与 journal 两条独立路径一致，可信度较高。
- **CPU 基线未标定**：1.8–2.1 核是否为该实例「正常暂停渲染」的水平，没有在干净实例上量过；这影响「CPU 无突增 ⇒ 非自旋」这条推理的强度。
