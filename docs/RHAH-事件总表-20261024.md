### 两份档案说法不同的条目

- **触点文件数本身**：doc2 对同一事件给出两套文件数（总表 grep 命中 vs 成本结论「必改 .cs 文件」），E10 是 15 vs 16、E9 是 9 vs 9（巧合相同）。本文两列分别取这两套，未强行统一——见第 0 节。
- **`I-001` 的人数上限**：doc1 写「饥荒年可到 30×3=90」；doc3 对同机制写「I-034/I-048 可到 24～57 人」。**不是矛盾**（不同事件的基数不同），但两者都是同一行代码（`RHAH_IncidentWeight.cs:102-107`）的后果：谁都不受 `maxEventPawns` 保护，只是数值区间不同。
- **`I-041`/`I-037` 的鼠疫判定**：doc1 记「读的是身份标记而不是实际 Hediff」（`I-008.md:76` 亦有记录），doc2/doc3 记「`!carriesPlague` 语义≠康复」。两种表述指向同一处代码（`RHAH_EventFollowMood.cs:266`），本文合并为第 25 条并保留两种措辞。

## 5. 给「想改事件内容/流程」的人的三条建议

> **以下三条是判断，非实测。** 依据只有第 1–4 节的成本表与缺陷表，没有新增代码阅读。

1. **只调数值（人数/概率/间隔）就从成本表尾部下手**：E19/E14/E9/E12/E13 这类几乎无专属代码的事件，改动集通常只是 `RHAH_IncidentWeight.cs` 一行 + 两版本 XML 一处，验证反馈最快；反过来，E17/E18/E21/E22/E23 的成本有一半花在硬编码 ID 分支与「两版本各一份」的同步上，不适合当试验田。（判断，非实测）
2. **改「内容/文案」前先确认这个事件有没有专属文案分支**：有专属分支的（E17 的 `RHAH_Arrival_GreatFamine_Text`、E20 硬编码在 Def XML 里的中文任务名）改一句话要连带两版本 XML + 最多 4 处语言文件；没有专属分支的（E19、E14）改文案等于只改 label，投入产出最低——真正的差异在行为里，不在文本里。（判断，非实测）
3. **要加新分支/新后续，先看两张全局表，再修两处结构性问题**：任何新 ID 必动 `RHAH_EventChainProvider.cs:22-33`（54 条硬编码链）与 `RHAH_EventFollowRules.cs:178-197`（11 个 ID 的长后续白名单），漏一处就静默退化成「通用短后续」；同时在动手前先接受 `PawnCount` 死值与「设置按组首 ID」这两个约束，否则新事件的开关和人数依旧无法独立调。（判断，非实测）
