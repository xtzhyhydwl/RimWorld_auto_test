# RHAH（鼠族：饥与祸）事件系统结构分析

分析对象：`RimworldMods/ratkin_hunger_and_havoc`（包名 `nanaloveyuki.ratkin.hungerandhavoc`，1.6 / 1.7 双版本）。
只读分析，未改动仓库任何文件。全文路径相对 `RimworldMods/ratkin_hunger_and_havoc/`。

标注约定：**【实测】** 读过代码/跑过命令；**【推测】** 只按命名或形态推断。
姊妹文档 `RHAH-叙事者与行为模式分析-20261024.md` 已覆盖叙事者与 Pawn 行为链，本文只做**事件**这条链：Def → 调度 → 执行 → 收尾/后续 → 状态。两文在「114 是两版本相加」这一点上口径一致。

## 0. 结论摘要

1. **114 个 IncidentDef 是两份拷贝。** 每版本 57 个，`1.6/Defs` 与 `1.7/Defs` 的 IncidentDefs 两个文件逐字节相同（MD5 相等）。**57 才是这 mod 的事件条目数**，其中 56 个参与抽取（`I-019` 已退出抽池，只服务旧档）。【实测】
2. **57 个条目里没有一个是「原版事件的鼠族版变体」**：`<workerClass>` 全部指向模组自己的类，没有一处 `RimWorld.IncidentWorker_*`；57 个 def 的 `<baseChance>` 全部为 0，因此**原版讲述者的类别池永远抽不到它们**。【实测】
3. **真正独立的「事件」约 23 类 / 约 11 种交互形态。** 57 = 20 个 `Original` + 37 个 `Sequel`，而 37 个 Sequel 里 15 个是鼠疫变体、9 个是「3 种货物 × 3 种情报站点」的组合矩阵。作者自己的 `docs/references/incidents.md:3` 也写「23 个事件类，包含 56 个活动来源场景」。用户体感的「二三十个」＝**23 类**，不是 57，更不是 114。【实测 + 作者文档】
4. **调度是自己写的一套，和原版机制是「绕过抽池、复用执行」的关系**：`RHAH_IncidentSchedule` 用 Harmony Postfix 挂在 `Storyteller.StorytellerTick` 上，自己算间隔、自己按权重抽、自己入队，然后用 `IncidentDef.Worker.TryExecute(parms)` 执行。原版的类别权重与财富点数曲线完全不参与；`parms.points` 来自目录里的 `DebugPoints`，所以**事件强度与殖民地财富脱钩**。【实测】
5. **收尾/后续是「半框架 + 大段手写」**：定时与实例持久化确实收在一套 ODF（Oxygen DSL Framework）事件链框架里（`Source/EventMgr/`，脚本只有 2 个共 603 字节的 `.oxy`），但「这个事件结束后玩家心情怎么变」是**按 DisplayId 字符串分派的手写 switch**，落在 `RHAH_EventFollowRules` / `RHAH_EventFollowMood` / 三个 `RHAH_Long*Follow`。57 个条目里 **22 个有后续反应，35 个没有**。【实测】
6. **最大的结构问题是「事件身份」没有类型载体**：一个事件的属性散在 9 张以 `"I-0NN"` 字符串为键的表里。非测试代码里有 **257 个 `case "I-0NN"` 标签**（8 个文件）+ **226 处 `== / != "I-0NN"` 比较**（28 个文件），合计 483 处字符串分支。加一个事件平均要改 6–10 处，其中 2 处是 Def XML（两版本各一份），其余全在 C# 的 switch。【实测】

## 1. 事件规模的构成：114 → 57 → 23 → 11

| 口径 | 数量 | 证据 |
| --- | --- | --- |
| 1.6 + 1.7 的 IncidentDef 总数 | 114 | 每版本 57（`RHAH_M1.xml` 17 + `RHAH_M2.xml` 40）【实测】 |
| 单版本 IncidentDef | 57 | 同上 |
| 参与新抽取的场景 | 56 | `RHAH_IncidentGroups` 收录 56 个 id；`I-019` 不在任何组（`RHAH_IncidentGroups.cs:8-33`）【实测】 |
| 作者定义的事件类 | 23 | `RHAH_IncidentGroups.cs:8-33` 的 23 个数组，单元素组 8 个【实测】 |
| 交互形态（玩家感知的「不同的事」） | 11 | 8 个有效 `RHAH_ChoiceKind`（Aid/Intel/Refugees/Abandoned/ChildExchange/Kinship/Airdrop/Visitors）+ 3 类无选择分支（威胁信 / 普通到达通知 / 商队交易）【实测：`RHAH_RequestRules.cs:85-126` + `RHAH_IncidentFacts.cs:304-360`】 |
| Origin=Sequel 的条目 | 37 | `RHAH_IncidentCatalog.cs:102-138`【实测】 |
| 其中鼠疫变体 | 15 | `I-036`..`I-050`【实测】 |

**数字落差的来源，按贡献排序：**

- **×2：两套版本目录各一份 Def**（差 57）。
- **约 ÷2：变体**。57 个条目里有 28 个是组合配置：`I-015..I-019` 是「接济」一种流程的 4 种货物 + 婴儿；`I-020..I-028` 是「情报换货」的 **3 种货物 × 3 种站点**笛卡尔积（`RHAH_RequestRules.cs:92-100` 这 9 行 case 只差一个三元组）；`I-036..I-048`/`I-050` 共 14 个是把已有场景复制一份加上「携带鼠疫」标记（`RHAH_IncidentFacts.cs:99` 只读 `entry.Category == Plague`）。
- **没有「难度档」维度**：难度不是靠不同 Def，而是靠 `RHAH_IncidentScale.RawCount` 的 switch 与荒年倍率（`RHAH_IncidentWeight.cs:123-186`）。
- **`-01` 子事件**：`I-008-01/I-009-01/I-010-01` 是「原版野人」变体，独立 worker（`IncidentWorker_RHAH_Feral.cs:75-94`）。

> 结论：**用户体感「二三十个」是对的**。23 类事件、11 种交互形态，是这套系统真正的规模。

## 3. 调度层：`Source/EventMgr/` 是什么，和原版是什么关系

### 3.1 EventMgr 的角色【实测】

`Source/EventMgr/`（17 文件 / 5,163 行）**不是事件管理器，也不是调度器**。它是：

1. **ODF 事件链的 provider**：`RHAH_EventChainProvider : IEventChainProvider`（`Source/EventMgr/RHAH_EventChainProvider.cs:14`），注册 57 个定义（54 个 `I-0NN` + 捕食者到达 + 王国篇两条，`:22-34`）。定时与实例持久化由外部依赖 `Oxygendsl.Mod.GameComponent_Oxygendsl` 负责，本模组只拥有一个 provider 分区。
2. **两条 `.oxy` 脚本**：`RHAH_EventFollow.oxy`（394B，3 个分支）、`RHAH_PredationArrival.oxy`（209B，1 个分支）。**整个 mod 的「事件流程图」就是这 603 字节。**
3. **「后续反应」的内容库**：`RHAH_EventFollowRules`(541) / `RHAH_EventFollowMood`(312) / `RHAH_LongFollowRuntime`(897) / `RHAH_LongMotherFollow`(914) / `RHAH_LongClaimFollow`(852) / `RHAH_LongAdoptionFollow`(560)。

**真正的调度器在 `Source/Incidents/`**：`RHAH_IncidentSchedule`（抽取）+ `GameComponent_RHAH_Game`（队列与执行）+ `RHAH_Scheduler`（调试入口）。

### 3.2 和原版机制的关系：**绕过抽池，复用执行**

| 原版环节 | 本 mod 的做法 | 证据 |
| --- | --- | --- |
| `StorytellerComp_RandomMain` 选类别/选事件 | **绕过**。全部 `baseChance=0`，另用 `Rand.MTBEventOccurs` 自算 | Def XML；`RHAH_IncidentSchedule.cs:152` |
| `IncidentDef` 的类别权重 / `baseChance` | **绕过**（不参与抽选） | 全部 `baseChance=0`；权重由 `RHAH_IncidentWeight.Evaluate` 自算（`RHAH_IncidentSchedule.cs:263-293`） |
| `minRefireDays`、`TargetAllowed` 等 def 级执行闸门 | **状态未定**：抽选阶段不参与；执行阶段若 `IncidentWorker.TryExecute` 内部仍调用 `CanFireNow`，则可能生效 | 抽选绕过【实测】；`CanFireNow` 内部逐项未核对原版源码【推测】 |
| `StorytellerUtility.DefaultThreatPointsNow`（财富点数） | **绕过**。`parms.points` 来自目录里的 `DebugPoints` 或玩家设置 | `GameComponent_RHAH_Game.cs:367-374` |
| `IncidentWorker.TryExecute` / `CanFireNowSub` | **复用** | `GameComponent_RHAH_Game.cs:259` |
| `IncidentParms.target/points/forced`、`LetterMaker`、`LetterStack` | **复用** | `GameComponent_RHAH_Game.cs:158, 239`；`RHAH_IncidentFacts.cs:328-359` |
| 讲述者难度对威胁间隔的影响 | 只对**穗音**这一个叙事者打 Prefix（`RHAH_EndingRuntime.cs:223-262`），且只改 `ChooseRandomCategory` | 同左 |

所以准确说法是：**并存（沿用 IncidentDef/Worker/Letter 数据结构）+ 绕过（自己决定何时、选谁）+ 包装（自己排队、自己走路、自己收尾）**。

### 4.2 `IncidentWorker_Sequel` 与 `Source/Narrative/` 的真实关系

- **`IncidentWorker_Sequel` 名字里的 Sequel 是「目录标签」，不是「上一件事的续集」。** `RHAH_IncidentOrigin.Sequel` 只是 `RHAH_IncidentCatalog` 给 `I-015..I-051` 打的分类标记（`RHAH_IncidentCatalog.cs:19-23, 269-289`），没有任何代码「因为 A 发生过所以触发 B」。37 个 Sequel 和 20 个 Original 走同一个抽池、同一条入队路径（全仓库 `QueueIncident(` 的调用点只有 3 处：调试 `RHAH_Scheduler.cs:33`、抽取 `RHAH_IncidentSchedule.cs:166`、广播 `RHAH_BroadcastMenu.cs:125`）。【实测】
- **`Source/Narrative/`（1 文件 / 438 行）不是后续层**。`NarrativeState : GameComponent` 只存穗音信任与剧情标记（`Source/Narrative/NarrativeState.cs:36-98`），事件相关只做两件事：`NoteIncident`（写 `SuiyinFacts` 供日记/统计）与 `Snapshot().Trust`（供权重与到达态度降档，`RHAH_IncidentSchedule.cs:426`、`RHAH_IncidentArrival.cs:36-41`）。
- 真正承载「事件之后」的是 `Source/EventMgr/`（通道 C/D）与 `Source/Incidents/RHAH_ChoiceRuntime.cs`（玩家点了以后结算，761 行）。

### 4.3 有后续 vs 没有后续：22 / 35

判据：出现在任一后续判定入口的 DisplayId 分支里（`AtFourteen` / `OnChildDeath` / `OnStarvedChild` / `OnJoinedAfterHarm` / `OnRelief` / `OnBirth` / `OnTraderPlague` / `OnChoice` / `NoteDependentVisitors` / 三个 `Long*Follow` 的 `Handles`）。

**有后续（22）**：
`I-002, I-003, I-004, I-006, I-007, I-012, I-013, I-015, I-016, I-017, I-018, I-019, I-029, I-032, I-033, I-037, I-038, I-040, I-041, I-044, I-046, I-047`

其中：

- **只有心情**：`I-004, I-006, I-007, I-015..I-018, I-029, I-044`；
- **有跨月长链**：`I-002, I-012, I-013, I-019, I-032, I-033, I-037, I-038, I-041, I-046, I-047`（`RHAH_EventFollowRules.cs:178-197`）。

**没有后续（35）**：
`I-001, I-005, I-008, I-009, I-010, I-011, I-014, I-020..I-028, I-030, I-031, I-034, I-035, I-036, I-039, I-042, I-043, I-045, I-048, I-049, I-050, I-051, I-052, I-053, I-054, I-008-01, I-009-01, I-010-01`

**判定：既不是「一套统一框架」，也不是「每个事件各自手写一段」，而是两者的混合，且分界线在「是否被作者登记进 Family 表格」：**

- **统一的部分**：定时、重试、暂停、期限、`receipt`、存档、信件 UI、心情落地（`Apply`）。这些确实是框架，且设计得比多数 RimWorld mod 更严谨（有 ADR、有 `save-ownership.md` 契约、有迁移与失败保留）。
- **手写的部分**：「这件事之后该后悔还是庆幸」全部是 `switch (subject.DisplayId)`。`AtFourteen` 一个方法里 12 个 case、每个 case 2–4 行内联魔法数（`RHAH_EventFollowRules.cs:249-316`）。**加一个新事件要在这 14 个入口（S6 清单）里逐个判断「我该不该在这里加一个 case」，代码和文档都没有任何地方会提醒你漏了哪个。**
- **反例**：`I-005/I-042`、`I-036`、`I-043` 这些与 `I-001/I-006` 同类的场景，在 `AtFourteen` 里没有对应 case，所以「乞讨队伍帮了会怎样」有、鼠疫版就没有 —— 这种缺口是**手写 switch 的必然产物**，不是设计选择。【推测：作者可能有意省略，但代码里没有「明确不提供后续」的标注】

### 4.4 「后续」实现的三个具体模式（各给一例）

1. **同一票人在若干天后判定年龄 + 存活 + 关系**：`AtFourteen`（`RHAH_EventFollowRules.cs:249`）由 `LongAdoptionFollow.Ready/Choose` 在长链 stage 3 驱动。
2. **玩家选择被记成每人的字符串标记，之后判定时读**：`RHAH_EventFollowMood.OnChoice` 往 `CompRHAH_Pawn.State.extraData` 写 `"rhah:bought"` / `"rhah:gave"` / `"rhah:foodSub"`（`RHAH_EventFollowMood.cs:39-52`），`AtFourteen` 再读 `subject.Bought` / `GaveChild` 决定台词。
3. **旧窝记物实体跟随**：`RHAH_LongFollowRecord.Keepsake`（`Thing` 引用，`LookMode.Reference`，`RHAH_LongFollowRecord.cs:43, 82`），被拿走也继续追踪。

- `CompRHAH_Pawn.State.extraData` 里 14 个 `"rhah:*"` 键（`RHAH_EventFollowMood.cs:12-18`、`RHAH_LongFollowRuntime.cs:21, 530`、`RHAH_QuarantineMigration.cs:15` 等），值是**字符串**（`"1"`）、甚至是**两字符位图**（`"u"/"t"/"f"` 记录两个闸门原覆盖，见 `save-ownership.md:99`）。
- 后果：键名拼错 = 静默失效；两字符位图 = 无法局部推理。**这是唯一没有类型或常量表覆盖的状态协议**（对比：存档键本身有 `save-ownership.md` 清单）。

### S9. 前缀当协议【实测】

`SuiyinRules.cs:1593`：`if (displayId.StartsWith("I-02") && displayId != "I-029") return 7;` —— 靠「id 落在 I-02x 且不是 I-029」表示「情报交易类」。新增 `I-029` 之后的 id（如 `I-030`）若按编号紧邻就会被误判；实际靠 `I-029` 已经被占用才碰巧没出错。

### S10. 异常吞掉（catch 后无日志）【实测】

非测试代码 18 个 `catch`，其中 2 处**不记日志**：
- `Trade/TradeEventRouter.cs:106` `catch { Cleanup(attackers); return false; }` —— 商队伏击生成失败时，玩家与日志都看不到原因（唯一完全静默的一处）。
- `Incidents/IncidentWorker_RHAH_BanditAttack.cs:61` `catch { Cleanup(attackers); throw; }` —— 仅清理后重抛，可接受。

其余 16 处都有 `Log.Error`/`Log.Warning`（`Log.Error` 25 处、`Log.Warning` 17 处、`Log.Message` 6 处）。**整体不是「异常吞掉」型代码**，这点要说清楚。

### S11. 没有 `DeepProfiler`（0 处）【实测】

整个非测试代码 **0 处 `DeepProfiler`**。而事件链里有若干每 tick / 每小时的循环：`GameComponentTick` 每 tick 调 6 个 `Suiyin*Runtime.Tick`（`GameComponent_RHAH_Game.cs:71-76`）+ `RHAH_ChoiceRuntime.Tick` + `TrySpawnPending` + `TickPlague`；`MapComponentTick` 每 tick 判捕食与粮洞（`:766-780`）。这些在 200+ 模组的中期存档里是首要嫌疑，但没有分段计时手段。

### S12. 「DebugPoints 直接当生产点数」【实测 + 名字推断】

`GameComponent_RHAH_Game.cs:367-374`：
```
PointsFor(displayId) → entry.DebugPoints 或 settings.IncidentDebugPoints(...)
```
自然抽取（`RHAH_IncidentSchedule.cs:166`）与调试触发（`RHAH_Scheduler.cs:29-32`）用的是**同一个字段**。后果：**事件强度与殖民地财富无关**（原版 `DefaultThreatPointsNow` 完全不参与），只有接济/交易物资量按 `wealthWatcher.WealthTotal` 缩放（`RHAH_IncidentFacts.cs:268`）。这是玩法层面的结构决定，不只是命名问题。

### S13. 队列是 3 条平行 List【实测】

`pendingIncidentDisplayIds` / `pendingIncidentPoints` / `pendingIncidentTargetIds`（`GameComponent_RHAH_Game.cs:15-17`），所有增删都靠「下标三处同步」：`QueueIncident`（`:360-362`）、`DropPending`（`:376-397`）、`ExposeData` 里 6 个 while 补齐/截断（`:465-483`）。任何一个只改一条 List 的新代码路径都会造成错位。

### S14. 判定逻辑重复：`CanFireNowSub` 在 `TryExecuteWorker` 里被再调一次【实测】

`IncidentWorker_Sequel.cs:45` `if (entry == null || !CanFireNowSub(parms)) return false;`，而 `IncidentWorker.TryExecute` 本身已经先调过 `CanFireNow`（原版契约）。同时 `IncidentWorker_Sequel.CanFireNowSub`（`:10-35`）与 `IncidentWorker_RHAH_Group.CanFireNowSub`（`:15-19`）又是同一段「解析地图 + 找落点」的复制品（`RHAH_IncidentFacts` 之外还有 3 份 `FindAnySpawnCell`：`IncidentWorker_Sequel.cs:36-40`、`IncidentWorker_RHAH_Group.cs:59-63`）。全仓库 `RCellFinder.TryFindRandomPawnEntryCell` 出现 4 次。

### S15. 双次 Def 查找，且第二次不判空【实测】

`TrySpawnPending` 在 `:150-156` 检查 `def != null && def.Worker != null`，然后 `ExecutePending` 在 `:259` 重新 `DefDatabase<IncidentDef>.GetNamedSilentFail(entry.DefName).Worker.TryExecute(parms)` —— 丢弃了刚校验过的局部 `def`，且不再判空。当前只可能因「两次调用之间 Def 被移除」而 NRE，属低频；但形态上把「已验证」的保证作废了。

### S16. 事件结束没有统一的「结束」概念【实测 + 推测】

- 没有 `OnCompleted` 之类的回调。`RHAH_EventChainEntry.NoteStarted`（`:12`）只负责「开链」，谁把链结掉取决于后续家族：`RHAH_LongFollowRuntime.Complete`（`:464`）、超时（`RHAH_ChoiceRuntime.cs:138-142`）、地图销毁、或**永远不结**（`RHAH_EventFollow.oxy` 的 `return event.wait(-1)` 是休眠，不是结束）。
- 结果：`longFollows` 记录会一直堆在 `GameComponent` 里（只在 `Complete` 时改 `Completed`，并不从 List 移除），`RHAH_LongFollowRuntime.FindRecord` 是线性查找（`:37-45`）。【推测：长期存档里这个列表只增不减】

## 7. 1.6 / 1.7 分叉

### 7.1 结论：**同一份 C#，编译期开关；Def 是逐字节复制**

| 项 | 事实 | 证据 |
| --- | --- | --- |
| 源码 | 一份 `Source/`，两种目标框架 | `Source/HungerAndHavoc.csproj`：`net48` / `net10.0` 按 `$(RimWorldVersion)` 切换；`OutputPath` 写进 `../$(RimWorldVersion)/Assemblies/` |
| 版本宏 | `RIMWORLD_1_7`，由 `Directory.Build.props` 在 1.7 时注入 | `Directory.Build.props`：`<DefineConstants>...;RIMWORLD_1_7</DefineConstants>` |
| `#if` 规模 | **36 处 `#if RIMWORLD_1_7`**，分布在 **20 个文件**（另有 1 处 `RHAH_IRISMENUS`） | 全量扫描；集中在 `Narrative/NarrativeState.cs`(4)、`Storyteller/Suiyin/*`(9)、`Pawn/*`(7)、`Incidents/RHAH_FoodTransaction.cs`(4)、`Tests/*`(5) |
| 运行时版本判断 | **没有** `if (version == 1.6)` 这类分支（0 处） | 全文搜索 `1.6` / `RimWorldVersion`：命中的全是注释、`ModsConfig.*` 依赖判断、测试里的 XML 路径 |
| Def | **39/40 个 XML 文件逐字节相同**，唯一差异 `Defs/WorldObjectDefs/RHAH_KingdomSite.xml` 的贴图路径（1.6 用 `Settlement`，1.7 用 `DefaultSettlement`） | 对 1.6/1.7 全树做 MD5 比对 |
| 程序集 | 两版本各自一份 `Assemblies/HungerAndHavoc.dll`（内容不同），1.7 另有 `Guard/Assemblies/HungerAndHavocGuard.dll` 与三语 `Guard.xml` | 同上比对 |

### 7.2 `#if` 的实际内容（按风险看）【实测】

多数是「原版 API 签名差异」的小差异，例如：
- `Core/ModEntry.cs:63-68`：1.7 才绘制 `RHAH_EndingRuntime.DrawForceSettings`；
- `Incidents/RHAH_IncidentSchedule.cs:427-429`：1.7 才用 `RHAH_EndingRuntime.NarrativeActive` 把 trust 归零；
- `Incidents/RHAH_IncidentArrival.cs:38-40`：1.7 叙事未启用时不做信任降档；
- `Narrative/NarrativeState.cs:80-98`：1.7 引入 `suiyinNarrativeForced` 字段与 `NarrativeEnabled` 语义（1.6 恒为 true）—— **这是唯一带存档键差异的一处**（1.6 不读写该键，见 `save-ownership.md:60`）。

风险点：`RIMWORLD_1_7` 是**编译期**的，所以两版本行为差异在源码里不会互相报错，改一处 1.6 分支时 1.7 分支可能静默不同步；`Source/Tests/RimWorldAssemblies.cs:55-68` 里也按版本切换被测程序集，测试不会替你比较两版本行为。

### 7.3 Def 复制粘贴的代价

`RHAH_M1.xml` / `RHAH_M2.xml` 在两版本里完全一样，却各自存在。改一个事件 → 必须改两次（且只能靠人工或哈希比对发现漏改）。当前 40 个文件中 39 个哈希相同，说明**目前是同步的**，但没有任何机制保证它继续同步。
