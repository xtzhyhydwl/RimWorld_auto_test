# RHAH（鼠族：饥与祸）代码结构审计

> 审计对象：`RimworldMods/ratkin_hunger_and_havoc`（下称 RHAH），支持 RimWorld 1.6 / 1.7。
> 审计目的：回答「这个库好不好改」，衡量标准是**改一个事件需要动几处**。
> 审计方式：**只读**。未修改/移动/删除任何仓库文件，未 commit，未编译，未运行测试。
> 时间：2026-10-24。所有路径以 `ratkin_hunger_and_havoc` 为根。

## 4. 1.6 / 1.7 双份 Defs（【实测】）

先纠正上游前提：`1.6\Defs\` 与 `1.7\Defs\` **各 32 个 XML（不是 56 对）**，同名集合完全一致（无增无减）。

| 比较对象 | 对数 | 逐字节相同 | 不同 |
|-|-|-|-|
| `1.6\Defs\**` vs `1.7\Defs\**` | 32 | **31** | 1 |
| `1.6\Patches\**` vs `1.7\Patches\**` | 4 | **4** | 0 |
| `Guard\Languages\**` vs `1.7\Guard\Languages\**` | 3 | **3** | 0 |

唯一不同的文件是 `1.6\Defs\WorldObjectDefs\RHAH_KingdomSite.xml` vs `1.7\Defs\WorldObjectDefs\RHAH_KingdomSite.xml`，2 行差异，性质是**1.7 换了原版贴图路径**：

```diff
-    <texture>World/WorldObjects/Settlement</texture>
+    <texture>World/WorldObjects/DefaultSettlement</texture>
-    <expandingIconTexture>World/WorldObjects/Expanding/Settlement</expandingIconTexture>
+    <expandingIconTexture>World/WorldObjects/Expanding/Camp</expandingIconTexture>
```

**结构结论：这是"全量复制 + 1 处版本差异"。** 规模：改一个 def（例如调事件文本/分类、加一条 ThoughtDef、改 BackstoryDef）要**同步改 2 个文件**；涉及面是 **32 个 Def 文件 + 4 个 Patch 文件 + 3 个 Guard 语言文件 = 39 个"要改两处"的 XML**（其中 38 个当前逐字节相同）。

补充事实与边界：
- `LoadFolders.xml` 按版本只加载一份（v1.6 加载 `1.6`，v1.7 加载 `1.7`），所以**运行期不需要双份共存**，双份纯粹是"维护时抄一份"的产物。
- `Guard` 的 DLL 由同一份源码构建到两个目录（`Guard\Source\HungerAndHavocGuard.csproj`：1.6 → `../Assemblies/`，1.7 → `../../1.7/Guard/Assemblies/`），因此两份 DLL 哈希不同属正常；但 **6 个 DLL 全部入库**（`1.6/Assemblies/HungerAndHavoc.dll`、`1.7/Assemblies/HungerAndHavoc.dll`、两份 `HungerAndHavoc.Api.dll`、两份 `HungerAndHavocGuard.dll`，`git ls-files` 实测），与本仓库"二进制放 `artifacts/`"的约定不一致。
- 语言也是三份全文：`Languages\{ChineseSimplified,English,Japanese}` 各 74 个 XML，两两**无一对哈希相同**（说明是真翻译，不是复制），但改一句事件文本要改 **3 个语言文件**。

## 9. 整体判断

> **一句话：这是一个「分层与约定清楚、但事件身份没做成数据」的代码库——不是靠复制粘贴堆出来的，只是把 57 个事件摊成了 8 张并行的字符串 switch 表 + 两套全量复制的 Defs，所以"改事件"这件事比它应有的样子贵 3–5 倍。**

支持这句话的 3 条最强证据：

1. **分层是真的，且被文件内约束强制**：13 个域目录 + 每个目录一份 `AGENTS.md` 域边界 + 6 篇 ADR + 21 篇单事件设计文档；`Data\` 目录明确"不依赖存档/设置/当前游戏"，而 `RHAH_ContentCatalog.cs` 1567 行确实只有 6 个方法、纯字面量（:13-1480）。这不是说出来的分层，是代码里能验的分层。
2. **实现是拆开写的，不是糊的**：全库 >120 行的方法只有 9 个（最长 315 行还是 Scribe 单行列表）；事件流程被统一成 `Ready/Tick/Options/Choose` 四段协议（`RHAH_LongMotherFollow.cs:71/150/312/375`、`RHAH_LongClaimFollow.cs:50/144/278/322`、`RHAH_LongAdoptionFollow.cs:12/86/98/185`），公共能力沉在 `RHAH_LongFollowRuntime.cs`（55 个方法）。行级重复率 19.1%，主要是样板而非逻辑。
3. **但事件身份这个抽象缺位，代价可量化**：`"I-###"` 字面量 805 处 / 54 个 ID、`case "I-###"` 252 处集中在 8 张平行表；`RHAH_IncidentEntry` 只装了 7 个字段，权重/请求/心情/相位各长一张表；加上 32 个 Def（31 个逐字节相同）+ 4 个 Patch 双份、3 语言全文重打，"加一个事件"= 12 处以上触点。

同样值得记的**反证（避免过度批评）**：`IncidentPace` 把"事件节奏"做成了用户可写的表达式（`RHAH_IncidentPace.cs:31 Resolve(formula,…)`，默认 `averageDays`），设置项把 clamp 全部委托给各域规则（`RHAH_Settings.cs:1045-1110`），中文文本 0 条硬编码在 C# 里（全库仅 1 处 `"鼠族"` 字符串匹配，`Source\Generation\RHAH_XenotypeResolver.cs:281`）——这些是"想清楚了"的迹象，不属于 AI 堆砌的典型症状。

**给后来者的可执行判断**：
- 只改**文案/数字**：安全，改 `IncidentCatalog` + 3 个语言文件。
- 改**事件流程/新事件**：先读 `docs\adr\` 与 `docs\references\events\`，然后预期要动 8 张 switch 表；**建议动工前先把 8 张表合并进 `RHAH_IncidentEntry`**，否则每加一个事件都在复利这笔债。
- 改 **Def**：记得 1.6/1.7 双份，`git diff --no-index` 现已只剩 1 处合理差异，是可控的。
