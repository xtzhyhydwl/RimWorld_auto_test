- 对象：`RimworldMods\ratkin_hunger_and_havoc`（下称 RHAH，「鼠族: 饥与祸」，1.6 / 1.7 共用 `Source\`）
- 方式：**只读静态阅读**。未编译、未运行游戏、未跑测试、未改任何文件。
- 口径：**「实测」= 本次读到代码行**；「推测」= 由代码推演但无程序集/无运行证据。凡无把握处写「未确认」。

## 0. 结论先行

1. **不是 E12 孤例，是一类通病。** 根因是**状态与视图之间没有任何统一对账机制**：`RHAH_ChoiceRecord.Settled`（`Source/Incidents/RHAH_RequestRules.cs:555`、`Open => :574`）是唯一「已解决」真值，全 mod **没有任何按 `Settled` 收信的通例**；唯一的按状态收信逻辑只服务武装索粮（`Source/Incidents/RHAH_ChoiceRuntime.cs:144`、`:148-167`），其余信件一律「谁结算谁顺手删信」。
2. **8 个 ChoiceLetter 子类里，4 个属于「靠回调」，1 个（武装索粮形态的 Request）实际是「高危」**：`ChoiceLetter_RHAH_Request`（武装分支）、`_Visitors`、`_Revisit`、`_LongFollow` 都是「只有某个回调会移除」；`_Request` 在武装索粮期间同时满足「右键禁用 + 无 Close 按钮 + 无超时」，一旦记录卡在 `Open`，就是永久挂屏。
3. **5 个类显式禁用了右键 dismiss**（`Request` 动态禁用、`Visitors`/`GrainHole`/`Envoy`/`Revisit`/`LongFollow` 硬 `false`），`AutoArchive` 全 mod **0 处**。
4. **E12 的代码里其实有 3 条自动收信路径**（`ArmedDemand.Refresh` 见 `:86-92`、每小时 `RemoveSettledArmedLetters` 见 `:144`、Lord 丢失/倒地通知见 `LordJob_RHAH_Visitor.cs:166-186`），mod 自己的测试也断言「最后一名合格围攻者消失 → 记录 Ignore」（`Source/Tests/RHAH_AttackChoiceTests.cs:202-227`）。**但用户实测「全部杀死后信件永久挂屏、只有交付食物能消」与这些路径冲突** —— 本文把它记为「代码应有兜底但现场未生效」，原因**未确认**，见 §7 与 §9。
5. 系统性修法只有一种是对症的：**在 `RHAH_ChoiceRuntime.Tick`（`Source/Incidents/RHAH_ChoiceRuntime.cs:108-146`）里加一条按 `Settled`/引用有效性对账的统一收信兜底**，而不是逐个信件类打补丁；同时在武装索粮的 `ArmedDemand.Tick`（`Source/Pawn/RHAH_ArmedDemand.cs:103-112`）加硬截止。见 §8。

## 3. 泄漏风险分档表

判定标准（本审计口径）：
- **安全**：有 ≥2 条独立关闭路径，且其中至少一条**不依赖玩家点选项**（tick 对账 / 玩家随时可关）。
- **靠回调**：只有某个特定回调（结算成功、结案、交付）会删信；其它分支留在信栈，靠玩家在「已失效」状态下点 Close 兜底。
- **高危**：`CanDismissWithRightClick=false` **且**无 Close 按钮产出条件 **且** 无 mod 侧超时 **且** 自动兜底依赖易失效条件 → 状态一卡即永久挂屏。

| 信类 | 档 | 依据（行号） | 卡死面 |
| --- | --- | --- | --- |
| `ChoiceLetter_RHAH_Request`（**武装索粮分支**：I-014/I-030/I-045，默认设置） | **高危** | dismiss 永久禁（`:17`+`:140-144`）；Close 不产出（`:24-28`）；`ArmedDemand.Tick` 在 `ArmedAssault=true` 后**永不** Timeout（`RHAH_ArmedDemand.cs:110`）；`Resolve(Ignore)` 也不 `Finish`（`:164`：`StartsAssault(Ignore)` 为假 → 直接 return）；唯一程序化兜底是 `Owner(record)==null`（`:86-92`、`:67-84`） | 只要还有 ≥1 名「spawned、未倒地、可下令」的成员，就既无超时也无可关按钮；玩家打不到也交不了粮时即死锁（详见 `docs/RHAH-E12-收尾机制与死锁追踪-20261024.md` R1/R2） |
| `ChoiceLetter_RHAH_Request`（**普通/交易/换子分支**，15 个 ID） | **靠回调** | 结算成功即删（`:136`）；超时只结算记录不删信（`RHAH_ChoiceRuntime.cs:133-142`）→ 但 `ExpireTick` 过后 `Pending` 为假，Close/右键恢复（`:17`、`:24-28`） | 玩家不去点就长期挂着一封「已过期请求」；不会永久卡死 |
| `ChoiceLetter_RHAH_Visitors`（28 个 ID） | **靠回调** | 只有 `Settle` 成功删信（`:262`）；dismiss 永久禁（`:16`） | ①记录 `Open` 且成员还活着但玩家永不做选择 → 只能等 `ExpireTick` 结算后才出现 Close；②`CloseUnavailable` 要求 `PawnLoadIds.Count>0`（`RHAH_ChoiceRuntime.cs:127-128`），**若这批没登记 pawn（`PawnLoadIds` 空）则永不触发**——但仍可由 `!Open` 后的 Close 兜底 |
| `ChoiceLetter_RHAH_Revisit` | **靠回调** | 唯一移除在 `Choose`（`:133`）；dismiss 禁（`:18`） | 目标 pawn 活着、会面条件不成立时只给「失效」+Close（`:38-46`），玩家点了就消失；**但 `record.Revisit` 仍是 `None`、`RevisitSeen` 仍为 true**（`RHAH_Revisit.cs:237`），重访分支等于静默作废（不是挂屏，是状态丢） |
| `ChoiceLetter_RHAH_LongFollow` | **靠回调** | dismiss 禁（`:11`）；移除全在各家族逻辑（`RHAH_LongFollowRuntime.cs:454-462` 的 26 个调用点） | `record.LetterOpen` 与真实信栈无对账：若某条路径把信删了却没把 `LetterOpen` 置 false，后续 `!LetterOpen` 才重开信的逻辑（如 `RHAH_LongAdoptionFollow.cs:504`）会永久不再发信；反之 Close 按钮只在链已推进时出现（`:18-22`），不会永久挂屏 |
| `ChoiceLetter_RHAH_GrainHole` | **安全（偏靠回调）** | dismiss 禁（`:15`），但 `Refresh` 每小时对账（`RHAH_GrainHole.cs:230-241`）+ 空地图清理（`:244-271`）+ 4 个动作都删信 | 洞仍在、玩家不选：信会一直留着（设计如此），不构成卡死 |
| `ChoiceLetter_RHAH_Envoy` | **安全** | `Watch` 每 2 小时（`RHAH_Envoy.cs:23-48`、`:113-143`）→ 结案即 `Complete→RemoveLetters` | 使者一直「在现场」且玩家不选 → 信长期在；属设计 |
| `ChoiceLetter_RHAH_KingdomArc` | **安全** | 只有 Close，且总能产出（`:16-22`） | 无状态可卡。副作用相反：旧信不会被回收，会**堆积** |
| `ChoiceLetter_RHAH_BanditAttack` | **安全** | 只有 Close，且总能产出（`:9-15`） | 无状态可卡 |

汇总：**高危 1 类（`Request` 的武装分支，覆盖 I-014/I-030/I-045 三个 ID）**；**靠回调 3 类（`Request` 普通分支、`Visitors`、`Revisit`）+ `LongFollow`（弱靠回调）**；**安全 4 类**。按 Def 算：10 个带 `letterClass` 的 Def 中 6 个（`ChoiceRequest`、`ChoiceRequestGreen`、`ChoiceVisitors`、`ChoiceVisitorsGreen`、`Revisit`、`LongFollow`）落在「靠回调/高危」。

**全 mod 0 处**（`grep AutoArchive` 无命中）。即：本 mod 没有任何一封信会「自动归档到历史」，只能被 `RemoveLetter` 或玩家点 Close。这与原版部分信件（如死亡通知）的行为不同，也是「信堆在右侧」体验的一部分。

## 6. 状态 / 视图脱钩检查（根因级事实）

**问题 5 的答案：没有任何通用轮询按 `Settled` 收信。** 逐个 tick 入口核对：

| tick 入口 | 位置 | 是否检查 `Settled` 并收信 |
| --- | --- | --- |
| `GameComponent_RHAH_Game.GameComponentTick` | `Source/Core/GameComponent_RHAH_Game.cs:59-77` | 只把工作分派给 `RHAH_ChoiceRuntime.Tick`(`:63`) 与 6 个子系统 `Tick`(`:71-76`) |
| `RHAH_ChoiceRuntime.Tick` | `Source/Incidents/RHAH_ChoiceRuntime.cs:108-146` | **唯一**涉及信件：`:144` 每小时 `RemoveSettledArmedLetters`（**仅武装记录**）；`:127-132` 的 `Present==0` → `CloseUnavailable`（**先被 `:122-126` 的武装 `continue` 跳过**）；`:133-142` 到期只 `Settle(Timeout)` + `Leave()`，**不删信** |
| `MapComponent_RHAH_Map.MapComponentTick` | `Source/Core/GameComponent_RHAH_Game.cs:766-780` | 只驱动捕食与 `RHAH_GrainHole.Tick`（粮洞自有对账） |

| `RHAH_Envoy.Tick` / `RHAH_Revisit.Tick` / `RHAH_RecordSite.Tick` / `RHAH_EndingRuntime.Tick` | `GameComponent_RHAH_Game.cs:71-76` | Envoy 有 `Watch→Complete→RemoveLetters`（`RHAH_Envoy.cs:113-143`、`:171-185`）；Revisit 的 `Tick` **只发信不收信**（`RHAH_Revisit.cs:16-34`） |
| ODF / LongFollow 运行时 | `Source/EventMgr/RHAH_LongFollowRuntime.cs` | 有 `CloseLetter`，但由家族逻辑触发，**不是**「按状态对账」 |

结论（读代码）：
- **「请求/选择」这条主干的信，其存在完全依赖「谁结算谁顺手删」**。一旦某次结算分支没有走删信、或状态卡在 `Open` 且没有玩家可点的出口，信件就与状态永久脱钩。
- `openChoices` 里的记录**只改 `Settled`、永不从列表移除**（`Source/Incidents/RHAH_RequestRules.cs:555`/`:574`；`Source/Core/GameComponent_RHAH_Game.cs:437` 只做序列化），所以「记录消失」绝不会成为兜底条件——兜底只能来自 `Settled` 或引用失效判定。
- 已有 3 条「引用失效」兜底（`CloseUnavailable` 的 `Present==0`、`ArmedDemand.Owner()==null`、`GrainHole.Refresh`），但**它们各自只覆盖一部分信**，且都需要「引用真的消失了」。

### 6.1 Dismiss 后残留（问题 6）

- `Option_Close` 是原版 `ChoiceLetter` 提供的选项，行为是**只把信从 `LetterStack` 移除**（推测：不改本 mod 任何字段；仓内取证文档只确认它存在，`语音副官/docs/取证-提示信息出口.md:48`）。
- 本 mod 对「Close 时记录是否已结算」有事实上的前置保护：每个类的 Close 只在 `record==null \|\| !record.Open` / `!Pending` / `!Open(record)` / `!LetterOpen` 时才产出（`Request.cs:24-28`、`Visitors.cs:23-27`、`GrainHole.cs:22-31`、`Envoy.cs:21-31`、`Revisit.cs:32-46`、`LongFollow.cs:18-22`）。→ **正常运行下不会「关信不置位」。**
- 但存在一个**窄窗口**：`Request.Pending` 在 `ExpireTick` 已过、`RHAH_ChoiceRuntime.Tick` 尚未跑到时返回 false（`Request.cs:140-144`），玩家此时关信 → 记录仍 `Open`，要等下一次整点 tick 才 `Settle(Timeout)`。这段时间里记录 `Open` 而信已消失；**没有重发信逻辑**（`SendLetter` 只在 `RHAH_IncidentFacts.cs:300` 到达时调一次），所以不会重复弹信，也不会重复触发事件。
- 唯一「关信后状态丢」的是 `Revisit`：点 Close 之后 `RevisitSeen=true`、`Revisit=None`，案件永久停在「已见过但未处理」（`RHAH_Revisit.cs:213`、`:237`）。不重复弹信，但分支白白消耗。
- **武装索粮没有 dismiss 窗口**（`:17`），因此不存在「关信不置位」；它的反面问题是「根本关不掉」。

## 7. E12 的代码事实 vs 实测冲突（必须写清）

**代码事实（实测阅读）**
1. 武装索粮信在 `record.Open` 期间：右键禁（`:17`）、无 Close（`:24-28`）。
2. `ArmedDemand.Tick` 只在整点或 `ExpireTick` 当 tick 跑（`Source/Pawn/RHAH_ArmedDemand.cs:107`）；`ArmedAssault=true` 后不再 Timeout（`:110`）。
3. `Resolve(record, Ignore)` 在 `Enabled` 时**不** `Finish`（`:164` 提前 return）→ 点「忽视」只关对话框，信不动、记录不结算。
4. 唯一「玩家主动」出口是交付（`CanPay`→`TryPay`→`Resolve(Deliver)`→`Finish`，`:216-251`、`:153-162`）。
5. 自动出口 3 条，全部要求「引用消失」：`Refresh`（`:86-92`，`Owner()==null`）、`RemoveSettledArmedLetters`（`RHAH_ChoiceRuntime.cs:144-167`，要求记录**已**结算）、Lord 通知（`LordJob_RHAH_Visitor.cs:166-186`）。`Owner()` 的判据见 `:67-84`（要求成员 `Spawned && !Downed && CanOrderLeave && SpawnedBatchId 匹配`）。
6. mod 自带测试断言「downed/dead/joined/captured/lostLord → `Settled=Ignore`」（`Source/Tests/RHAH_AttackChoiceTests.cs:202-227`）与「已结算记录清残留信」（`:229-261`）。

**实测冲突（用户游戏内反复确认）**：把围攻者**全部杀死**后信仍永久挂屏，只有交付食物能让它消失。

**因此（推测 + 待验证，按可能性排序）**
1. `GameComponentTick` 的 tick 链在到达 `RHAH_ChoiceRuntime.Tick` 的清扫前**每 tick 抛异常**（`GameComponent_RHAH_Game.cs:59-77` 顺序：`TickPlague()`→`RHAH_ChoiceRuntime.Tick`→…；RimWorld 对 `GameComponentTick` 逐组件 try/catch，异常会吞掉该 tick 的后续）。这一条能同时解释「只有玩家主动触发的交付有效、所有自动兜底不生效」。
2. 玩家看到的那封信**不绑定到一个 `Open` 记录**（`choiceId` 对不上 / 同批重复发信后残留一封）：`RemoveSettledArmedLetters` 与 `Finish` 都按 `choiceId == record.Id` 匹配（`RHAH_ChoiceRuntime.cs:159`、`RHAH_ArmedDemand.cs:99`），对不上的信永远不会被自动删。
3. `Owner()` 仍返回非 null：某成员「还 spawned、未倒地、可下令」但玩家打不到/交不了粮（文档 R1/R2 场景，`docs/RHAH-E12-收尾机制与死锁追踪-20261024.md:192-193`）。
4. 真正的卡点不在信而在**信之外的入口**：`SendLetter` 在 `RHAH_IncidentFacts.cs:300` 无条件发信（即使 `RHAH_ChoiceRuntime.Open` 复用了同批已存在的记录，`:24-28`），同批两次到达会产生两封共享 `choiceId` 的信；交付只删当前实例（`Request.cs:136`），另一封就成了「只有交付才动」的观感。

> 这四条都属**推测**，需要一次进游戏取证（打印 `record.Settled`/`record.Id` 与信栈里每封 Request 信的 `choiceId`）才能定案。本次任务只读，未做。

## 8. 统一兜底建议（可挂接的具体类与行号）

目标形态：**一条「状态 ↔ 视图对账」的单一所有者**，所有请求类信件都靠它收口，而不是各个 `Settle` 里各删各的。

1. **主干兜底（首选）**：在 `RHAH_ChoiceRuntime.Tick`（`Source/Incidents/RHAH_ChoiceRuntime.cs:108-146`）把 `:144` 的 `RemoveSettledArmedLetters(records)` 泛化为 `ReconcileLetters(records)`：
   - 对信栈里每封 `ChoiceLetter_RHAH_Request` / `ChoiceLetter_RHAH_Visitors`，用 `choiceId` 找记录；
   - `record == null` → 收信（当前只在各自 `Choices` 里体现，改成主动收）；
   - `!record.Open` → 收信（覆盖目前所有「结算了但忘了删」的分支）；
   - 记录 `Open` 但**引用已死**（武装：`RHAH_ArmedDemand.Owner(record)==null`；非武装：`Present(record).Count==0`）→ 先按现有语义 `Settle(Ignore)` 再收信，并给一条 `Messages.Message`（现在 `Finish` 是静默的，玩家会以为「赢了但什么都没发生」）。
   - 现成的可复用件：`RemoveSettledArmedLetters`（`:148-167`）的匹配循环、`CloseUnavailable`（`:169-180`）的「引用失效」判据。
2. **不要让武装记录绕过对账**：`:122-126` 的 `continue` 使武装记录拿不到 `:127-132` 的 `Present==0` 检查。建议把「武装 tick」与「引用失效对账」分开，二者都跑（`RHAH_ArmedDemand.Tick` 继续管进攻/到期，对账管信）。
3. **给武装索粮加硬截止**：`RHAH_ArmedDemand.Tick`（`Source/Pawn/RHAH_ArmedDemand.cs:103-112`）在 `Refresh` 成功后，若 `job.ArmedAssault` 且 `tick >= record.ExpireTick + N 天`（N 可读设置，缺省 2–3 天）→ `Resolve(record, Ignore)`，使 `Finish` 一定被调用（`Resolve` 的 `Ignore` 分支现在在 `Enabled` 时直接 return，需一并改 `:164` 附近的分支，让「超期强制收尾」走到 `Finish`）。
4. **视图层最小放宽**：`ChoiceLetter_RHAH_Request.cs:17` 的 `CanDismissWithRightClick` 与 `:24-28` 的 Close 产出，改成「武装记录已进入 `ArmedAssault` 且无可用交付（`!ArmedDemand.CanPay`）时允许关闭」，关闭时只关信**不动 `Settled`**——因为信只是视图，`ArmedDemand.Tick` 仍会独立推进（这与 `docs/references/incidents.md:18`「保留信与原期限」的语义冲突，需先与作者确认）。
5. **顺手收敛的两处一致性问题**：
   - `ChoiceLetter_RHAH_KingdomArc` / `_BanditAttack` 没有任何 `RemoveLetter`，只靠玩家关；若希望「阶段推进后旧叙事信自动退场」，在同一处对账里按 `InstanceId`/`Stage`（`ChoiceLetter_RHAH_KingdomArc.cs:8-9`）收掉陈旧信。
   - `ChoiceLetter_RHAH_Revisit` 应在 Close（失效）时把 `RevisitSeen` 复位或落一个终态，避免「分支被静默消耗」（`RHAH_Revisit.cs:213`、`:237`）。
