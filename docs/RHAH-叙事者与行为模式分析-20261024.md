# RHAH（鼠族：饥与祸）叙事者与行为模式分析

分析对象：`RimworldMods/ratkin_hunger_and_havoc`（包名 `nanaloveyuki.ratkin.hungerandhavoc`，支持 1.6 / 1.7）。
方法：静态阅读源码与 XML，**未启动游戏**。全文路径相对 `ratkin_hunger_and_havoc`。
标注约定：**【实测】**＝本次读到的代码/文件内容可直接支持；**【推测】**＝由代码结构推断的运行后果，未在游戏内验证。

---

## 0. 结论摘要

1. **叙事者是"换参数的原版叙事者"，不是新机制。** 全库**没有任何** `StorytellerComp` / `StorytellerCompProperties` 子类（实测：`Source/` 全树无 `: StorytellerComp` 声明）。`StorytellerDef` 完全由原版 comp 在 XML 里拼装（`1.7/Defs/StorytellerDefs/RHAH_Storytellers.xml:11-132`）。唯一的自有机制是一个 Harmony Prefix 改写 `StorytellerComp_RandomMain.ChooseRandomCategory`（`Source/Storyteller/Suiyin/RHAH_EndingRuntime.cs:222-262`），用"信任度"缩放 `ThreatBig` 的权重与强制间隔。**"穗音"的差异化其实发生在叙事层（信件/案件/日志），不在叙事者机制层。**
2. **"特殊行为模式"不是 MentalState，是"Lord + Duty + JobGiver/JobDriver + 每 pawn 状态机"四件套**，四件全部通过原版扩展点接入：2 个 `ThinkTreeDef` 插进原版 `Humanlike_PostDuty` tag、2 个 `DutyDef`、每个版本 12 个 `JobDef`、1 个 `CompRHAH_Pawn`（角色/生命周期/16 个行为闸门）。**没有自定义 MentalStateDef（全库 0 处）。**
3. **"挪用原版拼装"成立，而且相当彻底**：`LordJob/StateGraph/LordToil/Transition/Trigger_Memo`、`Toils_Goto`/`Toils_General.Wait`、`JobDefOf.Goto`/`Wait`/`Wait_Combat`、`DutyDefOf.TravelOrWait`/`WanderClose_NoNeeds`/`AssaultColony`/`ExitMapNearDutyTarget`、`ThinkNode_ConditionalPrisoner`、`JobGiver_AIFightEnemies`、`IWaitForItemsLordToil`——全是原版零件，RHAH 写的是"哪个人、在什么条件下、用哪个零件"。
4. **`Source/Narrative/` 只有一个文件**（`NarrativeState.cs`，438 行），是 **GameComponent 形态的存档容器**，不含运行逻辑。它被 `EventMgr`、`Storyteller`、`Incidents` 三方直调，同一件事在事件生成处被手工写进 3～4 个系统（`Source/Incidents/RHAH_IncidentFacts.cs:104,110,115,117`）。**这个库的核心抽象不是叙事者，而是 `CompRHAH_Pawn`（来源身份＋生命周期＋行为闸门）＋"GameComponent 驱动的若干静态 runtime"。**
5. **"糙"的证据集中在**：硬编码 `DisplayId` 字符串决定行为、197/205/250 tick 魔数轮询、自造 `TicksPerDay=60000`、死常量（`WaitTicks`、`KeepsAge` 参数、`Counts(settings)`）、以及人物被俘/死亡/离图时 `foodReceivers` 与 `gateOverrides` 只做了部分清理。

### 2.3 唯一注入的机制：`RHAH_ThreatTempoPatch`（Harmony Prefix）【实测】

`Source/Storyteller/Suiyin/RHAH_EndingRuntime.cs:222-302`

- 目标：`StorytellerComp_RandomMain.ChooseRandomCategory`（:223）。
- 生效条件：`Find.Storyteller.def.defName == "RHAH_Suiyin"` 且目标是玩家家园地图（:238）；否则 `return true` 走原版。
- 逻辑：`factor = RHAH_EndingRules.ThreatFactor(trust) = 1 - trust/400`（`Source/Storyteller/Suiyin/RHAH_EndingRules.cs:17-21`），于是
  - 强制 `ThreatBig` 的判据变成 `60000 * maxThreatBigIntervalDays / factor`（:251-255）→ 信任高（factor 小）阈值变大，间隔拉长；
  - 随机选类时 `ThreatBig` 权重乘 `factor`（:276、:293）→ 信任低者更容易来大威胁。
  这与 XML 描述（:7）方向一致【实测代码方向 / 未在游戏内验证数值手感】。
- 附带问题：类名叫 `RHAH_ThreatTempoPatch` 却定义在 `RHAH_EndingRuntime.cs` 里，与文件名不符。

**结论（针对任务 1）：这是"换参数的原版叙事者 + 一个外挂叙事层"，不是新叙事机制。** 它没有定义新的 comp、新的 `IncidentCategoryDef`、也没有改 `StorytellerUtility`；难度曲线是"兰迪的 categoryWeights + 一条 trust 调制"，内容差异全部由 114（每版本 57）个 IncidentDef 与叙事层承担。

## 3. "特殊行为模式"是怎么落地的

### 3.1 四层结构（全部走原版扩展点）

```
事件（IncidentDef ×57/版本，1.7/Defs/IncidentDefs/RHAH_M1+M2.xml）
  └─ IncidentWorker_RHAH_*(Source/Incidents) → RHAH_IncidentFacts.Submit
       ├─ RHAH_PawnFactory.Create ... 每个 pawn 挂 CompRHAH_Pawn（身份+状态，存档）
       │    state: role(17 种) / lifecycle(6 态) / 16 个 BehaviorGate 覆盖 / 子女关系 / foodWaitUntilTick
       └─ RHAH_VisitorGroup.TryStart → Lord + LordJob_RHAH_Visitor（自写状态图）
            └─ LordToil ×4+1：Travel / Seek / WaitFood / Leave / ArmedAssault
                 └─ UpdateAllDuties() 设置 pawn.mindState.duty = PawnDuty(RHAH_VisitorSeek|RHAH_VisitorLeave)
                      └─ DutyDef.thinkNode = ThinkNode_Priority → JobGiver_RHAH_Visitor（行为优先级 if 链）
                           └─ JobGiver_RHAH_{Beg,Steal,Gnaw,Feed,WaitFood,MotherFeed,Leave,...} → JobDef(RHAH_*)
                                └─ JobDriver_RHAH_* = 原版 Toil 积木（Toils_Goto / Toils_General.Wait）
```

另有一条"无 Lord 回退"通道：`1.7/Defs/ThinkTreeDefs/RHAH_ThinkTrees.xml:3-12` 把 `ThinkNode_ConditionalRHAH_Visitor`（自写，判 `CanOrderLeave`）插进原版 `Humanlike_PostDuty` tag，priority 100。

## 4. `Source/Narrative/` 的角色与三个目录的边界

### 4.1 它是什么【实测】

`Source/Narrative/` **只有 1 个文件**：`NarrativeState.cs`(438)。

- `NarrativeState : GameComponent`（:36）——存档型组件，字段即状态：`trust`/`rescued`/`lost`/`failed`/`revealedCount`、`SuiyinLedger suiyin`、`SuiyinBook book`、`KingdomArcState kingdom`、`endingE01..05`（保留但已退休，:66 注释）。
- 里面还有 `NarrativeSnapshot`（只读快照 DTO）、`NarrativeOutcome` 枚举、`NarrativeOutcomeCalculator`（:411-437，纯函数）。
- **没有任何 Tick 逻辑**：它被 `GameComponent_RHAH_Game`（`Source/Core/`）持有和驱动，自身在 `ExposeData` 里做 PullBook/PushBook 的存档编排（:296-408）。

一句话：**`Narrative` = "叙事事实的存档与判定"，不是"叙事运行引擎"。**

### 4.2 边界【实测】

| 目录 | 形式 | 管什么 | 存什么 |
|---|---|---|---|
| `Source/Incidents/` | IncidentWorker / ChoiceLetter / 规则静态类 | 生成人物、选角色、开选择信、上交"事实" | 无（写进 Comp、Lord、Narrative） |
| `Source/EventMgr/` | **ODF 事件链**（`RHAH_EventFollow.oxy` 14 行 DSL、`RHAH_PredationArrival.oxy`）+ 迁移 + 长期 follow-up runtime | 事件链**定时与实例持久化**、后续事件、旧档迁移 | `EventChainInstance`（ODF） |
| `Source/Storyteller/Suiyin/` | 静态 runtime（6 个）+ 王国主线 + UI | 穗音的案件/信件/王国剧情 | 写进 `NarrativeState.book`（`SuiyinBook`/`SuiyinLedger`） |
| `Source/Narrative/` | 1 个 GameComponent | 汇总与判定（信任、结局枚举） | 存档本体 |

`Source/EventMgr/AGENTS.md` 自己写明"ODF 是事件链唯一定时与实例持久化运行时……不增设双时钟"——**这条约束只覆盖 EventMgr 内部**，跨到 Narrative/Storyteller 就失效了。

### 4.3 "同一件事在三处都处理"——**有，且是结构性的**【实测】

1. **事件生成时一次写四个系统**：`Source/Incidents/RHAH_IncidentFacts.cs` 同一函数内
   - `:104` `NarrativeState.NoteIncident(SuiyinIncidentFact)` —— Narrative
   - `:110` `RHAH_JournalRuntime.Open(...)` —— Storyteller
   - `:115` `RHAH_EventChainEntry.NoteStarted(...)` —— EventMgr

**核心抽象判断（任务 3 的答案）**：这个代码库真正的中枢是 **`CompRHAH_Pawn` + `RHAH_BehaviorGate`（"这个人是谁、处于什么阶段、允许做什么"）**，其次是 **"GameComponent 每 tick 驱动一组静态 runtime"** 的调度风格。`Narrative` 只是最薄的一层存档聚合，`Storyteller` 是内容层，`EventMgr` 是定时器层。三层之间**没有共享抽象**，全部靠静态类直调和 `DisplayId` 字符串耦合——所以"同一件事多处处理"不是疏漏，而是当前抽象缺失的必然结果。

## 6. 1.6 / 1.7 分叉

### 6.1 XML：**纯复制，只有 1 处差异**【实测】

对比方法：对 `1.6/Defs/**` 与 `1.7/Defs/**` 逐文件 SHA256 比对（脚本见下），**32 个 Def 文件里 31 个字节完全相同**。唯一差异：

```
1.6\Defs\WorldObjectDefs\RHAH_KingdomSite.xml
- <texture>World/WorldObjects/Settlement</texture>
- <expandingIconTexture>World/WorldObjects/Expanding/Settlement</expandingIconTexture>
1.7\...
+ <texture>World/WorldObjects/DefaultSettlement</texture>
+ <expandingIconTexture>World/WorldObjects/Expanding/Camp</expandingIconTexture>
```

即：1.7 换了世界地图图标的贴图路径（原版 1.7 改了资源名）。**行为相关的 XML（ThinkTrees / Jobs / Duties / Storytellers）两版本完全一致。**

另外：`LoadFolders.xml` 的 `v1.6`/`v1.7` 两段结构相同，只是 `1.6` 段把 `1.6` 目录当模块根、`1.7` 段用 `1.7/Guard` + `1.7`；两段都带同一个双前置条件（`IfModActive=oxygendsl` 且 `IfModNotActive` 三个同类饥荒 mod）。

### 6.2 行为相关 C#：**有版本分支，用 `#if RIMWORLD_1_7`**【实测】

定义来源：`Directory.Build.props` 里 `RimWorldVersion == 1.7` 时追加 `RIMWORLD_1_7`；1.6 用 `net48`，1.7 用 `net10.0`；两版本输出到各自的 `Assemblies/`，因此**两个 DLL 不同**（hash `B987BF67…` vs `AB61FAAF…`）。

与"行为模式"直接相关的分支：

| 位置 | 1.7 | 1.6 |
|---|---|---|
| `Source/Pawn/LordJob_RHAH_Visitor.cs:420-424` | `Math.Max(0, needed - BeingHauledTo)`（防负） | 直接相减（可为负） |
| `Source/Pawn/LordJob_RHAH_Visitor.cs:513-517` | 待粮过期判据 `HasBeenFed && !RHAH_Feeding.NeedsFood(pawn)`（真实需求） | 只看 `HasBeenFed` |
| `Source/Pawn/JobGiver_RHAH_WaitFood.cs:33-37` | 同上，`!RHAH_Feeding.NeedsFood(pawn)` | `snapshot.HasBeenFed` |
| `Source/Narrative/NarrativeState.cs:80-85` | `NarrativeEnabled => suiyinNarrativeForced`（**默认 false，需要在设置里勾"强制穗音叙事"**） | `NarrativeEnabled => true`（恒定开启） |
| `Source/Narrative/NarrativeState.cs:87-98` | `SetNarrativeForced` 有实现，会暂停/恢复王国进度 | 空实现（`#if` 内全被裁掉） |
| `Source/Storyteller/Suiyin/RHAH_EndingRuntime.cs:14-18` | `NarrativeActive` 取组件值 | 恒 `true` |
| `Source/Storyteller/Suiyin/RHAH_EndingRuntime.cs:20-38` | 设置页出现"强制穗音叙事"勾选框 | 不出现 |

**这条最值得注意【实测 + 后果推测】**：在 1.7 上，默认设置下 `NarrativeEnabled == false` → `SuiyinAllows`（`NarrativeState.cs:129-132`）、`IdentityDue`（:249-258）、`RHAH_EndingRuntime.Tick`（:64-67）全部短路。也就是说 **1.7 里"穗音"开局只有原版 comp 的事件节奏 + 信任计数在跑，案件/信件/日志/身份/结局要玩家手动开**；而 1.6 恒开。这不是 XML 分叉，是编译期行为分叉。

## 8. 验证了什么 / 没验证什么

**已验证（实测读过文件）**
- 2 个 StorytellerDef 实为 1 个 defName 在两版本各一份，文件 hash 相同；`listOrder=55`；12 类 comp 全是原版。
- 全库 **0 个**自定义 `StorytellerComp`/`StorytellerCompProperties` 子类；唯一叙事者机制是 `RHAH_ThreatTempoPatch`（Harmony Prefix）。
