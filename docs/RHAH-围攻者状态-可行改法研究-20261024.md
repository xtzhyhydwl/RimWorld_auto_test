# RHAH 围攻者身体状态 —— 可行改法研究（2026-10-24）

> 目的：为「E12 乞食围攻（`I-014` / `I-030` / `I-045`）的围攻小人到场即濒临饿倒、撑不到/撑不住围攻」给出**可选改法**与取舍，供决策，不含实施。
> 只读完成：未修改模组、未修改游戏安装目录、未运行游戏、未编译。本文所有代码行号与 Def 行号都是当场读出来的。
> 前置研究：`docs/RHAH-E12-饥饿与战力机制-20261024.md`（同目录，已给出 0.25→0.61~0.79 的推演）。本文不重复其推导，只补「怎么改」。

**版本注记（重要）**：本机只找到一份 RimWorld 安装 —— `D:\SteamLibrary\steamapps\common\RimWorld`，`Version.txt` 内容为 `1.6.4871 rev590`，即 **1.6**。任务前提写的是 1.7，**本机没有 1.7 安装可用于核对原版 Def**。下文所有「原版 Def 实测」都来自这一份 1.6 安装；若 1.7 改过 `Hediffs_Global_Needs.xml`，数字需按 1.7 安装目录重核。

## 0. 结论与推荐（三行）

1. **最省事、且直接命中用户诉求的是「开场状态 + 开打时机」这一对**：先把 `famineArrivalMalnutrition` 从 0.25 调到 0.10 左右（零代码、滑条可回退，能多买 6–10 小时），同时在 C# 里加一条「任何成员营养不良 ≥ 0.7 就强制 `Timeout` 开打」的保底（只影响 3 个围攻 ID）。
2. **B 方案（临时 Hediff）是「正路」，但不要指望它靠 `Consciousness` 加成救场**：原版 `MeleeHitChance` 只吃 `Manipulation` 与 `Sight`，营养不良一档都不碰这两项 —— 加意识对「打得好不好」几乎无帮助，只有防止倒地这一件事有效；要吃满收益，buff 要加 `Manipulation` / `Moving` / `MeleeHitChance`。
3. **不要动默认值、不要收紧滑条上限、不要只加 trait**：改默认值对老档无效且波及 23 组事件 + 商队/拦截/难民营/使节；trait 体系改不了意识与倒地，抓错了杠杆。（以上为**判断，未实测**）

## 3. B 方案技术细节（临时 Hediff）

### 3.1 `HediffDef` 最小骨架与必填字段

按仓内两个现成文件对齐（`1.6/Defs/HediffDefs/RHAH_Refeeding.xml:3-35`、`1.6/Defs/HediffDefs/RHAH_Gnaw.xml:3-65`）：

- 必填：`defName`、`label`；建议全写：`description`、`hediffClass`、`initialSeverity`、`isBad`、`stages`（**至少要一个 `<li>`，否则 stage 为 null，capMods 无处可挂**）、`comps`（需要 comp 时）。
- `hediffClass`：要 comps 就写 `HediffWithComps`（`RHAH_Refeeding.xml:7`）；要自定义行为就写全名类（仓内 `RHAH_ClaySatiety` → `HungerAndHavoc.Pawn.Hediff_RHAH_ClaySatiety`，`RHAH_ClaySatiety.xml:7`）。不写默认用 `Hediff`。
- severity 边界：`minSeverity` / `maxSeverity`（`RHAH_ClaySatiety.xml:9-10`）、`initialSeverity`。
- 定时自灭：`<comps><li Class="HediffCompProperties_Disappears"><disappearsAfterTicks>90000~90000</disappearsAfterTicks><showRemainingTime>true</showRemainingTime></li></comps>`（`RHAH_Gnaw.xml:11-15`；原版同款 `Hediffs_Local_Infections.xml:82-85`）。`disappearsAfterTicks` 接受 `min~max` 区间。

### 3.2 `capMods` / `statOffsets` / `statFactors` 的写法与坑

**能力（capacity）—— 用 `capMods`**，槽位：`offset`（加性）、`factor`/`postFactor`（乘性）、`setMax`（钳制）：

- 加性抵消：原版 `severe` 是 `Consciousness offset -0.30`，所以 buff 写 `<capacity>Consciousness</capacity><offset>0.30</offset>` 正好抵平；写法照 `RHAH_Gnaw.xml:57-62`（`Consciousness -0.6`）与 `RHAH_Refeeding.xml:27-30`（`Consciousness -0.25`）。
- 正向能力加成在**原版有先例**：`FibrousMechanites` 的 `Manipulation`/`Moving`/`BloodPumping` 各 `+0.5`（`Hediffs_Local_Infections.xml:107-120`）。但注意**原版没有任何一条给 `Consciousness` 加正向 offset**（Core 全表只有负值与 `setMax`），所以「意识 +0.3」没有原版先例可抄，属自创用法。
- **坑 1（最关键）**：`extreme` 档用 `setMax 0.1`。能力合成是「先累加 offset/factor，再套 setMax 钳制」的顺序（原版机制常识，未在本机验证 —— 本机只有 DLL，`Source` 目录缺 `PawnCapacityUtility`）。若成立，**任何 `Consciousness +N` 的 buff 都救不了已进入 0.8 档的人**。→ 结论：buff 必须在 0.8 之前起作用，或者 buff 自带「压营养不良」的逻辑（见 §3.5 B2）。
- **坑 2**：能力上限本来是 1.0，`offset +0.3` 在「没病」的人身上不产生任何效果（不会超过 100%）；它只用来抵消别的 debuff。想让鼠族「比常人更强」必须走 `statOffsets`（命中/移速），不是 `capMods`。
- **坑 3**：`capMods` 的 `capacity` 必须写 `PawnCapacityDef` 的 `defName`（`Consciousness` / `Moving` / `Manipulation` / `Sight` / `Eating` …，见 `D:\...\Data\Core\Defs\PawnCapacityDefs\PawnCapacity.xml`）；拼错会在加载时报错或静默无效果（后者更常见于 `statOffsets`）。

**数值（stat）—— 用 `statOffsets` / `statFactors`**：

- 放在**stage 里**（与 `capMods` 同级），不是 HediffDef 顶层。仓内例子：`RHAH_Gnaw.xml:54-56`（`<statFactors><MaxNutrition>0.1</MaxNutrition></statFactors>`）。
- `MeleeHitChance` 的单位是**百分点**：原版 `noSkillOffset 4`（`Stats_Pawns_Combat.xml:75`）、`Brawler` 给 `4`（`Traits_Singular.xml:157-159`），仓内 `GranaryBreaker` 给 `3`（`RHAH_Traits.xml:780-782`）。给围攻者 `+5` 是合理量级。
- `MoveSpeed` 单位是**格/秒**，base 3.0（`Stats_Pawns_General.xml:5-12`）：`<MoveSpeed>0.3</MoveSpeed>` = +10%。
- **坑 4**：`statFactors` 写百分比类 stat（如 `MeleeHitChance`）是错的 —— 它是 0 基数的加性分，乘出来是 0。

- **`HediffDef` 走 `RHAH_DefOf` 静态字段**（`Source/Core/RHAH_DefOf.cs:10-16`），不要在业务代码里 `DefDatabase.GetNamed`（仓内 Hediff 只有一处例外：`Source/Pawn/RHAH_Begging.cs:434` 取 `Bruise`）。

### 3.4 移除时机的三个挂点（按推荐顺序）

1. **`RHAH_ArmedDemand.Resolve`（`Source/Pawn/RHAH_ArmedDemand.cs:140-169`）—— 唯一汇聚点，首选。** 它同时处理「交付/关闭」（`:153-162`）与「转敌对」（`:164-168`）两条出口，在这里 `Resolve` 后按 `members` 逐个 `pawn.health.RemoveHediff(...)` 就能覆盖「付了食 → 撤 buff」「拒绝/超时 → 撤 buff」。注意 `:145-149` 的 `Owner == null` 提前返回分支也要清（否则悬空 buff）。
2. **`LordJob_RHAH_Visitor` 的 toil 切换（`Source/Pawn/LordJob_RHAH_Visitor.cs:294-299`）** —— `toAssault.AddPostAction(...)` 与已有的 `TransitionAction_EndAllJobs()`（`:298`）同位置挂，等价于「Lord 建立即移除」。适合「只信 toil 不信 Resolve」的做法，但会漏掉 `Resolve` 的交付分支。
3. **`LordToil_RHAH_ArmedAssault.UpdateAllDuties`（`Source/Pawn/LordToil_RHAH_ArmedAssault.cs:13-22`）** —— 每次刷新 duty 都会被调用，适合「开打那一刻」精确撤（也适合在这里补一份「没撤掉的兜底撤」）。缺点是每帧刷新，不要在里做重活；另可配合 `HediffCompProperties_Disappears` 做时间兜底（存档/读档/Lord 丢失都不会悬空）。

**仓内「临时 hediff + 定时/条件移除」的现成样板（可直接指认）**：

- **`RHAH_RefeedingSyndrome`**：`HediffWithComps` + `HediffCompProperties_Disappears(120000~300000)` + 单 stage `capMods`，`1.6/Defs/HediffDefs/RHAH_Refeeding.xml:4-34`；加它的代码在 `Source/Pawn/RHAH_Feeding.cs:76-97`（`TryAddRefeeding`：先 `HasHediff` 判重、再 `AddHediff` —— 与 B 的加法一模一样）。
- **`Hediff_RHAH_ClaySatiety`**：自定义 hediff 类，用 `ShouldRemove` + `TickInterval` 里做 severity 衰减自灭（`Source/Pawn/Hediff_RHAH_ClaySatiety.cs:13-14,107-113`），不需要 `Disappears` comp。**B2 变体（压营养不良）应当照这个类写**。
- 移除调用样例：`pawn.health.RemoveHediff(hediff)`，`Source/Generation/RHAH_PawnBody.cs:56`、`Source/Generation/RHAH_FertilityPatch.cs:369`。

### 3.5 B 的两个变体（互相不替代）

- **B1 纯 Buff（低风险）**：`stages` 里给 `Consciousness +0.10~0.30`、`Manipulation +0.15`、`Moving +0.15`，`statOffsets` 给 `MeleeHitChance +5`、`MoveSpeed +0.3`；`comps` 挂 `Disappears`（例如 `60000~60000`）＋ 在 `Resolve` 撤。效果：0.2–0.6 档「几乎无感 → 满状态」，0.8 档救不回来（§3.2 坑 1）。
- **B2 压营养不良（真正解决问题的那半）**：自定义 `Hediff_RHAH_SiegeVigor : HediffWithComps`，`TickInterval` 里取 `HediffDefOf.Malnutrition`，若 `Severity > 0.75` 就写回 `0.75`（或按「等待剩余时长」线性回退）。效果：等人期间**永远不跨 0.8**；开打撤掉后营养不良从 0.75 继续涨 → 自然形成「撑到开打，打完就垮」的叙事。代价：一个自定义类 + 一处每 tick 的健康查询（按 `Source/AGENTS.md` 的高频约束，应做 `TickInterval(delta)` 且不 LINQ，样板见 `Hediff_RHAH_ClaySatiety.cs:107-113`）。
- **不要选**：「给 `Consciousness` 加 0.6 想让 0.1 上限变 0.7」—— 按 §3.2 坑 1 无效，即便有效也会让全队变成「饿到极限仍神智清醒」的怪设定。

## 4. 改默认值（`famineArrivalMalnutrition`）的影响面

### 4.1 读取点：全仓只有一处

- 业务读点：`Source/Generation/RHAH_FamineArrival.cs:28`（`settings == null ? 0.25f : settings.famineArrivalMalnutrition`）。
- 定义/持久化/夹取：`Source/Core/RHAH_Settings.cs:57`（字段默认 0.25）、`:349`（Scribe 默认）、`:1673`（夹取 0.01–0.5，越界回 0.25）。
- UI：`Source/Core/ModEntry.cs:139-140`（原版设置窗口滑条 0.01–0.5，无“默认/重置”按钮）；`Source/Pawn/Compat/RHAH_IrisMenusCompat.cs:1488`（Iris 版）、`:1546`（搜索索引）。
- 文档既有约定：`docs/references/save-ownership.md:699-700`（「全局 ModSettings，默认 0.25，范围 0.01..0.5」）。
- 测试把 0.25 钉死：`Source/Tests/RHAH_AttackChoiceTests.cs:653`（`Assert.Equal(0.25f, …Severity)`）—— 改默认值必须同步改这条断言。

### 4.2 波及范围（比「23 类事件」还宽）

`RHAH_FamineArrival.Initialize` 只由 `RHAH_PawnFactory.Create` 调用（`Source/Generation/RHAH_PawnFactory.cs:57`），而 `Create` 是**所有**场景来客的统一入口：

- 23 个事件组（`Source/Incidents/RHAH_IncidentGroups.cs:10-32`）里的全部「饥荒来客」—— 不只围攻，还有乞丐、难民、商人、使节、瘟疫队伍等；
- 商队/交易事件（`Source/Trade/TradeEventRouter.cs:69`）、拦截（`Source/Incidents/RHAH_Interception.cs:53`）、难民营（`Source/Incidents/RHAH_RefugeeCamp.cs:222`）、使节（`Source/Storyteller/Suiyin/RHAH_Envoy.cs:80`）、长线随访（`Source/EventMgr/RHAH_LongFollowRuntime.cs:624`）。
- 例外：`RHAH_PawnFactory.Generate` 的直调者（`Source/Incidents/IncidentWorker_RHAH_Feral.cs:36`）**不**经过 famine arrival，不受影响。

### 4.3 调低会不会破坏别的事件的前提假设？

按读到的东西，真正的耦合只有三处，都**不是硬前提**：

1. **叙事**：`RHAH_Settings_FamineArrival_Tooltip`（`Languages/ChineseSimplified/Keyed/Settings/RHAH_Visitors.xml:109-111`）明确写「到达时获得营养不良严重度」。调到 0.01–0.10 → 文档里写的是「较轻」以下，`trivial` 档只有 -5% 意识，玩家几乎看不出他们饿 —— 但**饥饿条仍是 0**，观感上仍是「来要饭的」，只是不虚弱。
2. **再喂养综合征**：`RHAH_Feeding.cs:89-96` 要求 `Malnutrition.Severity >= refeedMalnutrition`（默认 0.4，`Source/Core/RHAH_Settings.cs:219`、`Source/Pawn/RHAH_ReliefFood.cs:31`）。入场值降到 0.10 后，**要等 2.4–3.6 天**才会触发再喂养综合征 → 围攻这批人基本吃不到这个负面（本来也是「喂饱后」才结算）。副作用方向是「对玩家更宽容」，不会弄坏别的事件。
3. **Suiyin 安置计时**：暂停条件是「**存在**营养不良 hediff」而非严重度（`Source/Storyteller/Suiyin/SuiyinRules.cs:261-264`，使用点 `RHAH_SettlementProgress.cs:269-270`）。只要 famine arrival 还在加 hediff，**降到 0.01 也照样暂停**；真正会让它不暂停的是关掉 `famineArrivalEnabled`（`RHAH_Settings.cs:56`）。这条要单独说清，别把「调低」当成「修好计时」。
4. **`Malnutrition` 阶段边界**：从 0.25 降到 0.19 以下会掉出 `minor` 进 `trivial`（`socialFightChanceFactor` 3 档 → 1.5、`hungerRate +0.6 → +0.5`）。这对「来客互相打架/抢食」的既有观感有轻微改变（`RHAH_Trait_HungerRage`/`FoodSnatcher` 的 `socialFightChanceFactor` 是另一个乘数，不受影响）。

### 4.4 两个「改默认值」之外的结构性事实

- **改默认值对老档无效**：`Scribe_Values.Look(ref famineArrivalMalnutrition, "famineArrivalMalnutrition", 0.25f)`（`Source/Core/RHAH_Settings.cs:349`）—— 老档里已存了 0.25，默认值只在键缺失时生效。想让老档也变，必须加迁移代码或改成「按版本覆盖」，那是另一笔成本。
- **1.6 / 1.7 是两份物理文件**：`LoadFolders.xml` 的 `<v1.7>` 只装 `1.7/…`，而 `1.6/Defs` 与 `1.7/Defs` 下的同名文件**逐字节相同**（已比对 `RHAH_Refeeding.xml` / `RHAH_Gnaw.xml` / `RHAH_Traits.xml` / `RHAH_ThinkTrees.xml`：`IDENTICAL`）。所以**任何新增 Def（B/C）都必须同时写两份**，否则 1.7 玩家（= 用户）看不到。

## 5. 推荐排序（全部为**判断，未实测**）

1. **先做 A 的「玩家侧调值」，不做代码改动**：`famineArrivalMalnutrition` 0.25 → 0.10。零风险、可回退、当场可验证；但它只买 6.6–10 小时，属「先止血」，不能当结论。
2. **紧接着做 D2（阈值保底）**：在 `RHAH_ArmedDemand.Tick`（`Source/Pawn/RHAH_ArmedDemand.cs:103-112`）里加「任何存活成员 `Malnutrition >= 0.7` → `Resolve(Timeout)`」。约十行、只影响 3 个围攻 ID，直接消除「还没开打就先静默作废」这个最伤体验的路径。它是唯一能保证「围攻一定开得起来」的改动。
3. **想做「正路」再上 B，且按 B2 为主、B1 为辅**：B2 保证等待期不跨 0.8（叙事也顺：开打后才垮），B1 补命中和移速（因为意识加成对战斗几乎无用，见 §1.2）。成本是一个自定义 `HediffWithComps` + 两份 XML + 两处挂点。
4. **C（trait）不单独做**：trait 动不了意识与倒地，单独上只是「看起来改了」。真要做，只作为 B1 的可见性包装（沿用 `RHAH_Trait_HungerRage` / `RHAH_Hunger` 标签的现有 lore）。
5. **D3（等待期禁自由行动）先不做**：等待期本来就在 `Wait`，只有极少数会去啃树皮；收益比不过改动与新增闸门的维护成本。
6. **明确别做**：① 改 `RHAH_Settings.cs:57/:349` 的**默认值**（对老档无效 + 全局波及 23 组 + 商队/拦截/难民营/使节，且叙事被稀释）；② 收紧 `:1673` 的 0.5 上限（那只是玩家自由度）；③ 靠「意识 +0.6」硬顶 0.8 档（`setMax 0.1` 大概率会赢，且设定荒谬）。
