## 0. 结论速览

1. 现在仓里有 **四处** 等待/轮询，不是三处：`src/wait.js` 的 `waitFor`、`src/live.js` 的 `runLive`、`src/launcher.js` 的 `waitForBridge`，外加 `stopGame` 里的「等进程退干净」循环（`launcher.js:1087-1091`）。前三处语法与退出码各不相同，但**判定逻辑形状完全一样**：反复采样 → 判一个布尔 → 到点收工。【代码】
2. 合并的落点是：**`waitFor` 只留一个循环**，其余三处都退化成「采样函数 + 一个条件 JSON」。`waitFor` 的签名从「必须给函数」扩成「给函数（老用法）**或**给一个 `source` 规格（新用法）」，老调用点 `cli.js:431` 一行不用改。【代码】
3. 四类 source 的采样函数签名统一为 `(ctx) => Promise<object|null>`；`result.` 前缀对四类**同一个含义**：本次采样返回的载荷根（桥接=工具载荷 / 事件=事件快照 / 进程=进程快照 / 桥接就绪=就绪快照）。这让「条件 JSON」对四类源语法完全一致。【推断】
4. 15 个算子 **14 个可原样复用**，**必须新增 1 个**：`contains`（子串）。理由只有一个且很硬：`live --until` 的 `~` 是子串匹配（`live.js:101`），没有 `contains` 就无法把 `--until` 翻译成条件 JSON，`live` 也就变不成薄封装。窗口/计数一律用现有算子 + 探针参数表达，**不再加算子**。【代码】
5. `launcher.waitForBridge` **不该被删掉**，该被「掏空」：保留同名同签名同「抛错」语义（`start` 的退出码靠它），内部改为 `waitFor` + 一个 `bridge-ready` 采样 + 一个条件：`any[bridge.source=log, bridge.connected=true]`。它的「进程死了立刻失败」由采样函数抛错实现（`waitFor` 的探针异常分支正好就是「立刻失败」，`wait.js:135-148`）。【代码】
6. 条件登记表落 `src/conditions.json`（用户已定）。`wait --scenario <名字>` 引用；名字不存在用 `editDistance`（`src/toolname.js`，`wait.js:16` 已在用）给近似名后 exit 1。**加场景 = 只加一条数据**，前提是四类 source 与算子够用。【推断】

### 1.2 重叠与**不可直接合并**的差异

**重叠（形状相同，纯重复）**：三处都是「采样 → 判布尔 → sleep → 到点」。三处的 sleep 分别是 `setTimeout`（`wait.js:161`）、`setInterval`（`live.js:287`）、`await sleep(500)`（`launcher.js:1003`）——同一件事三种写法。【代码】

**差异 1：输出契约不同（最硬的一条）**
`wait` 的 stdout 是**一个 JSON 证据**（`cli.js:459`）；`live` 的 stdout 是**命中的那一行原文**（`live.js:296`）。
⇒ 合并后 `live` 的输出必须由**包装层**照原样打印，不能变成 JSON。`waitFor` 只能返回 `sample`，打印责任留在各命令分支。【代码】

**差异 2：`live` 是「逐行流式命中」，`waitFor` 是「对当前快照求值」**
`live` 对每一行单独判，命中即停（`live.js:290-300`）；`waitFor` 反复对同一份采样求值（`wait.js:150`）。
⇒ 事件源的采样**必须累积**（探针自己持有 follower 偏移 + 已读事件），否则 200ms 轮询之间到达并一闪而过的行会漏。`waitFor` 只要求「重复调用安全（不丢数据）」，不要求幂等。【推断】

**差异 3：超时/失败的语义不同**
`waitFor` 把「到点」当分支（`ok:false`），`waitForBridge` 把「到点」当异常。`start` 现在依赖后者（`cli.js:179` 直接 await，抛了就是 exit 1）。
⇒ 不能把 `waitForBridge` 直接换成 `waitFor` 的返回值：会静默把 `start` 的 exit 1 变成 exit 2。必须保留一层「把 `ok:false` 再抛出去」的适配。【代码】

**差异 4：`live` 的匹配是**字符串化比较**，`wait` 的 `equals` 是**严格深比较**
`live` 用 `fieldText` 把数字/布尔 `String()` 化（`live.js:89-95`），所以 `speed=1`、`opened=true` 成立；`wait` 的 `equals` 是 `deepEqual`（`wait.js:331-339`），`{"equals":"1"}` 对数字 `1` **不成立**。
⇒ `--until` 翻译成条件 JSON 时必须落在**字符串化视图**上（本文 §2.2 的 `result.texts`），否则 `live` 的语义会静默变窄。【代码】

**差异 5：`live` 的「默认从头扫」是语义，不是优化**
`--until` 问的常常是「那个事件**发生过**没有」，watcher 比游戏晚起是常态（`live.js:13-14`、`:281`）。`--from-start` 默认、`--new-only` 才跳到末尾（`live.js:256-259`、`:281`）。
⇒ 事件源采样必须带 `from:'start'|'now'` 参数，且 `'start'` 下第一次采样就要吞掉整段历史。【代码】

**差异 6：等的东西层级不同**
`waitForBridge` 的判据是「日志行 **或** 端口可连」（二选一，`launcher.js:971-980`），不是单一探针的一次返回值。⇒ 采样函数内部做这个 or，输出成一个布尔字段 `ready`，条件只写 `{"path":"result.ready","equals":true}`。这正好证明「条件即数据」能承载旧逻辑。【推断】

**差异 7：采样成本差 4 个数量级**（直接影响 interval 默认值）

| 采样 | 成本 | 依据 |
| --- | --- | --- |
| 事件采样（`statSync` + `readSync`） | 亚毫秒 | `live.js:128-168` |
| 进程存活 `probePid`（`process.kill(pid,0)`） | ~0.01ms | `proc.js:124-149` |
| 桥接工具调用（`callTool`） | 毫秒级往返；文档记录命中路径 5ms | `wait.js:107`、`docs/cli-wait-实测-20261024.md:19`、`:29-31`（该文档的实测，本设计未复测） |
| `canConnect`（TCP 连接） | 上限 700ms（`launcher.js:978`） | 同左 |
| `verifyInstance`（起 `powershell.exe`） | 0.2~1s | `proc.js:163-168`、`:221-254` |

⇒ 统一默认 `intervalMs = 200` 只对前三类安全；**带 `--verify-identity` 的进程采样必须把间隔抬到 ≥1000ms**（否则每轮起一个 powershell）。【推断】

## 2. 合并方案

### 2.1 一个 `waitFor`，两种第一参数

```js
// src/wait.js
export async function waitFor(probeOrSpec, opts = {}) { … }
```

| 第一参数形态 | 谁在用 | 行为 |
| --- | --- | --- |
| 函数 `(ctx) => Promise<any>`（老形态） | `cli.js:429-433`、离线测试、`src/smoke.js` | 与现在**逐字相同**（`wait.js:107-163` 原样保留） |
| 规格对象 `{source, profile, file, pid, probeName, args, from, windowMs, verifyIdentity}` | `cli wait --source event|process|bridge-ready`、`live`、`waitForBridge` | 由 `buildProbe(spec)` 产出同形态的采样函数，再走同一条循环 |

`opts` 除了现有 `{condition, timeoutMs, intervalMs, what}`，新增两个**可选、不影响老行为**的字段：

- `opts.onPoll({attempt, elapsedMs, sample})`：每轮「未命中」后回调一次。`start` 的点点点（`cli.js:179` 的 `onTick`）靠它还原。
- `opts.deadline`（毫秒时间戳，默认由 `timeoutMs` 算）：采样函数的 `ctx.deadline` 用它，桥接源才能把「单次 调用超时 = 剩余预算」写进采样（现在这段逻辑在 `cli.js:419`、`:431-432`，属于把预算知识漏到 CLI 层）。

### 2.2 四类 source 的采样函数签名

统一签名：

```js
/**
 * @typedef {(ctx: {attempt:number, deadline:number, remaining:()=>number}) => Promise<object|null>} Sample
 * 返回对象 = 本次采样的载荷，条件里的 `result.` 就是它（`wait.js:29`、`:267-296` 的根）。
 * 抛错 = 取不到观测（waitFor 会立刻失败，`wait.js:135-148`）；「文件还没建」「字段还没出现」这类
 * **正常的还没到**不许抛，要返回空壳（与 `wait.js:78-85` 把缺路径降级成"没成立"同一个哲学）。
 */
```

| source | 采样返回什么 | `result.` 是什么 | 抛错边界 | 默认间隔 |
| --- | --- | --- | --- | --- |
| `bridge` | `callTool(probeName, args)` 的原样载荷（**不套壳**） | 工具载荷根（`get_bridge_status` 的 `state`、`list_colonists` 的 `colonists`） | 调用失败/超时 ⇒ 抛（探针故障）；工具名不存在 ⇒ 循环开始前就抛（`cli.js:428`） | 200 |
| `event` | 事件快照（见下表 §2.2.1） | 快照根：`result.events` / `result.texts` / `result.counts` / `result.last` / `result.lineMatch` | 文件不存在/被截断/坏行 ⇒ **不抛**，返回空快照或跳过该行（沿用 `live.js:133-159`、`:200-210`） | 200（= `live.js:26` 的 `POLL_MS`，保住老手感） |
| `process` | 进程快照（见 §2.2.2） | 快照根：`result.alive` / `result.state` / `result.port.listening` / `result.bridge.*` / `result.instance.*` | `probePid` 不抛（`proc.js:139-149` 全是返回三元态）；`verifyInstance` 失败返回 `{ok:false,reason}`（`proc.js:221-254`）⇒ **一律不抛**，让条件来决定 | 200；`--verify-identity` 时 ≥1000 |
| `bridge-ready` | `{ready, host, port, token, source, connected, logTail}` | 快照根：`result.ready`、`result.source`、`result.connected` | **进程死 ⇒ 抛**（保留 `launcher.js:985-996` 的快速失败） | 500（= `launcher.js:954` 的 `pollMs`） |

#### 2.2.1 事件快照的结构（`--source event`）

```js
{
  file, source: 'events' | 'log',
  fromNow: boolean,           // --new-only ⇒ true
  linesRead: number,          // 本次 wait 从起点读到的行数（对应 live 的 newEvents，live.js:284/297）
  events: object[],           // 原始事件（有上限，见 §5 R4）：result.events
  texts:  object[],           // 与 events 同序的**字符串化视图**：result.texts（--until 兼容用）
  last:   object | null,      // result.last
  text:   object | null,      // result.text（last 的字符串化视图）
  counts: { [kind]: n },      // result.counts.<kind>；kind 取自事件的 kind 字段（--source log 恒为 'log'）
  kinds:  [{kind, count}],    // result.kinds —— counts 的数组形态，给 anyItem 用（kind 里含 '.' 时 counts 的路径不可达）
  lineMatch?: {index, raw},   // 只在 --until 兼容模式出现，且**命中前不带这个键**（见 §5 R7）
  truncated: boolean, dropped: number,
}
```

- 字符串化视图的规则 = 现在 `fieldText` 的规则（`live.js:89-95`）：数字/布尔按 JSON 字面量、`null` → `"null"`、对象 → `JSON.stringify`。**唯一的差别是键缺失时键也缺失**（`fieldText` 返回 `undefined` 也是"不匹配"，语义一致）。
- **`counts` 是对全部已读事件的精确计数**（不随 `events` 上限淘汰），所以「按 kind 计数」在超长会话里仍然精确；只有「按字段匹配某条历史事件」会受淘汰影响（§5 R4）。
- 表里没有「窗口」算子：窗口是**探针参数** `windowMs`，采样时只把最后 N 毫秒内的事件放进 `events`/`texts`。`{"path":"result.texts","anyItem":{…}}` 就是「窗口内出现」。【推断】

#### 2.2.2 进程快照的结构（`--source process`）

```js
import { probePid, verifyInstance } from './proc.js';   // 不再写第三份 PID 判断

{
  profile, pid,
  state: 'alive' | 'foreign' | 'none' | 'unknown',  // = probePid(pid).state（proc.js:139-149）
  alive: state === 'alive',                        // = isAlive(pid)（proc.js:158-160）
  port: { port, listening } | null,                // 监听来源：记录/日志里的 bridge.port
  bridge: { available, reachable, ready, source, host, port, reason } | null,  // = probeBridge（launcher.js:641-684）
  instance: { ok, reason, profile } | null,        // = verifyInstance(pid,{processesDir, expectedProfile})，仅 --verify-identity 时算
  record: { pid, startedAt, bridge: { port } } | null,
}
```

**为什么必须用 `proc.js` 而不是 `process.kill` 内联**：`probePid` 把 `EPERM` 单独成 `foreign` 态，而 `isAlive` 明确「EPERM **不算**活着」（`proc.js:151-160`）——2026-10-24 的故障正是把 `EPERM` 当活着，导致 `start` 一直报「已有实例在运行」。`wait` 若自己写一份判断，这个修复会被绕过。【代码】

**为什么 `verifyInstance` 默认不开**：它每次起一个 `powershell.exe`（`proc.js:163-168`，0.2~1s），200ms 轮询会把机器打满。默认只做 `probePid`；要「连的是不是自己那一局」才加 `--verify-identity`，并把间隔抬到 ≥1000ms。【推断】

#### 2.2.3 `live --until` 小语法怎么并进来（不破坏它）

**保留分词器，删掉第二套匹配器。** 现在是两步：`parsePredicate`（`live.js:67-86`，按 `key<op>` 切，值里允许空格）+ `matches`/`fieldText`（`live.js:89-104`，字符串化比较）。
改造后：

1. `parsePredicate` 原样保留（它就是语法本身，且 `--until` 的文案/用例不受影响）。
2. `fieldText`/`matches` **删除**，改成一个纯翻译函数：

```js
// src/events.js（或 src/live.js 内的私有函数）
/** 'kind=colony_started' / 'kind=log text~[VD] 1 incident' → 条件 JSON（落在字符串化视图上） */
export function untilToCondition(predicates) {
  return { path: 'result.texts', anyItem: { all: predicates.map(p => ({
    path: p.key,
    [p.op === '=' ? 'equals' : 'contains']: p.value,
  })) } };
}
```

3. 于是 `--until` 的每一行判定由**同一个** `matchesCondition` 完成（`wait.js:66-68`），不再有第二套 `matches`。【推断】

**逐条等价性核对**（这是"不破坏它"的判据）：

| `--until` 用例 | 旧行为（`live.js:89-104`） | 新行为（`texts` + `equals/contains`） | 等价 |
| --- | --- | --- | --- |
| `kind=colony_started` | `String(ev.kind)==='colony_started'` | `texts[i].kind === 'colony_started'` | ✔ |
| `speed=1`（数字） | `String(1)==='1'` | 视图里已是 `"1"` ⇒ `equals:"1"` | ✔ |
| `opened=true`（布尔） | `String(true)==='true'` | 视图 `"true"` | ✔ |
| `text~[VD] 1 incident` | `String(v).includes(...)` | `contains`（新增算子） | ✔ |
| 键不存在 | `fieldText` 返回 `undefined` ⇒ 不匹配 | 路径取不到 ⇒ 未成立、继续轮询（`wait.js:78-85`） | ✔ |
| 值里有空格 / `&&` 连接 | `parsePredicate` 已处理 | 不变 | ✔ |
| 对象字段 `x~…` | `JSON.stringify` 后子串 | 视图同规则 | ✔ |

**唯一的新增成本**：命中后要能打印**那一行原文**（`live.js:296`）。做法：兼容模式下采样函数除了累积 `events/texts`，还在每读到一个新事件时用同一个 `matchesCondition` 预判，第一次命中就把 `{index, raw}` 记进 `lineMatch`（粘性，不随后续行消失）。`waitFor` 的条件写成 `{"path":"result.lineMatch","exists":true}`——**命中前不带这个键**，否则 `null` 会被 `exists` 判真（`wait.js:210-215` 只看 hasOwnProperty）。这不是第二套判定：算子是 `matchesCondition`，循环仍然只有 `waitFor` 一个。【推断】

### 2.3 15 个算子：谁能原样复用

| 算子 | 事件 | 进程 | 桥接就绪 | 判定 |
| --- | --- | --- | --- | --- |
| `all` / `any` / `not` | ✔ | ✔ | ✔ | 原样复用（组合子与来源无关，`wait.js:169-188`） |
| `path` | ✔ | ✔ | ✔ | 原样复用（机制，不是算子） |
| `exists` | ✔ | ✔ | ✔（`{"path":"result.ready","exists":true}` 恒真 ⇒ 别这么写，见 R7） | 原样复用 |
| `equals` / `notEquals` | ✔（数字/布尔/字符串；字符串化视图见 §2.2.1） | ✔ | ✔ | 原样复用 |
| `in` / `notIn` | ✔（如 `{"path":"result.last.kind","in":["window","log"]}`） | ✔（`{"path":"result.state","in":["none","foreign"]}`） | ✔ | 原样复用 |
| `countEquals` | ✔（`{"path":"result.events","countEquals":0}`） | ✘（没有数组字段；套用会抛类型错 `wait.js:230-236`） | ✘ | 原样复用（用不到不算缺口） |
| `allItems` / `anyItem` | ✔ **事件源的主力**：`{"path":"result.events","anyItem":{"path":"kind","equals":"window"}}` | ✘ | ✘ | 原样复用 |
| `greaterThan` / `greaterThanOrEqual` / `lessThan` / `lessThanOrEqual` | ✔ **按 kind 计数**：`{"path":"result.counts.colony_started","greaterThanOrEqual":1}` | ✔（`{"path":"result.port.port","greaterThan":0}`） | ✘ | 原样复用 |
| **`contains`（新增）** | 必须 | 不需要 | 不需要 | **新增 1 个** |

**为什么只加 `contains`、不加别的**：

- `contains` 不是「想要」，是「必须有」：`live --until` 的 `~` 是子串（`live.js:19`、`:101`），现有 12 个叶子算子没有子串语义；不加它，`live` 只能保留自己那份 `matches`，于是"两套判定"原地复活。【代码】
- **不加** `withinMs`/`countInWindow`：窗口用探针参数 `windowMs` + `anyItem` 表达，语义完全等价，且不会让条件 JSON 膨胀成查询语言。【推断】
- **不加** `matchesRegex`：`~` 从来不是正则（`live.js:16-19` 明说"够用就行、不上表达式引擎"、"包含子串"），加正则只是多一类"写错了要等一万年"的条件面。【代码】
- `contains` 的严格定义：`{"path":"result.text.text","contains":"GABP server connected to GABS"}`，要求采样值是**字符串**且 `includes`；值必须是字符串；采样值不是字符串 ⇒ 抛（与 `countEquals` 的严格一致，`wait.js:230-236`）。这样"条件写错"仍能立刻 exit 1。【推断】

### 2.4 算子边界：算子只做单值判定，聚合一律进采样层（2026-10-24 用户定）

**原则**：条件是一棵「`path` + 一个算子」的树，组合靠 `all/any/not` 与 `allItems/anyItem`。
`all/any/not` + 两个量词已经能表达任意布尔组合（含否定与全称/存在），所以"更复杂的测试"应当是
**树更深**，而不是**算子更多**。

落点判据（照此判断，不要临场发明）：

| 想要表达 | 落点 | 理由 |
| --- | --- | --- |
| 子串 / 全等 / 枚举成员 / 数值比较 / 集合每一元素 | **算子** | 「一个值 vs 一个期望值」的单值语义 |
| 时间窗口（最近 N ms） | 采样参数 `windowMs` | 是「取多少数据」，不是「怎么比」 |
| 计数（某 kind 出现 3 次） | 采样层吐 `result.counts.<kind>`，判定用 `greaterThanOrEqual` | 聚合在采样层，判定层只比单值 |
| 派生量（tick 差、耗时） | 采样层吐 `result.ticksSince` 之类 | 同上 |
| 正则 | **暂不加**；`contains` 覆盖前不引入 | 与 `~` 的老口径一致（`live.js:16-19` 明确不上表达式引擎） |

**已知不完备（必须知道）**：`countEquals` 只能「等于」，没有「至少/至多」。要表达"至少 3 个"，
要么走「采样层给 `counts` + 数值比较」（推荐，保住原子性），要么补 `countGreaterThanOrEqual` 这类原子。
这是当前算子集**唯一**的语义缺口，不要靠现场加算子绕。

**新增算子的代价与硬约束**：求值器一个 `case` + 文档一行 + 离线矩阵几例，成本低；
但游戏侧 `rb.poll` 只有 15 个算子，新增的（`not`、`contains` 已是先例）**不能原样下发**，
含它们的条件只能在 Node 侧求值。⇒ 算子位要**少而正交**，宁可让采样层多干活。

这条边界正是 §6 Q1 切分的依据：`src/condition.js` = 原子判定；`src/wait-sources.js` = 取样与聚合。

### 4.3 引用方式、报错、与 `--args-file` 共存、扩展成本

**引用**：`node src/cli.js wait --profile voiced --scenario game.playable [--timeout 90000]`
`--scenario` 一次性填好 `source`/`probe`/`args`/`condition`；`--profile`/`--timeout`/`--interval` 仍然独立生效。

**名字不存在**（exit 1，`main().catch` 统一置 1）：

```

  登记表：src/conditions.json
```

近似名用 `editDistance`（`src/toolname.js`，已被 `wait.js:16` 用来给字段名提近似），阈值与 `wait.js:305-311` 同一量级 ⇒ 与「工具名不存在」（`cli.js:363` 的 `assertToolNameExists`）风格一致。【推断】

**`--list`**：打印一张 `名字 | source | 说明 | verified | 出处` 的表，exit 0。这是让子代理**自己发现**可用场景的入口（否则它还是靠猜字段名）。

**`--args-file` 与登记表共存**（三条规则，按优先级）：

1. 登记表给的是**默认值**；命令行显式给的字段**整份覆盖**同名默认值。
2. **不合并**两边的 `args`：`--args-file f.json` 给什么就是什么，登记表里的 `args` 整份作废。合并会造出「没人写过、也没人验过」的参数组合，正是登记表要消灭的东西。【推断】
3. `--source` / `--probe` 与登记表**冲突即报错**（不允许覆盖）：这两个是场景的**身份**；允许改 probe 就等于允许"拿别人的条件打自己的探针"。【推断】待拍板见 §6 Q4。
4. 每次覆盖都在证据 JSON 里留痕：`{"scenario":"game.playable","overridden":["condition"]}`，stderr 打一行 `[wait] 场景 game.playable：--condition 覆盖了登记表里的条件`。无覆盖时**不出现**这两个字段 ⇒ 老用例 A–I 的输出格式不变。

**以后加一个场景是不是「只加一条数据」**：

- **是**，如果 (a) `source` 已是四类之一，(b) 条件能用现有 13 叶子算子（含 `contains`）+ `all/any/not` 写出，(c) 探针是现成的只读工具。⇒ 只改 `src/conditions.json` 一个文件，零代码。【推断】
- **否**，两种情况要动代码：新 `source`（第四类之外）、新算子（例如以后真要正则）。这两条是**登记的边界**，写进 `description` 之外还应写进本文件的 `note`。【推断】

- (b) 全允许覆盖：灵活，但"拿别人的条件打自己的探针"这种组合会重新变成"字段名靠猜"的来源。
- (c) 一覆盖就报错：最严格，但调参（只想把 timeout 加大）都要改数据文件。

**Q5 `verified` 字段怎么用？**
- (a)【推荐】必填布尔；`verified:false` 的场景**允许** `--scenario` 用，但 stderr 必打 `[wait] 场景 X 未经真机验证：<evidence>`，且 `--list` 用 `未验证` 标出。理由：仓库口径要求区分实测/推断，登记表不标就会变成"看起来像真的"的字段路径批发商。
- (b) `verified:false` 直接拒绝 `--scenario`（只能 `--list` 看见）：最安全，但新场景一律要等一次真机验证才能用，落地慢。
- (c) 不做这个字段：省事，但登记表会与实测文档脱钩。
