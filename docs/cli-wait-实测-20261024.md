# `cli wait` 真机实测（2026-10-24）

> 口径：**实测** = 本次在真实 RimWorld 1.7.4985 rev1269 + RimBridgeServer 2.1.1 上跑出来的；
> **推断** = 没跑过。原始输出留在 `runs\闭环改造-验证-20261024\`（每个用例一个 `.out`）。
> 命令语法与算子表见 [cli-wait-用法-20261024.md](cli-wait-用法-20261024.md)。

## 环境

- profile `voiced`（轻档），窗口化 1600×900、副屏；桥接端口 5174；在线工具 **184** 个。
- 游戏进程由 `node src/cli.js start --profile voiced` 拉起；**桥接就绪 7.6 s**（自动探测，来源=env，即启动时预定的端口）。

**等待开销（实测，`Measure-Command` 墙钟，含 node 启动）**：同样一次 `get_ui_state`，
`cli call` = **71 ms**，`cli wait`（一次就命中）= **69 ms** ⇒ 命中路径**不额外付一个轮询间隔**，
开销差异落在噪声里。

**Agent 上下文体积（实测）**：`get_bridge_status` 完整载荷 8 KB 量级；`wait` 打印层截断到 2000 字符 +
`sampleTruncated:true`，并在 stderr 给出「要看完整载荷用 `cli call`」。

## 顺带确认的机制

- **`result.` 根**：`callTool` 原样返回载荷（`get_bridge_status` 根上就有 `state`，`list_colonists` 根上就有
  `colonists`/`count`），与 `rb.poll` 的 `result.` 同一含义 —— 4 个探针都验到了。
- **字段不存在 ≠ 条件不成立** 的区分是对的：C 与 I 都落到「路径一直没取到」的专门提示上，
  而不是让调用方猜「是不是我条件写错了」；D 那种真·写错仍在 1 秒内 exit 1。
- **预算**：`--timeout 1500` 实测 elapsedMs 1497；没有出现「超时后还发一次探针」的过冲。

## 未验证

- **改造前后的墙钟对比没有基线**（HANDOFF §5 的目标 1）：本次只测了单条 `wait` 的开销，
  没有跑「start → 进图 → 600 tick → 截图」的端到端前后对比。
- `--source event` / `--source process`（P1，故意未实现）。
- 长时间等待（分钟级）、桥接中途挂掉（`GABP_TIMEOUT`）在真机上没有被刻意制造过。
- 主菜单（H）只测了「命中」，没测「在 entry 态等 `playable` 会不会把 60 s 耗满」——
  按 A 的语义它应该一直轮询到进图，但这条链需要有人真的点进游戏才会走完。
- UI `windowCount` 归零的例子没写进 skill（载荷根字段没在本轮确证）。
