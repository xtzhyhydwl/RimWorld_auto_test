用户澄清（2026-10-03）：地板策略 + 工具优先级

## 1. 地板：默认不铺，将来按资源与心情决定

用户原话：
> 「地板它其实是可有可无的东西……一般来说，如果资源紧缺，就不造地板了。
>  等有额外资源的时候再去造地板。或者说有些时候小人他觉得周围的环境不够好看，
>  你也可以去就是在**卧室里面**造上地板。但这个其实是和**心情管理**那边比较有关系的。
>  我觉得前期最前期最简单的情况，**默认什么地板都不要造**，反而其实挺简单的。」

### 现阶段的结论：**地板不进样板、不进默认建造**

| 问题 | 答案 |
| --- | --- |
| 扫描器会把地板扫出去吗？ | **不会。** 扫描只认 `ThingCategory.Building` 的"格上的东西"；**地板是 `TerrainDef`**（改的是地表），所以天然不会被扫成槽位 |
| 将来能支持吗？ | **能。** `docs/s4-地板取证.md` 已实测证明地板**有蓝图形态**（`TerrainDef.blueprintDef = Blueprint_WoodPlankFloor`），两条放置路径都可行 |
| 现在的默认 | **不铺地板**（`BuildFloor = false` 已经是默认） |

### 地板的策略（记录，将来实现）

```
资源紧缺        → 不铺
有富余资源      → 铺
心情需要提升时  → 在**卧室**铺（和心情管理挂钩）
```

→ 这说明地板的触发条件**不是"能不能铺"，而是"值不值得铺"**，
   所以它应该是一个**独立的决策**（属于心情/舒适度域），而不是"住处域默认要做的事"。
   这个划分现在就先记下来，避免以后把地板硬塞进住处域。

## 2. 工具优先级：先要一个"能用的"，持久动作以后再说

用户原话：
> 「现阶段只要有**一个可用的工具**就可以了。至于是你说的 A 还是 B 的话，
>  如果 A 好用，那就 A 吧，就先有一个能用的工具，能把模板摘出来就行。
>  后续要固定成持久的、固定成一个实际的动作的话，这个甚至可以再做成**另外一个 mod**，
>  这个其实不是主要内容。」

→ **采纳**。不再往"自定义 designator 进建筑师菜单"（方案 B）投入时间。
   现有能力（`capture_grid` + `template-capture.mjs`）就是交付物：
   **给坐标 → 扫出来 → 存成可读 JSON**。

   这条路已经自测通过（`runs/template-capture-selftest/report.md`，10/10）：
   造一个已知的 13×13 四门方盒 → 扫出 44 墙 + 4 门、自动裁边、门位精确在中点。
