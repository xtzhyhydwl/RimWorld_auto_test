# S4 住处域：地板路径的取证（IL 推断 vs 实测）

> 这一页专门记录一个**方法论案例**：**IL 反汇编读出来的结论被实测数据推翻了。**
> 2026-10-03。

## 起因

S4 要盖"方块房"，用户在需求里说：

> 屋顶是自动铺的，主要就是要安排人去从事建筑的工作。
> ……合理的拓展墙壁，合理的拓展地板之类的。

所以地板要不要做、走哪条路，需要先搞清楚。

## 子代理的第一版结论（❌ 错的）

它用 `IlDump` 读了 `Designator_Build.DesignateSingleCell` 的 IL，得出结论：

> `Designator_Build(TerrainDef).DesignateSingleCell` 走的是 `TerrainGrid::SetTerrain`：
> 地形**立刻**变化、**蓝图增量为 0、框架增量为 0** ⇒
> **地板在游戏里没有"蓝图形态"**，是"直接改地形"。
> 因此 mod 默认**不铺地板**（`BuildFloor = false`）。

并把报告里的断言写成：

```
| ❌ | ★★ 地板没有蓝图形态（terrain.blueprintDef == null） | blueprintDef=Blueprint_WoodPlankFloor ... |
| ❌ | ★★ 地板是"直接改地形"：地形面积变了但蓝图增量为 0 | 地形 0 → 0，蓝图Δ=3，框架Δ=0 |
```

## 实测反证（✅ 地板有蓝图，而且做法很正规）

`foodprobe/floor_path` 的返回里**已经写着答案**，只是断言预期写反了：

```json
{
  "terrain_blueprintDef": "Blueprint_WoodPlankFloor",
  "terrain_frameDef": "Frame_WoodPlankFloor",
  "hasBlueprintForm": true,
  "blueprintDelta": 4,
  "frameDelta": 0,
  "terrainAreaBefore": 0,
  "terrainAreaAfter": 0,
  "verdict": "意外：居然产生了蓝图（请把这个结果记进文档）"
}
```

`foodprobe/list_buildings` 进一步确认地图上**真的有 5 个 `Blueprint_WoodPlankFloor`**：

```json
{
  "blueprintBuild_total": 5,
  "byBuildDef": { "WoodPlankFloor": 5 },
  "blueprintSamples": [
    { "x":126, "z":126, "blueprintDef":"Blueprint_WoodPlankFloor",
      "buildsDef":"WoodPlankFloor", "isDoorBlueprint":false }
  ]
}
```

**三条结论**（都有实读数支撑）：

1. `TerrainDef.blueprintDef` = `Blueprint_WoodPlankFloor`，**不是 null** ⇒ 地板**有蓝图形态**
2. `Designator_Build(TerrainDef).DesignateSingleCell` **产生蓝图**（`blueprintDelta=4`）
3. **地形没有立刻改变**（`terrainAreaBefore == terrainAreaAfter == 0`）

⚠ 注意第 2、3 条与第一版结论**正好相反** —— 而且工具自己都标了 `verdict: 意外`。

## 教训（比这个 bug 本身更重要）

> **IL 能告诉你"代码里写了什么"，但不能替代"跑起来会发生什么"。**

可能的原因（不需要查清，但要知道存在）：IL 里有多条分支、方法被 Harmony patch 过、
读 IL 时跟错了调用路径、或者 `Designator` 的状态（比如 `Find.DesignatorManager` 里选中的那个）
影响了实际走哪条路。

**这个项目已经因为"凭推断下结论"踩过好几次坑**，这次是第一次**由工具自己打脸工具**：
`floor_path` 的 verdict 字段写着"意外"，而报告却按原假设判失败。
→ **工具输出和预期不符时，第一反应应该是"我的预期错了"，而不是"把这条记成失败"。**

## 对实现的影响

- `BuildFloor` 应该**默认开启**（地板是蓝图，会正常走 Frame 与建造工作，不破坏游戏平衡）
- 地板用 `Designator_Build(TerrainDef)` 或（更正规的）`GenConstruct.PlaceBlueprintForBuild(TerrainDef, ...)`
  —— 后者待实测确认，若可行优先用它（与墙/门统一走一条路）
- ⚠ 保留一个"不要瞬间改地形"的守卫：如果哪天实测发现某条路真的会瞬间免费改地形，
  那它**不该用在生产路径**（会破坏游戏平衡），只作为取证手段

## 顺带记一个测试设计问题

调试开局**自带 662 面墙 + 28 扇门**，所以"已有住处就跳过"的守卫**正确地**拒绝了盖房 ——
域的逻辑没错，**是测试没法验到它**。

→ 需要给测试一个"强制盖一间"的钩子（`force` 模式），**且该模式不得在生产路径生效**。
这是"**功能正确但不可验证**"的典型情形，值得单独记一笔：
新功能上线时，如果它的正常工作条件在默认场景里不成立，就必须**主动造出能让它工作的场景**，
否则测试永远只能验到"它正确地什么都没做"。
