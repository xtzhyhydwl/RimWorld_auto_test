# S5 验收：3 个殖民者撑过 5 游戏天

> 这是整个阶段目标的**最终验收**。用户原话：
> 「等我们确实的就是测试发现这个殖民地能够撑过 5 天，并且是所有小人都有的吃，
> 然后心情也不崩溃的情况下，就可以再看看下一步。」
>
> 状态：**设计就绪，待 S4 完成后执行**（2026-10-03）

---

## 一、验收判据（必须先定，再执行）

「撑过 5 天」不能只看"游戏没崩"，必须逐条可判：

| # | 判据 | 怎么测 | 失败意味着 |
| --- | --- | --- | --- |
| 1 | **没人死** | 5 天前后殖民者名单一致（死亡会从 `list_colonists` 消失） | 硬失败 |
| 2 | **人人有饭吃** | 全程每人 `needs.food.CurLevel > 0.05`（不挨饿） | 硬失败 |
| 3 | **没有精神崩溃** | 全程没人进入精神崩溃（`MentalState` 非 null / 心情不触底） | 硬失败 |
| 4 | **殖民地粮食没断** | 全程 `foodcontrol-telemetry.jsonl` 里存量 > 0 | 硬失败 |
| 5 | **mod 真的在自主工作** | 遥测里出现多天的 `action.kind == PlantCrop`，且种植区面积真的增长 | 说明"活下来"不是 mod 的功劳 |
| 6 | **不振荡** | 种植区面积不出现"涨→砍→涨"的反复 | 设计文档验收 #5 |

> ⚠ **判据 5 是关键**：如果殖民者是靠开局自带的存粮活下来的，那这次验收
> **什么也没证明**。必须能指出"mod 在哪一天做了什么、结果粮食曲线怎么变的"。
> 这与项目一贯的纪律一致：**不要把"没出事"当成"功能正确"**。

## 二、ⓘ 一个容易被误读的点：debug 开局不是"从零开始"

实测：debug 开局自带
- **662 面墙 + 28 扇门**（所以"住处"域会正确地拒绝盖第二间）
- 一批食物（实测 51.3 nutrition ≈ 10.7 天口粮 / 3 人）
- **50 个被禁取物资**（S1 会在第一天解锁）

所以**默认场景很可能"什么都不做也能撑过 5 天"**（存粮够 10.7 天）。
→ 这样的验收**没有证明力**。

**必须造出一个"真的需要 mod 干活"的场景**，两个方向：

| 做法 | 说明 | 评价 |
| --- | --- | --- |
| **A. 削减初始食物** | 把存粮清到只剩 1~2 天（够撑到第一茬收获） | ✅ 推荐。逼 mod 必须种地，且不至于一开局就饿死 |
| **B. 延长观察期** | 跑 15 天以上，让初始存粮耗尽 | ⏳ 慢（15 天 ≈ 2 分钟），但更接近真实运营 |

**倾向 A**：它直接验证"mod 能不能在缺粮时把局面救回来"，
而这正是食物域存在的理由。B 可以作为补充（跑一次长程，看是否稳定）。

## 三、时间推进的现实约束

```
5 游戏天 = 300000 tick
play_for(Ultrafast) 实测约 7000 tick/s  ⇒ 约 43 秒
```

但**不能一次调到底**：

- `play_for` 会**提前返回**（实测一次只跑了 25 秒里的 8.9 秒就被外部暂停）
- 有 `forcePause` 窗口开着时会**静默跑 0 tick**（实测踩过，见 skill）
- 所以必须**分片 + 重试**，并**按 `advancedTicks` 累计计数，不信 `success`**

**采样策略**：每推进约 0.25 游戏日（15000 tick）采一次样，记录
`tick / 每人 food / 每人 mood / 殖民者数 / 粮食存量 / 种植区面积`。
5 天 ≈ 20 个采样点，够画曲线也够定位是哪一步出问题。

## 四、执行脚本要验的东西（`scripts/verify-s5-survival.mjs`）

```
① 前置：地图稳定（programState==Playing 且 ticksGame>0）+ 3 个殖民者
② 记录基线（殖民者名单 / 粮食 / 心情 / 种植区面积）
③ 【造场景】把存粮削到 1~2 天（可选开关，默认开 —— 否则验收没有证明力）
④ 循环推进 5 游戏天，分片 + 重试 + 采样
⑤ 逐条判据断言（上面那张表）
⑥ 交叉印证：遥测（mod 自述）vs 桥接回读（游戏真实状态）
⑦ 产出 runs/s5-survival/report.md + 采样明细
```

### 必须注意的实现细节（都是踩过的坑）

| 坑 | 对策 |
| --- | --- |
| `play_for` 静默跑 0 tick | 推进前查 `get_ui_state.windowsForcePause`，为 true 先关 Menu 标签页 |
| `play_for` 提前返回 | 按 `advancedTicks` 累计；`success` 不可信 |
| 地图突然没了 | readiness 必须查 `programState == 'Playing'` 且 `ticksGame > 0`，不能只看 `mapCount` |
| 从一次性命令启动游戏 | **绝对不行** —— 进程孤儿化 + 100% CPU 死循环。必须用长驻后台任务 |
| 断言"有决策日志" | ❌ 曾经因此漏掉"一天跑 900 次"的 bug。**要断言数量/趋势，不只断言有无** |

## 五、这次验收**不**覆盖什么（诚实边界）

- ❌ 不覆盖长期稳定（5 天≠长期；15 天以上另测）
- ❌ 不覆盖战斗、疾病、耀斑等事件（当前 mod 不管这些）
- ❌ 不覆盖"从零开始"（debug 开局自带墙/门/物资）
- ❌ 不覆盖多生物群系（只测当前这一张图）
- ❌ **不覆盖心情的主动干预**：心情是"吃住稳了自然不崩"，mod 不直接管娱乐/装饰

## 六、如果验收失败，正确的反应是什么

用户明确说过：

> **如果不行，结论应该是"前期需要靠采集/狩猎过渡"，而不是硬调参数掩盖。**

所以失败时**不要**去改 `MaxCellsPerDecision`、`ReserveDaysLow` 之类的参数来"调过"，
而应该：
1. 先分清是**哪一条判据**失败
2. 看遥测里 mod 那几天**决定了什么、执行成功了吗**
3. 如果是"地种下去了但来不及" → 这是**真实的游戏机制约束**（前期需要采集），
   应当如实报告，并把它变成下一步的需求
4. 如果是"mod 该做却没做" → 那是 bug，去修 bug
