# `tick/run_to` 归谁：引擎放自己 mod、通道怎么接（2026-10-25 讨论稿，未动游戏）

## 0 先纠正两件事（都是查过文件的）

1. **没有改别人的 mod。** `Mods\RimBridgeServer\**` 全树最后修改时间还是 **2026-09-27 12:39**（安装那天），
   我们今天只**新增**了 `RimWorld\BridgeTools\DSH.TickDriver\`（junction → 本仓库 `bridge\DSH.TickDriver`）。
   `BridgeTools` 是 RimBridgeServer 作者在 README 里写明的第三方扩展点，不是"改他的代码"。
2. **工坊更新碰不到它。** 本机 RimBridgeServer 是**手动装**在 `Mods\RimBridgeServer`（GitHub release，`PublishedFileId=3727949765`
   但工坊目录里**没有**这个 mod）。`BridgeTools` 在**游戏根目录**，不属于任何工坊包。工坊能覆盖的只有 Harmony（我们只是引用它）。

## 1 现在是谁在干什么（三层，别糊在一起）

```
Verse.TickManager.DoSingleTick          ← 游戏本体（只被 Harmony 挂前缀，不改文件）
      ↑
我们的引擎：刹车 + 状态机（tick/run_to 的全部逻辑）   ← 100% 我们自己的代码
      ↑
命令面：GABP 工具外壳（[Tool] 特性 + JSON 进 JSON 出） ← 借 RimBridgeServer.Sdk + 它的 BridgeTools 扫描
      ↑
cli call tick/run_to                    ← 我们自己的 CLI
```

**会"被工坊更新弄没"的只有第 3 层（外壳），不是第 2 层（引擎）。** 而且外壳坏了的修复成本是重编一次（1 分钟），
不是重新设计——因为引擎里没有一行 SDK 代码。

## 2 能不能搬进自己的 mod：能。三条落点，代价不同

### A 引擎进我们的 mod + 保留 BridgeTools 适配器（作者推荐布局，改动最小）

- 我们的 mod：`Mods\<我们的mod>\1.6\Assemblies\*.dll`，`[StaticConstructorOnStartup]` 里挂 Harmony、跑状态机。
- 伴生 DLL：`<RimWorld>\BridgeTools\<我们的mod>\*.BridgeTools.dll`，只做 `[Tool]` → 引擎的转发（~60 行）。
- README 原文就是这个布局：「deploy the mod into the active Mods folder and deploy its companion to that same install's
  sibling global BridgeTools root」。
- 依赖：仍然引用 `RimBridgeServer.Sdk`。SDK 大改 ⇒ 重编伴生；RimBridge 被停用 ⇒ 只剩外壳没了，引擎还在（但没人驱动）。

### B 引擎进我们的 mod + 自建文件通道（零第三方依赖）

- 命令：`<profile>\dsh-tick\command.json`（原子写：tmp + rename），mod 的 `GameComponentUpdate` 每帧看一眼；
- 状态：同一个目录 `status.json`（收尾写一次 + 每 250 ms 心跳）。
- CLI：新增或改 `advance` 的一个分支去写命令、读状态；不再需要 `cli call`。
- 代价：~150 行（读文件、解析、写文件、错误码）；延迟 1 帧（16 ms）——相对于几千 tick 的推进等于 0。
- 好处：**RimBridgeServer 在不在都能推时间**；这也是唯一"完全属于我们"的通道。

### C 引擎进我们的 mod + 自建 TCP（自己的端口/token）

- 完全独立、延迟最低，但要写 socket / 线程 / 协议 / 端口分配，成本最大，且和现有 `cli` 的桥接管理重复。
- 只有当 B 被证明不够用（比如要传大块二进制）才值得。

### 作者明确不建议的：companion 放进 `Mods\<mod>\1.6\BridgeTools\`

README 说这是「rare packaged-mod edge case」，本地配对开发别这么放。所以别指望"一个 mod 文件夹装完所有东西"。

## 3 建议（等用户拍板）

**引擎进自己的 mod（A 的第 2 层），通道做 A + B 双份。**
理由：真正该属于我们的是"刹车 + 状态机"，它和 RimBridge 无关；命令面用官方的伴生机制能立刻继续用 `cli call`，
再补一条文件通道当"永不断"的兜底。这样最坏情况（RimBridge 卸载/大改）只损失便利性，不损失能力。

## 4 必须先问用户的（结构问题，按 AGENTS 规则 3）

1. 引擎放**新 mod**（例如 `DSH_TickDriver`，`About/` + `Assemblies/`，加进 `base-mods.json` 的底座），
   还是并进现有的 `dsh.gamelink`（已有 `GameComponent`，天然有每帧入口）/ `dsh.autotest`（现在只有 Defs）？
   - 新 mod：边界干净、可单独开关；代价是多一个底座条目、每个 profile 要同步。
   - 并进 gamelink：少一个 mod；但"事件上报"和"驱动游戏"是两件事，混在一起违反"一个概念一个名字"。
2. 要不要同时做 B（文件通道）？只做 A 的话，能力仍然挂在 RimBridge 上。

## 5 未验证 / 风险

- **【未验证】** mod 程序集里挂 Harmony 与现在 companion 里挂，行为是否完全一致（理论上一样：同一 AppDomain、同一个 `TickManager`）。
  要真机验一次，必须重启实例 —— 用户已说明现在有别的进程在调环世界，**本轮不动游戏**。
- **【文档口径】** SDK 版本升级后伴生 DLL 可能加载失败；作者给了自检入口：`rimbridge/get_bridge_status` 的
  `companions.diagnostics[]`（我们在里面看到过 `Status=registered / ToolCount=4`）。
- 若引擎先进 mod、伴生后到，`tick/probe` 需要能区分"引擎在、通道没了"，所以引擎要自己写一份状态文件（哪怕最终选 A）——
  这是 A 和 B 的公共部分，先做它没有浪费。

## 6 追加讨论：事件驱动停点（2026-10-25 晚，用户提出）

需求：**让时间一直走，直到某件事发生就停**。这件事**不一定**触发原版的强制暂停（信件/模态窗），
所以不能靠"游戏自己停"；要在游戏内自己判。

### 6.1 结论：可行，但「每 tick 全查」不是最优解 —— 先按成本分层

| 档 | 判据类型 | 实现 | 每 tick 成本 | 精度 |
| --- | --- | --- | --- | --- |
| ① **钩子** | 信件入栈、杀死、加 hediff、加消息、alert 出现 | Harmony postfix 打在产生它的方法上，只置一个 `pending` 标志 | **0**（不查） | 源头级，不丢 |
| ② **O(1) 轮询** | tick 数、队伍人数、某个 pawn 的 `downed/dead/curJob`、某个计数器、当前档位 | 我们已有的 `DoSingleTick` 前缀里读几个字段 | 几纳秒 | 每 tick |
| ③ **O(地图) 扫描** | "地图上有没有某物"、"某房里的小人"、"所有 hediff 里找一种" | 只能轮询，但**必须限频**（`everyNTicks`，默认 15，可配 1） | 一次扫描 × (tick/s ÷ N) | 最多滞后 N tick，要写进返回值 |

- 11k tick/s 下：①不花；②≈10 万次/s 的字段读，可忽略；③如果每 tick 扫 4k 格 ≈ 4400 万次/s，**会把帧率吃光**。
  所以 ③ 一律限频，并在 `status` 里如实报 `polledEveryNTicks` 与 `maxLagTicks`。
- 用户说"测试环境负担大无所谓"成立，但没必要：把能做成 ① 的都做成 ①，剩下的 ③ 限频，精度损失只有 N tick，换来的是
  别把 180 tick/s 拖成 30 tick/s（那才是真正的代价 —— 时间变慢，不是变贵）。

### 6.2 语义（必须先定死，否则后面全是扯皮）

- **"钩子检测、边界刹车"**：条件在 tick N 内被检测到 ⇒ **不在 tick 中间抢停**（半截 tick 会留下没跑完的系统），
  而是让 tick N 跑完，在 tick N+1 的前缀上停。
  返回值记三个数：`detectedAtTick=N`（第一次为真）、`stoppedAtTick=N+1`、`overrunTicks`（相对"第一次为真"≤1）。
- 同一次运行可以给**多条**判据：**先命中者停**（`stopReason=<kind>:<which>`），并把命中的现场打包进返回值
  （信件的 defName/label、pawn 的字段快照、alert 的 label……），省掉"停下再补一次 call"。
- `toTick` 变成**可选**：`{toTick, stopWhen:[...]}` 谁先满足谁停；只给 `stopWhen` 就是"一直走到它发生"；
  必须同时给 `maxTicks` / `maxWallClockMs` 兜底（否则无人值守会跑到天荒地老）。

### 6.3 第一批判据（建议按这个顺序做，每条都是"测试真会用到"的）

1. `letter` / `letterDef:<defName>`（已有 `stopOnLetter`，扩成按 defName 过滤）
2. `pawnField:<pawnId 或 all>.{downed|dead|curJob|health|mentalState}`（O(1)，测"人倒了/在干某活"）
3. `alert:<labelKey>`（O(小)，测"出现了某条警报"）
4. `message:<text 包含>`（钩子，测 mod 自己的提示）
5. `thingCount:<defName> >= n`（③ 限频，测"物资/建筑到位"）
6. `speedForcedNormal`（游戏被事件钉回 1×，用来定位"为什么这一段变慢了"）

### 6.4 代价怎么证明（等游戏空出来再做）

同一个 `toTick`（比如 +20000 tick，Ultrafast）跑三遍：0 条判据 / 3 条 ② / 3 条 ③，比较 `ticksPerSecond` 与墙钟；
三遍的差值就是"停点判据的税"。`status` 里加 `checksRun`、`checksSkipped` 两个计数，别靠感觉。

### 6.5 还没定的两件事

1. 判据怎么表达：**固定 kind 的表**（`[{"kind":"pawnField","pawnId":"Thing_Human802","field":"downed","equals":true}]`，
   好验、好报错、好做既有字段校验）还是**表达式字符串**（`"pawn.downed == true"`，灵活但要自己写解析器、容易写错）。
   倾向：先固定 kind 表，等判据种类稳定了再考虑表达式。
2. ① 的钩子要打在哪几个方法上（`LetterStack.AddLetter`、`Pawn.Kill`、`HediffSet.AddHediff`、`Messages.Message`）——
   每个钩子都要真机确认方法名与签名（用 `tools\asmdump` 那套查），不能靠记忆。
