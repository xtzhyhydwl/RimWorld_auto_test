## 三、★ 怎么加一个新的快照类型（用户最在意的一点）

用户原话：
> 「我之后在实践的过程中，发现我们还需要**别的类型的快照**，要不然有些事情没法解释。
>  那么就要能够**快速地把那个东西加进去**，而不是要从头写一大坨代码，
>  然后可能**很多接口都变掉**，那就太糟糕了。」

**只做两件事**：

```csharp
// ① 在 SnapshotReaders.cs 末尾加一个类（照抄任何一个现有的）
public sealed class RoomBeautyReader : ISnapshotReader
{
    public string Id { get { return "roomBeauty"; } }
    public string DisplayName { get { return "房间美观"; } }
    public int Order { get { return 45; } }              // 插在哪
    public string ProvidedFields { get { return "extra[roomBeauty]"; } }

    public void Read(Map map, ColonySnapshot snap, SnapshotReadContext ctx)
    {
        foreach (Room r in map.regionGrid.AllRooms)
        {
            ctx.ItemsRead++;                              // ★ 一定要数，否则健康度量看不出问题
            // ...
        }
    }
}

// ② 在 RegisterBuiltIns() 里加一行
Register(new RoomBeautyReader());
```

**不用改**：`SnapshotBuilder` / `ColonySnapshot` 既有部分 / 其他 Reader / 任何接口。

- 新面要写**结构化**内容 → 往 `ColonySnapshot` **追加**一个字段（不动老的）
- 新面只要**零散**信息 → 塞 `snap.Extra["key"]`，**连 `ColonySnapshot` 都不用改**

⚠ **每个 Reader 必须 `ctx.ItemsRead++`** —— 否则健康度量会把它误报成"可疑 0 项"。

## 四、★ 可度量（用户提的"是否读取了足量"）

用户：
> 「因为现在我**无法知道我们现在是否读取了足量的快照**。」

三层：

**① `ReaderHealth`（每块一条）**：`reader` / `ran` / `items` / `error` / `warnings`
→ 区分「这一局真的没有存储组」（`items=0, error=null`）和「读法坏了」（`error!=null`）

**② `SamplingInfo`**：`intervalTicks` / `sincePrevTick` / `totalSnapshots` / `playedTicks` / `looksDropped`
（`sincePrevTick > intervalTicks * 1.5` 判为漏采）

**③ 健康摘要**（每 10 张写一条日志），含 **"可疑"** 栏：
**某块全程 `items=0` 且 `error=null` → 主动点名**。这是最难自己发现的情况。

日志样子：
```
[FoodControl][录制] #40 tick=246001 读取块 8/8 间隔 6000/6000 tick 可疑(0项)[storageGroups]
```

## 五、下一步（按优先级）

### 1. 分析端脚本（**还没写**）
读 JSONL → 出报告。至少要回答：
- **覆盖度**：每块的 `items` 分布；"可疑 0 项"的块是真没有还是读法失效
- **采样密度**：平均间隔 / 最长间隔 / 漏采次数 / 相对游戏时长够不够
- **对象变化点**：同一对象跨快照对比，标出**谁在什么时候变了**
  （⚠ 这不是"面向过程"：数据源仍是**对象**，时序只是同一对象的历史）
- **动机还原**：变化点 + 那一刻的基本面 → **"他为什么这么做"**
  例：「第12天把米饭目标20→40，因为第11天新生儿加入、人口3→4、日耗4.8→6.4、
       存量只够6天，低于他的10天舒适线」

### 2. 虚拟地图三层（用户明确要的，**还没做**）
用户原话：
> 「直接在地图上维护一个**虚拟的地图**。它**忽略一切环境因素**，或者
>  **只保留关键的环境因素** —— 比如水或沼泽地，就是'能在上面建造和不能建造'的那种地块。
>  先建一个没有多余信息的图，然后在上面**再重建玩家建造的图**，持续维护持续更新，
>  它就有一个**随着时间变化的图景**。」

```
第0层 可建造性（静态，只算一次）—— 能建/不能建，其余环境全丢
第1层 玩家建造物（随时间）—— 墙/门/家具/地板
第2层 功能分区（随时间）—— 种植区/储藏区/存储组
```

## 六、★ 硬约束 & 已经踩过的坑

### 立场约束（用户明确要求）
| 约束 | 说明 |
| --- | --- |
| **纯净** | 不要引入自动化逻辑；不要调 domain / coordinator |
| **只读** | Reader 与 Recorder **不得**修改地图上任何东西 |
| **静默** | 录制器失败**只记警告，绝不抛给游戏**（会毁掉用户的存档体验） |
| **按游戏 tick** | **不要**按真实时间采样（会随帧率漂移；游戏暂停时会拍一堆重复快照） |

### 技术坑（都实测过）
| 坑 | 说明 |
| --- | --- |
| **API 名字常常不是凭直觉的那个** | 编译期会被抓到，但要提前知道会有：`map.storageGroups`（**不是** `storageGroupManager`）、`g.GetStoreSettings()`（**不是** `g.Settings`）、`g.RenamableLabel`（**不是** `g.label`） |
| **`Bill.repeatMode` / `targetCount` 不在 `Bill` 基类上** | 用反射探测，拿不到不影响主功能 |
| **`start` 后台任务显示 completed 是正常的** | launcher 等到桥接就绪就退出，游戏继续跑。**别以为游戏没起来** |
| **游戏可能"端口在听但 HTTP 超时"** | 主线程卡住 → 重启实例 |
| **`start_debug_game_ready` 几乎总会先超时** | 但殖民地会建成功 → 容忍超时 + 自己轮询 |
| **`play_for` 会静默跑 0 tick** | 有 `forcePause` 窗口时（新殖民地的起名框 `Dialog_NamePlayerFactionAndSettlement`）→ 用 `foodprobe/close_force_pause` |
| **PowerShell 读中文会乱码** | 文件是好的；用 `read` 工具 |
| **PowerShell 里 `git commit -m "多行中文"` 会被引号拆坏** | 写进 `tmp/commit-msg.txt` 用 `git commit -F` |
| **别用 JS 正则改 C# 文件** | 引号会打架且容易替换到错位置 → 用 `edit` 工具 |
| **`snap.Seq` 忘了从 sampling 同步** | 会恒为 0 → `0 % 10 == 0` 永远成立 → "每 10 张报一次"变成"每张都报"。**已修**，但注意这类"默认值刚好让条件恒真"的 bug |
| **反射：元数据里"有这个成员" ≠ 默认绑定拿得到** | `RimWorld.ResearchManager.currentProj` 在 1.6 是 **private 字段**，公有侧**没有**"当前项目"的 getter（只有 `IsCurrentProject(proj)`）。所以 `GetProperty("currentProj")`（第一版）和 `GetField("currentProj")`（第二版，默认只找 public）**都恒返回 null** —— 同一个地方踩了两次。正解：先用公有 API（遍历 + `IsCurrentProject`），再退化到带 **`NonPublic`** 的反射；而且**必须在运行时打日志验证**（磁盘元数据会骗人，见 `[ColonyRecorder][诊断]` 那行日志） |
| **换局/读档会让 tick 倒退** | 新地图 tick 从 ~0 开始，而 `SnapshotBuilder` 的 `_lastTick`/`_seq` 是静态的 → `sincePrevTick` 会算成**负数**、序号接着上一局走。已加"tick 倒退 = 新的一局，清采样状态" |
| **静默 `catch {}` 会把"读不到"伪装成"没有"** | `designations` 一度是 `catch (Exception) { }`，标记读失败时看起来就像"这一局没有标记"。已改成记 `warnings`（本项目纪律：失败必须带原因） |
