## 四、★ 下一步（按优先级，含用户原话）

### 1. **实测"建造顺序 = 放置顺序"**（承重假设，**实验只跑了一半**）

用户：
> 「如果我没记错的话，**环世界小人执行这些命令的顺序，应该就是你放置蓝图的顺序**。
>  也就是说，如果你是先放的床后放的外墙，从逻辑上来说应该是先把外墙造好再去造床，
>  但是实际上就是**先造床，再再造外墙**的。」

- 我文档里**只记了"谁去做建造"**（`WorkGiver_ConstructDeliverResourcesToBlueprints` /
  `...ToFrames` / `...FinishFrames`），**从没确证排序规则**。**不能猜。**
- 工具已就绪：`foodprobe/place_blueprints`（按**给定顺序**放一组蓝图）、
  `foodprobe/frames_in_rect`（列出矩形内框架/蓝图/已建成，判断谁先被施工）
- 实验设计：`A(150,150)` 与 `B(155,150)` 各放一堵 → 看谁先出框架进度 →
  **然后换位置重测**（若结果跟着**放置顺序**走而非跟位置走，假设成立）
- ⚠ 上次跑只放下 1 个蓝图（`count:1`，第二个失败），没拿到数据

### 2. **修分类器**（语义错误，用户会因此拿到错样板）

`scripts/template-capture.mjs` 把 **`ChessTable`（国际象棋桌）** 归成了 `table`（餐桌），
**它其实是娱乐设施**。与它配对的 `Stool` + `HorseshoesPin` 合起来是一个**娱乐区**。

> 教训：语义分类**不能靠 Def 名字**（"ChessTable" 的字面名字骗了我）。
> 要查 `thingCategories` / `joyKind` 之类的**真实分类**。

### 3. **样板的语义层 + 数量策略**

用户：
> 「在这个 13×13 有内容的房间里，在我心目中也是**有建造顺序**的……
>  **有几个人造几个床**就可以了。」

- 语义层：结构 / **睡眠** / **进食** / **娱乐** / 照明 / 储物（娱乐是这次漏掉的）
- 数量策略：`fixed`（墙门）/ `perColonist`（**床**）/ `atLeastOne`（光源、娱乐）
  → 样板里的 8 张床是"**最多 8 个位置**"，3 个人只放 3 张，**其余留空**

### 4. **分段材料决策**（**推翻现在的"整栋一次评估"**）

用户：
> 「**不是**在造整个样板之前就决定，而是它可能有一个**分段的决策**。
>  先把外墙的命令下下去，也是用木头，然后发现木头不够了，
>  然后再把那个床的命令下下去，用的是铁。」

★ 现在 `MaterialPlanner` 是**整栋一次评估**，那是**又一次局部最优**：
```
需 320，木头 300，钢 900
整栋一次评估 → 钢够 → 全用钢 → ★ 木头 300 一点没用上
分段         → 外墙用木头（够）→ 剩 40 → 床用铁 → ★ 木头用掉了，钢用得少
```

### 5. **用户给的建造顺序**（**照抄，不要自己发明**）

```
1. 墙（先！）
2. 门 —— 用户说"造不造其实无所谓"（★ 注意：**门被降级了**）
3. 床
4. 桌子
5. 光源
6. 娱乐设施（最后）
```
★ 用户还说这间房「比单纯的 13×13 房间花的钱**多得多**」→ **成本按内容算，不是按面积**。

### 6. **开局清单 → `BootstrapStep`**
现在三步（允许物资 / 划两片储藏区 / 盖房）是**各域各自动手**的。
用户要的是**显式有序清单**：
> 「至少**开局一定要做的事情是可以完全被规定出来的**，那只要做到这些事情，基本上开局就稳了。」
见 `docs/开局流程-设计.md`。**可靠性排序：开局清单 > 样板库 > 域。**

### 7. **威胁响应域**（S5 证明这是唯一的致命缺口）
最低限度：敌意目标出现时**让小人躲进最近的封闭空间并关门**。
技术基础已有：住处域盖的房子就是封闭空间，账本知道它在哪。

### 8. **贴靠选址**（"扩建优先连着建造"的缺口）
用户：
> 「如果你要把两个房子连在一起，那么他们**中间的墙是可以复用的**……
>  能复用的话少一面墙，而且它其实**更像一个整体**。」

- **共享墙去重的 Core 逻辑已完成**（`TemplateRole.CanReuse` + `Plan` 的 `existingAt` 参数，23 条测试）
- ⚠ **但"贴靠选址"没做** → 现在 `FindBestSite` 只找空地，**两个房子根本不会挨着**，复用无从谈起

### ★ 三条贯穿全项目的设计原则（**都来自用户的纠正**）
1. **套公式 > 局部最优**（`docs/设计原则-套公式优于局部最优.md`）
   > 「你算法的最优，有些时候它只是**局部最优**……环世界**只要套公式能玩好 90% 的情况**。」
   - 判定法：如果一段选址逻辑需要**解释"为什么选这里"**（而不是"规矩就是这么定的"），它大概率就是"神秘算法"
2. **摆放规范**（`docs/摆放规范-设计.md`）—— 分区 + 规则；**"禁选"比"必选"更重要**
   - 已止血一处：**建筑不许盖到种植区上**（`TemplateBuildDomain.IsInAnyGrowingZone`）
3. **摘要必须带原因** —— 任何"没做成"的分支都要能说出**为什么**
   （这条已出现**四次**同类问题：去重 bug、坐标系 bug、`MaxCellsPerCluster`、探针反射读 null）

### 技术坑（都实测过）
| 坑 | 说明 |
| --- | --- |
| **`create_allowed_area` 会挂死桥接** | **不要调用** |
| **`spawn_thing` 生成 pawn 会崩** | 用 `execute_debug_action` |
| **`ZoneMaker.MakeZoneWithCells` 不注册** | 必须补 `RegisterZone`，否则是"僵尸区" |
| **`play_for` 会静默跑 0 tick** | 有 `forcePause` 窗口时（`Dialog_NamePlayerFactionAndSettlement`）→ `foodprobe/close_force_pause` |
| **`start_debug_game_ready` 几乎总会先超时** | 但殖民地会建成功 → 容忍超时 + 自己轮询 |
| **readiness 必须查 `programState=='Playing'` 且 `ticksGame>0`** | 只看 `mapCount>0` 不够 |
| **`start` 后台任务显示 completed 是正常的** | launcher 就绪后退出，游戏继续跑 |
| **`SpecialThingFilterDefOf.AllowCorpses` 不存在** | 只有 `AllowCorpsesUnnatural`/`AllowLargeCorpses`；`ThingCategoryDefOf` 没字段 → 按 defName 查 |
| **`TerrainAffordanceDefOf.GrowSoil` 不存在** | 判"能不能种"用**肥力** `map.fertilityGrid.FertilityAt` |
| **`yield return` 不能在带 catch 的 try 里** | CS1626 → 先收集再返回 |
| **`map.uniqueID` 每个新殖民地都是 0；世界种子也会复用** | 换图检测不可靠 → 测试用 `foodprobe/ledger_reset` |
| **API 名字常常不是凭直觉的那个** | `map.storageGroups` / `g.GetStoreSettings()` / `g.RenamableLabel` |
| **测试断言不能只断言"有没有发生"** | 要断言**数量/趋势**（曾漏掉"一天跑 900 次决策"） |
| **测"某功能"时会被它自己的守卫拦住** | debug 殖民地自带墙/蓝图 → 测建造用 force，测守卫用非 force |
| **PowerShell 读中文会乱码**；`git commit -m "多行中文"` 会被引号拆坏 | 用 `read` 工具；消息写 `tmp/commit-msg.txt` 再 `git commit -F` |

| **验收前必须验证"测试手段真的生效了"** | 曾因 `forbid_some` 打不到食物 → 验收"没有证明力"。现在用 `forbid_food` |

## 六、★ 最重要的方法论：验证要**独立回读**

本项目的验证哲学（**多次踩坑换来**）：

1. **不信 `success`** —— 桥接返回 `success: true` 不代表功能正确
   （曾遇到：`capture_grid` 报成功但把环境杂物当成家具槽）
2. **不信 mod 自述** —— mod 说"放下 48 格"不算数，
   必须用 `foodprobe/list_buildings` **独立数一遍蓝图**，两边对账
3. **断言数量/趋势，不是"有没有发生"**
4. **用已知答案验证工具** —— 造一个已知形状（13×13 四门方盒）看扫出来对不对，
   而不是"跑一遍看看有没有报错"
5. **回归测试必须验证"能抓住 bug"** —— 把修复还原，看测试是否**真的失败**
   （本项目已有 4 个这样的测试，每个都验证过）
