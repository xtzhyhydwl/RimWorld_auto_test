# 副官语音 v2 · 语音拼接设计

> 2026-10-17。用户指出：`施工图.md` 的模块表里有 `Utterance{片段序列}`，但**没有讲拼接**。
> 这是旧 mod"做得最费劲的一部分"。本文专门对齐。

## 1. 旧 mod 为什么费劲（复盘 §3.3 / §6 的推论）

一句话 = `Slot` 序列，每槽要么预录、要么**单独**发一次 HTTP，**串行等待**。四个后果：

| 症状 | 根因 |
|---|---|
| 一句话断断续续 | 片段之间只有 `clip.length + 0.05s` 硬接，没有句读停顿 |
| 名字每次都要等 | 缓存键是**整句原文**，换个名字整句重算 |
| 忽大忽小 | 预录 ogg 与 Edge TTS 的 WAV 响度不同，没做归一 |
| 慢 | 片段的 HTTP 请求串行发，一句话 3 个片段 = 3 个 RTT |

## 2. 核心分叉：整句合成 vs 片段拼接

| | A 整句 TTS | B 片段拼接 | **C 混合（推荐）** |
|---|---|---|---|
| 自然度 | 最好（一个韵律） | 有拼缝 | 接近 A |
| 首次延迟 | 一次 RTT | N 次 RTT（串行） | 一次并行 RTT |
| 稳态延迟 | 0（整句命中缓存） | 0（片段命中） | 0 |
| 缓存效率 | 低（100 人 × 20 事件 = 2000 条） | 高（100 条名字） | 高 |
| 代码量 | **最少** | 多 | 中 |

**关键洞察**：稳态延迟在 A 和 B 里都是 0，差别只在**缓存命中率**。
片段缓存的条目数少一个量级（名字 100 条 vs 整句 2000 条），但每次未命中都要多次 RTT。

## 3. 推荐的 C 方案：整句优先 + 片段兜底 + 整句回填

```text
Utterance = 一句完整文本 + 它的片段切分
  例：["侦测到袭击，", "机械族，", "从东边来。"]

合成顺序：
  1. 整句缓存命中？ → 直接播（零延迟，绝大多数情况）
  2. 未命中 → 并行请求各片段（不是串行！）
  3. 全部回来 → 按顺序排进 dspTime 游标，片段间插固定句读间隙
  4. **把整句也写回缓存** → 同一句第二次零延迟
  5. 顺便把每个片段也写进片段缓存 → 换名字时只缺那一个片段
```

这样：
- 第一次遇到「张三被机械族袭击」→ 并行 3 个片段，1 个 RTT 的墙钟时间
- 第二次同样的人和派系 → 整句命中，零延迟
- 「李四被机械族袭击」→ 只缺"李四"，其余两个片段已缓存，只发 1 个请求

## 4. 必须解决的四件事（旧 mod 没做）

1. **响度归一**：所有进入播放队列的 clip（预录 ogg + TTS wav）统一按峰值归一到 −3 dBFS。
   RimWorld 的 `AudioClip.GetData` 可以拿到 float[]，写一个 `LoudnessNormalizer` 在载入时跑一次并缓存结果。
   **这一条是听感差异最大的一条，不要省。**
2. **句读间隙**：片段之间固定 `gapMs`（默认 120ms，可在设置里调 0–500）。
   旧 mod 的 50ms 太短，听起来像连读；整句合成没有这个问题。
3. **并行合成**：一句话的所有片段同时发请求，`Task.WhenAll`，全部回来才入队。
   部分失败时：失败的片段替换为"省略"（跳过），而不是整句沉默；并在调试页记一条。
4. **预合成（warm-up）**：殖民者**加入殖民地**、派系**首次出现**、商人类型**首次出现**时，
   立刻在空闲时合成名字片段。这样真正播报时大概率已命中。

## 5. 与模块表的对应（补上缺的）

| 新模块 | 职责 |
|---|---|
| `Utterance.cs` | 一句完整文本 + 片段切分（`string FullText`, `List<string> Segments`） |
| `SegmentPlanner.cs` | 决定"哪一段是固定短语、哪一段是变量"，产出 `Utterance` |
| `SegmentSynthesizer.cs` | 并行请求 + 失败降级 + 回填缓存（整句与片段都回填） |
| `LoudnessNormalizer.cs` | 峰值归一（−3 dBFS），结果按 clip 缓存 |
| `WarmupScheduler.cs` | 空闲时预合成名字/派系名，节流（每秒最多 1 条） |

`SpeechQueue` / `VoicePlayer` 不变：它们只消费"排好序的 clip 列表 + 间隙"。

## 6. 数字与专有名词

- **数字**：不预录"三十五"。TTS 念数字是可靠的，且中文 TTS 会把 `35` 读成"三十五"。
  若某模型读成"三 五"，再退化到「数字转中文」的字符串预处理（一个纯函数，20 行）。
- **殖民者/动物名**：无限动态 → 必走 TTS。名字里可能有 `.` `-` 等字符（如 `鼠条.18`），
  送 TTS 前要清洗（旧 mod 缓存里就有这种名字）。
- **派系名**：有限（原版 19 个 + mod）→ 预合成一次，之后永久命中。
- **疾病名/袭击策略/抵达方式/规模**：纯枚举 → **预录最划算**（这是旧 mod 121 条资产的价值所在）。

## 8. 实测到的硬约束（2026-10-17，`runs/tts-probe/`）

1. **SiliconFlow 的 WAV 头长度字段是占位值**：实测 `data` size = `4294967040`（0xFFFFFFA0）、RIFF size = `a6ffffff`。
   `System.Media.SoundPlayer.Load()` 成功但 `PlaySync()` 立刻返回、**播不出声**；把两个字段改写成真实值后正常播 4.3 s。
   ⇒ **自写 WAV 解析器必须不信任 header 里的长度**：以实际数组长度为准，或按 `data` 起始 + 剩余长度重算。
   ⇒ **Unity 的 `AudioClip` 也可能被这个坑到**，探针第一件事就要验"Unity 能不能直接吃这个字节流"。
2. **域名**：`api.siliconflow.cn` 通，`api.siliconflow.com` 用国内 key 返回 401。默认填 `.cn`。
3. **首次请求延迟实测 0.61 s**（4.16 s 音频）。这决定了"拼缝"到底能不能被感知——0.61 s 是**整句**的代价。
4. **key 明文躺在游戏配置里**：`Config\Mod_3551203752_Settings.xml` 的 `<simpleApiKey>`（RimTalk 的设置）。
   ⇒ 我们自己的 mod 里，key 存盘方案照抄这点是**可接受的**（玩家自己负责），但 UI 必须给掩码 + 风险提示。
5. **本会话 PowerShell/curl 的 HTTPS 不可用**（Schannel 缺失），探测必须走 Python/Node。见 skill `环境陷阱.md` §七。
