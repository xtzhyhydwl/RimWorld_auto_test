## 结论（5 行）

1. **会抢，但抢的不是"进程"而是"日志/桥接"**：同一 profile 并发 `start` 只有「查记录 → 起进程」的检查-再动作（`launcher.js:479` 检查、`:575` 才 spawn），中间没有锁；更严重的是 1.7 全机共用 `Player.log`，**两个会话的 CLI 会解析到对方的桥接端口**（今天 18:53 实测：`status --profile voiced` 报到 `127.0.0.1:5175`，而 voiced 自己的端口是 5174，5175 是 rhah 的实例）。
2. **有没有"被对面杀掉"的实测证据：没有直接证据；只有"实例无声消失"的痕迹**。今天 18:49:14 一个 voiced 实例（NDJSON 心跳到 `tick 1251 / Playing`）再无任何事件，18:49:18 立刻起了新实例；那个新实例（PID 23352）**共享日志里一行都没写**、18:51:10 前消失。没有 WER 崩溃记录、没有 4689 审计事件，**无法判定是自杀、被 stop、还是被 --force**。
3. **`stop` 默认按"本 profile 记录里的 PID"匹配**（`launcher.js:725`，`taskkill /PID` 不带 `/F`，`:741`），**不是按进程名全杀**；`stop --force` / `--all` 才是**按映像名枚举全机 RimWorld 并 `/T /F` 强杀**（`:713-723`、`:752-757`）。
4. **立即规避：一个 profile 一个会话，且同一时刻只允许一个会话起游戏**（1.7 共享日志决定了"不同 profile 并发"也不安全）；`--force` 一律不用；等事件只用 per-profile 的 `runs/live/<profile>.ndjson`。
5. **要加锁**：至少两把 ——（a）`start` 前按 profile 的锁文件（`runs\locks\<profile>.lock`，`wx` 打开 + 写 PID + 死 PID 自动回收）；（b）1.7 下"全机只许一个实例"的显式开关（默认拒绝并发，`--allow-concurrent` 才放行）。

## A. 机制层面（实测，带行号）

### A1. 有没有锁文件 / pid 文件 / 端口占用检测？

| 机制 | 位置 | 说明 |
|---|---|---|
| 锁文件 | **无**。`grep -i "lock|mutex|flock" src\*.js` 在 `cli.js`/`launcher.js`/`proc.js`/`prefs.js` 里 0 命中 | 只有 `src\colonyrecorder\*.cs` 的 C# 内存 `lock`，与本问题无关 |
| "pid 文件" | 有，但它是**记录**不是锁：`runs\game-process.<profile>.json`（`launcher.js:121-123` `processRecordPath`，`:625` `fs.writeFileSync(recordPath, …)`） | 每次 `start` **覆盖写**，没有 O_EXCL、没有租约 |
| 读记录 | `launcher.js:399-405` `readProcessRecord`（`JSON.parse` 失败即 null） | 只是读文件 |
| 「已在跑」判定 | `launcher.js:479-485`：`const status = await gameStatus(profile); if (status.recordedAlive) throw …` | 只看**本 profile 记录里的 PID 是否存活**（`:299` `isAlive(record.pid)`） |
| 端口占用检测 | **有**，且只在启动时点测一次：`launcher.js:410-418` `isPortFree`（listen→close）、`:424-433` `pickFreePort` | 见 A4 |

**实测**：`src\` 下没有任何 lock/pid-file 机制，「一个 profile 一个实例」完全靠 `launcher.js:479-485` 这一次检查。

### A2. 两个进程同时 `start --profile rhah` 会发生什么？

代码顺序（`launcher.js:447-627`）：

1. `:479` `gameStatus(profile)` → 读记录 + 判 PID 存活；
2. `:480-485` 若 `recordedAlive` 为真则抛错（**这是唯一的守卫**）；
3. `:488-492` 机器上有**别的** RimWorld 进程只打 `[警告] …并行启动，互不影响存档`，**不拦**；
4. `:575-593` `spawnDetached(exe, args, …)` 起进程；
5. `:625` 写记录（覆盖）。

⇒ **推断（未实跑并发）**：两个 `start` 若在同一秒内到达第 1 步，**双方都会看到"记录里 PID 已死或没有记录"，于是各起一个实例**（典型 TOCTOU）。后果不是"第二个被拒"，而是：

- 后写记录的把前一个的 pid 覆盖掉 ⇒ **前一个实例变成"无人跟踪的野实例"**，`stop` 再也杀不到它；
- 两个实例共用**同一个 `-savedatafolder=profiles\rhah`**（`:554`）⇒ 同一个 `Saves\`、`Config\` 被两个游戏同时读写 → **存档/配置互相踩**（这是比"杀进程"更坏的一档）；
- 1.7 下两者还共用同一份 `Player.log`（见 A5），后启动者的日志会抹掉前者的。

若两次 `start` 相隔足够久（第一个已经写进记录且活着），第二个会被 `:480-485` 拒绝，报错文案是「profile「X」已有测试实例在运行（PID N …）先执行 `node src/cli.js stop --profile X`，或用 --profile 换一个 profile」。
**注意这句话的副作用**：它等于教调用方"先 stop 同一个 profile 再 start"——而 `stop` 杀的是记录里的 PID，**也就是对方会话正在用的那个实例**。这是"互相杀"最可能的现实路径（代码允许、文档没禁止），但今天没有实测抓到这次调用。

### A3. `stop --profile rhah` 怎么匹配？

`launcher.js:710-767` `stopGame({profile, force})`：

- **非 force（默认）**：`:725` `list = record?.pid ? [record.pid] : []` —— **只按本 profile 记录里的 PID**，不枚举、不看进程名；
  - `:739-742` 先 `taskkill.exe /PID <pid>`（**不带 `/F`** ⇒ 发 WM_CLOSE，正常退出）；
  - `:744-750` 轮询 20 s（`timeoutMs`）等它自己退；
  - `:752-757` 仍未退才 `killForce(pid)` + `taskkill /PID <pid> /T /F`。
- 记录不存在 ⇒ `:728-737` 直接返回 `alreadyStopped:true`，`cli.js:426` 打印「没有 <p> 的运行记录」，exit 0。
- **所以：不会误杀别的会话/玩家的实例**（前提是"一个 profile 只有一个实例"成立；A2 的竞态一旦发生，`stop` 只杀记录里那个，另一个泄漏）。

### A4. `--force` 的行为（破坏性出口）

`cli.js:426`：`stopGame({ profile, force: Boolean(flags.force || flags.all) })`

`launcher.js:713-723`：

```

const pids = new Set(enumeration.processes.map((p) => p.pid));    // RimWorld.exe / RimWorldWin64.exe
if (record?.pid && isAlive(record.pid)) pids.add(record.pid);

… console.warn('[stop --force] 破坏性操作：…（含你自己那一局）：PID …')
```

- 枚举口径：`proc.js:162-184` `tasklist /FI "IMAGENAME eq RimWorld.exe"`，失败退 `proc.js:213-241` `Get-Process -Name RimWorld`；映像名由 `launcher.js:56-61` `detectGameImage()` 决定（1.7 = `RimWorld.exe`）。
- 杀法：`:752-757` 全部 `killForce` + `taskkill /T /F` ⇒ **全机所有 RimWorld 一起死**，包括别的会话的实例、用户自己那一局。
- **profile 完全不参与匹配**，`--force` 只用来决定"要不要枚举全机"。这与 `AGENTS.md` 的硬约束一致（"只有用户明确要求才用"），代码层面没有任何二道闸（不认识 `--profile`、不比对 `-savedatafolder` 命令行）。

## C. 建议

### C1. 现在能防住两个会话抢同一个 profile 吗？

**不能。** 依据（全部实测于代码）：

1. 唯一的守卫是 `launcher.js:479-485` 的"读记录 + 判 PID 存活"，**检查与 spawn（`:575`）之间没有任何互斥**，记录也是普通覆盖写（`:625`）⇒ 并发 `start` 双方都能过。
2. 即使守卫生效，它给的出路是"先 `stop --profile X` 再 start"（`:481-484` 报错文案），而 `stop` 杀的正是记录里的 PID ⇒ **A 会话可以合法地杀掉 B 会话的实例**。
3. 1.7 共享日志让"不同 profile"也不安全：`status/call/wait/logs` 的桥接解析（`launcher.js:185-220` + `:226-249`）会取"最后启动的那条记录"⇒ 实测 `--profile voiced` 报到 rhah 的 5175。
4. 真正强杀全机只有一个入口（`--force`，`:713-723`/`:752-757`），**今天没被调用**（无证据），但它没有任何 profile 维度的限制。

### C2. 最小修复（按性价比排序）

| # | 改哪 | 怎么改 | 代价 |
|---|---|---|---|
| 1 | `launcher.js:479`（`startGame` 守卫处） | 加**按 profile 的锁文件**：`runs\locks\<profile>.lock`，`fs.openSync(path,'wx')` 拿不到就抛"另一个会话/进程正持有 profile X（PID n，起始时间）"；锁里写本进程 PID + 时间；进程死（`isAlive` 假）则视为陈旧锁、删掉重试 | ~30 行 + 一个 `locks\` 目录；要处理崩溃遗留（用 PID 判活已经够了）；**能彻底堵住 A2 的 TOCTOU** |
| 2 | `launcher.js:185-220`、`:226-249` | 1.7 下**不再用"最后启动的记录"代表整份日志**：`readBridgeInfo` 显式收 `profile`，`sinceOffset` 只取**该 profile 记录**的 `logStartOffset`；拿不到就返回 `null`（让 `withBridge` 报"该 profile 没有可用桥接信息，先 start"） | ~10 行，风险低。**修掉 A6 的串台**（当前最危险的一条：会把工具调用打到别人的实例上） |
| 3 | `launcher.js:447-460`（`startGame` 函数头）+ `cli.js:122-132` | 1.7（`layout.waylith`）且**枚举到任何非本记录存活的 RimWorld 进程**时**默认拒绝启动**，需显式 `--allow-concurrent` 才继续（现在只是 `:488-492` 打警告） | ~10 行 + 一个 flag。理由：共享日志下并发必然互相抹日志，收益是"要么串行、要么明确知道自己在并发" |
| 4 | `launcher.js:713-723`（`--force` 分支） | `--force` 加两道闸：(a) 必须 `--all` 或 `--force --yes` 二次确认；(b) 枚举改按**命令行匹配** `-savedatafolder=<profiles\<p>>`（`Win32_Process.CommandLine`，`proc.js` 加一个 `listRimWorldCommandLines()`），只杀匹配到本 profile 的 | ~40 行 + 多一次 WMI 查询（~200–800 ms）。收益：`--force` 从"全机核弹"变成"本 profile 兜底" |

> 不建议改的：`stop` 的默认路径（`launcher.js:725` 按记录 PID）现在已经是对的；`spawnDetached`（`proc.js:112-122`）不需要动。

### C3. 当下可立即执行的规避（不改代码）

1. **一个会话一个 profile**：`rhah` 给 0008 验证线，`voiced` 给闭环改造线；`vanilla`（561 项）**不要碰**；`bike` 留给共享单车线。
2. **但"不同 profile"并不足以并行**（1.7 共享日志）⇒ 加一条硬约定：**同一时刻只让一个会话起游戏**；另一个会话要起之前，先 `node src/cli.js status --profile <自己>` 看 `processList` 里有没有别人的 PID，有就等（用 `live` 挂 job 等事件，不要睡）。
3. 必须并行时的自检（30 秒内可做）：`status --profile <自己>` 的 **`bridge.port` 必须等于 `lastLaunch.bridge.port`**；不等就说明解析串台了，此时**不要**发 `call`/`wait`（会把场景摆到别人的局里）。
4. `--force` 一律禁用；要停只停自己那个 profile，且确认 `status` 的 `recordedPid` 是自己的。
5. 等状态优先用 **`runs\live\<profile>.ndjson`**（`live.js:50-58` 按 profile 分文件，**目前唯一真正按 profile 隔离的通道**）；`--source log` 与 `logs` 命令读的是共享日志，**并发时会看到别人的行**（`cli.js:392-398`）。
6. 并发期间**不要用 `logs` 判断自己实例的死活**，改用 `status` 的 `recordedAlive` + `runs\live\<profile>.ndjson` 心跳。
7. **别手工写/删 `runs\game-process.*.json`**：它不只是"记录"，还是桥接解析的输入（`findRecordByLogFile` 取 `startedAt` 最新的一条）——手写一条假的（如今天的 `dshwait-check`）会**当场改变所有会话连哪个端口**。要试 `wait` 的参数，用假的 **NDJSON 事件文件**（`--file`）或离线单测，别碰 process 记录。
