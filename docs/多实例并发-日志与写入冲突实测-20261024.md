# 多实例并发：日志与写盘冲突实测（2026-10-24）

> 环境：RimWorld **1.7.4985 rev1269**（.NET 10 + Waylith），`RimWorld.exe`，工程 `RimWorld_auto_test`。
> 标注约定：**[实测]** = 本次真跑命令/真读文件得到的输出；**[旁证]** = 别人实例在跑、我只读观测；**[推断]** = 由代码/现象推出、未跑验证。
> 全程：**未用 `Start-Sleep`**（等进程用 `Wait-Process`，等事件用 `live --until`，等游戏状态用 `wait --source bridge`）；**未用 `stop --force`**；未碰玩家存档（`%LocalLow%\…\Saves` 仍 190 个）。

---

## 结论（5 行）

1. **能共存**：两个不同 profile 的实例可同时跑（本机实测 PID 31000/voiced 与 PID 10660/rhah，各自窗口、各自桥接）。
2. **日志共用**：1.7 下两个实例写**同一份** `%LocalLow%\Ludeon Studios\RimWorld by Ludeon Studios\Logs\Player.log`（`-logFile` 被忽略，两实例命令行都指着它）。
3. **会互相覆盖（双向、且是字节级覆盖）**：后启动者把先启动者的日志截断；先启动者仍按旧偏移写 ⇒ 产生 **48,185 字节 NUL 空洞**；先启动者退出时又把后启动者的可见行**物理覆盖掉**（实测 `[VD]` 行 18 → 0）。
4. **端口独立**：5174/5175 各自 LISTENING，互不冲突；**但** `node src/cli.js --profile X` 的桥接解析会串台到"最后启动的那个 profile"（实测 `wait --profile voiced` 打到了 rhah）。
5. **共用写盘点**：只有共享日志（+ 它的 `Player-prev.log` 轮转）与 `runs\game-process.*.json` 的**读取解析**是全机共享的；`runs\live\<profile>.ndjson`、`profiles\<p>\{Saves,Screenshots,Config,ShaderCache,TextureCache}` 都按 profile 分开（实测）。

### B.5 只读状态查询"互不干扰"—— **不成立**

[实测] 两个实例都在跑时：

```

  recordedPid=31000  bridge.port=5175  source=env  reachable=True
  lastLaunch.pid=31000  lastLaunch.port=5174          ← 自己的端口是 5174

```

[实测] 更直接的证据（voiced 自己还在主菜单）：

```
node src/cli.js wait --profile voiced --source bridge \
  --probe rimbridge/get_bridge_status \
  --condition-file runs\tmp\multi-instance\ingame.json     # {"path":"result.state.hasCurrentGame","equals":true}
→ exit 0, attempts=1, elapsedMs=10, sample: programState="Playing", playable=true, hasCurrentGame=true

对照（直连 voiced 自己的 5174 + 它自己的 token）：
→ hasCurrentGame=false, inEntryScene=true, programState="Entry"
```

⇒ **`--profile voiced` 的查询实际打到了 rhah 的实例**。反方向已用直连验证：5174/5175 各用各的 token 都能独立握手（`RimBridgeServer 2.1.1.0`），所以**端口与桥接本身是隔离的，串台发生在 CLI 的解析层**（`launcher.js readBridgeInfo → findRecordByLogFile` 取"最后启动的那条记录"）。

| 19:12:31（我停完两个实例） | 357,086 B（pid 10660 头） | 不存在 |
| 19:13:40 | 9,463,237 B（pid 24528 头，19:13:06 起） | **357,086 B（mtime 19:12:24）= 我这次实验的最终日志，被干净轮转保存** |

⇒ 日志轮转规则（实测归纳）：**启动时若文件空闲 ⇒ `Player.log` → `Player-prev.log` + 新建 `Player.log`；若文件被另一个实例占用 ⇒ 先删掉旧的 `Player-prev.log`，然后或截断写入（19:09:25 这次）、或干脆一个字也写不进（18:56:50 那次）**。

## 能区分两个实例的标识是什么？

| 通道 | 能否区分 | 实测依据 |
|---|---|---|
| `Player.log` 启动头 | 只能区分**赢家** | `headers=1`；`Process: pid 31000/10660`、`Command: …-savedatafolder=…\profiles\<p>`、`Started:` 都只属于当时持有文件的那个 |
| `Player.log` 普通行 | **不能** | 行首只有时间戳；非 ASCII 路径段还是 mojibake（`E:\2026.7浠ュ悗鐨勬柊宸ョ▼\…`），`profiles\rhah` 这段 ASCII 能看清 |
| `Player.log` 桥接行 | 能（间接） | `GABP server … on port 5175` / `5174`，但**只保留最后一次**（本次最终文件里只剩 5175） |
| `runs\live\<profile>.ndjson` | **能**（靠文件名） | 事件 JSON 里**没有** profile/pid 字段（`"profile"` 命中 0），只有 `ts/seq/kind/tick/…` |
| 桥接响应 | **不能** | `rimbridge/get_bridge_status` 载荷里没有 pid/profile，只有 `programState/inEntryScene/…` |
| 端口 + token（记录文件） | 能 | 记录 `runs\game-process.<profile>.json` 里的 `bridge.port/token` 是唯一可靠的实例寻址方式 |

**结论**：**日志层面无法可靠区分两个实例**（同一时刻只有一份头，且内容会被覆盖）；**唯一可靠的区分手段是 ndjson 文件名 + 记录文件里的端口/token**。

## 对自动化测试的影响（哪些断言会因此不可靠）

1. **所有"读 `Player.log` 做断言"的路径在并发下不可靠**：`node src/cli.js live --source log`、`cli logs`、任何 grep `Player.log` 的检查——可能读到别人的行，也可能自己刚写的行被对方覆盖/被截断。
2. **`logStartOffset` 机制失效**：它是"启动那一刻的文件大小"，一旦文件被别的实例截断/改写，偏移与实际内容不对应（本次 `logStartOffset 280608` vs 实际文件 126,605）。
3. **主菜单等待（`live --source log --until 'text~GABP …'`）会串台**：共享日志里别的实例的桥接行也算命中。
4. **`--profile` 只是文件名，不是路由**：`status/call/wait/logs` 可能作用到别人的实例（实测 `wait --profile voiced` 返回 rhah 的 `Playing`）。任何"用 `--profile` 保证只动自己那一局"的断言都不可信。
5. **ndjson 通道是唯一可靠的**，但要注意：`seq` 每进程从 1 重来、同一 profile 多次启动追加进同一文件、8 MB 轮转到 `.1`。
6. **"今天跑了几次游戏"无法从日志统计**（每次启动只有最后一个头存活）。

## 建议

### 1. 要不要每实例独立日志目录？—— 要，但 1.7 下拿不到

- 事实：`-logFile` 被忽略，日志固定落在 `%LocalLow%\…\Logs\Player.log`（两个实例命令行都指它，实测内容只有一个实例）。
- 现实可行的三层替代：
  1. **串行化（首选）**：`start` 在 1.7 下若枚举到任何非本 profile 的存活 RimWorld，默认拒绝，需 `--allow-concurrent` 才放行（现在只打一行警告）。并发时的日志本来就没有可信度，收益极低。
  2. **每实例日志快照**：`start` 成功后立刻把 `Player.log` 复制到 `runs\<runId>\<profile>\Player.log`，`stop` 前再复制一次；并在记录里标注"本次是第几个启动者（是否发生截断）"。这只能保住"最后一次启动者"的完整日志 + 被覆盖前的快照，不能根治。
  3. **[推断，未验证]** 用独立的 Windows 用户/`USERPROFILE` 跑每个实例，让 `LocalLow` 分家——需要另开账户或沙箱，成本高，本次未测。

### 2. 要不要每次测试用独立 `runs\` 子目录？—— 要

- 现在 `runs\live\<profile>.ndjson` 是**跨 run 追加**的（本次 rhah.ndjson 已 6.27 MB，靠 8 MB 轮转分代），`voiced.ndjson` 也跨多次启动累积；`seq` 每进程从 1 重来 ⇒ 事后很难把一条事件归到某一次 run。
- 建议：每次 `start` 生成 `runId`，用 `DSH_LIVE_DIR=runs\<runId>\live`（`LiveChannel` 已支持 `DSH_LIVE_DIR` 环境变量，`src/live.js:50-58` 也按它找），并让记录、截图、报告都落 `runs\<runId>\`。

### 3. 必须修的一处（本次实测的直接根因）

- `readBridgeInfo()` / `findRecordByLogFile()` 必须**按 profile 取记录**，取不到就返回 null（让 `--profile X` 报"该 profile 没有桥接信息"），而不是"取全机最新一条"。否则并发时 `--profile` 等于随机选一个实例，且一条手写的假记录能改掉所有会话的端口（C.3 实测）。
