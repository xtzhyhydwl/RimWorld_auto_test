# 多实例并发安全 ①②③④ 修复记录（2026-10-24）

> 范围：①日志被重写、②解析串台、③同 profile 并发 start 锁、④假记录排除，
> 以及 ⑤ 在 `launcher.js` 的 5 处调用点（⑤ 的 `proc.js` 原语与 ⑥ `call` 超时见
> [docs/并发安全-进程身份原语与call超时-修复-20261024.md](并发安全-进程身份原语与call超时-修复-20261024.md)）。
> 标注：**【实测】**＝真跑过并贴输出；**【静态检查】**＝读代码核对；**【未验证】**＝没跑。

## 0. 结论一览

| 项 | 做法 | 状态 |
|---|---|---|
| ② 解析串台 | 有 profile 时**记录即权威**，不再去共用日志里刮；没有 profile 时才走 logFile 匹配，且候选要过数据校验 + 活 PID 优先 | 【实测】 |
| ② 权威校验 | 新增 `resolveBridge(profile)`：记录可信 / PID 命令行确实是本 profile / 端口一致 / token 一致，四道全过才允许连接 | 【实测】→ 但「活实例」上只验到前三道的失败分支 |
| ① 日志被重写 | 启动时写 `logAnchor`（大小 + 末尾 256B 的 sha1），读时对不上就**放弃日志解析**，不再「读整份」 | 【实测】 |
| ③ 并发 start 锁 | `runs\locks\<profile>.lock`，`openSync('wx')` 原子抢占，死 PID 自动回收，正常结束即释放 | 【实测】 |
| ④ 假记录 | `recordTrust()` 拒 `pid<=0` / 端口不在 5174-5183 / 哨兵 token；记录加 `schema/source/writer`；写入口只留 `startGame` 一处 | 【实测】 |
| ⑤ launcher 5 处 | `status`/`stop`/`--force` 收集/两处 `taskkill`/`stillAlive` 全部改成**身份校验**或三态探针 | 【实测】4 处 / 【未验证】真机杀进程 |

## 1. ② 解析串台：为什么以前会打到别人的局

旧逻辑（`launcher.js`）：

```js
export function readBridgeInfo(logFile, { sinceOffset } = {}) {
  const rec = readProcessRecord(profileFromLogPath(logFile)) ?? findRecordByLogFile(logFile);
  ...
  txt = buf.subarray(from >= buf.length ? 0 : from).toString('utf8');   // ← ① 和 ② 一起坏在这
```

两个洞：**(a)** 1.7 的共用日志路径里没有 profile 名，`profileFromLogPath` 反推出的是 `Logs`，于是永远掉进
`findRecordByLogFile` 这个「按 `startedAt` 取最新」的兜底；**(b)** 偏移比文件大时它回退成**读整份**，
而 1.7 每次启动都整份重写该文件 ⇒ 读到的是别人的行。

【实测】修前基线（当时 `voiced` 的桥接真在 5174，PID 31000）：

```
$ node src/cli.js call rimbridge/get_bridge_status --profile voiced
  → [错误] 无法连接 GABP 127.0.0.1:5175 —— connect ECONNREFUSED 127.0.0.1:5175
$ node src/cli.js status --profile voiced
  → gameRunning: true，但证据里是「桥接不可达 127.0.0.1:5175」
$ Get-NetTCPConnection -State Listen -LocalPort 5174 → OwningProcess 31000
```

5175 是 `runs\game-process.rhah.json`、`bike.json` 记的端口。此刻只是「连不上」；一旦那句 rhah 的桥起来，
同一条命令就会**打进 rhah 的那一局**，而返回看起来正常。

修后（同一台机器，游戏已被关掉）：

```
readBridgeInfo voiced  {"port":5174,"source":"record","how":"profile「voiced」的记录"}
readBridgeInfo vanilla {"port":5174,"source":"record","how":"profile「vanilla」的记录"}
readBridgeInfo rhah    {"port":5175,"source":"record","how":"profile「rhah」的记录"}
resolveBridge voiced   NO | PID 31000 不存在
resolveBridge vanilla  NO | PID 21492 不存在
$ node src/cli.js call rimbridge/get_bridge_status --profile voiced
  → [错误] 拒绝连接 profile「voiced」的桥接：PID 31000 不存在
     判据：
     - profile「voiced」的记录 通过基本校验
     - PID 31000 不存在
```

注意 `voiced` 与 `vanilla` 的记录**都写着 5174** —— 光看端口分不出谁是谁，这正是为什么必须有
`resolveBridge` 的 PID 身份校验（见 ⑤）。现在「端口属于我」这件事不再靠端口号猜。

`status` 的 `bridgeResolution` 字段把这套判据机器可读地吐出来（`ok/reason/evidence/port/recordedPort`），
`cli bridge` 与 `status` 用的是同一个 `resolveBridge`。

## 2. ① 日志被重写：用锚点判，而不是用偏移猜

启动时记录 `logAnchor = { size, sha1(末尾 256B) }`；读取时 `logAnchorHolds()` 判定，不成立就
`warnOnce` 一条「日志已不是本实例启动时那一份」并**跳过日志解析**，直接走记录。

【实测】（`$env:TEMP` 下的临时日志，非仓库文件）：

```
anchor append  -> true  (期望 true)     // 追加内容后锚点仍成立
anchor rewrite -> false (期望 false)    // 整份重写后锚点失效
anchor shrunk  -> false (期望 false)    // 文件变短同样失效
```

原方案「按实例快照到 `runs\<session>\Player-<startedAt>.log`」**没有采用**：快照只能保住启动那一刻之前的内容，
而桥接行是启动**之后**才写的，快照里根本不会有。1.6 的私有日志布局还保留原来的归档逻辑（`Player-<时间>.log`），
1.7 的共用日志绝不改名/移动（那可能是用户自己那一局的日志）。

## 3. ③ 同 profile 并发 start 锁

`runs\locks\<profile>.lock`，内容是 `{schema, profile, pid, startedAt, session, note}`。
锁只覆盖**启动临界区**（claim → 记录落盘），跑起来之后由记录 + PID 身份校验负责 ——
若把锁当长期锁，「谁持有」的答案是「一个已经退出的 `node` 进程」，第二个 start 会被永久挡住。

【实测】（`$env:TEMP` 脚本驱动，锁文件为 `selftest`，跑完已清）：

```
1 首次 claim: true | 文件存在: true
2 第二次 claim 被拒: EPROFILELOCKED | profile「selftest」正在被另一个进程启动：PID 24408（起始 …）
3 release: {"released":true} | 文件存在: false
4 陈旧锁(死 PID 999999) claim: true | 持有者 PID 现在是自己的: true
   [警告] 回收陈旧的启动锁 …（持有者 PID 999999，状态 none，起始 1970-01-01T00:00:00.000Z）
5 release: true | 文件存在: false
6 再 release: {"released":false,"reason":"没有锁文件"}
```

`startGame` 里所有失败退出（记录了存活实例、spawn 抛错）都会 `releaseProfileLock`，
不会把下一次 start 挡在自己的锁上。

## 4. ④ 假记录排除

`recordTrust(rec)` 三条拒绝理由全部来自实测事故：

```
trust voiced    {"ok":true}
trust vanilla   {"ok":true}
trust rhah      {"ok":true}
trust bike      {"ok":true}
trust fake      {"ok":false,"reason":"假记录 的 pid=0 不是正整数"}
trust sentinel  {"ok":false,"reason":"哨兵token 的桥接 token 是哨兵值（看似离线测试留下的）"}
```

- 端口不在 `5174..5183` 同样被拒（`5288` 那条假记录就是撞在这里）。
- 逃生口 `RIMBRIDGE_ALLOW_FAKE_RECORD=1`：放行但**每次启动只告警一次**，默认必须拒绝。
- 记录新增 `schema:2 / source:'launcher.startGame' / writer:'src/launcher.js'`；读侧兼容无 `schema` 的旧记录。
- 写入口仍只有 `startGame` 里那一处 `fs.writeFileSync(recordPath, …)`（全仓库 `Select-String` 核对过）。

## 5. ⑤ 在 `launcher.js` 的 5 处调用点

| 位置 | 旧 | 新 |
|---|---|---|
| `gameStatus` 的 `recordedAlive` | `isAlive(record.pid)` | `verifyInstance(pid, {processesDir: profiles, expectedProfile})`，只有「确认是这个 profile 的实例」才算在跑 |
| `stopGame` 收 `--force` 的 PID | `isAlive(record.pid)` | 同上校验通过才收 |
| `stopGame` 的 `taskkill /PID` | 直接发 | **先校验**，不通过就写进 `skipped` 并跳过 |
| `stopGame` 的强杀 | 直接 `killForce` | 强杀前**再校验一次**（等待期间 PID 可能已被复用），不通过就放弃 |
| `stillAlive` / 等待退出 | `isAlive(pid)` | `probePid(pid).state !== 'none'`（「还有东西占着这个 PID」≠「我们的进程还活着」） |

`waitForBridge` 的内层判定也改了：`none` 报「已退出」，`foreign`（EPERM）单独报
「PID 已被别的进程占用，本实例已经不在了，但别去 stop 它」。

【实测】`status` 在记录 PID 已死时走早退分支，不付 PowerShell 代价：`status --profile voiced` 136 ms（含 node 启动）。

## 6. 需要调用方一起改的地方（已改完，记录在此）

`cli.js` 原来有 3 处直接 `readBridgeInfo(logPathFor(profile))`，现在改成 `resolveBridge(profile)`：

| 位置 | 改动 |
|---|---|
| `withBridge()` | 先 `resolveBridge`，不 ok 就**不发命令**并打印判据；`call`/`tools`/`wait`/`live`… 全部走它 |
| `status` | 用 `resolveBridge` 产出 `bridgeResolution`，并把判据逐条并进 `runningEvidence` |
| `bridge` | 同样走 `resolveBridge`，输出 `ok/reason/evidence` |

`smoke.js` 只 import 了 `readBridgeInfo` 但从没调用（`Select-String` 核对过），不受签名变化影响。

## 7. 结构性决定与代价

1. **记录优先于日志**：1.7 的端口/令牌是我们用环境变量发下去的，记录就是真相。代价：1.6 若出现「游戏自己换了端口
   但记录没更新」的情况，会先连记录里的端口失败一次 —— 用 `--profile` 明确传 profile 时才会这样，且报错清楚。
2. **`status` 每次多一次 `Get-CimInstance`（约 0.3 s）**，只在「记录的 PID 活着」时才付；PID 已死走早退（实测 136 ms）。
3. **锁是启动期锁**，不是实例期锁（理由见 §3）。代价：`start` 期间并发会被拒；启动完成后并发由记录挡住。
4. **`logAnchor` 增加一次读日志末尾 256B + sha1**（微秒级），换来「日志被重写」可判定。

## 8. 仍未验证

- **`startGame` 全链路没在真机跑**（本轮不允许起停游戏，另一个会话可能正用真游戏）。改动涉及
  spawn 的 try/catch、`logAnchor` 写入、锁的释放，**只有语法与静态检查**。
- **两个 start 真并发抢同一个 profile**：只单进程测了「第二次 claim 被拒」，没有两个真进程对撞。
- **`resolveBridge` 的四道校验在活实例上走通**：抓基线时游戏在跑，但那时 `resolveBridge` 还没写；
  写完时游戏已被关掉，只验到「PID 不存在 ⇒ 拒绝」这一支。
- **`stop --force` 的身份校验**：没真杀过进程（`--force` 是破坏性出口，本轮禁用）。
- 1.6 的私有日志布局（`profiles\<p>\Player.log`）没有回归测试，本机已经是 1.7。
