# 游戏层（C#）架构审计：框架可扩展性 / 接口明确性 / 重复代码

审计对象：

- `src/foodcontrol-game/`（20 个 `.cs`，全部读完）
- `bridge/DSH.FoodProbe/`（3 个 `.cs`）

**不在**审计范围：`src/foodcontrol-core/`（用户自己在审）、`tools/`、`scripts/`、`src/*.js`。

审计方式：**只读**。没有修改 `src/` 下任何文件、没有编译、没有启动游戏、没有调用桥接。
所有行号来自按 LF 逐行读取的原始行号（`ShelterDomain.cs` 实际 **1623 行**、`TemplateBuildDomain.cs` **789 行**；
用户提到的 1275 / 640 是 `Measure-Object -Line` 的口径，两者相差的是被该口径合并掉的行，本文统一用原始行号）。

证据分级：

- **【读码确认】** = 我在源码里读到的原文，可直接核对。
- **【全仓 grep 确认】** = 用全仓标识符搜索确认"只有定义、没有使用"或"共 N 处"。
- **【推测】** = 我的判断，未在游戏内验证。

## 一句话结论

**`INeedDomain` 这个接口本身是对的，坏在"主组件 + 探针"这一层没有走接口**：四个域里有三个
（`StockpileDomain` / `TemplateBuildDomain` / `ShelterDomain`）在 `FoodControlGameComponent` 上各自挂了
一串**具体类型的静态钩子**（10 个方法、3 个单例字段、4 处 `new`），所以**加一个域要改主组件、撤一个域也要改主组件**——
这恰好就是用户说的"加/撤功能要改整个代码流程"。
更糟的是 `FoodDomain.RunCycle`（`FoodDomain.cs:84-139`）和 `FoodControlGameComponent.RunCycle`
（`FoodControlGameComponent.cs:662-720`）是**同一段食物闭环的两份实现**，而手动测试钩子走的是
**组件里那一份**、日常调度走的是**域里那一份** —— 测试测的不是生产路径（项目自己的脚本
`scripts/verify-s2-domains.mjs:230-246` 已经断言了这一点）。

同时，`ShelterDomain` 不是"1275 行揉成一团"，它有清晰的分节注释，但**它把四个域共用的基础设施
（`PlacementReport` / `TryPlace` / `CountConstructionWorkers` / `CountBlueprintBuilds`）藏在自己类里**，
于是"样板建造域"反过来依赖"程序化兜底域"（`TemplateBuildDomain.cs:10,152,312,336`）。
裁掉 `ShelterDomain` 必须先把这四样东西搬出去 —— 这是"不易更改"的**唯一根因**，不是代码太长。

| 成员 | `FoodDomain` | `StockpileDomain` | `TemplateBuildDomain` | `ShelterDomain` |

| `Id` | `"food"` :29 | `"stockpile"` :53 | `"templatebuild"` :60 | `"shelter"` :180 |
| `Priority` | 10 :40 | 20 :64 | 25 :71 | 30 :191 |
| `IsSurvivalCritical` | `true` :45 | `false` :69 | `false` :76 | `true` :197 |
| `OnDayStart` | 委派 `ColonySetup.Tick` :57-61 | `return null` :74-77 | `return null` :81-84 | `return null` :202-205 |

**偏差 1：契约成员 `IsSurvivalCritical` 是死的。**
【全仓 grep 确认】`IsSurvivalCritical` 全仓共 **5 处命中**：接口声明 1 处 + 4 个实现，
**没有任何一处读取它**。


注释写的是"用于**将来**的保命线"——也就是说它是一个**为想象中需求预留的空接口位**，
四个域都老实实现了它，但代码里没人问过这个问题。这类成员会让接口看起来比实际能力强。

**偏差 2：`DomainCycleResult` 里塞了 5 个"食物域专用"字段，且全是只写不读。**
【读码确认】写点在 `FoodDomain.cs:113-117`；【全仓 grep 确认】**读点 0 处**。


一个"所有域共用"的结果类型，字段却是某个域的私有载荷 —— 加第五个域时，
新域作者会看到这 5 个字段然后犹豫"我要不要填"。接口明确性直接受损。

**偏差 3：`Enabled` / `CheckEveryDays` 不在接口上，每个域各写一份。**
【读码确认】三个域各写一遍同样的取模逻辑：


**这个不一致已经造成了一个实际故障点**：探针的"关掉所有自动调度"是按**类型名字符串列表**
去反射设 `Enabled` 的（见 A2），而 `FoodDomain` 没有这个字段：


（不报错、不失败）。探针自己的注释（"每个域都自带"）已经不成立了。

**偏差 4：`Enabled` 到底是"不调度"还是"不执行"？四个域三种语义。**

- `ShouldRunToday` 里查 `Enabled`：`StockpileDomain.cs:87`、`TemplateBuildDomain.cs:92`、`ShelterDomain.cs:215`

**偏差 5：四个域的 `RunCycle` 步骤编号方式完全不同。**
`FoodDomain` 用 `①②③④⑤⑥⑦`；`StockpileDomain` 用 `①②③④⑤⑥` 然后**在 ⑥ 里面重新用 ①②**（`:202`、`:209`）；

`ShelterDomain` 用 `①②③③b④⑤⑥⑦`。同一个框架下四套编号法。
