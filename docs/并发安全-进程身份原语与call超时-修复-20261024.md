## ⑤ 进程身份：从「PID 活着」改成「这个 PID 是我的实例」

### 为什么原来会错【代码 + 实测】

`src\proc.js` 旧版：

```js
export function isAlive(pid) {
  try { process.kill(pid, 0); return true; }
  catch (err) { return err.code === 'EPERM'; }   // 「存在但没权限，仍算活着」
}
```

在 Windows 上 `EPERM` 的真实含义是「**这个 PID 被别的、我们拿不到权限的进程占着**」，与「我们的游戏还活着」是两件事。
记录里的 pid 一旦被复用（受保护进程），`isAlive` 恒真 ⇒ `start` 永远报「该 profile 已有实例在运行」。

【实测】本机 PID 4（System）复现了这个态：

```
probePid(4)      → {"state":"foreign","code":"EPERM"}
probePid(31000)  → {"state":"alive"}        // 真正的 RimWorld
probePid(999999) → {"state":"none","code":"ESRCH"}
```

### 现在有什么

`src\proc.js` 新增（**只有这一份实现**，别的文件不许再自己判 PID）：

| 函数 | 机制 | 用途 |
| --- | --- | --- |
| `probePid(pid)` | `process.kill(pid,0)`，同步 ~0.01 ms | 三态：`alive` / `foreign`(EPERM) / `none` / `unknown` |
| `isAlive(pid)` | = `probePid().state === 'alive'` | **语义已变**：`foreign` 不再算活着 |
| `describeProcess(pid)` | `Get-CimInstance Win32_Process`，0.2~1 s | 拿映像名 + 完整命令行；不存在返回 `null` |
| `verifyInstance(pid, {processesDir, expectedProfile})` | 上面两者 + 命令行解析 | 判「这个 PID 现在是**我们某个 profile 的实例**吗」，返回 `{ok, reason, process, profile}` |

`verifyInstance` 的三条判据（缺一不可）：PID 存在 → 命令行里有 `-savedatafolder=…` → 该目录在给定的 `profiles\` 下（给了 `expectedProfile` 时再比 profile 名）。
**只比 `profiles\<profile>` 这一段**，不比整条路径 —— 实测记录里的 `profileDir` 会带乱码（`2026.7浠ュ悗鐨勬柊宸ョ▼`），整路径比较会假阴性。

### 实测（2026-10-24 19:5x，真机、只读）

```
verifyInstance(31000, {processesDir: <repo>\profiles})
  → {ok:true, profile:"voiced", reason:"PID 31000 是 profile「voiced」的实例（RimWorld.exe）"}
verifyInstance(31000, {expectedProfile:"vanilla"})
  → {ok:false, reason:"PID 31000 是 profile「voiced」的实例，不是「vanilla」"}
verifyInstance(4)
  → {ok:false, reason:"PID 4（System）命令行里没有 -savedatafolder，不是本工具的实例"}
```

即：**`vanilla` 那条陈旧记录（pid 21492 已死、port 撞 5174）再也不可能被认成 voide 的实例**。

## ⑥ `cli call` 默认超时 300 s → 60 s

`src\gabp.js` 现在导出唯一常量 `DEFAULT_REQUEST_TIMEOUT_MS = 60_000`（构造函数的默认值也用它）；
`src\cli.js` 的 `call` 分支不再自己写 300000，改成引用该常量，并把 `--timeout` 的合法性校验补上
（以前传 `--timeout 0` 会静默回落到默认值）。

【实测】改后全仓库只剩一个默认值：

```
Select-String src\*.js -Pattern '300000'               → 无匹配
Select-String src\*.js -Pattern 'DEFAULT_REQUEST_TIMEOUT_MS'
  → gabp.js:66（定义 60_000）、gabp.js:94（构造函数默认）、cli.js:17（import）、cli.js:319（call 使用）
Select-String src\*.js -Pattern '300_000'              → 只剩 smoke.js:156
```

`smoke.js:156` 的 `300_000` 是**单次长操作显式传的值**（不是默认值），保留是对的。

【实测】`node --check src\proc.js src\cli.js src\gabp.js` 全部通过。

【实测】但 `node --check` **抓不到作用域错**：第一版把 `callTimeoutMs` 写在了 `withBridge` 的回调里、
却在回调外的第三参数用，运行时报 `callTimeoutMs is not defined`。是下面这条真机命令抓到的：

```
node src/cli.js call rimbridge/get_bridge_status --profile voiced
  → [错误] callTimeoutMs is not defined        （修复前）
  → [错误] 无法连接 GABP 127.0.0.1:5175 …      （修复后，方向正确：真的走到连接了）
```

修法是把超时计算挪到 `withBridge(...)` 之前（连接与单次调用共用一个值，本来也必须先算）。
教训：`cli` 的改动至少要跑一次真命令，语法检查不算验证。

副作用（有意）：`call` 复用的连接也按 60 s 建 `requestTimeoutMs`；需要长时间的操作（开殖民地、`play_for`、跑 tick）
必须显式 `--timeout`。这与 `wait`/`live` 的默认值一致，不再有「一个命令等 1 分钟、另一个等 5 分钟」的语义分裂。

## 附：修前基线（真机实测，2026-10-24 约 20:1x）

这一份是**② 修之前**的现场证据，值得单独留：当时正有一个**别的会话的 `rhah` 实例在启动**
（PID 10660，命令行含 `-savedatafolder=…\profiles\rhah`），而 `voiced`（PID 31000）的桥接在 `5174`。

```
$ node src/cli.js call rimbridge/get_bridge_status --profile voiced
  → [错误] 无法连接 GABP 127.0.0.1:5175 —— connect ECONNREFUSED 127.0.0.1:5175
$ node src/cli.js status --profile voiced
  → gameRunning: true（PID 31000 存活，对的）
    但 runningEvidence 里是「桥接不可达 127.0.0.1:5175」
$ Get-NetTCPConnection -State Listen -LocalPort 5174  → OwningProcess 31000（voiced，真正在听的那个）
```

即：**同一个 profile 的桥接真实端口是 5174，而 `readBridgeInfo` 解析出 5175**
（那是 `runs\game-process.rhah.json` / `bike.json` 里记的端口，而 `voiced` 那条记录的 `logFile`
与它们同为 1.7 的共用日志路径，于是「按最新记录」挑到了别人的端口）。
此刻 `call --profile voiced` 只是**失败**（5175 没人听）；一旦那句 rhah 的桥接起来，同样的命令
就会**打进 rhah 的那一局**，而返回看起来「正常」。这就是 ② 要堵的病，且它正在发生。

顺带一条对 `AGENTS.md` 的补充证据：`status` 的「桥接可达性」这一支**同样受影响**（它也用 `readBridgeInfo`），
所以「用 `status` 判断我连的是谁」不仅是口径问题，是真的会给出错端口。
