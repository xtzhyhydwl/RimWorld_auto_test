# 建筑账本（Colony Building Registry）设计

> 用户 2026-10-03 提出：
> 「我们要维护一个**我们目前为止建造过的所有建筑的大致的样貌**，
>  就是你要有它的**全局数据**，就是**剥离开地图原有的元素**。
>  我们要能够在任何时候想知道的时候都能知道**我们到底造了些啥**。
>
>  当然假如说是因为不可抗力，比如说被火烧或者说被破坏，墙体的那些建筑我们没法跟踪。
>  但是至少我们可以知道我们造了一些什么。这个至少是第一步，我觉得是应该要做的一步。
>
>  那在这种情况下，我们要从一间 13×13 的房扩展扩建到两间的话，
>  那可以优先选择**连着建造**，一间挨着一间。这样**省材料以及更紧凑**。
>  那在这个过程中，我们就可以去查阅我们一直在维护的**建筑地图**，
>  就可以知道放在哪大概率是 OK 的。」

---

## 一、为什么需要它（三个理由，按重要性）

### 1. 它比"从地图推理"可靠 —— 因为我们放的时候就知道

现在的做法是**每次都从地图重新看一遍**：数蓝图、数墙、判断"是不是已经有住处了"。
这条路有很多噪音：

- **debug 开局自带 662 墙 + 28 门**（实测），和"我们造的"完全混在一起
- 地图上还有**小人自己造的**东西（玩家手动、或其他 mod）
- 地图原有的**废墟/遗迹**也是 Building

→ 而我们**自己放蓝图的那一刻**，是唯一能 100% 确定"这是我们造的"的时机。
   **在那里记一笔，比事后从地图猜准得多。**

### 2. 它是"贴靠选址"的前置条件（架构缺口 A）

上一轮发现：`FindBestSite` 只找空地，所以**两个房子永远不会挨着**，
共享墙复用也就无从谈起（见 `docs/样板拼接-共享墙设计.md`）。

**要"贴着已有建筑盖"，必须有"已有建筑在哪"这个数据。**
账本就是这个数据。没有它，贴靠选址只能靠扫描地图猜。

### 3. 它让"我们造了啥"变成可回答的问题

现在要回答"我们造了几间房、在哪"，只能数地图上的墙 —— 而那会被
地图原有元素污染。有了账本，这是个直接查询。

## 二、诚实的边界（用户自己说的，我完全同意）

> 「假如说是因为不可抗力，比如说被火烧或者说被破坏，墙体的那些建筑我们没法跟踪。
>  但是至少我们可以知道我们造了一些什么。」

**账本记录的是"我们曾经下了什么蓝图"，不是"现在地图上还剩什么"。**

这两种语义**必须分开**，而且**都要保留**：

| 数据 | 语义 | 会"过期"吗 |
| --- | --- | --- |
| **我们下过的蓝图** | 意图历史（append-only） | **不会** —— 这是历史事实 |
| **当前地图状态** | 现在还剩什么 | 会（被烧/被拆） |

所以账本**不去维护"当前状态"**（那等于又变成扫描地图），
而是维护**"我们的意图历史"**，并且在需要时用地图数据**校验**它。

→ 被烧掉的墙：账本里**仍然有那一笔**（我们知道造过），
   但校验时会发现"地图上没有" → 标记为 `Missing`（不见了），**不删除**。

## 三、设计

### 数据

```
BuildingRecord {
    string Id;              // 稳定标识
    string TemplateId;      // 用哪份样板盖的（空 = 手写几何）
    int    OriginX, OriginZ;// 左上角
    int    Rotation;        // 朝向
    bool   Mirrored;
    int    Day;             // 第几天盖的
    int    Tick;            // 更精确的时间
    List<CellRecord> Cells; // 逐格：地图坐标 + 角色 + Def
}

CellRecord { int X, Z; string Role; string DefName; }

BuildingRegistry {
    List<BuildingRecord> Records;
    // 查询
    IEnumerable<CellRecord> AllCells();
    bool IsOurs(int x, int z);                    // ★ 这一格是我们造的吗
    List<BuildingRecord> At(int x, int z);        // 这一格属于哪几栋
    List<BuildingRecord> Near(int x, int z, int radius);   // 附近有哪些（贴靠选址用）
    string Summary();                              // "我们造了 N 栋，共 M 格"
}
```

### 关键接口：`IsOurs(x, z)`

这是整个账本最有用的一个方法，两个场景都要它：

1. **贴靠选址**：找一个"边缘挨着我们的建筑、内部是空的"位置
2. **共享墙复用**：那一格如果是**我们造的墙** → 可以复用

⚠ 注意第 2 条**不能**放宽成"那一格有墙就复用" —— 地图原有的墙
（废墟、其他 mod 的墙）**不该**被当成我们的墙来复用，否则：
- 我们以为省了墙，其实那面墙不是我们的
- 拆掉那栋建筑时会连带拆掉别人的东西

### 持久化

存成 JSON，放在存档目录（`GenFilePaths.SaveDataFolderPath`）。
**不能用 `Scribe` 的 `GameComponent` 序列化**吗？—— 可以用，而且更好
（跟着存档走，读档自动恢复）。但那样要处理版本迁移。

**取舍**：先用**独立 JSON 文件**（简单、可读、可 git diff、便于调试），
因为它不涉及存档格式兼容问题。如果以后需要跟存档强绑定再换。

## 四、和现有代码的关系

| 现有 | 变化 |
| --- | --- |
| `TemplateBuildDomain` | 放完蓝图后，把这次放置**记进账本** |
| `TemplatePlacer.FindBestSite` | 加"贴靠模式"：查账本找可贴靠的位置 |
| `TemplatePlacer.Plan` 的 `existingAt` | 由账本提供（我们造过的）+ 地图现状（其他东西） |
| `ShelterDomain`（程序化兜底） | 也应该记账 |
| "已有住处就跳过"的守卫 | **改成查账本**（更准，不受 debug 开局的墙干扰） |

★ 最后一条尤其重要：现在的守卫是 `ShelterDomain.HasAnyShelter(map)` ——
它会被 **debug 开局的 662 堵墙**骗到（这也是我上一轮"验证被守卫拦住"的原因）。
改成"账本里有没有我们造的住处"就准了。

## 六、优先级

**在 S5 之后、贴靠选址之前。** 理由：

- 它本身**不阻塞 S5**（一间房就够撑 5 天）
- 但它是**贴靠选址和共享墙复用的共同前置**，所以必须排在它们前面
- 而且它能**顺手修掉"守卫被 debug 开局的墙骗到"**这个问题，
  那个问题一直在干扰我的测试（上一轮就撞到过）
