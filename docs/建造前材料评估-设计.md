## 一、问题：现在的失败方式是最差的一种

| 做法 | 结果 | 评价 |
| --- | --- | --- |
| 不造 | 小人去干别的，等有料了再造 | 可接受 |
| **换材料造** | 用钢把房子盖出来 | **最好** |
| **不够也硬造** | 放一堆蓝图 → **没人建得完** → 小人卡在建造上 | **最差** ← 现状 |

**为什么"硬造"最差**：
1. 所有人被建造任务吸住，**别的活都不干了**（种地、搬东西）
2. 房子永远建不完（半成品壳子）
3. 料被占着（蓝图会预留材料），**其他要用这种料的地方也动不了**
4. 玩家/我们看到的是"一直在建但建不好"，最难诊断

## 二、正确做法：**先算够不够，再决定**

```
① 这份样板整栋要多少料（按当前选定的材料算）
② 地图上实际有多少这种料（可搬运的）
③ 够 → 造
   不够 → 试下一个材料（木 → 钢 → 石砖 → …）
          有哪个够 → 用它造
          都不够 → ★ **不造**，并报告"缺什么、缺多少"
```

### 关键点 1：要算的是**整栋**，不是"一格一格试着放"

现在 `PickStuffFor` 是**逐格**挑材料的：放第一格时木头够，就选木头；
放到第 30 格时木头没了，但那格的代码还是会选木头（它只看"还有没有剩"，
不看"够不够整栋"）→ 结果就是**一半木一半钢的壳子**，或者干脆建不完。

→ 必须**先算整栋总需求**，再一次性定材料。

### 关键点 2：材料的"数量"要按**建造成本**算，不是"有几堆"

RimWorld 里：
```
一堵墙要 5 个材料（costStuffCount）
木墙 ×44 = 220 木头
```
而地图上可能有 300 木头 → 够；有 100 木头 → 不够。

所以判据是 `可用数量 >= Σ(每格 costStuffCount)`，不是"有没有木头"。

### 关键点 3：不够就**不造**，而且要说清楚

用户明确说了这个分支现在可以"就到这一步"：
> 「那确实没办法，现在其实卡到这一步就够了。」

但**必须报告**（这是本项目的纪律）：
"要 220 木头，只有 100；要 220 钢，只有 50 → **不造**"

### 关键点 4：**计划采集资源**是下一步（本轮不做，但留好接口）

用户：「以后预期会有一个分支，就是说预计资源是不够，那我们从现在开始就要计划采集资源。」
→ 先把"发现不够"这个信号做出来，采集计划以后接。

## 三、实现位置

### Core（纯逻辑，可离线测）

```
MaterialPlan {
    string ChosenStuff;        // 最终选的材料（null = 不够，不造）
    int    NeededTotal;        // 整栋需要多少
    int    AvailableChosen;    // 选的这种料有多少
    List<MaterialOption> Options;  // 每种料的 需要/可用/够不够
    string Reason;             // "够" / "缺 X 个" / "所有材料都不够"
}
```

`TemplatePlacer.PlanMaterials(tpl, costPerCell, availableByStuff)` ——
**在选择任何格子之前**先算，产出"用哪种料"或"不造"。

★ 它必须是 Core 里的纯函数：这样"够不够"的判定可以离线测试，
  而不用每次进游戏才发现"又是材料不够"。

### 游戏层

1. `CostPerCell(stuffDef)` —— 每格要几个材料（`def.costStuffCount`）
2. `CountStuffAvailable(map)` —— 地图上可搬运的材料数量（按 defName 分组）
3. `TemplateBuildDomain`：**先调 PlanMaterials，不够就直接返回"不造"**，
   不再逐格挑

## 四、测试计划（纯逻辑）

- [ ] 木头够 → 选木头
- [ ] 木头不够、钢够 → **选钢**（这是用户要的核心行为）
- [ ] 都不够 → **ChosenStuff = null**，且 Reason 里带"缺多少"
- [ ] 刚好够 → 选它（边界）
- [ ] 多格/多材料的成本累加正确（44 墙 × 5 = 220）
- [ ] 没有材料选项时（accepts 为空）不炸
- [ ] ★ 绝不返回"够"当其实不够（宁可保守不造，也不要硬造）
