# 快照读取结构：**可拓展** + **可度量**

> 来源：用户 2026-10-03，在看到录制器跑起来之后。
>
> 用户原话：
> 「我希望这种**读快照的形式在后边还要有拓展**。
>  因为现在我**无法知道我们现在是否读取了足量的快照**。
>  那么假如说后续有需要去**读取别的类型的内容**的话，
>  那么我们要有一个**易于拓展的结构**，把新的快照内容加进去，
>  就是一定要保证它**易于更改、易于拓展**，就整个读快照的结构。」

---

## 一、要求拆解

| # | 要求 | 含义 |
| --- | --- | --- |
| **1** | **易于拓展** | 加一个新"读取块"时，**不改现有代码**（开闭原则） |
| **2** | **可度量** | 能回答"**快照够不够**" —— 覆盖了哪些面、漏了哪些、采样密度对不对 |

---

## 二、设计：**读取块注册表（Reader Registry）**

### 核心：每个"面"是一个独立的 Reader

```
interface ISnapshotReader {
    string Id;            // 稳定标识，如 "zones" / "storageGroups" / "bills"
    string DisplayName;   // 人话
    int    Order;         // 执行顺序（小的先）
    void   Read(Map map, ColonySnapshot snap, SnapshotContext ctx);
    IEnumerable<string> ProvidedFields { get; }   // 我往快照里写了哪些字段（供覆盖率核对）
}
```

`SnapshotBuilder` 变成**只负责遍历注册表**：

```
Build(map, tick):
    snap = new ColonySnapshot(tick)
    foreach reader in Registry.Ordered():
        try { reader.Read(map, snap, ctx) }
        catch (e) { ctx.RecordFailure(reader.Id, e) }   // ★ 一块失败不影响其他块
    return snap
```

### 为什么这样就能"易于拓展"

| 要加新内容 | 要改什么 |
| --- | --- |
| 加"房间质量/美观度" | **新增一个 `RoomBeautyReader`**，注册一下 |
| 加"装备与武器" | **新增一个 `EquipmentReader`** |
| 加"科技树详情" | **新增一个 `ResearchDetailReader`** |
| 改某个面的读法 | **只改那一个 Reader** |

→ **不改 `SnapshotBuilder`、不改 `ColonySnapshot` 的现有部分、不改其他 Reader。**

### 关键细节

1. **失败隔离**：每个 Reader 独立 try/catch，**一块坏不拖垮整张快照**
   （mod 组合千差万别，某个 Def 可能不存在）
2. **`ProvidedFields`**：每个 Reader **声明自己提供哪些字段** —— 这是"可度量"的基础
3. **扩展字段逃生口**：`ColonySnapshot.Extra: Dictionary<string, string>`
   万一某个 Reader 要写非结构化内容，不污染主结构

## 三、设计：**可度量**（回答"快照够不够"）

用户说「**无法知道是否读取了足量的快照**」。所以要两个维度的度量：

### A. **覆盖度**（读了哪些面）

每个 Reader 在快照里留一条**自检记录**：

```
ReaderHealth {
    string ReaderId;
    bool   Ran;              // 跑了吗
    long   ElapsedTicks;     // 花了多久（游戏 tick）
    int    ItemsRead;        // 读了多少个对象（0 可能是"真的没有"也可能是"读法失效"）
    string Error;            // 失败原因
    List<string> Warnings;   // 部分失败（比如某个 Def 找不到）
}
```

→ 分析端可以问：**"`storageGroups` 这个 Reader 全程 `ItemsRead=0`，
   是这一局真的没建存储组，还是我读法坏了？"**
   —— 这就是"够不够"的第一层。

### B. **采样密度**（快照够不够密）

每条快照带**采样元信息**：

```
SamplingInfo {
    int Tick;                  // 这一张的 tick
    int IntervalTicks;         // 设定间隔
    int SincePrevTick;         // 距上一张多少 tick（★ 应该 ≈ IntervalTicks）
    int DroppedEstimates;      // 有没有漏采（SincePrev > Interval*1.5 就是漏了）
    int TotalSnapshots;        // 累计
    int PlayedTicks;           // 这局一共玩了多少 tick
}
```

→ 分析端能回答：
- **"平均间隔是不是 6000？"**（不是 → 采样有漂移/漏采）
- **"这局玩了 90 万 tick，只拍 5 张 → 太稀，看不出过程"**
- **"中间有 12 万 tick 没快照 → 那段时间在做什么不知道"**

### C. 一个总的**健康摘要**

每 10 张快照写一条汇总（日志 + 快照内的 `health` 字段）：

```
快照健康：#40  覆盖 8/8 个读取块  平均间隔 6002 tick（目标 6000）
          区间 0~6000 张数 40  最长间隔 6100
          读取块失败：无
          可疑：storageGroups ItemsRead 全程 0（本局确实没建组？）
```

★ **"可疑"这一栏是关键** —— 它把"看起来正常但可能没读到"的情况**主动指出来**，
  这正是用户说的"无法知道是否读取了足量"的解药。

## 四、落地顺序

| # | 做什么 |
| --- | --- |
| 1 | `ISnapshotReader` 接口 + 注册表 |
| 2 | 把现有读法**拆成 Reader**：zones / storageGroups / things / pawns / bills / research / wealth / designations |
| 3 | `ReaderHealth` + `SamplingInfo` 进快照 |
| 4 | 健康摘要（每 N 张汇总一次） |
| 5 | 分析端的"够不够"报告（读 JSONL → 出覆盖度与密度） |

---

## 五、和前面几条原则的关系

| 原则 | 内容 |
| --- | --- |
| 套公式 > 局部最优 | 能用公式/样板的，不要用算法 |
| 面向对象 > 面向过程 | 读游戏已存好的对象，不推断事件 |
| 关注面 + 反馈环 | 不要只看一个指标；基本面是连环的 |
| **可拓展 + 可度量**（本文件） | **录制器本身要能长大，而且要能自证"读够了"** |

★ 这一条是**工程约束**，前三条是**内容约束**。
  两者合起来才是"能长期用下去"的录制器 ——
  因为**分析会不断提出新的数据需求**（用户说的"后续有需要读取别的类型的内容"），
  而**没有度量就无法知道数据够不够**。
