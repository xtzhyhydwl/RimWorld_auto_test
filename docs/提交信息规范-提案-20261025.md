# 提交信息规范 · 提案（2026-10-25）

> 口径：**实测** = 本机 `git log`/目录/原文读到；**给证** = 派活方口述，本机未复核。依据（实测）：`RimworldMods` 单仓 390 提交、340 条带前缀（fix 131 / feat 124 / chore 24 / deploy 22 / docs 15 / build 13，另有 perf 7 / refactor 3 / art 1）、**无 tag**、README 版本号标题充当 CHANGELOG、subject 中位 46 字符最长 77（早期口径记 41，统计范围待确认）；型样底稿 `docs/_tmp-rhah-0008-msg.txt`。

## 一句话规则
标题 `<type>[<module>]: <subject>`——**本仓库采用方括号 `[]`**，不用圆括号；正文三段 `Why：` / `What：` / `Now：`；**一个 ticket = 一个提交**。

## 语言口径

- 默认**中文**：作者和人类都是中文母语，英文不带来信息增益；保持 ASCII/原文的只有 `type`、`module`、代码标识符（`PawnCanOpen`）、错误原文、路径、版本号。切换条件：**出现非中文维护者**（外部评审/接手/上游 PR）时整体切英文，全仓一次切换，不逐条混用。

## 标题规则

| 要素 | 取值 | 约束 | 示例 |
|-|-|-|-|
| `type` | `fix` 修缺陷/回归，改行为不改契约（131 次先例）· `feat` 新功能/新事件/新行为面（124） | 小写；后接半角 `:`；module 用**方括号 `[]`** | `fix[rhah/events]: …` |
| | `docs` 只改文档（15）· `chore` 仓库杂务：清理/脚本/目录/依赖，玩家不可见（24）· `build` 只重编译/工程文件，**不升版本**（13） | 同上 | `build[core]: …` |
| | `deploy` 发版：产物 DLL + 版本号、README 标题同步（22，多为 `deploy: v1.1.4`）· `initial` 仅用于仓库初始化（**依据：实测历史只有 `initial:` 1 次 + `Initial commit` 13 次，无 `init`**），几乎用不到 | 同上 | `deploy: v1.1.5` |
| `module` | 子 mod 名 / 行为域 / 二者用 `/` 连接（`rhah/events`，见下） | 一眼看出「涉及哪方面、不涉及另一方面」；**按行为归属选，不按改了哪个文件** | `rhah/events` |
| `subject` | **中文短句**，一句话概括整个改动 | 不带句号；**整条 title（含 `fix[rhah/events]: `）≤60 字符**（中文 1 字 = 1 字符）；脱离正文也能读懂 | `离场来客优先走门，走不通再凿墙` |

**module 候选（由实测的 `Source/` 12 个目录 Api/Caravan/Core/Data/EventMgr/Generation/Identity/Incidents/Narrative/Pawn/Storyteller/Tests 归纳）**：`visitors`(Pawn 的 lord/giver) · `events`(Incidents/EventMgr) · `narrative`(Narrative) · `storyteller`(Storyteller/Suyin) · `identity`(Identity) · `caravan`(Caravan) · `trade`(Trade) · `generation`(Generation) · `settings`(Core 的 RHAH_Settings) · `api`(Api) · `ui`(ModEntry/设置界面) · `compat`(跨 mod、1.6↔1.7 兼容)；必要时 `core`（跨域基础设施）、`build`（工程/Def 双写）。**这份是按源码目录归纳的候选，不是命名要求**；实际怎么取见下条「module 口径」。

- **选法**：问「玩家会看到哪一方面的变化」→ 取那个词；跨两域时取**主行为**，另一个写进 `What：`。
- **module 口径（已定，2026-10-25）**：**子 mod 名 或 行为域名，或两者用 `/` 连接**——这三种仓库历史里都在用，所以 `rhah/events` 这种组合不越界。**命名以仓库历史里实际出现过的 scope 为准，不自造新词**。
  依据（**实测**：`git log --format=%s -n 400` 扫 391 条 subject，按 `^(type)(scope)` 统计，圆括号与方括号都算）：40 条带 scope（39 条旧圆括号 + 本条方括号）、25 个不同 scope；前几名 **`rhah` 4 · `events` 4 · `ratkin-recycle` 3 · `irismenus` 3 · `prisonernames` 3 · `KeepYourIdentity` 2 · `docs` 2 · `ui` 2** ⇒ **子 mod 名（`rhah`/`ratkin-recycle`/`irismenus`）与行为域名（`events`/`docs`/`ui`）他都在用**，历史里没有 `visitors` 这个 scope。
  代价是前缀更长、60 字符额度更紧（`fix[rhah/events]: ` 占 18 字符）。

| 差 | 好 | 差在哪 |
|-|-|-|
| `fix: 修了门的 bug` | `fix[rhah/events]: 离场来客优先走门，走不通再凿墙` | 缺 module；subject 是「bug」不是行为；看不出涉及哪方面 |
| `fix[rhah/events]: 修了离场来客被困房间走不出去也打不开门最后只能一直游荡的问题。` | 同上（**范例 title = 33 字符**） | 一句话概括变成过程复述；带句号；远超 60 字符 |

## 正文三段规则

| 段 | 写什么 | 写多少 | 可以贴 |
|-|-|-|-|
| `Why：` | 为什么修：现象 + 根因（哪个机制/判据错了） | 2–5 行 | 报错原文、tick/HP 数字、`文件:行号` |
| `What：` | 怎么修：**行为面**改了哪几条（增删/顺序/兼容取舍） | 2–5 行 | 关键标识符、Def/设置的增删 |
| `Now：` | 现在什么表现：怎么验证的 + 结论 + 未验证项 | 2–5 行 | 构建输出（0 警告 0 错误）、游戏内实测数字 |

- 段间空一行；行宽 ≤72 显示列（汉字记 2 列，约 36 汉字）；标签固定 `Why：`/`What：`/`Now：`，冒号全角、全文一致。
- **不要写**：改了 A/B/C 文件（`git show --stat` 已有）、过程抱怨、探路失败记录、给自己的 TODO。`Now：` 必须写「怎么测的」，没测就写 `未验证：…`，**不许把推断写成实测**。下面范例取自 0008 的真实提交 `d274d7d`（正文按三段各压到 3 行；title 33 字符）。

```
fix[rhah/events]: 离场来客优先走门，走不通再凿墙

Why：默认设置下，住满或被拒绝的来客进入 Leaving 后既不开门也不凿墙。
门禁对活跃来客一律把 PawnCanOpen 置 false，而离场逻辑用
TryFindBestExitSpot 找不到出口就放弃 ⇒ 只在房间游荡、永远不走。

What：删掉 famineVisitorsOpenDoors 设置，门禁写死为
「该不该管 → 敌情禁止 → 离场放行 → 其余禁止」；搜不到出口时
先切离场 duty 再调凿墙子类；Def 未动，XML 与 6ab44c7 逐字节相同。

Now：RimWorld 1.7.4985 实测。有门：从门格走出并离图，门 HP 104、
23 面墙不变；全墙封死时 curJob=Mine，墙 5460→5145 被打穿并离图；
两场景 0 异常，1.7 构建 0 警告 0 错误。未验证：敌情、多来客、1.6。
```
**反例（常见坏写法）**

| 坏写法 | 为什么坏 |
|-|-|
| `fix: 修了门的 bug` | 无 module；subject 是「bug」不是行为；看不出涉及哪方面 |
| `fix：修复`（全角冒号）；正文一坨 `改了一些东西，动了好几个文件。Refactor 了一下，顺便修了 bug。` | 全角冒号让 `type` 检索失效且 subject 零信息；正文无三段、先说「改了什么」而非「为什么」、文件数是流水账、`Refactor` 与 type 冲突 |

## 一个 ticket = 一个提交

```
git reset --soft <base> && git reset   # HEAD 回 base；改动都留着
git add <每条路径>                     # 逐个文件，不用 -A
git commit -F .git/COMMIT_EDITMSG        # 正文从文件读，不手打
```

- **不要 `git add -A` / `git commit -a`**：`1.6|1.7/Assemblies/*.dll` 常是构建产物（0008 期间 4 个 DLL 一直是 `M`），一条 `-A` 就把二进制写进历史；提交前 `git status --short` 核对，只应有源码/Def/文档。
- **默认压成 1 个提交**：0008 就是这样收尾的——`d274d7d`（父 `6ab44c7`，16 files / +171 / −27，title `fix[rhah/events]: 离场来客优先走门，走不通再凿墙` 33 字符）。例外仅在「每组改动能各自通过构建」时才拆成多个（可 bisect）；过程 `wip`/`fix: typo` 不进最终历史，留 `backup/<ticket>-before-cleanup` 兜底。

## 判定清单（review 用，逐条 yes/no）
1. 标题是 `type[module]: subject` 三段式，`type` 在枚举内，**方括号 `[]`** 与冒号是**半角**？
2. 标题是**中文短句**且整条（含前缀）**≤60 字符**？（范例 33）
3. `module` 能看出改动归属（涉及哪方面 / 不涉及另一方面）？
4. `Why：`/`What：`/`Now：` 三段齐全、各 2–5 行；正文无文件清单与过程抱怨；`Now：` 写了「怎么测的」，没测处标 `未验证：`？
5. 一个 ticket 一个提交（或每个提交能单独编过）？
6. `git show --stat` 里没有 `*.dll` / `obj/` / `runs/`？

## 转 skill：硬规则 vs 风格建议

**硬规则（违反即返工，可自动判定）**：`type` 枚举；`type[module]: subject` 形态（方括号）与半角标点；title ≤60 字符（含前缀）；subject 中文、无句号、非空话；三段标签齐全；`Now：` 含验证方法与结论或 `未验证：`；一票一提交；不提交二进制。
**风格建议（可放宽，不作阻塞项）**：每段 2–5 行、行宽 ≤72 列；`module` 的粒度（`events` 还是 `pawn`）；数字/行号/哈希贴多少；语气（先现象后根因）；跨域时取哪个 module。
