# 摆放规范（Placement Rules）—— 一套统一的结构

> 来源：用户 2026-10-03，一口气指出了 4 个问题之后说：
> 「这些其实都涉及一个**摆放的规范**的问题，就是各种各样的建筑、各种各样的区域
>  **摆放规范**的问题……我想着应该找一种**统一的结构**，给它统一起来，
>  就是**几条简单的规则**，就可以避免大多数的问题。」

---

## 一、病根：我在"让算法挑位置"，而位置本该被"规定"

回头看，我做的每个选址都是**一个独立的优化问题**：

| 对象 | 我用的方法 | 结果 |
| --- | --- | --- |
| 种植区 | 找最肥沃的连片 | 形状随机、可能太小 |
| 储藏区 | K-means 聚类跟着资源走 | **形状必然随机**（团块） |
| 住处 | 滑窗找最近的空地 | **和种植区打架**（盖到田上） |

**每一个单独看都"合理"，合起来就互相打架。** 这就是没有统一规范的代价。

而真实玩家的做法**根本不是优化**，而是**一套固定规矩**：

> 先找块平地画个方田 → 找个靠近中心的地方画个方仓库 →
> 房子挨着盖 → 东西搬进屋里

**规矩是确定的，所以不会打架。** 这才是对的方向。

---

## 二、核心结构：**分区（Zones）**，而不是"各自找位置"

### 规则 0：殖民地是一张被划分的地图

```
┌─────────────────────────────────────────────┐
│  地图边缘区（丢弃区）                          │
│  ┌───────────────────────────────────────┐  │
│  │  生活区（Core）                        │  │
│  │   ┌─────────┐   ┌─────────┐          │  │
│  │   │ 建筑区   │   │ 建筑区   │  ← 挨着长 │  │
│  │   └─────────┘   └─────────┘          │  │
│  │   ┌───────────────────┐              │  │
│  │   │ 种植区（方田）      │              │  │
│  │   └───────────────────┘              │  │
│  └───────────────────────────────────────┘  │
└─────────────────────────────────────────────┘
```

**关键**：先划**区**，再往区里放东西。而不是每个东西各自去地图上找最优解。

### 规则 1：每种对象有**互斥的落位条件**

| 对象 | 必选 | 禁选 |
| --- | --- | --- |
| **种植区** | 可耕种地表、**无屋顶**、连片 | 岩石/水/已有建筑/**未来建筑区** |
| **建筑** | 平地、可承重 | **种植区**、已有建筑（除非贴靠）、丢弃区 |
| **储藏区（生活）** | 靠近基地中心 | 种植区、**建筑区内部**（除非在室内） |
| **丢弃区** | 地图边缘 | 生活区内 |

★ **"禁选"比"必选"更重要** —— 打架全部来自"没禁什么"，而不是"没选到最优"。

### 规则 2：**形状由规则给定，不由算法生成**

用户原话：
> 「一般来说我们拉一个**正方形**的区域就 OK 了……**形状随机反而让我感觉不太稳定**。」
> 「找土地上画一个**正方形**，反正就是**矩形**嘛就够了。」

| 对象 | 形状 |
| --- | --- |
| 种植区 | **矩形**（边长由"够吃"算出，见规则 4） |
| 储藏区 | **矩形** |
| 丢弃区 | **10×10 方框**（已实现） |
| 建筑 | 由**样板**给定（已经是了） |

→ **一律用矩形**。不再出现"跟着资源走的团块"。

### 规则 3：**先来后到 = 优先级**（解决"盖到田上"）

用户指出的硬伤：
> 「你在种植区上面盖房子……一旦你把墙体封闭之后，种植区上面就覆盖了房顶，
>  那种植区覆盖了房顶，**它植物没法得到光照，它是不会长大的**。所以那种等于说没种。」

两条防线（**都要**）：

1. **建之前**：建筑的选址必须**排除种植区格**
2. **建之后**：种植区要**周期性自检**，把"被屋顶盖住"的格**从区里去掉**
   （因为屋顶可能来自我们盖的房，也可能来自地图原有结构）

★ 第 2 条尤其重要：它不只是防我们自己的 bug，也防**山洞屋顶/普通屋顶**这种
  "本来就有的"情况 —— 那些格子本来就不该在种植区里。

### 规则 4：**尺寸由需求算，不是拍脑袋**

用户：
> 「三个人就那么点田肯定是没法持续发展的……后边会有断节、会有断层。」

- 种植区边长 → 由"要供 N 人吃"反算（`docs/s5-5天生存验收设计.md` 里已有公式）
- 储藏区大小 → 按当前物资总量估
- **不设"最小格数"这种拍脑袋的下限**，而是"算出来是多少就是多少"

### 规则 5：**物资要进屋**（用户提的物理规律）

用户原话：
> 「前期就是找一个地方，先把物资聚集一下。**等到有房子之后，就应该把外边的
>  存储器删掉，把存储器移到房间里面来**。就是你存放在房子里的物资是**不会腐坏**的。
>  一个物体暴露在外边，它是会逐渐坏掉的。包括如果你把食物放在外边，
>  **野生动物会来吃**。那等于说我们并不是三个人，可能野生动物也会吃，
>  那我们的食物就估计得不对。」

**这是双重损失**：
1. **物资真的少了**（腐坏 + 被吃）
2. **我的食物计算系统性偏高**（我只数了"地图上有多少营养"，没扣掉"会坏掉/被吃掉的"）

→ 所以：
- **有房子之后，生活区储藏区应该搬到室内**
- 食物预测里要**扣除**暴露损失（或至少：暴露的食物不算"安全存粮"）

## 三、落地顺序（按"能不能立刻止血"排）

| # | 做什么 | 为什么先做 |
| --- | --- | --- |
| 1 | **种植区排除被屋顶盖住的格**（周期性自检） | ★ **正在造成实际损失**：盖了房 → 田废了 → 但 mod 以为还在种 |
| 2 | **建筑选址排除种植区** | 防下一次 |
| 3 | **储藏区改成矩形**（不再 K-means 团块） | 用户明确要求 |
| 4 | **种植区改成矩形 + 按需求算尺寸** | 用户明确要求 |
| 5 | **统一的分区模型**（把上面的规则写成代码结构） | 长期不再互相打架 |
| 6 | 物资进屋（室内储藏区） | 需要 3、4 稳定之后 |
| 7 | 食物预测扣除暴露损失 | 需要 6 之后 |

## 四、和现有代码的关系

| 现有 | 变化 |
| --- | --- |
| `StockpileDomain`（K-means 聚类） | **废弃聚类选址**，改成"找一块矩形空地"（聚类只保留给"资源在哪"的参考） |
| `FoodDomain` / `PlotPlanner`（种植区） | 加"矩形 + 无屋顶 + 排除建筑区"，加**周期性屋顶自检** |
| `TemplateBuildDomain.FindBestSite` | 加"排除种植区格" |
| `EdgeDumpPlanner`（边缘方框） | ✅ **已经符合规范**（10×10 方框、贴边）—— 可以作为其他对象的范本 |
| `BuildingRegistry`（账本） | 继续用，且**分区信息也应该进账本**（哪块地是干嘛的） |

★ 注意：`EdgeDumpPlanner` 是**唯一一个已经符合这套规范的实现**
（用户当时说"直接靠边画个 10 乘 10，不用管了"）。
**其他对象都应该照它的样子做** —— 这是个很好的信号：用户的口径一直是一致的，
是我在别处没照做。

## 五、一条元教训

这次用户一口气说了 4 个问题，**它们看着零散，其实是同一个缺失**。

> **当用户反复指出"同一个类别"的问题时，不要再逐个修 —— 去找那个缺失的结构。**

我前几轮一直在"修单个 bug"（坐标系、材料、守卫…），那些确实是 bug。
但**摆放**这一层我从来没有建立过结构，所以它每次都以不同面貌冒出来。
