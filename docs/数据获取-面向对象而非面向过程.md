# 数据获取方法论：**面向对象读取**，而不是面向过程记录

> 来源：用户 2026-10-03，在我做了"快照 + 差分事件流"之后。
>
> 用户原话：
> 「我相信这个游戏它本身也在用一种**结构化的方式**来存储这个世界当中发生的一些特殊变更……
>  玩家一旦玩了，他要去造建筑、要划分各种各样的区域。比如说他要划一个存储区，
>  那么这个存储区会被叫做**存储区一**，或者说它会被划分成一个**存储组**。
>  特别是比如说两个存储单位被**链接**起来之后，它会被划分到一个**组**，
>  这个组承载着特定的存储内容。也就是说假如说我的**存储组一**专门用来存储烹饪过的食物，
>  那么它在游戏中肯定会存在一种**数据集合**记录这个组，
>  同时记录**应用了这个组的存储单位、存储单位在哪**。
>
>  我想表达的就是游戏肯定在以**结构化的方式**存储一些信息。
>  那我们可以去**读取那些结构化的东西**，或者说在我们后续考虑要自动化游玩游戏的时候，
>  我们就要考虑那些**被结构化存储在存档内的那些信息**。
>
>  就像是你没有必要去记录"我对一个存储区做了什么样的操作" ——
>  那是一种**面向过程**的思路。比如说我在某个时间点创建了某个存储区，
>  又在某个时间点把存储区的性质改变了。这其实是一种面向过程的思路，
>  它也可以记录存储区的全貌。但是我觉得这个**不是正确的方法**。
>
>  感觉还是得**面向对象**：就是说当你**扫描整个存档的所有存储区**的时候，
>  你发现好像比之前**新增了一个存储区**，或者说某个存储区的**性质发生了改变**。
>  你会发现有的存储区专门用来存食物，有的专门用来存原材料，对吧？
>  那你就可以从中发现：在游戏的前期或中期，到了某一个阶段，
>  我们**需要专门创建存储区来存储特定的物品**。
>
>  总之我们**先把数据拿到**。至于 AI 究竟能从中剖析出多少规则，这个先不说，
>  至少我们能够**用正确的结构把数据完整地获取到**。
>
>  ……那么像是建筑的例子，我们**直接在地图上维护一个虚拟的地图**。
>  这个虚拟的地图**忽略一切环境因素**，或者说它**只保留关键的环境因素**
>  ——比如水或者沼泽地，就是"能在上面建造建筑和不能建造"的那种地块。
>  先建一个没有多余信息的图，然后在上面再重建一个我们已知的、
>  玩家在上面建造的那种图。那么可能我在某一个时间点建了一个 13×13，
>  那么在下一个时间点又建了，那么就**持续维护、持续更新这个图**……
>  它就有一个**随着时间变化的图景**。
>
>  我想说的就是，**在记录的一开始就要找准方法、找准结构去存储所有的信息**，
>  才能保证后续的分析是正确的。」

## 一、两种思路的对比

| | **面向过程**（我做的） | **面向对象**（用户要的） |
| --- | --- | --- |
| 记什么 | "T 时刻创建了区#3"、"T2 改了它的过滤器" | **"扫全存档：多了一个存储组；某个组的性质变了"** |
| 数据来源 | 我**推断**出来的事件 | **游戏已经存好的对象** |
| 本质 | 猜"人做了什么" | 读"世界现在是什么样" |
| 粒度 | 定死在事件上 | **快照在，以后能用不同粒度重新分析** |
| 抓漏风险 | 两次快照之间的瞬时变化**永久丢失** | 只要最终状态在，就不会丢 |
| 和存档的关系 | 平行的一套数据 | **直接对应存档里的结构**（可校验） |

### ★ 为什么"面向过程"是错的（用户的核心论点）

用户说得很准：
> 「它也可以记录存储区的全貌。但是我觉得这个**不是正确的方法**。」

面向过程的记录**只能回答"发生了什么"**，而用户要的是
**"这个殖民地现在是什么样、有哪些种类的对象、它们承担什么职责"** ——
因为**规则要从对象结构里长出来**，而不是从操作序列里长出来。

例：
- 面向过程 → "用户在第 2 天划了储藏区，第 5 天改了过滤器"（**这说明不了任何通用规则**）
- 面向对象 → "殖民地有 3 个存储组：一个专存食物、一个专存原材料、一个存尸体"
  → **"需要按用途分组建存储"这条规则自己就浮出来了**

## 二、游戏里**确实存在**这些结构化对象（已确证）

用户的直觉是对的。用 `AsmDump` 确证：

```csharp
RimWorld.StorageGroup {
    string        label;      // "存储组一"  ← 用户说的那个名字
    int           loadID;
    Map           map;
    List<IStorageGroupMember> members;   // ★ 被链接起来的存储单位（存储区/架子）
    StorageSettings settings;            // ★ 这个组"承载的特定存储内容"
    // 读：CellsList / HeldThings / MemberCount / GroupingLabel
}

Verse.StorageGroupManager {
    List<StorageGroup> groups;                    // ★ 全部存储组
    List<StorageGroup> StorageGroupsForReading;   // ★ 公开只读入口
    bool HasGroupWithName(string label);
    StorageGroup NewGroup(string label = null);
}

RimWorld.IStorageGroupMember {
    StorageGroup   Group;                 // 它属于哪个组
    StorageSettings StoreSettings;        // 它自己的存储设置
    string         StorageGroupTag;
    Map            Map;
}

RimWorld.StorageGroupUtility            // 组相关的工具
RimWorld.Planet.MoveableStorageGroup    // 可搬运的组（远行队？）
```

★ **一句话**：`StorageGroupManager.StorageGroupsForReading` 就是用户要的
"**记录这个组的数据集合**"，而 `StorageGroup.members` 就是
"**应用了这个组的存储单位、在哪**"。

→ **不需要推断，直接遍历即可。**

## 三、正确的记录结构（重设计）

### ① 对象层：每次快照，**遍历对象**（不是差值）

| 对象 | 读什么 | 对应存档里的 |
| --- | --- | --- |
| **存储组** | `label` / `members`（位置）/ `settings`（允许/禁止的 Def） | `StorageGroup` |
| **存储单位** | 每个 `IStorageGroupMember` 的位置 + 它属于哪个组 | `Zone_Stockpile` / `Building_Storage` |
| **区域** | 种植区/储藏区的格子集合、作物、过滤器 | `ZoneManager.AllZones` |
| **建筑** | 每个建筑对象的 Def/材质/位置（**按对象，不按事件**） | `listerThings` |
| **工作优先级** | 每人的 工作类型→优先级 | `Pawn_WorkSettings` |

**"发现新增了一个存储组"是两次对象快照对比的自然结果**，而不是我事后推断的事件。

### ② 虚拟地图（用户明确要的）

用户：
> 「直接在地图上维护一个**虚拟的地图**。它**忽略一切环境因素**，或者**只保留关键的环境因素**
>  ——比如水或者沼泽地，就是"能在上面建造建筑和不能建造"的那种地块。
>  先建一个没有多余信息的图，然后在上面**再重建一个玩家建造的图**……
>  持续维护、持续更新……它就有一个**随着时间变化的图景**。」

所以虚拟地图有**三层**：

```
第 0 层：可建造性（静态，只算一次）
         能建 / 不能建（水、沼泽、岩石、深水…）
         ★ 这是"关键环境因素"，其余环境（肥沃度、温度、美观）全部丢掉

第 1 层：玩家建造物（随时间变化）
         墙/门/家具/地板 —— 按对象记录，持续更新

第 2 层：功能分区（随时间变化）
         种植区/储藏区/存储组 —— 按对象记录，持续更新
```

→ **时间序列 = 这三层的历次快照**，可以"回放"整个殖民地的成长。

### ③ 为什么这比事件流更适合后续分析

- **可重新分析**：以后想到新问题（"存储组大小随时间怎么变？"），
  **用旧快照就能算**，不用重新录
- **可校验**：对象直接对应存档结构，读错了能对照存档查
- **不依赖"我猜对了什么重要"**：事件流必须**事先**决定记什么，
  而对象快照是**全量**的

## 五、一条元教训（第二次同类）

上一轮用户纠正我"**套公式 > 局部最优**"；
这一轮用户纠正我"**面向对象 > 面向过程**"。

**两次都是同一个模式：我在"自己造一套"，而正确的做法是"用现成的结构"。**

- 上一轮：我造算法 → 应该用公式/样板
- 这一轮：我造事件流 → 应该**读游戏已存好的对象**

→ 所以以后遇到"要记录/要决策"的时候，**先问：游戏里是不是已经有这个结构了？**
  用户两次都比我更清楚游戏里"本来就有什么"。
