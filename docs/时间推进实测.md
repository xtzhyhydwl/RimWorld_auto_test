# 时间推进速度实测与 `play_for` 陷阱

> 独立于食物 mod 的**通用**发现，已同步进 skill `rimworld-auto-test`。
> 日期：2026-10-03　全部为**本机实测**

## 为什么要测这个

食物闭环的验收需要「跑 15 游戏天」，而 `step_game_ticks` 上限≈帧率。
如果 15 天要跑半小时，长跑就进不了日常回归。所以先量化代价。

---

## 一、两种推进方式的速度（实测）

脚本：`scripts/recon-speed-compare.mjs`　原始数据：`runs/food-recon/speed-compare.json`

| 方式 | 请求 | 实测墙钟 | 实际推进 | tick/s |
| --- | --- | --- | --- | --- |
| `step_game_ticks` | 15000 tick | 25348 ms | 15000 tick | **591.8** |
| `play_for` Ultrafast+boost | 25348 ms | 8888 ms | 63200 tick | **7110.7** |

推算 15 游戏天（900000 tick）：**`step` 25.3 分钟 / `play` 2.1 分钟** —— 差 **12 倍**。

### 结论：分工使用

- **长跑推天数 → `play_for`**（Ultrafast + `forceRequestedSpeed` + `ultraSpeedBoost`）
- **精确断言 → `step_game_ticks`**，但**必须显式传 `timeoutMs`**
  （工具级默认 10000，不传就 `timedout`，只推进 3515–5576 tick）
- **两者都不要信 `success`**，按 `advancedTicks` 累计
  （实测 `play_for` 出现过 `success:false` 但 `advancedTicks=63200`）

## 二、⚠ `play_for` 秒退陷阱（排了半天，根因很隐蔽）

### 症状

`play_for` **全部调用**返回：

```
elapsedMs: 6
advancedTicks: 0
initiallyPaused: true
message: "Game was paused externally after 3ms, before the requested 2000ms elapsed."
```

且**此后永久如此**，`Normal` / `Fast` / `Superfast` 都一样，
不传 `forceRequestedSpeed` 也一样，`pause_game` 也救不回来。

### 误判（记录一下，第一直觉是错的）

对比两个脚本，发现「失败的脚本在 `play_for` 前调了 `get_game_info`」，
于是怀疑是它。**二分实验证明这是错的**：

`scripts/recon-playfor-bisect.mjs` 的 D 组「setSpeed → getInfo → play_for」
**第一次成功（2295 tick）、紧接着重跑就失败（0 tick）**。
→ 变量不是调用序列，是**累积状态**。

### 根因

**某个 `forcePause` 的窗口开着，每帧强制暂停，把 `play_for` 的 unpause 覆盖掉。**
实测是 `RimWorld.MainTabWindow_Menu`。

`get_ui_state` 里两个字段直接指认：

```json
"windowsForcePause": true,
"forcePauseWindows": ["RimWorld.MainTabWindow_Menu"],
"openMainTabId": "main-tab:Menu"
```

### 确认实验

脚本：`scripts/recon-playfor-rootcause.mjs`　数据：`runs/food-recon/playfor-rootcause.json`

| 状态 | `windowsForcePause` | `play_for` 结果 |
| --- | --- | --- |
| 修复前 | `true`（Menu 标签页） | ❌ 0 tick |
| `close_main_tab {tabId:"main-tab:Menu"}` 后 | `false` | ✅ 15509 tick / 2.0 s |
| 紧接着再跑 | `false` | ✅ 15363 tick |
| 又跑 2 次 | `false` | ✅ 14923 / 12602 tick |

修复后稳定 **7755 tick/s**。

### 诚实边界

- ❌ **反向对照没做成**：想重开 Menu 标签页验证"再开就该再失败"，
  但 `open_main_tab` 的参数名是 **`mainTabId`**（不是 `close_main_tab` 的 `tabId`），
  传错所以没打开。所以只有「关掉就恢复」的**单侧证据**（4 次复现）。
  **建议补做**：用 `mainTabId` 重开 → 预期再次 0 tick。
- ❓ **Menu 标签页是谁开的没查出来**。排除了 `press_cancel`（实测 UI 无变化）；
  侦察脚本里 `open_main_tab` 开的是 `main-tab:Work`。**记为未查明**。

### 对策（已写进 skill）

长跑前必做：

```js
const ui = await call('rimworld/get_ui_state');
if (ui.windowsForcePause) {
  await call('rimworld/close_main_tab', { tabId: 'main-tab:Menu' });  // 参数名是 tabId
}
await call('rimworld/play_for', { durationMs: 10000, speed: 'Ultrafast', forceRequestedSpeed: true });
```

补充事实：
- `rimworld/pause_game` **只暂停、不解除**（两次调用报文都是 `"Game paused"`）
- 没有独立的 unpause 工具；解除强制暂停只能靠**关掉那个窗口**

## 三、光周期（顺带确认，影响预测器）

侦察实测：**晚上作物 Growth rate = 0%**（原因 `needs light 51%`）。
同块水稻在白天推进时 11% → 24%（年龄 12h → 1 天 22h）。

→ **15 天产出不能按 24 小时线性外推**，温带户外约只有半天有效生长。
→ 这使「预测 vs 实际」成为**真正有验证价值的测试**（不能拿同一假设自证）。

**待实测**：按季节/纬度/室内水培分别测精确的有效生长小时数。
