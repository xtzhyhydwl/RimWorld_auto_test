# 样板语义层 / 建造纲要 / 分段材料决策（设计 + 落地记录）

> 用户 2026-10-03 提的三件事，本次**在 Core 层落地**（纯逻辑、离线可测、**未部署**）：
> ① 样板要有**语义**（不只是形状）② 数量要**按人头**动态 ③ 材料要**分段决策**。
> 另有第四件事**被实测否定**（建造顺序 ≠ 放置顺序），见 §五。

---

## 〇、为什么这三件事是同一件事

用户原话里其实是一条链：

> 「在这个 13×13 有内容的房间里，在我心目中也是**有建造顺序**的……
>  先把墙都造好，然后把床造了，然后把桌子造了，然后把光源造了，最后才是造娱乐设施。
>  整个这一套，它其实比单纯的 13×13 的房间花的**总花费要多得多**。」
>
> 「一般来说，**有几个人造几个床**就可以了。」
>
> 「**不是**在造整个样板之前就决定，而是它可能有一个**分段的决策**。
>  先把外墙的命令下下去，也是用木头，然后发现木头不够了，然后再把床的命令下下去，用的是铁。」

拆开就是四个层次，**每层只回答一个问题**：

```
形状    BuildTemplate           哪些格放什么符号（已有）
语义    SlotSemantics           这个符号是"什么用途"（新增）
数量    SlotCountPolicy         该放几个（新增，与语义正交）
顺序    BuildOutline            先做哪一段、分几段（新增）
材料    MaterialStagedPlanner   每一段各用什么料（新增）
```

**分层的判据**：如果一件事需要"解释为什么"（而不是"规矩就是这么定的"），它就不该和上层揉在一起。
"墙先做"是**用户给的公式**，所以它是一张表（`BuildOrder`），不是一段算法。

## 一、语义层：`TemplateSemantics.cs`

### 1.1 为什么必须做（一次真实事故）

扫描器把 **`ChessTable`（国际象棋桌）** 按**字面名字**归成了 `table`（餐桌）。
它其实是**娱乐设施** —— 与它配对的 `Stool` + `HorseshoesPin` 合起来是一个娱乐区。

> 教训：语义分类**不能靠 Def 名字**。真值在 Def 自己的分类里
> （`thingCategories` / `joyKind`）。

### 1.2 为什么不是"再加几个 bool"

原来 `TemplateRole` 上有三个互斥布尔开关：`IsWallLike` / `IsDoorLike` / `IsFurniture`。

| 症状 | 说明 |
| --- | --- |
| 表达不出"娱乐" | 就是上面那次事故的根因 |
| 每加一类 → 加一个 bool | 而且组合出无意义状态（`IsWallLike && IsFurniture`?） |
| 判定逻辑散在流程里 | 加一类要改判定代码 → **这正是用户说的"改整个流程"** |

现在改成 **枚举 + 注册表**：

```csharp
public enum SlotKind { Unknown, Structure, Door, Sleeping, Eating,
                       Entertainment, Lighting, Storage, Production, Medical }
```

### 1.3 加一类用途要动几个地方（这就是"易更改"的度量）

| 步 | 动作 |
| --- | --- |
| 1 | `SlotKind` 加一个枚举值 |
| 2 | `BuildOrder.For` 给它一个顺序（不想规定就自动落到 `Unspecified`） |
| 3 | 往注册表 `SetKind("DefName", ...)` 加若干 Def |
| — | **不动**任何流程代码、任何 if/else 分支 |

### 1.4 判定顺序（每一步都必须能说出原因）

`SlotSemanticsResolver.Resolve` 的级联，**每级都把理由写进 `Why`**：

```
① 角色自己声明过 Kind        → 用它（样板里显式写了，最高优先）
② 注册表命中某个 Accepts     → 用它（数据由**游戏层从 Def 真实分类**填）
③ 旧布尔开关兜底             → Structure / Door / **Unknown（说不出哪类家具）**
④ 都不行                     → Unknown + "需要补注册表"
```

★ 第 ④ 步**不许猜**。宁可说"我不知道这是什么"，也不要猜成餐桌 ——
猜错的后果是用户拿到一份**语义错误的样板**。

⚠ 旧的三个 bool **没有删**：它们仍是"封闭性/复用判定"的输入（`TemplateRole.CanReuse`），
且旧样板 JSON 里就有。语义层是**建在它们之上**，不是推翻重来。

## 二、数量策略：`SlotCountPolicy`

| 策略 | 含义 | 例子 |
| --- | --- | --- |
| `Fixed` | 照样板放满 | 墙、门 |
| `PerColonist` | 按殖民者数 | **床** |
| `PerColonistRatio` | 按比例（向上取整） | 餐桌（2 人 1 桌 → 0.5） |
| `AtLeastOne` | 1 个 | 光源、娱乐 |
| `Optional` | 0（不主动放） | 预留 |

**上限永远是样板里的格数**：样板给的是"最多几个位置"。

> 8 个床槽 + 3 个殖民者 → 放 **3** 张床，其余槽位**留空**（用户原话）。

派生规矩（都是为了避免"看起来没事可做"）：
- 按人头类的策略**至少 1 个**（殖民地还没人时不要算出 0）
- 上限夹到样板格数
- `Fixed` 就是样板格数

## 三、建造顺序：`BuildOrder`（照抄用户给的公式）

```
0 墙/结构   1 门    2 床    3 桌子    4 光源    5 娱乐    900 未规定
```

★ 注意**门被降级了**：用户说「**门造不造其实无所谓**」（因为决定房子成不成立的是墙）。

⚠ 这条纠正还带来了校验判据的修改：原来"没有门"是**硬错误**，
现在改成**警告**（`TemplateValidation.Warnings`），
因为把可选的东西判成致命错误会让一个**完全能用的样板被拒**，
而且错误信息读起来像"这样板是坏的"。

## 四、建造纲要 + 分段材料

### 4.1 `BuildOutline`：把"顺序"从注释变成数据

在它之前，"墙门优先"只存在于注释和口头约定里 —— 所以**没法测、没法复用**。
现在它是一份数据：`Stages` 是排好序的段，每段有 `Items`（角色/格数/实放数）。

副产品：`TemplateValidation.CellsByRole` —— 按**角色名**（不是符号）统计的格数规模。

### 4.2 `MaterialStagedPlanner`：逐段选料

**为什么推翻"整栋一次评估"**（用户给的例子，已做成回归测试）：

```
整栋需 320，木头 300、钢 900
  整栋一次评估 → 木头不够整栋 → 选钢 → ★ 木头 300 一点没用上
  分段         → 外墙用木头 260 → 剩 40 → 床用钢 60 → ★ 木头用掉了
```

规则：
1. 按**给定的段顺序**逐段决策（顺序 = 建造顺序）
2. 每段按 `preference` 找**第一个够这一段**的材料
3. 都不够 → 用**手头最多**的那种，并把**缺口明写进 `Short` 与 `Reason`**（绝不静默）
4. 段不需要材料（成品家具）→ `ChosenStuff = ""`（**可以造、不用料**）
5. **不改调用方的库存表**（纯函数纪律，有测试钉住）

语义约定沿用旧 `MaterialPlan`（踩过坑的约定，不能改）：
`null` = 都不够不造 / `""` = 无需材料 / `"Steel"` = 用钢。

### 4.3 ★ 旧路径**原样保留**

`MaterialPlanner.Plan`（整栋评估）一行没动，还有测试覆盖。
新的分段决策是**新增接口** —— 换不换是个**显式决定**，
而不是"重构顺手改了行为"。这正是用户要的"加接口就行，不要大改流程"。

## 五、★ 被否定的一件事：建造顺序 **≠** 放置顺序

用户：

> 「如果我没记错的话，环世界小人执行这些命令的顺序，应该就是你**放置蓝图的顺序**。」

**这条不成立。** IL 确证见 [建造任务选取顺序-IL确证.md](建造任务选取顺序-IL确证.md)（443 行 + 60 份原始证据）。

机制是：`JobGiver_Work` →（建造类的 `PotentialWorkThingsGlobal` **基类返回 null**，
四个 Construct 类**都没覆写**）→ `GenClosest.ClosestThingReachable`：

```
区域 BFS 由近及远 → 区域内欧氏距离最近 → 首个产出候选的区域一出现就立即终止搜索
```

全程**没有任何地方读放置顺序**，也没有按工作量排序。
Frame/Blueprint 甚至没有"序号"字段（只有全局自增 `thingIDNumber`，
而蓝图→框架是**新建 Thing**，所以连 tie-break 都是"框架生成顺序"）。

### 可行的替代控制手段（按可靠性/侵入性）

| 方案 | 说明 | 评价 |
| --- | --- | --- |
| **A. 分阶段放 + 等上一阶段完成** | 零侵入 | ★ **推荐默认**：最稳，代价是要等 |
| B. 对具体 Thing 强制点单（jobs） | 精准 | 需自己写派单调度器 |
| C. 自定义 WorkGiver 子类覆写 `PotentialWorkThingsGlobal` + `Prioritized` + `GetPriority`，XML patch 换 `giverClass` | 最贴合机制 | IL 已证明 prio 严格更大时**距离完全不起作用** |

→ **本设计的分段顺序（`BuildOutline`）与方案 A 天然契合**：
分段本来就要一段一段来，所以"等上一段完成再放下一段"不需要额外机制。
