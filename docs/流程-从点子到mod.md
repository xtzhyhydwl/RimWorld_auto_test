# 从点子到 mod：流程（**本项目案例版**）

> ⚠️ **方法的权威已迁至 skill：`.dsh\skills\rimworld-mod-pipeline\`**
> （`SKILL.md` = 骨架与 Gate；`阶段详法.md` = 每阶段怎么做；`环境陷阱.md` = 工具失效模式）
>
> **本文保留的是本项目的具体案例与教训**（共享单车这条线），作为**例证与项目记录**。
> 两者冲突时，**以 skill 为准**——本文含大量"当时以为对、后来被推翻"的过程内容，**不要当作方法来源**。

> **这份文件是框架，不是经验集。** 目的是：下次有一个点子时，不用从零想"下一步该干什么"。
> 适用：RimWorld mod（增加物品、增加机制类）。其它工程可借用骨架。
>
> 读法：**阶段 0→7 顺序走，每阶段有 Gate；Gate 不过就不进下一步。**
> 附在每阶段里的"踩过的坑"是**该阶段特有的**，不是通用清单。

---

## 全景

```
0 意图澄清 ──► 1 约束与许可 ──► 2 机制侦察(静态) ──► 3 可行性裁决
                                                          │
                                        ┌─────────────────┘
                                        ▼
                                   4 设计(施工图) ──► 5 地基探针(真实游戏)
                                                          │
                                                          ▼
                                   6 产品代码(6.1…6.6) ──► 7 验收与发布
```

**两个"环"**（不是直线）：
- **3 → 4 会回退到 0**：如果可行性裁决发现某件事做不成，**可能是需求要改，不是设计要改**
- **5 → 3 会回退**：探针推翻假设 ⇒ 更新未确证清单 ⇒ 可能回到设计

---

## 阶段 0：意图澄清（**用"拷打"完成，不要自由聊天**）

**输入**：一个点子（一句话，通常模糊）

### 方法：设计树 + 轮次拷打

> 本仓库有 `grilling` skill，就是这套方法。**用 skill，不要凭感觉聊。**

把需求看成一棵**设计树**：每个决定会分叉出依赖它的决定。按**轮次**推进：

- **frontier（前沿）** = **前提都已确定、现在就能问**的那些问题
- **一轮只问前沿**：把前沿上**所有**问题**一次问完**，每条**编号**，并**给出你推荐的答案**
- 用户答完一轮，前沿向外扩 ⇒ **重算前沿**，问下一轮
- ⚠️ **一个问题的答案依赖另一个本轮还没答的问题 ⇒ 它属于后面的轮次，不要塞进本轮**

**取证是执行方的活，不是用户的活。** 需要环境事实（文件、工具、游戏行为）时**派子代理去查**，不要问用户能查到的东西。正在查的事实只阻塞依赖它的那几条问题，**其余前沿照问**。

**结束条件**：**前沿为空**——每条分支都走到了，没有任何东西是"默默假定"的。
**前沿空之前，不许开工。**

### 前沿上至少要有这几个问题

1. **要"效果"还是"这个东西"？** ← **最基础的一问，跳过它后面全白做**
   - **效果** = "玩家/小人获得某个结果"（更快、更多、更强）
   - **这个东西** = "地图上/系统里真实存在某个实体，它的状态由使用过程长出来"
   - **效果几乎总能更简单地实现**（改数值、加特性、加装备、加建筑）。
     **只有"这个东西"才要求实体、才值得付复杂度。**
2. **一句话说清玩家会看到什么**（玩家视角，不是实现视角）
3. **不可替代性**：同样的效果有没有更简单的实现？如果有，**为什么还做这个？**
4. **平衡支点**：它凭什么不会太强？
   （稀缺性？位置成本？时间成本？代价？—— **答不出来，这个设计大概率会破坏平衡**）
5. **明确"不做"**：划出范围之外的东西（防范围蔓延）

**产出**：`docs/<mod名>-设计意图.md`，**≤1 页，不含任何实现细节**

**Gate**：能用一句话回答「**提供什么 / 凭什么值得做 / 凭什么不破坏平衡**」，**且前沿为空**

**失败形态**：用"自由聊天"代替拷打 ⇒ 关键分叉没被问到
（真实案例：共享单车做到"准备写码"时，才发现"**要东西还是要效果**"从未被明确回答，项目在此转向。
**这个问题在第 1 轮前沿上，本来一问就能问出来。**）

## 阶段 1：约束与许可

**做什么**：

| 项 | 要查什么 |
| --- | --- |
| **依赖** | 要依赖别人的 mod 吗？**先查它的许可**：能不能改、能不能再分发。`CC BY-NC-ND` 类 ⇒ **只能依赖，不能修改或再分发** |
| **自己的许可** | 打算用什么？影响能不能用别人的代码/素材 |
| **发布渠道** | Steam 工坊的 "Required Items" 与 `About.xml` 的 `modDependencies` **是两回事，都要写** |
| **目标版本** | 当前稳定版是哪个？跨大版本（如引擎换代）怎么留位？ |
| **素材/AI** | 美术从哪来？有没有披露义务？ |

**Gate**：**没有一条约束能一票否决当前设计**

**失败形态**：设计做完才发现许可不允许 / 依赖不可分发

## 阶段 2：机制侦察（静态取证）

**输入**：阶段 0 的设计意图

**做什么**：列出这个功能要用到的**每一个**游戏机制，逐个取证：

- 类型 / 方法 / 字段：**存在吗？全名是什么？签名是什么？**
- Def 的**字段名**与取值域（XML 写错通常只报红字、不报编译错）
- **有没有原版先例**（有先例 = 风险低；没有先例 = 高风险信号）
- **挂载点性质**：是 `public virtual`（0 补丁）还是必须 Harmony？

**产出**：**符号台账**（append-only 台账，例如 `docs/<mod名>-机制真值表.md`）

每条至少含：
```
符号（全名）| 签名 | 确认级别（实测/IL确证/转述/未确证）| 来源（文件:行 或 取证目录）| 反例（如果曾被误写）
```
并且**单独维护一份"不存在"清单** —— 它和"存在"一样重要：
**"`Verse.MinifiedThing` 不存在、`RimWorld.MinifiedThing` 才对"这类知识，猜是猜不出来的。**

**Gate**：设计要用到的符号**全部有条目**（确证 / 未确证 / 不存在，三者之一）

**本阶段铁律**：

1. **关键结论必须用第二个独立仪器复算。**
   用错工具会得到**看起来完全合法**的假结论——本次多次发生。
2. **先知道工具的失效模式**，再信它的输出。（清单见附录 A）
3. **追不到证据的，只进"待确证"，不许进正式节。**
4. **反例要留着**。它防止下一个人（或下一个你）写出同一个错。

**失败形态**：单一工具的假阴性被当成事实（"这个类型不存在"其实是被工具静默丢弃了）

## 阶段 3：可行性裁决

> **这是最容易漏掉、代价最大的一步。**
> 它的作用：把"我知道很多"变成"**我明确知道自己哪几件事没把握**"。
> **它和阶段 5 是同一件事的两端：这里负责「列出」，阶段 5 负责「变成事实」。**

**做什么**：读台账，把每个**还不确定**的点列出来，逐条判定：

```
未知量 | 现在是"猜"还是"确证" | 猜错的后果 | 怎么才能确证（读代码? 跑一次?）
```

**后果分三档**（这是排序依据）：

| 档 | 含义 |
| --- | --- |
| 🔴 **重构级** | 猜错 ⇒ 架构要改、要重写核心 |
| 🟡 **返工级** | 猜错 ⇒ 某个模块重写，但架构不动 |
| 🟢 **改名级** | 猜错 ⇒ 改个名字/改个数值 |

**产出**：**未确证清单，按后果排序**

**Gate**：**没有任何 🔴 重构级项**
- 有 🔴 ⇒ 二选一：**先解决它**，或**改设计绕开它**
- **绝不允许带着 🔴 进阶段 4**

**怎么做这一步（本次验证有效的方法）**：
> 找一个**完全不知道这个项目**的代理，**只给它文档**，让它回答：
> - 「照这些文档，你能写出实施方案吗？」
> - 「**哪里你必须猜？猜错会怎样？**」
> - 「哪里你读到了两个不同说法？」
>
> **作者本人做不了这件事**——缺口在读者脑子里，而作者不缺任何东西。

**失败形态**：把"读了很多文档"误当成"没有未知量"

## 阶段 4：设计（施工图）

**做什么**：写施工图

**要求**：

1. **决策与证据分层**
   - 施工图 = **只放当前结论 + 指向台账的引用**
   - 证据、反例、更正历史 = **放台账**（append-only）
   - 理由：混在一起时，读者分不清"这是当前真相还是历史反例"
2. **假设必须标"假设"**；**每个数字标来源**：`实测` / `取自 <文件:行>` / `假设`
   （真实案例：一个阈值依赖凭空假定的参数，**活过多轮评审**，最后只有实验能抓出来）
3. **代码片段标"未执行"**，跑过之后再改成"已执行 + 证据"
   （真实案例：施工图里的示例代码给一个没定义 `stuffCategories` 的 def 传了 stuff，
   而且让同一个 def 兼作两种用途 ⇒ 真跑起来两条红字。**是探针照抄它才暴露的**）
4. **跨文档引用只用「文件名 §节号」，不用行号**
   （行号在并发修改下不稳定，而且不同读取器对裸 `\r` 的处理不同 ⇒ 行号会静默分裂）
5. **每个挂载点标注**：`public virtual`（0 补丁）还是必须 Harmony
6. 明确列出**必须打补丁的位置**——补丁数量直接决定跨版本升级的崩溃风险

**Gate**：**阶段 3 的那套"空上下文读者"能照它写出方案，且它"必须猜的"里没有 🔴**

## 阶段 5：地基探针（真实游戏内）

> **它不是"验收"，是"刺探"。**
> 阶段 3 负责**列出**你不知道的事，阶段 5 负责**把它们变成事实**——**同一件事的两端。**
> 所以它的产出**不是"通过 / 不通过"，而是"设计需要改什么"。**

**做什么**：写一个**用完即弃**的最小 mod，把阶段 3 的 🔴/🟡 未知量**变成事实**。

**探针承担三类任务，反馈去处不同——不要混：**

| 任务 | 例子 | 答案是"不能"时怎么办 |
| --- | --- | --- |
| **(a) 能不能** | 这个机制游戏到底支不支持 | **先改设计**；设计改不动 ⇒ 才回退到阶段 0 改需求 |
| **(b) 是多少** | 某个耗时 / 阈值 / 容量 | 填进设计，**不影响可行性** |
| **(c) 怎么样** | 观感、手感、平衡感受 | 回写设计（可能要调数值或改交互） |

**环路：4 → 5 → 4。** 探针**几乎总会改设计**，这是正常的，不是失败。
只有当 **(a) 的答案是"不能"且设计改不动**时，才回退到阶段 0。

**要求**：

1. **每项一个可观测判据**（看哪个字段、哪行日志、哪张截图）
2. **尽量给每项配一个"阴性对照"**
   （把该实现旁通掉，重跑同一场景）
   > **这是把"它工作了"变成"它因为 X 才工作"的唯一手段。**
3. **自检本身也要有对照**：故意验一个不存在的东西，确认自检会报错
   （否则"自检通过"毫无意义）
4. **探针代码不得被产品代码 import**；跑完销毁（把销毁清单写进接力文件）
5. 结论**回写台账**并标【运行时实测】

**Gate**：**所有 🔴 项都已变成事实**（结论可以是"能"/"不能"/"能但代价是 X"），**且设计已按事实更新**

**什么时候可以省这一步**：阶段 3 没有 🔴 项、且所有未知量都是 🟢 改名级

**失败形态**：探针范围失控 ⇒ 变成"写了个迷你版产品"而没测到关键点

**本次正面案例**：
- 探针**自己抓到了作者的错**——框架的 `PatchAll()` 在没有注解时**不抛异常、什么都不挂**。
  如果直接写产品代码，会带着"补丁已挂"的错觉走完整套设计。
- 阴性对照证明了"车没丢"**确实是因为那个前缀**。

## 阶段 6：产品代码（分小步，每步有 Gate）

**顺序（接口先行，别一次写完）**：

| 步 | 做什么 | Gate |
| --- | --- | --- |
| 6.1 | **骨架 + Def**（清单、依赖、能加载） | 游戏里能加载，能生成出这个物体 |
| 6.2 | **承重行为**（这个 mod 的核心那一件事） | 核心场景**无人干预**能自动跑通一次 |
| 6.3 | **边界与解绑**（死亡 / 离图 / 被俘 / 地图卸载 / 读档 / 传送…） | 逐条走完触发点清单，每条之后回读状态 |
| 6.4 | **存档往返** | 存档 → 退出 → 读档，状态与存档前一致 |
| 6.5 | **贴图**（可并行、可后置） | 见下 |
| 6.6 | **发布准备** | 见阶段 7 |

**贴图的工作方式（按实际分工）**：

**先留占位图 + 冻结「像素尺寸 / 锚点 / 方向数」**，让逻辑线先跑通；美术（或本人）后补图。
**关键契约**：后补的图必须**同尺寸、同锚点、同方向数**
⇒ **替换 = 纯文件替换，不改任何 XML**。

⚠️ 两个硬要求：
- **占位清单必须登记**，发布前"归零"是硬 Gate（否则会把借来的原版贴图发布出去）
- **像素密度一旦冻结就不要中途改**（上游改了、下游所有已出的图全废）

**每步的铁律**：

1. **回读状态确认，不要相信"调用成功"。** 接口返回成功只说明调用返回了。
2. **变化驱动，不是时间驱动。** 等一个**可观测条件**成立，不要 `sleep`。
   （固定等待既不是必要条件也不是充分条件，而且它把"等够了没有"变成不可观测的东西）
3. **改了就立刻在游戏里验。** XML 常可热重载，C# 一般要重启——按这个决定批次。
4. **边界清单要穷举着走**，不要只测"正常路径"。

## 阶段 7：验收与发布

> **验收的主体是自动化测试，不是人。**
> 需求分析绕不开、编码现在也快，**所以最大的卡点是"验收能不能提效"**。
> **自动化测试设计得越好，需要人工补的部分越少——这是最该优化的方向。**

### 7.1 自动化验收（**先做，覆盖面尽量大**）

- 每条判据必须**可观测 + 可重复**（看字段 / 看日志 / 看结构化返回 / 看截图）
- **判据要在写代码之前定下来**（"预注册"）——否则会不自觉地照着结果调判据
- **等条件成立，不等时间**（变化驱动）；**每步回读**，不信"调用成功"
- **每遇到一条"人要去看一眼"的判据，追问一次：「这个能不能变成可观测字段？」**
  —— 每变一条，人工验收就少一条

### 7.2 人工验收（**只做自动化做不到的**）

- 范围：观感、手感、平衡感受（"骑着顺不顺"、"是不是太强"）
- **把人工部分当成"自动化测试的缺口清单"**：每发现一处"这个本该自动测出来"，
  **回头把它补成自动化判据**（这样下一次的人工部分就更小）

### 7.3 发布准备

- 许可文件齐备
- **依赖声明**（`About.xml` 的 `modDependencies` + 渠道的 Required Items —— **两回事，都要写**）
- **占位资源归零**（占位贴图、占位 def、调试开关）
- **探针 / 实验代码零残留**（源码、Defs、链接、配置、产物）
- 跨版本留位（如双目标框架）

**Gate**：自动化判据全过 + 人工部分无遗留 + 无占位资源 + 无实验残留

# 横切纪律（每一步都适用）

1. **事实要有来源**；数字标 `实测` / `取自 <文件:行>` / `假设`
2. **关键结论要有第二个独立来源**
3. **"不报错"不等于"发生了"** ⇒ 回读 + 阴性对照
4. **坐标用节号，不用行号**
5. **写入结构化内容后，断言一个与语义无关的不变量**（行数/列数/字符计数/字节数）
   —— 写入通道可能静默改写内容（竖线、行尾）
6. **长内容写文件，对话只留决策与下一步**
7. **子代理**：写文件 + 回报"路径 + ≤200 字"；提示词自包含；**要求它区分"实测"与"推测"**
8. **"做不到"要先排除前置条件**，再下结论
   （本次：UI 缺 hover 前置、工作台没通电、地面资源默认禁止——三步各伪装成"功能不存在"）

# 附录 A：工具失效模式（不记住就会得到假结论）

| 现象 | 真相 |
| --- | --- |
| 反编译器输出空白 | 可能是**含默认接口成员（DIM）的类型被静默丢弃**，不是"类型不存在"。**且不是固定名单** |
| 调用点扫描返回 0 | 可能只是**过滤器语义不对**（有的要求全名精确相等，有的支持子串） |
| IL 输出看起来像"直筒式" | 该打印器可能**把分支指令丢掉了** ⇒ **凡结论是"没有别的路径/无条件"的，必须换一个保留分支的解码器复核** |
| 输出文件是空的 | 可能是**过滤器写错导致静默输出空文件**（不是"没有这个类型"） |
| 对 mod 程序集整体失效 | 可能是缺依赖程序集（mod 引用了开发环境里没有的 DLL） |
| 特性扫描 0 命中 | **可能是假阴性**——有的 mod 不用注解，运行时手工注册 |
| 用 `>` 重定向写文件 | 可能是 **UTF-16**，不是 UTF-8 |
| **行数对不上**（同一个文件两个工具报不同的行数） | **默认读取器的编码假设**。实测：`Get-Content`（不带 `-Encoding UTF8`）读 **UTF-8 无 BOM 的中文文件**会**静默少算约 30% 的行**（3/3 份文档中招）。**行号只能信 `[IO.File]::ReadAllLines` 或显式 `-Encoding UTF8`**；文件真实行数应以 **LF 字节数**为准 |

# 附录 B：游戏内前置条件清单（漏一步就会误判成"功能不存在"）

```
① 地面资源是否可用（很多开局默认是"禁止"状态）
② 目标建筑是否放好
③ 目标建筑是否通电（开发者选项里的"无限电力"未必真的供电）
④ 界面操作是否有前置步骤（例如点击前需要先悬停）
⑤ 相关工作类型是否已开启
```
