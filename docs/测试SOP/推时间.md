# 推时间：选哪个手段、推多少、怎么证明真的走了

> 时间只按 tick 推进，每次推进都要能用返回值证明「真的走了」。
> 本文件的速度数字都是 **2026-10-24 本机实测**；换机器先重标定（见 §2.2），不要沿用。
> 环境类数字（帧率、激活 mod、时间速度上限、日志路径）**不要照抄本文件**——跑 `node src/cli.js env-check --profile <p>` 取本次值
> （字段含义见 [环境探针](环境探针.md)；2026-10-24 已落地并真机验过）。

## 0 三种手段

| 手段 | 调用形状 | 速度（实测） | 什么时候用 |
| --- | --- | --- | --- |
| `step_game_ticks` | `{ticks, pauseFirst:true, timeoutMs}` | **精确但慢**：**每帧 1 tick**（`advancedFrames == advancedTicks`）⇒ 吞吐 = 帧率。**600 tick = 6010 ms ≈ 100 tick/s**（另三段 6007 / 6024 ms） | 要**精确 tick**、要把 `advancedTicks` 当断言 |
| `play_for` | `{durationMs, speed:'Fast'}` | **按墙钟，tick 不精确**：Fast `durationMs:1000` → **182 tick**（≈182 tick/s）；600 ms → 112 tick、800 ms → 144 tick | **长跑**、需要真实跑帧（刷渲染） |
| `set_time_speed` | `{speed:'Paused'|'Normal'|'Fast'|…}` | 只改速度，不推进 | 只调倍速；推时间仍靠上面两种 |

- `play_for` 的 `speed` 接受 `Normal|Fast|Superfast|Ultrafast`（`runs/tools.json` schema 原文）。
  **本轮只实测 `Fast`**；`Superfast` / `Ultrafast` **未实测**，这里不写数字。
- 仓库策略：推时间速度**上限仍是 `Fast`**（取向是宁可慢、不拿漏事件换时间）。
  `Superfast` / `Ultrafast` / `ultraSpeedBoost` / `forceRequestedSpeed` **要用户当次同意**。
- `rimworld/play_until_letter` 也在工具表里，但它默认 `speed:4`（= `Ultrafast`）且默认带 boost ⇒ **不在默认可用范围**，本轮未实测。

## 1 推之前：三个前置

1. `get_ui_state.windowsForcePause === false`。为 true 时 `play_for` 会静默 0 tick（报文里只有一句 `Game was paused externally`，`success` 有时还是 true）。
   常见强制暂停窗口之一是主菜单：`close_main_tab{tabId:'main-tab:Menu'}`。注意两个工具的参数名不同——`close_main_tab` 收 `tabId`，`open_main_tab` 收 `mainTabId`。
   究竟当前有哪些窗口、窗口类型是什么，读 `get_ui_state` / `get_screen_targets` 本次返回，别背清单。
   【未验证】`step_game_ticks` 能不能穿过强制暂停：本轮**没有造出**强制暂停窗口，旧文档里「step 能穿透」这句话没有实测支撑，当**未知**处理（真遇到就先关窗口）。
2. 地图就绪。刚开完殖民地时 `step_game_ticks` 可能 `status=failed` 且 0 tick（`readiness=mapData` 只保证数据就绪）：
   推之前挂一次 `rimbridge/wait_for_game_loaded{readiness:'currentMap', pauseIfNeeded:true}`，失败就重试（`src/smoke.js` 就是这个模式）。
3. 推完要回读什么，先想好（见 §4）。

## 2 推的时候：四条纪律

1. **`step_game_ticks` 一律显式给全三个参数**：`{ticks, pauseFirst:true, timeoutMs}`。
   - `pauseFirst:false` 不是"先不暂停"，而是把"游戏得先暂停"的责任交给调用方；缺省时实测三次全 failed、0 tick。
   - 工具级 `timeoutMs` 默认 10 000：实测 `{2000,pauseFirst:true}` 不传 `timeoutMs` ⇒ 10017 ms 后 `status:timedout`、只走 **999/2000**。
   - **`timeoutMs` 是硬顶**：3000 tick 在 `timeoutMs:30000` 下仍 `status:timedout`、只走 **2996**。这是实现硬顶，不是估算问题——请求越多，越必须留足。
2. **预算按实测 ≈100 tick/s 算，留 100% 余量**：`timeoutMs ≈ ticks / 100 × 1000 × 2`。

   | 请求 tick | 纯推进（≈100 tick/s） | 建议 `timeoutMs` |
   | --- | --- | --- |
   | 600 | ≈6 s（实测 6.0–6.1 s） | 12 000 |
   | 1 200 | ≈12 s | 24 000 |
   | 3 000 | ≈30 s（实测 30 s 内跑不完） | 60 000 |
   | 6 000 | ≈60 s | 120 000 |

   慢帧机器上 100 tick/s 会更低 ⇒ **每段都看实际耗时**，出现「耗时接近 `timeoutMs`」就把余量加大、把段切短。
3. **判据是 `advancedTicks`，不是 `success` / `status`**：跨游戏天边界可能 `status=failed` 但推进有效；实测 `step_game_ticks` 请求 3000 得 `success:false` + `advancedTicks=2996`。按 `advancedTicks` 累计。
4. **分段**：每段显式 tick 数，段间回读业务字段 + 查新事件；不要一次推一大段再回读。

### 2.1 段长怎么定（最要紧）

- **段长不由"速度"决定，由被测事件可能的最小间隔决定。** 速度只决定「这段要花多久」。
- 现在的"停下来"**不是硬件触发**：靠 agent 轮询读到（`live --until` / `wait`）再下 `rimworld/pause_game`。
  ⇒ 从"事件发生"到"游戏真的暂停"之间有一段**盲窗**：一次工具往返 + 轮询间隔 + 人/agent 决策。
  段越长，盲窗覆盖到的 tick 越多，越可能**整段吞掉事件窗口**（事件发生了、后续 tick 把状态又推过去了，回读看不到）。
- 默认 **600 tick/段（≈6 s）**：本轮 5 段全部 600/600，成本 ≈6 s/段，可控。
- **窗口敏感用例 100–300 tick/段**：跨天边界、信件/事件刚触发、短 job（搬运、进食、开门）、任何"只在几十 tick 内可见"的状态。
- **宁可多分几段**：多一段只多一次工具往返（秒级），漏一次事件要整轮重跑。
- 分段不等于安全：段内事件仍可能被吞。真正要卡时间点，用**事件驱动**（`live --until` 挂后台 job）而不是"推完再看"；见 `日志与事件取证.md`。

### 2.2 换机器先标定

跑一段 `step_game_ticks{600,pauseFirst:true,timeoutMs:12000}`，取返回值里的 `advancedTicks` / `advancedFrames` / `DurationMs`（`19-step600-ce.json` 就是这三个字段）：

- `advancedFrames == advancedTicks` ⇒ 1 tick/帧，吞吐 = 帧率；
- `600 ÷ (DurationMs/1000)` = 本机 tick/s，用这个数重算 §2 的预算表。

## 3 推多少

| 目的 | 量 | 依据（实测优先） |
| --- | --- | --- |
| 看 pawn 走几个格 / 做完一个动作 | 600 tick 起，逐段加 | 本轮 5 段 600/600，≈6 s/段 |
| 等游戏内一天（60 000 tick） | 分段 `step`：**≈600 s**（≈100 tick/s）；`play_for` Fast：**≈330 s（估算**，按 182 tick/s 外推，未跑满一天） | 60 000 ÷ 100 = 600 s |
| 只为了让渲染跟上、准备截图 | `play_for` 400–1000 ms（≈73–182 tick） | 实测 600/800/1000 ms → 112/144/182 tick；渲染追平见 `截图取证.md` |
| 跨天/跨季节事件 | 分段 + 段间查事件（`live --until` / `runs/live/<p>.ndjson`） | 事件比 tick 更早给出信号 |

> 旧数字一律作废：`≈541–592 tick/s`、预算公式 `请求tick ÷ 400 × 1000`、"一天 60 000 tick ≈ 100 s"
> 都是按别的机型/别的口径写的，与本轮实测差 4–6 倍。

## 4 推完

- 立刻回读业务字段：位置、HP、`curJob`、`spawned` 这类都要独立回读，不拿推进返回值代替。
- 要截图或交给人看的，先 `play_for` 400–1000 ms 让真实帧跑起来（暂停态 `step_game_ticks` 之后 pawn 绘制位置不更新，2026-10-24 实测）。
- 推进结果进报告：请求 tick / `advancedTicks` / 耗时 / `status` 四列，每段一行。
