# 环境探针（`cli env-check`）

> **环境事实不写死在文档里**——机器、游戏版本、profile 的 mod 清单、端口一变，写死的"事实"就成了最大的坑。
> 每次开测**先跑一次**，把本次事实钉进自己的上下文：
>
> ```powershell
> node src/cli.js env-check --profile <p>          # 人读；exit 0 = 无阻塞项，exit 1 = 有阻塞项（不是崩溃）
> node src/cli.js env-check --profile <p> --json   # 机器读；字段即下表
> ```
>
> 只读：不 `start`/`stop`、不写文件、不推时间。桥接不通只把相关项降级成 `unknown`，整条命令不崩。

## 1 字段 → 含义 → 什么算合格

| 输出行 | 字段（`--json`） | 含义 | 合格 |
| --- | --- | --- | --- |
| 结论 | `verdict.ok` / `verdict.blockers[]` | 所有阻塞项的合并判定 | `ok:true` 才开测；`false` 时**`blockers[]` 就是"照着做什么"**（每条是一句可直接执行的动作），不另写诊断 |
| 进程 | `process.running` `pid` `identityOk` `cmdlineHasProfile` `runningState` | 本 profile 的实例是否在跑；身份判据 = 命令行含 `-savedatafolder=…\profiles\<p>` | 开测前 `running:true` + `identityOk:true`；`runningState` 是三态，`unknown` 是判据不足，别读成 false |
| 桥接 | `bridge.reachable` `resolutionOk` `host` `port` `source` `reason` | 归属校验 + 握手；`source` 说明端口从哪来（记录/日志/prefs） | `reachable:true` 且 `resolutionOk:true`；`resolutionOk:false` ⇒ 端口上答话的是**别的实例**，别连 |
| mods | `mods.activeModsCount` `baseModsRequired` `baseModsMissing` `baseModsNote` `loadedInSession` | 清单里的激活数 + 底座差额（真源 `base-mods.json`）+ 本次会话真加载的 | `baseModsMissing:[]` 且 `activeModsCount` 已知；`loadedInSession` 只在连上桥接时有效（未连时是空列表，不是"没加载"） |
| 加载顺序 | `loadOrder.queried` `restartRequired` `sessionMismatchCount` `orderingIssues[]` | 运行中实例对 mod 配置的看法 | `queried:true`、`restartRequired:false`、`orderingIssues:[]` |
| 能力 | `capabilities.gameLinkEvents` `characterEditor` `ceToolCount` `toolCount` | 本次能不能用事件 / 摆读小人 / `ce/*` 反射 | 按需项缺了也停手：要用就必须 `true` / 非 `null`；`ceToolCount:null` = 没连桥接，**不等于**没有 ce 工具 |
| 时间 | `time.windowsForcePause` `timeSpeed` `paused` `policyMaxSpeed` | 推时间的前置事实 | 推时间前 `windowsForcePause:false`；`policyMaxSpeed` 恒为 `unknown`（速度上限是 AGENTS.md 硬约束 6 的约定，代码不替文档猜值） |
| 登记表 | `registry.scenarios` `byLevel` `errors[]` | 条件登记表的规模与错误 | `errors:[]`；有错就 `node src/cli.js wait --list` |
| 路径 | `paths.profileDir` `screenshotsDir` `eventsFile` `recordPath` `logFile` | 本次证据该去哪取 | 照抄进报告，不要自己拼 `runs/` 路径 |
| 限制 | `limits.stepGameTicksTicksPerFrame` `measuredTicksPerSecond` | 引擎事实：tick/帧是实测，tick/s 要自己标定 | `stepGameTicksTicksPerFrame:1`；`measuredTicksPerSecond:null` 是正常（env-check 不推时间） |

## 2 没有实例在跑时，正常输出长这样（**设计行为**；**数值随环境变，这里只是形状**）

`env-check` 在没有游戏时照样完整输出，并把"该做的事"写成阻塞项；它**不会**为了查到东西去启动游戏。下面是 2026-10-24 本机 `voiced` 的一次实测——**读形状、别对数字**（`pid` / 端口 / 时间戳 / 激活数 / 场景数都会变）：

```
$ node src/cli.js env-check --profile <p>
env-check profile=<p>  <ISO 时间戳>
  结论     ✗ 1 个阻塞项（退出码 1，不是崩溃）
  进程     running=false pid=<数> identityOk=false cmdlineHasProfile=false runningState=not-running
  桥接     reachable=false resolutionOk=false 127.0.0.1:<port> source=record
           原因：归属校验未通过：PID <数> 不存在
  mods     activeModsCount=<数（随 profile 变）> 底座 11 个、缺 0 个 本次已加载=unknown（未连桥接）
  加载顺序 queried=false restartRequired=- 问题 0 条
           原因：桥接不可达，未查询（原因见桥接项）
  能力     GameLink 事件=true CharacterEditor=true ce/* 工具=- 工具总数=-
  时间     windowsForcePause=unknown timeSpeed=unknown paused=unknown 速度上限=unknown（AGENTS.md 硬约束 6）
           原因：桥接不可达，没查到时间速度（原因见桥接项）
  登记表   <数> 个场景 {"wait-verified":<n>,"field-verified":<n>,"inferred":<n>}，错误 0 处
  路径     profile=E:\<仓库根>\profiles\<p>
           截图=E:\<仓库根>\profiles\<p>\Screenshots
           事件=E:\<仓库根>\runs\live\<p>.ndjson
           记录=E:\<仓库根>\runs\game-process.<p>.json
  限制     step_game_ticks=1 tick/帧；tick/s=未测（不推时间）
  阻塞项（照着做就能清掉）：
    - profile「<p>」没有确认在运行的实例：要开测先跑 node src/cli.js start --profile <p>（会真起游戏、抢一次窗口焦点；先确认没在玩你自己那一局）。
```

读法：这里的 `exit 1` / `结论 ✗` 意思是**"还没开测"**，不是故障；`-` 与 `unknown` 都表示"没连上所以不知道"，不是"没有"。
**底座差额可以离线判**，所以它在没实例时依然是有效结论（上例 `缺 0 个` ⇒ 阻塞项里只有"没有实例"这一条；缺 N 个时会多一条 `底座缺 N 个：<packageId>, ……`）。

## 3 与「状态自检」的分工

skill `rimworld-auto-test-closed-loop` §2 的四项检查（桥接归属 / 底座 mod 已加载 / 加载顺序 / 按需能力）就是**本文件 §1 表的一个子集**，细节与"缺了怎么补"在 [环境自检](环境自检.md)，判据定义不在这里重复。
开测顺序：`env-check` 一次拿全事实 → 照 `blockers` 清掉 → 再跑一次确认 `verdict.ok:true` → 按 SOP 进入「起实例」。
