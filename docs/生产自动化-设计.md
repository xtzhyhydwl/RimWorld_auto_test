# 生产自动化 mod · 设计

> 目标：让 mod 根据殖民地当前状态**自动安排生产**，先在「食物」这一条线上打通闭环，
> 之后有可能升级为「AI 接管大部分生产活动」。
>
> 状态：**设计讨论中**（等 `docs/食物自动化-技术侦察.md` 的实测结论回填）
> 日期：2026-10-03

---

## 一、问题定义

### 用户诉求（原话归纳）

原版的生产管理是**手动**的，两件最烦的事：

1. **工作面板**：十几个工作类型 × N 个殖民者，用数字排优先级。生产需求一变就要重调；
   新殖民者来了默认全部工作参与、优先级全一样，还得按他擅长的东西重排。
2. **生产安排**：比如种田，其实大多数时候「AI 自动画一块地去种」就够了。

**先做局部**：针对一条线路做闭环。第一条线路选 **食物**。

### 为什么选食物当第一条线

- 指标好定义、好测量（Nutrition 是一个标量）
- 有明确的执行手段（种田、狩猎）
- 反馈周期中等（几天），可以在测试里用 tick 加速跑完
- 失败后果清晰（饿死），容易写断言

## 二、闭环的四个环节（这是整个设计的骨架）

不管上层是脚本还是 LLM，下面这四层是**不变的**：

```
   ①感知  ──→  ②预测  ──→  ③决策  ──→  ④执行
  (现在有多少)  (将来会有多少)  (要不要动手)  (去种/去猎)
       ↑                                      │
       └──────────  ⑤观测回流  ←──────────────┘
```

**关键工程原则：①感知和④执行必须是确定性的代码；②预测是纯函数；只有③决策是可替换的。**

这样一来，「上层用脚本还是 LLM」就退化成一个**局部改动**——决策层换个实现，
其它四层和所有测试都不用动。这是本设计最重要的一个决定。

### ①感知：把殖民地状态读成结构化数据

需要读的东西：

| 数据 | 用途 |
| --- | --- |
| 当前食物总量（nutrition） | 分子 |
| 殖民者数 + 每人每日消耗 | 分母 |
| 在种的作物：Def、格数、生长进度、土壤肥力、种植者技能 | 预测输入 |
| 地图上可采集的野生食物（浆果丛等） | 修正项 |
| 库存里的食物明细（按 Def 分类） | 诊断 / 长期 |
| 当前季节、温度（影响能否种） | 可行性约束 |

**统一单位：Nutrition（营养值）。**
原版换算参考：成年人类每天消耗 1.0 nutrition（📖 待实测确认）。
用 nutrition 而不是「食物个数」，因为不同食物每单位营养不同，混在一起没法算。

派生指标：

```
stock        = 当前食物总 nutrition
burnRate     = 实测的每日消耗（用最近 N 天的存量差 + 产出反推）
reserveDays  = stock / burnRate                     ← 最直观的健康度
```

### ②预测：未来 15 天的食物供给曲线

这是用户需求里最核心、也最容易做错的部分。

对**每一块在种的作物**算：

```
剩余生长天数 = (1 - growth) / 每日生长率          每日生长率取决于土壤肥力 × 温度 × 光照
成熟后产出   = 格数 × 每株产量 × 收获系数(受种植者技能影响)
```

把每块地的产出**按成熟天数摊到今天起的 15 天轴上** → 得到 `projectedSupply[d]`，d = 1..15。

再叠加：

```
projectedReserve[d] = stock + Σ(projectedSupply[1..d]) - burnRate × d
```

**`projectedReserve[]` 就是我们的被控量**，而不是「当前存量」。
这正是用户说的「现在有多少是现在的事，之后 15 天每天预计多少」。

> ⚠ **诚实的边界**：这个预测只能算「已种下的地」。
> 还没种的地是 0——而决策恰恰是去种地。所以闭环是：
> 决策 → 种下 → 下一轮预测才看见它。**预测器只负责回答"照现状走下去会怎样"**，
> 「如果我再种 X 格会怎样」是由决策层用**同一个预测函数**做 what-if 仿真来回答的。
> 这一点必须在代码里体现：预测是纯函数，可以被决策层反复调用。

### ③决策：这是唯一可替换的一层

决策层只做一件事：**给定状态和预测，输出一个"动作"**。

动作空间（action space）——先定小，后扩：

| 动作 | 参数 | 立即能用吗 |
| --- | --- | --- |
| `PlantCrop` | 作物 Def、格数 | 待侦察确认（画种植区 + 指定作物） |
| `HuntAnimal` | 目标种类、数量 | 待侦察确认 |
| `DoNothing` | — | 是 |

**决策的目标函数**（用户的「健康水平」）用一个**目标带（target band）**表达：

```
设定：targetDays = 10   （希望常备 10 天口粮）
      bandLow  = 7     （低于此开始补）
      bandHigh = 20    （高于此停止扩张，避免无限种地）

决策规则（脚本版，v1）：
  1. 用预测器算 projectedReserve[15]
  2. 找最小的 d 使得 projectedReserve[d] < bandLow × burnRate
  3. 若无此 d → DoNothing（健康）
  4. 若有 → 算缺口 gap = bandLow×burnRate - min(projectedReserve)
     然后 what-if：在候选空地上加 N 格作物，用预测器重算，取最小 N 使缺口补平
  5. 产出动作 PlantCrop(作物, N)
```

这个规则**完全可离线单元测试**（喂合成状态 → 断言输出动作），不需要开游戏。
这是选它做 v1 的核心理由。

### ④执行：真的去种、去猎

分成两个层次，按可靠性递减：

| 执行路径 | 可靠性 | 说明 |
| --- | --- | --- |
| **A. 游戏内 C# 直接调 API** | 高 | mod 自己就是游戏的一部分，直接建 `Zone_Growing`、`Designation` |
| **B. 桥接 architect designator** | 中 | `apply_architect_designator` 支持矩形，实测中 |
| **C. 驱动真实 UI** | 低 | 慢、脆，只当兜底和取证 |

**MVP 走 A**——因为 mod 本来就要在游戏里跑，直接调 API 最稳，还不依赖测试框架。
B/C 留给「测试时从外部注入动作」用。

### ⑤观测回流

每一轮决策都要落一条**日志记录**（内存环形缓冲 + 写文件）：

```
{ tick, stock, burnRate, reserveDays, projectedReserve[15], decision, reason }
```

这份日志有三个用途：诊断、画趋势图、以及**给 LLM 当上下文**（如果将来上 LLM）。
必须从第一天就有，不能后补。

## 三、顶层用脚本还是 LLM？—— 设计讨论

### 三个候选方案

| 方案 | 描述 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **S. 纯脚本** | 阈值 + 规则，全在 C# 里 | 快、确定、可回归测试、零成本 | 规则僵化；换场景要改代码 |
| **L. LLM 实时在环** | 每个决策周期把状态发给 LLM，LLM 直接输出动作 | 灵活 | 慢（秒级）、贵、不确定性破坏可回归性、调试地狱 |
| **H. 混合（推荐）** | 脚本做实时闭环；LLM 只做**策略/参数层**，并在异常时介入 | 兼顾确定性与灵活 | 需要把策略参数化 |

### 推荐：H —— 脚本在环内，LLM 在环上

**理由（这三条是决定性的）：**

1. **可回归性是本项目的立身之本。** 这个仓库的全部价值在于「跑出可信的测试报告」。
   如果决策层每次输出都不一样，回归测试就退化成「重跑一遍看看」，断言写不出来。
   → 实时决策必须是确定的。
2. **LLM 在环内有硬伤**：每次调用秒级延迟 + token 成本，而生产决策一个游戏天要算很多次；
   更糟的是**游戏主线程不能被网络调用阻塞**（桥接调用排在主线程上，会挂死整个游戏）。
3. **LLM 的真实价值在"环上"而不是"环内"**：
   - **参数/策略**：设定目标天数、目标带、作物配比、狩猎阈值
   - **异常解释**："为什么昨天突然开始疯狂种地？" → 把 ⑤的日志喂给它
   - **场景适配**：冰盖 vs 温带 vs 热带，规则要调整 —— 这是 LLM 擅长的
   - **扩线规划**：从食物扩到「食物+药品+布料」时，多目标权衡是 LLM 擅长的

**具体形态：两级时间尺度**

```
慢环（每游戏天 / 或事件触发）：LLM 或玩家  →  写策略参数 policy.json
                                              { targetDays, bandLow, bandHigh, cropMix, ... }
                                                    ↓
快环（每游戏小时）：确定性脚本  →  读策略参数 + 状态  →  动作
```

慢环的输出是一个**声明式的参数文件**，快环只是读它。这样：
- 快环永远确定、可回归、零成本
- 慢环可以随时换（人手工写、脚本算、LLM 生成），**互不影响**
- 即使 LLM 挂了/超时，快环用**上次的策略或默认策略**继续跑 —— 不会把殖民地搞崩

> **这也回答了"能不能让 Agent 接管大多数生产活动"**：能，但接管的姿态应该是
> **"Agent 当指挥官，脚本当士兵"**，而不是"Agent 当士兵"。原版游戏对「每秒都做决策」
> 的要求，LLM 顶不住；但"每天给一次战略调整"，LLM 绰绰有余。

### 什么时候值得真的上 LLM（触发条件）

先别上。满足下面任意两条再说：
- [ ] 脚本版在 ≥3 种不同生物群系跑通基础闭环
- [ ] 出现「规则写不出来、但人能一眼判断」的决策（典型：多目标权衡、危机取舍）
- [ ] 需要 mod 用自然语言解释自己的决策
- [ ] 扩到第二条、第三条线，参数组合爆炸，手工调不动

**在上 LLM 之前，先把"策略参数化"做好** —— 这是通往 LLM 的必要前置，而且它本身就有价值
（玩家可以手改参数，不用改代码）。

## 四、关于「工作优先级自动化」（用户提的第一个痛点）

**这条要单独说，因为它和食物闭环不是同一类问题。**

食物闭环是**控制问题**（被控量 + 执行器 + 反馈），工作优先级是**组合优化问题**：

- 变量：N 个殖民者 × M 个工作类型 → `priority[pawn][workType] ∈ {0..4, -1=不参与}`
- 目标：最大化某种产出（食物/建材/研究…），约束：技能匹配、专家分配、每人每天工时有限
- 规模：10 殖民者 × 13 工作类型 ≈ 130 个变量，**规模小到可以直接搜索**

**判断：工作优先级更适合"搜索/求解"而不是 LLM。**

- 目标函数可以量化（产出速率、闲置率、关键岗位覆盖率）
- 可以用**局部搜索 / 贪心 + 修复**在毫秒级求解
- 结果**可解释**（"把 A 放到种植是因为他技能 12 且现在没人种"）
- 完全可离线测试

**所以分期：**

| 期 | 内容 | 上层 |
| --- | --- | --- |
| **P1** | 食物闭环（感知→预测→决策→执行） | 确定性规则 |
| **P2** | 工作优先级自动排布 | 局部搜索 + 量化目标函数 |
| **P3** | 策略参数化 + LLM 慢环 | LLM |
| **P4** | 多目标（食物 + 药品 + 布料 + 建材） | LLM 权衡 |

P2 依赖一个关键能力：**读写工作优先级**。这大概率要写 RimBridgeServer 伴生 DLL
（现成工具里似乎没有）。待侦察确认。

## 五、MVP 范围（P1）—— 刻意收窄

**目标**：一个能自己判断"该不该多种点吃的，该种多少"的 mod，跑得起来、测得出来。

**做什么：**
- 感知：食物总量、殖民者数、在种作物
- 预测：未来 15 天 `projectedReserve[]`
- 决策：目标带规则（确定性）
- 执行：自动建/扩种植区（走路径 A，游戏内 API）
- 观测：决策日志 + 暴露给桥接的状态查询工具

**明确不做（推后）：**
- ❌ 工作优先级（P2）
- ❌ LLM（P3）
- ❌ 其他生产线路（P4）
- ❌ 作物轮作 / 土壤优化等高级农业策略
- ❌ 战斗、贸易、医疗

**验收标准（先定，再写代码）：**

| # | 断言 | 怎么测 |
| --- | --- | --- |
| 1 | 食物充足时**不动手**（不无脑种地） | 给足食物 → 跑若干天 → 断言种植区面积不变、决策日志为 `DoNothing` |
| 2 | 食物不足时**自动建种植区** | 清空食物 → 断言出现 `Zone_Growing` 且面积 > 0 |
| 3 | 种植面积与缺口**单调相关** | 缺口 2 倍 → 种的地 ≥ 原来的地（不做精确值，避免脆弱） |
| 4 | 预测值**与实际对得上** | 种下 → 推进 N 天 → 对比预测 `projectedSupply` 与实际收获 |
| 5 | **不振荡** | 连续观察 15 天，断言种植面积变化次数 ≤ 阈值（关键！防止"种了铲、铲了种"） |
| 6 | 长跑不崩 | 连续跑 15 游戏天，无报错、内存平稳 |

**断言 5 是重点**：控制类 mod 最常见的失败模式就是**振荡**，
而它恰恰是「连续跑一跑」看不出来的（看起来在工作，其实在空转）。必须显式断言。

## 六、可测试性设计（这是本项目的独特优势）

这个仓库有完整的桥接 + 隔离实例 + tick 精确推进，所以可以做到**别人做设计时做不到的事**：

1. **决策层离线单测**：决策是纯函数，喂合成状态断言输出动作。**不开游戏**，毫秒级。
2. **预测器回验**：种下 → `step_game_ticks` 推进 → 读实际生长/收获 → 对比预测值 → 算误差。
   这是**最有价值的一个测试**，因为预测准不准是整个闭环的地基。
3. **场景注入**：用 debug action 摆出「零食物」「冬天」「肥沃土 vs 石地」「存粮爆仓」等边界场景。
4. **状态注入而非等**：周期太长（作物几天才熟）→ 用 debug action 直接改存量、改生长进度，
   而不是真的等。**把"等"变成"设"**，测试时间从分钟级降到秒级。
5. **长跑压缩**：`step_game_ticks` 可精确推进，跑 15 游戏天不需要 15 天。

**给 mod 加一个测试钩子**（RimBridgeServer 伴生 DLL，仓库已有可跑范例）：
把 mod 内部状态暴露成 `food/state`、`food/project`、`food/decisions` 等只读工具，
测试就可以直接断言内部状态，不用从 UI 反推。

## 七、实测结论回填（2026-10-03）

详见 `docs/食物自动化-技术侦察.md`（逐条【实测】/【推测】）与 `runs/food-recon/`。
下面只写**影响架构的结论**。

### 7.1 原设计被推翻的两点

| 我原来的假设 | 实测结果 | 后果 |
| --- | --- | --- |
| 感知可以靠桥接扫格凑合 | 桥接的 `things[]` 只有 10 个键，**nutrition / stackCount / ThingCategory 全读不到**（stackCount 只能从 label 的 `"x7"` 抠） | ❌ **必须写 DLL**，或者手抄营养表（脏数据源，否决） |
| 执行层走桥接建筑师设计器 | 建区能建（见 7.3），但**改作物只能走 UI** | ⚠ 执行层分层：建区可用桥接，**指定作物必须用自己的 API** |

### 7.2 感知：确认必须写伴生 DLL 【实测支撑】

- `get_game_info` 只有 4 个字段（`status` / `ticksGame` / `mapCount` / `selectedPawns`），**没有地图范围、没有资源汇总**。
- 全图 62500 格用 `get_cells_info` 32×32 批扫：**64 次调用 / 0.75–0.9 秒 / ~15 MB** —— 速度上完全现实，
  **但读不到我们需要的字段**，所以这条路是死的。
- `get_selection_semantics` 对非 Pawn（比如一堆食物）**直接崩**；`run_lua` 里没有全局对象，不能当旁路。
- **代价只有一次遍历**：mod 在游戏内用 `map.listerThings.AllThings` 自己算，是 O(n) 而不是 O(62500)，
  比桥接扫格快 2~3 个数量级，而且是精确值。

### 7.3 执行层：能建区，但改作物得靠自己

- `Growing zone` 设计器 id = `architect-designator:zone:highlight-designator-zoneadd-growing`，
  **实测建出了 `RimWorld.Zone_Growing`（16 格）**，`list_zones` + 格级 `zone` 双回读确认 ✅
- ⚠ **只接受 Gravel / Soil**：Sand **100% 被拒**，而这张地图 55% 是 Sand。
  → 选址逻辑必须**先查地表可种性**，不能随便拉框。
- 新区的默认作物是 **`Plant_Potato`（土豆）**（不是水稻）。
- **改作物只能走 UI**：`execute_gizmo(Command_SetPlantToGrow)` → FloatMenu → 点整行 button ✅（实测生效）。
  代价是踩已知地雷（FloatMenu 在后台注入下留不住、列表行要按 `screenRect` 精确配对）。
- 生长进度**只能从 inspect 文本读**（`"2% grown"` / zone 的 `Average plant age: 12 hours (11% grown)`），
  精度差。

### 7.4 执行层：狩猎可驱动，工作优先级读不到

- **狩猎完全可驱动**【实测】：Hunt 设计器下达后，`cell.designations` 能回读
  `{defName:"Hunt", targetThingDefName:"Muffalo"}` ✅
  → 这降低了狩猎进 MVP 的门槛（但狩猎的**不确定性**依然是独立问题，见 §八）。
- ⚠ **工作优先级完全读不到，必须写 DLL**：`list_colonists` 的 28 个字段里没有；
  Work 标签页 106 个优先级格子 `isChecked` / `valueText` 全是 null，优先级颜色也不在快照里。
  → **P2 的启动成本比预想高**：不是"写个规则"，而是"先写一个读写工作面板的 DLL"。
- 技能可读且够用（`ce/get_skills`，与 Bio 标签页一致）。
- **右键菜单路径永久废弃**：三次尝试全失败，后台注入留不住 FloatMenu。执行层不要依赖它。

### 7.5 时间：这是最贵的一个约束

- `step_game_ticks` 的**工具级 `timeoutMs` 默认 10000**，不显式传就会 `timedout`，只推进 3515–5576 tick。
  **调用时必须显式传大值**（这是又一次"`success` 不代表做完了"的实例）。
- 实测 **541 tick/s**（≈ 帧率，`advancedFrames == advancedTicks`）：
  **2500 tick = 6.4 s；15000 tick = 26.1 s；15 游戏天（900000 tick）≈ 28 分钟**。
- 生长确实推进（同一块水稻 11% → 24%，年龄 12h → 1 天 22h）✅
- ⚠ **晚上 Growth rate = 0%**（`needs light 51%`）。

### 7.6 对预测器的影响（最关键的一条）

**15 天产出绝对不能按 24 小时线性外推。** 作物只在有光时生长，温带户外作物约
**12 小时有效生长 / 天**（📖 比例待实测）。这是预测器**最容易算错**的地方，
也让验收断言 4（预测 vs 实际）变成**真正有价值的测试**，而不是走过场。

### 7.7 对验收标准的影响

15 天 ≈ 28 分钟，**长跑不适合放进日常回归**。修正：

| 原断言 | 修正 |
| --- | --- |
| 5 | 长跑从 15 天缩到 **3~5 游戏天**（够覆盖一次"种下 → 接近成熟"） |
| — | 另外增加一条**离线预测器单测**：喂合成的光照/生长参数 → 断言光照周期被正确计入 |

真正做 15 天验证时，单独跑一次（约 28 分钟），或用 `set_time_speed` / `play_for` 走真实速度
（速度待 `scripts/recon-speed-compare.mjs` 实测）。

### 7.8 速度对比实测：长跑用 `play_for`，精确断言用 `step_game_ticks`

`scripts/recon-speed-compare.mjs`（原始数据 `runs/food-recon/speed-compare.json`）：

| 方式 | tick/s | 15 游戏天预计 | 特性 |
| --- | --- | --- | --- |
| `step_game_ticks` | **591.8** | 25.3 分钟 | 精确，返回 `advancedTicks` 可当断言；上限≈帧率 |
| `set_time_speed('Ultrafast', boost) + play_for` | **7110.7** | **2.1 分钟** | **快 12 倍** |

结论与用法分工：

- **长跑（推天数、等作物熟）→ `play_for`**：快 12 倍，15 天从 25 分钟降到约 2 分钟，
  这让「15 天回归」第一次变得可以接受。
- **精确断言（我要恰好推进 N tick）→ `step_game_ticks`**，且**必须显式传 `timeoutMs`**。
- 两者都**不能信 `success`**：`play_for` 实测出现过 `success:false` 但 `advancedTicks=63200`
  （tick 真的推进了）。**一律按 `advancedTicks` 累计计数。**

### 7.9 ⚠ 新踩到的坑：forcePause 窗口会让 `play_for` 永久失效

这是本轮排查花时间最多、也最值钱的一条，**已独立于 food 成为通用经验**。

**症状**：`play_for` 秒退 —— `elapsedMs≈6`、`advancedTicks=0`，
报文 `"Game was paused externally after 3ms"`，且**此后所有 `play_for` 调用全部失败**，
换速度（Normal/Fast/Superfast）、不传 `forceRequestedSpeed`、调 `pause_game` 都无法恢复。

**误判过程（值得记录，因为第一直觉是错的）**：
一开始对比两个脚本，发现「失败的脚本在 `play_for` 前调了 `get_game_info`」，
于是怀疑是它。**这个假设是错的** —— 二分实验（`scripts/recon-playfor-bisect.mjs`）显示
D 组「setSpeed → getInfo → play_for」**第一次成功、第二次就失败**，
说明变量不是调用序列，而是**累积状态**。

**真正根因**：某个 `forcePause` 的窗口开着。实测是 **`RimWorld.MainTabWindow_Menu`**。
`get_ui_state` 里两个字段直接指认：

```
"windowsForcePause": true,
"forcePauseWindows": ["RimWorld.MainTabWindow_Menu"]
"openMainTabId": "main-tab:Menu"
```

它每帧强制暂停，把 `play_for` 的 unpause 覆盖掉。

**确认实验**（`scripts/recon-playfor-rootcause.mjs`，`runs/food-recon/playfor-rootcause.json`）：

| 状态 | forcePause 窗口 | `play_for` |
| --- | --- | --- |
| 修复前 | `MainTabWindow_Menu` | ❌ 0 tick |
| `close_main_tab {tabId:"main-tab:Menu"}` 之后 | 无 | ✅ 15509 tick / 2.0 s（**7755 tick/s**） |
| 紧接着再跑 | 无 | ✅ 15363 tick |
| 又跑 2 次 | 无 | ✅ 14923 / 12602 tick |

**诚实边界**：**反向对照没做成** —— 想重新打开 Menu 标签页验证"再开就该再失败"，
但 `open_main_tab` 收的参数名是 `mainTabId`（不是 `close_main_tab` 的 `tabId`），
我传错了所以没打开。因此这条结论是「关掉就恢复」的**单侧证据**（4 次复现），
没有「打开就复现」的另一侧。**建议下次用 `mainTabId` 补做反向对照。**

**另外**：Menu 标签页**是谁开的没查出来**。排除了 `press_cancel`（实测 UI 无变化）；
侦察脚本里 `open_main_tab` 开的是 `main-tab:Work`。**记为未查明**，不编故事。

**给测试代码的硬性要求**（已写进 skill）：

> 任何 `play_for` 长跑之前，先查 `get_ui_state`；
> 若 `windowsForcePause == true`，**先关掉那些窗口**（尤其 `MainTabWindow_Menu`），否则会静默跑 0 tick。

### 7.10 光周期：预测器的核心难点已确认

侦察实测「晚上 Growth rate = 0%（`needs light 51%`）」，**所以 15 天产出不能按 24 小时线性外推**。
温带户外作物大约只有**半天**有效生长时间。

这条直接决定了 §二 的预测器必须**显式建模光周期**，而不是把 `growth` 线性外推到 15 天后。
也因此 `acceptanceTest #4`（预测 vs 实际）**必须用真实推进的 tick 来验**，
不能用解析公式自证 —— 否则就是拿同一个错误假设验它自己。

**待实测**：精确的有效生长小时数（按季节/纬度/是否室内水培分别测）。
