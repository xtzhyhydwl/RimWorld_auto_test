## 0. 结论速览（先看这个）

1. **官方在 1.6 重构了寻路**：不再是"一个 `PathGrid` + `FindPath`"，而是 `Map.pathing`(`Verse.AI.Pathing`) 持有 `Dictionary<PathGridDef, PathingContext>`，寻路请求变成 `Verse.PathRequest` 对象 + `IPathFinderDataSource.ComputeAll/UpdateIncrementally`。【一手·本机】
2. **给小人加速有且只有一个正规出口**：`Pawn.TicksPerMove(bool diagonal)`，它内部调 `StatExtension.GetStatValue(thing, StatDefOf.MoveSpeed, ...)`。IL 已确证。【一手·本机】
3. **往思考树插节点的官方机制是 `<insertTag>`**，Ludeon 在 vanilla XML 里亲手写了 "Insertion hook for modders" 的注释和示例。这是本需求的"要不要去骑车"决策的落点。【一手·XML】
4. **Giddy-up 的真实做法**：不造载具 Pawn，只是 `[HarmonyPatch(typeof(Pawn), "TicksPerMove")]` 的 Postfix，把结果替换成坐骑的 `TicksPerMoveDiagonal/Cardinal`，加上 `Pawn.DrawAt` 的 Prefix 把骑手画在坐骑位置。骑手始终是正常 spawned Pawn。【一手·源码】
5. **Vehicles Framework 路线很重**：载具是 Pawn（`Vehicles.VehiclePawn`，ThingDef `<category>Pawn</category>` + 完整 `<race>` 块），乘客上车后被 **despawn**（`pawn.InVehicle() && !pawn.Spawned`），有独立的角色/座位系统和自己的一套预约系统。【一手·XML + 源码】
6. **官方 shuttle 是 Building+Comp**（`Building_PassengerShuttle` + `CompShuttle` + `CompTransporter`/`CompLaunchable`），它解决的是**世界层投送**，不是地图内通勤。【一手·本机】
7. **对"共享单车"这个具体需求，我独立判断仍选 (a) Thing+Comp 路线**，但**必须避开 Hediff 和 Apparel 两种加速载体**（理由见 §3.5、§4）。你的倾向是对的，但落地方式要改。
8. **最大的坑不是速度，是"释放语义 + 存档"**：见 §4。

### 1.1 Vehicles Framework（SmashPhil）—— 最关键的先例

**它如何表示载具？—— 载具是一个 Pawn。**

【一手·XML】`1.6/Defs/VehiclesDefs/VehiclePawnBase.xml`（[链接](https://github.com/SmashPhil/Vehicle-Framework/blob/develop/1.6/Defs/VehiclesDefs/VehiclePawnBase.xml)）：

```xml

    <category>Pawn</category>
    ...
    <passability>PassThroughOnly</passability>
    <pathCost>250</pathCost>
    <race>

        <thinkTreeConstant>Vehicle_Constant</thinkTreeConstant>
```

确证点：
- 载具的 Def 元素名是 `Vehicles.VehicleDef`（即 `VehicleDef : ThingDef`，加了自己的字段），`thingClass` 是 `Vehicles.VehiclePawn`。
- `<category>Pawn</category>` + 完整 `<race>` 块 → 这是 RimWorld 里 Pawn 的表示方式。**`VehiclePawn : Pawn` 这个继承声明本身我没读到**（该 .cs 不在我能取到的文件树片段里），但按 vanilla 规则 `ThingDef.category=Pawn` + `thingClass` + `<race>` 只有 Pawn 子类能成立。标为"高度确证"。
- **它在 `race` 里专门关掉 vanilla 假设**：`<doesntMove>true</doesntMove>`（注释明确写"prevents vanilla from considering it capable of being downed"）、`<needsRest>false</needsRest>`、`<alwaysAwake>true</alwaysAwake>`、自定义 `<fleshType>MetalVehicle</fleshType>`、空 body（`<body>emptyBody</body>`）、`<trainability>None</trainability>`、`<baseHealthScale>1.0</baseHealthScale>`。这张清单就是"当一个 Pawn 但不想当 Pawn"的代价表。

**它有没有独立的寻路器？—— 有自己的一整套网格/区域，而不是改 vanilla 的。**

【一手·源码】仓库源码树里存在这些文件名（通过 jsDelivr 对 `SmashPhil/Vehicle-Framework@develop` 的完整文件列表读取，注意 GitHub API 当时被限流）：`Source/Test_Vehicles/Benchmarking/Benchmark_PathGridGeneration.cs`、`Benchmark_RegionGridGeneration.cs`、`Benchmark_MapGrid.cs`、`Benchmark_AllRegions.cs`、`Source/Test_Vehicles/Tests/Test_PathGridVehicle.cs`、`Test_PathGridPawn.cs`、`Test_RegionGridOwner.cs`、`Test_MapGridOwners.cs`、`Test_TerrainGrid.cs`、`Test_ThingGrid.cs`（[Source 目录](https://github.com/SmashPhil/Vehicle-Framework/tree/develop/Source)）。README 自称提供 "vehicle pawns, **custom pathing**, component-based vehicle health..."（[README](https://github.com/SmashPhil/Vehicle-Framework/blob/develop/README.md)）。

【一手·源码】`Test_VehiclePawn_Pathing.cs` 显示它**不改 pawn 的寻路 API，而是给载具另开一个可达性入口**：`vehicle.CanReachVehicle(gotoLoc, PathEndMode.OnCell, Danger.Deadly)`，并且明确以**多格**载具为前提（`group.vehicle.def.Size`、`TestUtils.GetTestArea(vehicle.Position, vehicle.def.size)`、`gosliLoc.Walkable(group.vehicle.VehicleDef, group.vehicle.Map)`）。（[链接](https://github.com/SmashPhil/Vehicle-Framework/blob/develop/Source/Test_Vehicles/Tests/Test_VehiclePawn_Pathing.cs)）

乘客模型（这是全篇最有价值的一段）：
- 载具有"角色（role）"概念：`VehicleRole { key = "Driver"/"Passenger"/"Gunner", slots, slotsToOperate, handlingTypes }`，每个角色对应一个 `VehicleRoleHandler`，每个 handler 有自己的 `thingOwner`。

- **它自己实现了一套预约系统**：`VehicleReservationManager`（一个 **MapComponent**，`group.vehicle.Map.GetCachedMapComponent<VehicleReservationManager>()`）+ `VehicleHandlerReservation`。

- `<doesntMove>true</doesntMove>` 关掉 downed 判定；`needsRest/alwaysAwake/foodType=None` 关掉需求；空 body + 自定义 fleshType 关掉身体/血肉逻辑；`PointlessVehicleRenderTree` 换渲染树。
- 自定义 inspector tab（`ITab_Vehicle_Passengers` 等）。
- 自带网格/区域生成，不依赖 vanilla 的 `PathGrid` 语义。
- 自定义 `VehicleDef : ThingDef` 承载载具专属字段（`properties.diagonalRotation`、`customThingCosts`、`statEvents` 等）。

### 1.2 Giddy-up! 系列（骑乘动物）

【一手·源码】存在一个带**完整 C# 源码**的镜像仓库：<https://github.com/RimWorld-zh-mods/GiddyUpCore>（注意：这套源码用的是 `using Harmony;`（Harmony 1.x 命名空间）+ HugsLib，属于 1.0–1.4 世代；但**补丁目标在 1.6 依然存在**，见下）。

**A 骑在 B 上是怎么实现的？—— A 完全不变，只是"画在 B 身上"+"用 B 的速度"。**

`Source/Giddy-up-Core/Harmony/Pawn_DrawAt.cs`（[链接](https://github.com/RimWorld-zh-mods/GiddyUpCore/blob/master/Source/Giddy-up-Core/Harmony/Pawn_DrawAt.cs)）：
```csharp
[HarmonyPatch(typeof(Pawn), "DrawAt")]
[HarmonyPatch(new Type[] { typeof(Vector3), typeof(bool) })]
static class Pawn_DrawAt {
  static bool Prefix(Pawn __instance, Vector3 drawLoc, bool flip = false) {
    ExtendedPawnData pawnData = Base.Instance.GetExtendedDataStorage().GetExtendedDataFor(__instance);
    if (pawnData.mount != null) {
      drawLoc = pawnData.mount.Drawer.DrawPos;
      ...
      __instance.Drawer.DrawAt(drawLoc);   // 手动画
      return false;                         // 跳过原方法
    }
    return true;
  }
}
```

**骑乘速度怎么算？** `Source/Giddy-up-Core/Harmony/Pawn_TicksPerMove.cs`（[链接](https://github.com/RimWorld-zh-mods/GiddyUpCore/blob/master/Source/Giddy-up-Core/Harmony/Pawn_TicksPerMove.cs)）：
```csharp
[HarmonyPatch(typeof(Pawn), "TicksPerMove")]
static class Pawn_TicksPerMove {
  [HarmonyPriority(Priority.Low)]
  static void Postfix(Pawn __instance, ref bool diagonal, ref int __result) {
    ExtendedPawnData pawnData = Base.Instance.GetExtendedDataStorage().GetExtendedDataFor(__instance);
    if (pawnData.mount != null) {
      __result = diagonal ? pawnData.mount.TicksPerMoveDiagonal : pawnData.mount.TicksPerMoveCardinal;
    }
  }
}
```
→ **速度 = 坐骑的速度**，不是"小人速度 × 系数"。这否证了"骑乘是给小人加一个 multiplier"的常见想象。

**状态存在哪？** `Storage/ExtendedPawnData.cs`：
```csharp
public class ExtendedPawnData : IExposable {
  public Pawn mount = null;          // 就是一个小人引用
  public float drawOffset = -1;
  public void ExposeData() { Scribe_References.Look(ref mount, "mount", false); ... }
}
```
存放在 HugsLib 的 `UtilityWorldObject`：`UtilityWorldObjectManager.GetUtilityWorldObject<ExtendedDataStorage>()`（`Base.cs`）。
→ 【推断】没有用 ModExtension/Comp 挂在小人身上，而是用了一个世界级扩展数据容器（mod 各自的常见做法）。

**它 patch 了哪些方法（Core 全部 3 个）**：
| 文件 | 目标 | 类型 | 作用 |
|---|---|---|---|
| `Pawn_TicksPerMove.cs` | `Pawn.TicksPerMove(bool)` | Postfix（`Priority.Low`） | 速度换成坐骑的 |
| `Pawn_DrawAt.cs` | `Pawn.DrawAt(Vector3, bool)` | Prefix 返回 false | 把骑手画到坐骑位置 |
| `Pawn_HealthTracker.cs` | `Pawn_HealthTracker.MakeDowned` / `SetDead` | Postfix | 倒地/死亡时 `pawnData.reset()` 解绑 |

**已知限制（本仓库源码可证 + 【推断】）**：
- `Pawn_HealthTracker` 的补丁是用 `Traverse.Create(__instance).Field("pawn")` 反查私有字段的 → 对 vanilla 内部改动脆弱（【推断】，但反查私有字段这件事是源码明写的）。
- 骑手仍是真实 Pawn，**位置没有被强制同步**：只有"贴图"和"速度"被改。这意味着骑手与坐骑是各自寻路的两个实体，靠速度一致 + 渲染覆盖来"看起来像在一起"。【推断】这也解释了为什么会有"上马/下马"的 Job 在配套 mod（Giddy-up! Ride and Roll）里，而 Core 只做速度与渲染。
- 论坛原帖：<https://ludeon.com/forums/index.php?topic=37323.0>

**对本需求的意义**：Giddy-up 是"**(a) 路线的极简形态**"的存在性证明 —— 不做新实体、不被 despawn、不碰寻路，只改 `Pawn.TicksPerMove` + `Pawn.DrawAt` 两个补丁点。**共享单车如果只追求"效率提升"，这正是最小可行架构。**

**这是不是官方给出的"载具"范式？—— 不是。它给出的是"地图内建筑 + 世界层投送"的范式。**

- 它在**地图内不移动**。没有任何地图内路径跟随。

**是不是瞬移？** 不是"瞬移"，是**"装进容器 → 世界层投送 → 由 `Skyfaller` 重新进入地图"**。证据链：
- 乘客/物资进入 `CompTransporter.innerContainer`（`ThingOwner`，它是 `IThingHolder`：`GetDirectlyHeldThings()` / `GetChildHolders()` 都在）。
- 目的地是 `PlanetTile`（世界层），到达动作用 `TransportersArrivalAction`。
- 重新入场时用 `RimWorld.ShuttleIncoming : RimWorld.Skyfaller` 这类天降物（穿梭机与运输舱共用这套）。
→ **所以地图内 A→B 的"飞行"是不存在的**；pods 也无法做"殖民地内通勤"（它跨 `PlanetTile`）。

**pawn 在飞行中还是"真实"的吗？** 被放进 `ThingOwner`（即不再是 `map.mapPawns` 里的 spawned pawn）。它的 Job/精神状态如何中断，我**没有**从一手源码确证 → 需 IL 确证（建议 ILSpy 看 `CompTransporter.Notify_ThingAddedAndMergedWith` 与 `Pawn.DeSpawn`）。【推断】参考 VF 的同类断言，被持有期间不会正常 tick 需求。

### 2.1 移动速度：`StatDefOf.MoveSpeed` 是怎么被消费的（IL 已确证）

**唯一的消费出口是 `Pawn.TicksPerMove(bool diagonal)`。** 我扫了全程序集 IL，`RimWorld.StatDefOf.MoveSpeed` 字段的读取者里，与移动直接相关的是它：

```
### Pawn.TicksPerMove(Boolean diagonal) : Single
  @1  ldsfld StatDefOf.MoveSpeed : StatDef
  @8  call StatExtension.GetStatValue(Thing thing, StatDef stat, Boolean applyPostProcess, Int32 cacheStaleAfterTicks) : Single
  @15 call Pawn.get_Downed() : Boolean
  @28 callvirt Pawn_HealthTracker.get_CanCrawl() : Boolean
  @36 ldsfld StatDefOf.CrawlSpeed : StatDef
  @43 call StatExtension.GetStatValue(...) : Single
  @50 call RestraintsUtility.InRestraints(Pawn pawn) : Boolean
  @66 ldfld Pawn.carryTracker : Pawn_CarryTracker
  @96 ldfld Thing.def / ThingDef.category        (搬运中物品类别惩罚)
  @163 ldfld Map.roofGrid : RoofGrid
  @174 callvirt RoofGrid.Roofed(IntVec3 c) : Boolean
  @188 ldfld Map.weatherManager : WeatherManager
  @193 callvirt WeatherManager.get_CurMoveSpeedMultiplier() : Single
```

并且：
```
### Pawn.get_TicksPerMoveCardinal() : Single   -> call Pawn.TicksPerMove(Boolean)
### Pawn.get_TicksPerMoveDiagonal() : Single   -> call Pawn.TicksPerMove(Boolean)
```
（`Verse.Pawn` 的一手成员表也确证：`P Single TicksPerMoveCardinal`、`P Single TicksPerMoveDiagonal`、`M Single TicksPerMove(Boolean diagonal)`。）

**还没有 tick 级的速度字段** —— `Pawn.TicksPerMove` 是属性/方法，`Verse.Pawn` 上**没有** `TicksPerMove` 字段，也**没有** `Pawn.MoveSpeed` 字段（我按名字扫过全程序集：只有 `RimWorld.StatDefOf.MoveSpeed`、`Pawn.debugMaxMoveSpeed`、`WeatherDef.moveSpeedMultiplier`、`PawnKindDef.moveSpeedFactorByTerrainTag`、`RimWorld.StaggerHandler.staggerMoveSpeedFactor`、`RimWorld.Planet.CaravanTicksPerMoveUtility.MoveSpeedFactorAtZeroMass`、`Verse.CameraMapConfig.moveSpeedScale`）。

**一条移动 = 一个方法调用的完整链路**：
```
Pawn_PathFollower.PatherTick()
  -> NeedNewPath() -> GenerateNewPathRequest() : PathRequest
       (IL: 读 pawn.Map，调 PathFinderCostTuning.For(pawn)，调 GuestUtility.PrisonerCanReturnToCell(pawn))
  -> TryEnterNextPathCell() -> SetupMoveIntoNextCell() -> CostToMoveIntoCell(IntVec3)
  -> CostToPayThisTick()
  -> 每 tick 从 nextCellCostTotal 里扣
```

`CostToPayThisTick()` 的 IL：`Pawn_StanceTracker.stagger : StaggerHandler` → `StaggerMoveSpeedFactor` / `Staggered`；`Pawn.get_Flying()`；`RaceProperties.flightSpeedFactor`；`nextCellCostTotal`。

**给小人加速的正规手段清单（按"副作用从小到大"排序）**：

| 手段 | 怎么做 | 副作用 | 等级 |
|---|---|---|---|
| **Harmony Postfix `Pawn.TicksPerMove(bool)`** | 与 Giddy-up 完全相同，读你自己的状态后改写 `ref int __result` | 无明显副作用；但它是全局出口，任何"非骑车状态"必须能正确还原；**别用 Prefix 返回 false** | 【一手·源码确证可行】Giddy-up 在用 |
| **自定义 `RimWorld.StatPart` 挂到 MoveSpeed 的 `<parts>`** | 继承 `RimWorld.StatPart`，实现 `TransformValue(StatRequest req, ref float val)` 与 `ExplanationPart(StatRequest)`，然后 XML patch `StatDef[defName="MoveSpeed"]/parts` 加一行 | **这是 vanilla 自己在用的机制**（见下），最"正规"；会自动出现在小人的属性面板解释里；但 `StatRequest` 里能不能可靠拿到"当前在骑哪辆车"需要确证 | 【一手·本机】vanilla 存在该基类 |
| **HediffDef 的 stage `statOffsets` / `statFactors`** | `HediffDef.stages[i].statOffsets` | ⚠️ 会进健康面板；`tendable`/`isBad`/`makesSickThought`/`makesAlert`/`alwaysShowSeverity` 会带来治疗、心情、警报、手术交互；`Hediff` 要挂 body part；被"医疗"类 mod 一动就没了 | 【一手·本机】`Verse.HediffStage` 确有 `statOffsets`/`statFactors`/`statOffsetsBySeverity`/`statFactorsBySeverity` |
| **Apparel / 装备** | `ThingDef` + apparel 组件 | 占装备槽；倒地/被剥光/囚犯化/麻醉时**会掉**；和品质/材质/外观系统纠缠 | 【推断】 |

**关于 Hediff 的关键纠正**：`Verse.HediffDef` **本身没有** `statOffsets`/`statFactors` 字段。这些字段在 **`Verse.HediffStage`** 上（`List<StatModifier> statOffsets`、`List<StatModifier> statFactors`、`List<StatModifierBySeverity> statOffsetsBySeverity`、`statFactorsBySeverity`、`List<PawnCapacityModifier> capMods`、`painFactor`…）。所以 XML 必须写成 `HediffDef/stages/li/statOffsets`。【一手·本机】

**vanilla 的 MoveSpeed 定义**（【一手·XML】`Data\Core\Defs\Stats\Stats_Pawns_General.xml`）：
```xml
<StatDef>
  <defName>MoveSpeed</defName>
  <defaultBaseValue>3.0</defaultBaseValue>
  <minValue>0.15</minValue>
  <capacityFactors><li><capacity>Moving</capacity><weight>1</weight></li></capacityFactors>
  <parts>
    <li Class="StatPart_Glow"> ... </li>
    <li MayRequire="Ludeon.RimWorld.Anomaly" Class="StatPart_RevenantSpeed" />
    <li MayRequire="Ludeon.RimWorld.Odyssey"  Class="StatPart_TerrainMoveSpeed" />
  </parts>
</StatDef>
```
→ **`StatPart_TerrainMoveSpeed` 就是官方"地形影响移动速度"的现成实现**：`RimWorld.StatPart_TerrainMoveSpeed : RimWorld.StatPart`，只有 `TransformValue` 与 `ExplanationPart` 两个重写（【一手·本机】）。**这是你做"骑车走某条路更快"时最该抄的一个类。**

`RimWorld.StatPart` 基类（【一手·本机】）：字段 `float priority`、`StatDef parentStat`；方法 `void TransformValue(StatRequest req, ref float val)`、`string ExplanationPart(StatRequest req)`、`IEnumerable<string> ConfigErrors()`、`IEnumerable<Hyperlink> GetInfoCardHyperlinks(StatRequest req)`、`bool ForceShow(StatRequest req)`。vanilla 有 90+ 个 `StatPart_*` 子类可作模板。

**`CostToMoveIntoCell(Pawn, IntVec3)` 的真实 IL（这是本报告最重要的一段）：**

**由此可得到结论（这才是能指导架构的东西）：**

1. **"让某条路上骑车更快"不该改 terrain。** terrain 的 `pathCost` 是**全局**的，改它会让所有小人、所有动物、所有敌人都受益。要按"这个小人此刻在骑车"来定价，正确落点是：
   - `Pawn_PathFollower.GetPawnCellBaseCostOverride(Pawn, IntVec3)` → `Nullable<int>`，**逐小人逐格的基础代价覆盖**（IL 显示它在 terrain/building 代价之前被调用，返回非空会短路后面）。这是我最推荐的单点补丁。
   - 它的调用者只有 2 个：`Pawn_PathFollower.CostToMoveIntoCell(Pawn, IntVec3)` 和 `RCellFinder.CanWanderToCell(...)`（IL 确证）。**改动面极小**。
2. **`Building.PathWalkCostFor(Pawn p) : UInt16` 是一个虚方法** → 你可以做一个自定义建筑（"自行车道/单车道"），只对它认得的 pawn 返回低代价。这是**不需要 Harmony 的官方入口**（继承 vanilla Building/`Building_Door` 之类）。
3. **`PawnKindDef.moveSpeedFactorByTerrainTag` 是数据（Dictionary<string,float>）**，配合 `TerrainDef.tags` → 你可以定义 `<PawnKindDef>`/地形 tag 组合来做"装甲兵在泥地上慢"。但它是 **PawnKindDef 级**的，不能表达"这个人今天骑了车"。【一手·本机 + 推断】
4. **`Verse.PathGridDef.workerType` 是 `Type`** → 【推断】理论上可以加一个自己的 `PathGridDef`（自定义 worker）来获得第三套网格。**worker 的基类/接口未能确证**（相关类型在 .NET Framework 下加载失败）→ 需 IL 确证。

### 2.3 寻路能被 mod 介入吗？调用链与补丁落点

**调用链（IL 确证的部分）**：
```
Pawn_PathFollower.PatherTick()
  ├ TrySetNewPathRequest()      -> SetNewPathRequest()          [IL 确证]
  ├ GenerateNewPathRequest() : PathRequest                      [IL 确证]
  │   读 pawn.Map；调 PathFinderCostTuning.For(pawn)            [IL 确证]
  ├ TryEnterNextPathCell() -> SetupMoveIntoNextCell()
  └ CostToMoveIntoCell(IntVec3)
       └ static CostToMoveIntoCell(Pawn, IntVec3)               [IL 确证]
            ├ Pawn.TicksPerMoveCardinal/Diagonal
            ├ Pawn_PathFollower.GetPawnCellBaseCostOverride(Pawn, IntVec3)   ★
            ├ Pathing.For(Pawn) -> PathingContext
            ├ Building.PathWalkCostFor(Pawn) : UInt16                        ★
            └ TerrainDef.tags x PawnKindDef.moveSpeedFactorByTerrainTag
```
之后 `PathRequest` 被交给某个 pathfinder 实现（`IPathFinderDataSource.ComputeAll` / `UpdateIncrementally`；`Map.pathFinder` 字段存在）。**`PathRequest` 里带 `tickDeadline`，说明 1.6 的寻路是异步/可延迟的**（还有 `Verse.PathFinderJob`、`Verse.PathFinderMapData`、`Verse.PathFinder+ScheduledGridJob`、`PathFinderMapData+<>c__DisplayClass37_0` 这些嵌套类型存在）。

**诚实结论**：
- ❌ 我**不能**确证"1.6 里还有没有一个叫 `FindPath` 的 map 级寻路方法"。我扫了全程序集所有名字含 `FindPath` 的方法，**只找到 `RimWorld.Planet.WorldPathing.FindPath(PlanetTile, PlanetTile, Caravan, Func<...>)`**（世界层，不是地图层）。但地图层的几个核心类型（`Verse.PathFinder`、`Verse.PathFinderMapData`、`Verse.PathFinderJob`、`Verse.AI.PathingContext`）在 .NET Framework 下**加载失败**，所以扫描会漏掉它们的方法 → **"`PathFinder.FindPath` 是否还存在"必须用 ILSpy/dnSpy 打开 `Assembly-CSharp.dll` 确证**。请不要按"肯定还在"去写补丁。
- ✅ 但**你大概不需要 patch 寻路**：如果目标只是"骑车更快"，改 `Pawn.TicksPerMove`（§2.1）或 `GetPawnCellBaseCostOverride`（§2.2）就够，两者的改动面比 patch 寻路器小一个数量级。
- 关于"有没有只算代价、不返回路径的公开入口"（做 A/B 决策需要）：**未确证**。`PathRequest` + `IPathFinderDataSource` 的存在暗示"提交请求、稍后取结果"是可做的，但**没有任何一手证据表明它是 mod 可用 API**。→ 需 IL 确证。**架构上请按"没有"来设计**（见 §4）。

参考：Multiplayer mod 有一个 1.6 的 issue 标题就是 *"PathFinderTick can cause desync for 1.6"*，佐证 1.6 寻路被大改（[rwmt/Multiplayer#837](https://github.com/rwmt/Multiplayer/issues/837)）。RimWorld Wiki 也记录了 1.6.4518 起引入 VTR（变率 tick）（[RimWorld Wiki:To-do](https://rimworldwiki.com/wiki/RimWorld_Wiki:To-do)）。

### 2.4 "先走路到载具、再骑到目的地"这个决策放在哪？（好消息：官方有专用插槽）

**先厘清概念（【一手·本机】类型确证 + 【二手】常规理解）**：
| 概念 | 类型 | 职责 |
|---|---|---|
| `ThinkTreeDef` | `Verse.ThinkTreeDef : Def`，字段 `thinkRoot : ThinkNode`、`insertTag : String`、`insertPriority : float` | 一棵"这个 pawn 每 tick 怎么想"的树 |
| `ThinkNode` | `Verse.AI.ThinkNode`（抽象），`subNodes`、`priority`、`tag`、`parent`、`TryIssueJobPackage(Pawn, JobIssueParams)` | 树的节点；"要不要做某事、优先级多少" |
| `JobGiver` | `Verse.AI.ThinkNode_JobGiver : ThinkNode`，`Job TryGiveJob(Pawn pawn)` | **决定"现在给什么 Job"** ← **"要不要去骑车"属于这里** |
| `WorkGiver` | （殖民者的工作分配） | 只回答"殖民地有什么活要干" |
| `JobDriver` | `Verse.AI.JobDriver`，`MakeNewToils()` | **怎么把 Job 拆成步骤序列（Toil）** ← "走过去→上车→骑→下车"属于这里 |

**官方插入机制（这是最重要的发现）：**

vanilla `Data\Core\Defs\ThinkTreeDefs\Humanlike.xml` 里有：
```xml
<!-- Insertion hook for modders -->
<li Class="ThinkNode_SubtreesByTag">
  <insertTag>Humanlike_PreMain</insertTag>
</li>
...
<!-- Insertion hook for modders -->
<li Class="ThinkNode_SubtreesByTag">
  <insertTag>Humanlike_PostMain</insertTag>
</li>
```

3. `JobDef` + `JobDriver` 定义步骤：

   ```xml
   </JobDef>
   ```

   `MakeNewToils()` 大致是：`Toils_Goto.GotoThing(bike, PathEndMode.Touch)` → 预约车（`Toil` 里做）→ "上车"标记（Instant Toil）→ `Toils_Goto.GotoCell(dest)`（此时 `Pawn.TicksPerMove` 已被你的状态改变）→ "还车"（Instant Toil，把车放到脚下/旁边合法格）→ `AddFinishAction` 做兜底清理。

4. **官方自证**：`RimWorld.JobGiver_BoardOrLeaveGravship : Verse.AI.ThinkNode_JobGiver` + `JobDriver_BoardOrLeaveGravship`（Odyssey）就是官方做"让小人自发上下载具"的方式。【一手·本机】

**不要用 WorkGiver。** WorkGiver 回答的是"殖民地有什么活要干"，会被工作优先级/技能/区域限制过滤，而且它天然属于"工作清单"。共享单车是**移动行为**，不是工作。

**一个更保守的替代方案（【推断】 推荐给第一版）**：不插 ThinkTree，而是 hook 到"小人要远行"这个既有事件上。最省事的两个补丁点：
- `JobDriver`/`Toils_Goto` 层不好整；更实际的落点是 `Pawn_PathFollower.SetNewPathRequest()`/`GenerateNewPathRequest()`（IL 确证存在且被 `PatherTick` 调用）——在这里你可以看到"想去哪"，如果距离超过阈值就**顺便**让小人先"路过"最近的车位。但这会污染寻路调用，风险较高。
- 或者最朴素：一个 `MapComponent` 每 250 tick 扫一遍"当前目的地很远且附近有车"的小人，给它们 `jobs.TryTakeOrderedJob(job)`。可控、易调试、易熔断。

|---|---|---|
| **私有**（床、王座、餐桌位） | `RimWorld.CompAssignableToPawn : Verse.ThingComp` | 成员：`assignedPawns`、`MaxAssignedPawnsCount`、`AssigningCandidates`、`HasFreeSlot`、`TotalSlots`、`CanAssignTo(Pawn) -> AcceptanceReport`、`TryAssignPawn(Pawn)`、`TryUnassignPawn(Pawn, bool sort, bool uninstall)`、`ForceAddPawn/ForceRemovePawn`、`AssignedAnything(Pawn)`、`ShouldShowAssignmentGizmo()`、`GetAssignmentGizmoLabel/Desc()`、`IdeoligionForbids(Pawn)`、`CompGetGizmosExtra()`。它是"玩家在 UI 上指派所有者"的东西（有 gizmo + 覆盖图标）。【一手·本机】 |
| **共享**（工作台、娱乐设施、门） | **不用 CompAssignableToPawn**；用 `ReservationManager` 在 Job 的 `TryMakePreToilReservations` 里 `Reserve`，Job 结束时框架自动 `Release`（`JobDriver`/`Toils_Reserve` 负责） | 【一手·本机】`ReservationUtility.Reserve` 的签名要求传 `Job job`，说明预约天然绑定 Job 生命周期 |
| **共享且不能被抢** | `RimWorld.CompForbiddable`（vanilla，`Source\RimWorld\ThingComps\CompForbiddable.cs` 本机随游戏发行）+ `Thing.IsForbidden` | 【一手·本机（源码文件存在）】 |
| 需要跨 Job 保持"已占用" | 自己写 MapComponent（**VF 就是这么干的**：`VehicleReservationManager` + `VehicleHandlerReservation`） | 【一手·源码】 |

**对共享单车（【推断/建议】）：**
- **不要**用 `CompAssignableToPawn`。它是"玩家指派私有物"，共享单车恰恰相反。
- **不要**只靠 `CompForbiddable`。
- 用 `ReservationUtility.Reserve(pawn, bike, job, maxPawns:1, stackCount:1, layer, ...)`：`maxPawns: 1` 天然实现"一个人骑一辆"，Job 结束时框架释放 → 天然"用完还给别人"。**这正是你要的"共享"语义。**
- **但有个陷阱**：预约是栓在 Job 上的。如果小人被战斗/饥饿/精神崩溃打断，Job 会结束、预约会释放 —— 这是对的（车回到可用池），**但车的物理位置必须此时就是正确的**（人下车了车留在原地），否则会出现"车跟着一个已经放弃骑行的小人跑"。所以：**车的位移必须在"上车/下车"这两个瞬时点写入，而不是每 tick 跟随**（见 §4）。
- 如果你要"车被骑走后，别人能看到它现在在哪"（共享单车的核心），车的 `Position` 必须实时正确 → 你必须在校验通过后立刻更新车的 `Position`（或在 Job 结束时统一 `DeSpawn`+`Spawn` 到新位置）。这会产生寻路成本重算（`Pathing.RecalculatePerceivedPathCostAt(IntVec3)` / `RecalculatePerceivedPathCostUnderThing(Thing)` 是官方给的工具，【一手·本机】）。

## 3. 「载具」在 RimWorld 里的表示方式之争

### 3.1 对比表

| | 表示方式 | 优点 | 致命缺点 | 实现难点在哪 |
|---|---|---|---|---|
| **(a) Thing/Building + Comp**<br>小人"拿起/骑上"，速度靠修饰 | 一个普通 `Thing`（或 `Building`），携带一个 `Comp`；骑乘状态存在一个单独的 `IExposable` 容器/Comp 里 | ①车天然是"地图上的东西"，`Spawned/Position/DeSpawn` 全部免费；②闲置车不 tick AI，不进 `map.mapPawns`，不干扰 storyteller / 袭击 / 精神能力 / 机械族逻辑；③共享/预约直接用 `ReservationManager`；④和原版工具台/仓储/搜索系统天然兼容（"Bicycles and more!" 就是在锻造台造）；⑤**不需要为它写 AI** | ①"骑行中"这个状态必须由你维护，游戏不知道人和车是一体的（Giddy-up 同样如此）；②车的贴图与人的贴图叠加需要自己处理（Giddy-up 的 `Pawn.DrawAt` Prefix 就是范例）；③车是可通行 Thing 时，会和 `Pawn_PathFollower` 的碰撞/绕行逻辑打架（`WillCollideWithPawnAt`） | 状态机 + 存档；"人和车"的位置一致性；渲染 |
| **(b) Pawn（VF 路线）** | `Vehicles.VehiclePawn : Pawn`，自己的 ThinkTree/渲染/网格/角色座位系统 | ①载具自带完整生命值、着火、炮塔、燃料、伪装涂装；②多格占位与自己的寻路/可达性；③乘员有一套明确的 role/slot 抽象；④已经有人踩过坑（源码 + 测试齐全） | ①**乘客会被 despawn**（`pawn.InVehicle() && !pawn.Spawned`），需求/心情/社交/装备/技能全停摆，日常高频上下车要反复 despawn/respawn；②每个闲置载具都是一个 ticking Pawn，人口多时成本高；③**必须为它写一套 AI**（连"待命"都要 `JobGiver_AwaitOrders`）；④要关掉一堆 vanilla Pawn 假设（VF 的 XML 里那张 `doesntMove/needsRest/alwaysAwake/emptyBody/MetalVehicle` 清单就是代价）；⑤内容和 VF 强耦合（加载顺序、VF 版本跟随） | 巨大的工程量；且**"上下班通勤"不是 VF 的设计目标** |
| **(c) 固定轨道 / 线路** | 一条道路/传送带/公交线的 Def（terrain 或 building）+ 站点 | ①最简单、最便宜；②完全没有"抢车"问题（位置固定）；③可以用 `TerrainDef.pathCost` / `Building.PathWalkCostFor(Pawn)` 让"沿线上走更快" | ①不是"共享单车"的体验（用户要的是"停在四处、随取随还"）；②`TerrainDef.pathCost` 是**全局**的，会让所有人（含敌人）都受益；③要表达"只有某条线更快"就必须写自定义 Building/Grid | 想让"线路"只对特定 pawn 生效，落点是 `Building.PathWalkCostFor(Pawn)`（虚方法，官方入口）；但想做"沿线加速"而不是"沿线便宜"就得上 `StatPart`/`TicksPerMove`，而那时你需要知道"pawn 在哪条线上"→ 又回到 (a) 的状态问题 |
| **(d) 官方 shuttle / `CompShuttle` 改装** | `Building_PassengerShuttle` + `CompShuttle` + `CompTransporter` + `CompLaunchable` | ①官方已实现的"装人 + 投送 + 落地"，代码量省；②`CompShuttle` 已经处理了 `acceptColonists`/`onlyAcceptHealthy`/`autoload`/`requiredPawns`/`HasPilot` 一堆边界 | ①**它是世界层投送**：目的地是 `PlanetTile`，不是地图内格。地图内它根本不移动；②它依赖 `Skyfaller`/`FlyShipLeaving` 做进出场动画，不适合"骑 20 格再停下"；③改装它=和 Odyssey/Royalty 的 quest 系统纠缠 | 你要的不是它解决的问题域 |

### 3.2 我的独立判断：选 (a)，但**不是**你设想的那种 (a)

**选 (a) 的三条硬理由（都基于上面的确证）：**

1. **"共享"的前提是"东西在地图上独立存在"**。`ReservationManager` 的 `Reserve(target...)` 要的是一个 `LocalTargetInfo`（一个地图上的 Thing/格），Job 结束自动 `Release` —— **vanilla 自带的语义恰好就是"共享"**。而 (b) 里乘客是 despawn 的，共享的对象实际上变成了"一个 Pawn 的座位"，你得自己造一套预约（VF 确实自己造了）。
2. **闲置成本**。用户的需求是"停在地图各处"→ 会有很多闲置载具。闲置的 `Thing` 几乎不花代价；闲置的 `Pawn` 要 tick、要 AI、要进 `map.mapPawns` 的各种遍历。
3. **(c) 不够，(d) 不对路**。(c) 是"线路"不是"共享"；(d) 是跨世界投送。用户的核心体验"到达后载具留在原地供别人用"只有 (a) 能自然表达。

**但必须放弃三个看似顺手的实现（这是我要修正你倾向的地方）：**

- ❌ **不要用 Hediff 做加速载体**。`HediffDef` 会进健康面板、可被治疗/手术/移除、`isBad`/`makesSickThought`/`makesAlert`/`tendable` 都会触发副作用，任何医疗类 mod 都会干扰它。【一手·本机：`Verse.HediffDef` 的字段表里就有 `tendable`/`isBad`/`makesSickThought`/`makesAlert`/`alwaysShowSeverity`/`countsAsAddedPartOrImplant`/`chronic`/`displayWound`】
- ❌ **不要用 Apparel/装备做载体**。倒地、被剥光、囚犯化、麻醉时装备会掉 → "车凭空消失"。而且和品质/材质/外观系统纠缠。
- ✅ **正确做法**：车速 = `Pawn.TicksPerMove` 的一个 Postfix（Giddy-up 验证过的路径，且 1.6 仍是唯一出口），或更"正规"地加一个 `RimWorld.StatPart` 到 MoveSpeed 的 `<parts>`（vanilla 自己就用 `StatPart_TerrainMoveSpeed` 这么干）。

**另一个关键修正（这个比上面三条更重要，见 §4）：**
> **不要让"骑车"进入寻路代价的计算，也不要为它建第二套寻路。**
>
> 我原本以为需要"用真实路径代价做 A/B 比较"。但调研后我认为：RimWorld 没有**已确证**的"只算代价不返回路径"的公开入口，而 1.6 的寻路已经异步化（`PathRequest` + `tickDeadline` + `IPathFinderDataSource.UpdateIncrementally`），硬插进去风险极高。
>
> **更稳的设计是：让"骑车"变成 Job 序列里的一步，而不是寻路器的一个变量。**
> - 小人的 Job 仍是普通的 `Goto`（走真实路径），只是在中间插入一次"去取车"。
> - "骑车更快吗"的判断，用**几何估算**（起点/车距/终点的直线距离 × 各自速度），这是原版本身就在用的精度级别，而不是精确路径代价。
> - 于是你**完全不用碰寻路器**，只需要：`Pawn.TicksPerMove` 一个补丁 + 一个 ThinkNode_JobGiver + 一个 JobDriver + 一个 Comp + 一个 MapComponent。
>
> 代价：决策偶尔会不最优（比如中间隔着一堵墙）。收益：你不会因为 1.6 寻路重构而在两年内反复重写。**第一版就应该这么定。**

### 3.3 建议的架构（【推断/建议】，供一次设计对）

```
MyMod_SharedBike
├─ Defs/
│   ├─ ThingDef_SharedBike.xml        ThingDef (含 CompProperties_SharedBike)
│   ├─ ThingDef_BikeRack.xml          停靠桩（可选）
│   ├─ JobDef_SharedBike.xml          <driverClass>MyMod.JobDriver_RideSharedBike
│   ├─ ThinkTreeDef_RideSharedBike.xml  <insertTag>Humanlike_PostMain</insertTag> + <insertPriority>
│   └─ StatDef patch (可选)            给 MoveSpeed 加你的 StatPart
├─ Source/
│   ├─ CompSharedBike.cs              IExposable；字段：是否被骑、当前骑手、上次还车 tick
│   ├─ SharedBikeManager.cs           MapComponent：上车索引/空间分桶、最近车查询缓存、熔断
│   ├─ JobGiver_RideSharedBike.cs     ThinkNode_JobGiver；决策"要不要去取车"
│   ├─ JobDriver_RideSharedBike.cs    Toils: Goto车 → 上车(Instant) → Goto终点 → 还车(Instant)
│   └─ Patch_TicksPerMove.cs          Harmony Postfix Pawn.TicksPerMove(bool)，读 Manager 状态
└─ Patch/                             Harmony patch（只 patch Pawn.TicksPerMove）
```

要点：
- 车的位移**只在"上车/下车"两个瞬时点写入**（还车时用 `CellFinder`/`GenPlace` 找一个合法格，或就近放入停靠桩的 `ThingOwner`）。
- 断线兜底：`JobDriver.AddFinishAction` + `Pawn_HealthTracker.MakeDowned/SetDead` 补丁（Giddy-up 的 `Pawn_HealthTracker.cs` 就是范例）→ 任何情况下都必须"人车解绑 + 车停原地"。
- 所有跨 tick 状态必须 `IExposable`（`Scribe_References.Look(ref currentRider, ...)` / `Scribe_Values.Look`）。
- 查询"最近的闲车"必须缓存/分桶，不能每 tick 全图遍历。

## 4. 最难的部分：哪 20% 决定了 80% 的成败？

### 4.1 那 20%

**不是"给小人加速"，也不是"插思考树"。** 两者各自只需要 20–60 行。真正决定成败的是这三件事：

**① 「人车解绑」必须是一条无死角的总线（占 ~40% 的成败）**
只要有一处执行路径没走解绑，就会出现：小人已经死了/倒地/被关进监狱，但车永远挂在它身上 → 全殖民地少一辆车、且这个 bug 只在特定情况下偶发。
必须覆盖的路径（每条都是真实存在的）：
- Job 正常完成 / Job 被打断（战斗、Draft、饥饿、疲惫、精神崩溃、lord 征召）
- 小人倒地（`Pawn_HealthTracker.MakeDowned`）、死亡（`SetDead`）、被囚禁、被麻醉/手术
- 读档（`ExposeData`）、存档时人在车上
- 车本身被摧毁/烧毁/被拆除（`Comp` 的 `PostDeSpawn`）
- 小人被 `Teleport`/远行队带离地图
Giddy-up 的处理方式（`Pawn_HealthTracker.MakeDowned/SetDead` 两个 Postfix + `ExtendedPawnData.reset()`）是**下限**，不是完整解 —— 它就没有覆盖"存档中途"。**你必须在第一版就把这条总线设计出来，否则第二版必然重构。**

**② 「车停在哪」的规则（占 ~25%）**
- 还车时把车放到小人脚下 → 可能生成在门洞里、墙上、别人身上、屋顶外、不可通行格。必须用格合法性搜索（`GenPlace`/`CellFinder` 系列，具体 API 需确证）。
- 目的地会形成"车的堆积"（所有人都骑到同一个仓库）→ 需要"停靠桩 / 车位"概念，或定期把车"回收"。
- 车是可通行的 Thing → 会不会挡路？会不会被 `Pawn_PathFollower.WillCollideWithPawnAt` 当成小人绕行？会不会被 Haul 任务搬走？→ 需要 `CompForbiddable` / 禁止搬运 / 特殊 `ThingCategory`。

**③ 存档格式（占 ~15%）**
"骑行中"是**跨对象、跨 tick 的状态**（小人 ↔ 车 双向引用）。`ExposeData` 写错一个引用（比如忘了 `Scribe_References.Look`，或者用了 `Scribe_Values` 存了一个 ThingID 但没做 null 校验），读档后就是"人速度永久异常"或"车永久被占用"。**这个 bug 只在玩家玩到一半存档再读时出现 —— 你测试时不一定碰得到。**

### 4.2 看起来难、其实简单（别在这里过度设计）

| 看起来难 | 实际 |
|---|---|
| "往思考树插新行为，肯定要 Harmony patch 一堆 vanilla 树" | **一行 XML**：自己的 `ThinkTreeDef` 写 `<insertTag>Humanlike_PostMain</insertTag>` + `<insertPriority>`。Ludeon 的注释明确说这是给 modder 的 hook，且多个注入按 priority 排序。【一手·XML】 |
| "加速要改 StatDef / PawnCapacityDef / 各种系统" | 只需要一个 Postfix 打在 `Pawn.TicksPerMove(bool)` 上。Giddy-up 就是这么做的，而且 1.6 的这个方法**仍然是唯一出口**（IL 确证 `TicksPerMoveCardinal/Diagonal` 都汇到它）。 |
| "共享 = 得自己写一套占用管理" | `ReservationUtility.Reserve(..., maxPawns: 1, stackCount: 1, layer, ...)` + Job 生命周期自动 Release，就是"一人一辆、用完归还"。vanilla 工作台就是这么共享的。 |
| "骑乘要把小人 despawn、要处理需求冻结、要重新入场" | **不需要**。Giddy-up 的路线里小人**始终是正常 spawned Pawn**，只改速度和渲染。【一手·源码】 |
| "要自己做 A/B 路径代价比较才能决策" | 【推断】建议不要。用直线距离估算 + 阈值即可（见 §3.2）。原版自己的 AI 就是这个精度。 |

### 4.3 看起来简单、其实很坑（这里会吃掉你最多次迭代）

| 看起来简单 | 实际 |
|---|---|
| "给小人挂个 Hediff 就加速了" | 会进健康面板、可被治疗/手术移除、`isBad`/`makesSickThought`/`makesAlert`/`tendable` 全都会产生可见副作用；任何医疗类 mod 都可能清掉它。而且 **`statOffsets` 不在 `HediffDef` 上，在 `HediffStage` 上**（XML 层级容易写错）。 |
| "做成装备/Apparel 就行" | 倒地/被剥光/囚犯化/麻醉时装备会脱落 → 车凭空消失。还会占装备槽、和品质材质外观系统纠缠。 |
| "车是可通行 Thing，随便放" | 会和寻路碰撞逻辑、Haul 任务、`CompForbiddable`、区域/房间判定产生一连串交互。 |
| "骑车状态存个 bool 在小人身上就行" | 存档时双向引用（`Pawn` ↔ `Thing`）必须 `Scribe_References`；只存 ID 不存引用、或忘了在 `PostExposeData` 里做 null/死亡校验 → 读档即坏档。 |
| "每 tick 找最近的车" | O(小人 × 车)。人口一多直接掉帧。必须 MapComponent + 空间分桶 + 脏标记。原版 1.6 为这种"脏了就重算"专门提供了 `Pathing.RecalculatePerceivedPathCostAt(IntVec3)` / `RecalculatePerceivedPathCostUnderThing(Thing)` / `DisableIncrementalDirtying()`（【一手·本机】），说明这种缓存脏化是原版自己都在打的仗。 |
| "人口越多越划算"（用户的期望） | **【推断】这个期望只在特定条件下成立**：车数固定、人口上升 → 争用上升 → 等待时间上升 → 收益反而下降。要让它"随人口增长产生正收益"，需要：(i) 车数随人口增长（可由玩家或自动建造策略决定）；(ii) 目的地分散（否则大家挤向同一个仓库，此时该建的是"传送/公交线"而不是"共享单车"）；(iii) 有一个轻量的调度——例如按最近/最久未用选车，避免"总有人骑走你要的那辆"。**这条需求本身就是设计上的坑，建议在原型阶段就用数字验证，而不是靠直觉。** |
| "改 terrain 的 pathCost 来造自行车道" | `pathCost` 在 `Verse.BuildableDef` 上，是**全局**的：所有人、动物、袭击者都受益。要做"只对骑车者便宜"，落点是 `Pawn_PathFollower.GetPawnCellBaseCostOverride(Pawn, IntVec3)`（IL 显示它正是 `CostToMoveIntoCell` 的第一步），或自定义 `Building.PathWalkCostFor(Pawn)`。 |

## 5. 需求 → 机制映射（一句话版）

| 需求 | 机制 | 状态 |
|---|---|---|
| 车停在地图各处、谁都能用 | `Thing` + `CompSharedBike`（`IExposable`）+ `MapComponent` 索引 | 【推断/建议】 |
| 小人骑上去更快 | `Harmony` Postfix `Pawn.TicksPerMove(bool)`，或 `RimWorld.StatPart` 挂到 `MoveSpeed/parts` | 【一手·本机】出口确证 |
| 小人自己去骑车 | 自定义 `ThinkTreeDef` + `<insertTag>Humanlike_PostMain</insertTag>` + `JobGiver` + `JobDriver` | 【一手·XML/本机】机制确证 |
| 判断"骑车是否更快" | 直线距离估算（**不要**接寻路代价） | 【推断/建议】 |
| 两人抢一辆车 | `ReservationUtility.Reserve(..., maxPawns:1, stackCount:1, layer, ...)`；Job 结束自动 Release | 【一手·本机】API 确证 |
| 到达后车留在原地 | Job 最后一 Toil：找合法格 → 写入车的 `Position`（`DeSpawn`+`Spawn` 或 `Thing.Position` 变更） | 【一手·本机】API 存在；具体 API 需确证 |
| 存档/读档安全 | 所有跨 tick 状态 `IExposable` + `Scribe_References` | 【一手·本机】API 存在 |
