# 把测试需求变成一次可执行的测试

## 什么时候用

用户说「测一下这个 mod / 验证这个行为 / 跑一遍游戏测试 / 这个功能是不是真的生效」，
或者你要断言任何**游戏内状态**（小人、物件、UI、地图、时间、事件）时。

## 你在做什么

一次测试 = **动作**（改状态）+ **等待**（等到可观测条件）+ **取证**（截图/回读/事件）+ **断言**（证据 vs 期望）。
本仓库已经把「等待」收敛成一条命令：`node src/cli.js wait`（四类来源、一套条件 JSON）。
你的工作不是发明流程，而是**把需求拆成这四件事，逐件用现成原子表达**。

## 七条硬规则（违反即不合格）

1. **禁止 `Start-Sleep` / 固定延时**。动作之后一律用 `wait` 等一个**可观测判据**；判据写不出来 ⇒ 走「停手」流程。
2. **`success: true` 不是证据**。动作返回成功只说明调用过去了，必须回读状态或截图确认。
3. **先查表再猜字段**：`node src/cli.js wait --list`。表里有场景就直接用 `--scenario`；没有才去实测字段名，**并把结果回填成一条登记**。
4. **多实例先归属**：`node src/cli.js status --profile <p>` 的 `bridgeResolution.ok` 为 false ⇒ **不发任何命令**（工具内已有这道闸，别绕开它）。
5. **证据落盘**：产物写 `runs/<日期>-<主题>/`；报告里只给路径 + 结论，不贴长 JSON。
6. **资源纪律**：只开轻 profile；推时间 `Fast` 为上限；`--force` / `--all` 只在用户明确要求时用；不写 `runs/game-process.*.json`（假记录会让别的会话打进假桥）。
7. **不许自己造一次性脚本留在仓库**。要探什么，用 `cli call` / `cli wait` 组合出来。

## 六阶段 SOP

### 1 起实例

```powershell
node src/cli.js start --profile <p> --width 1600 --height 900 --monitor 2   # 会抢一次窗口焦点
# 单独一条 start 命令跑完会连进程树被杀 ⇒ 多步驱动要把启动挂成保活 job（见 skill「起实例」一节）
```

进入下一步的判据：`node src/cli.js wait --profile <p> --source bridge-ready --condition-file ready.json`
（`{"path":"result.ready","equals":true}`）。**「桥接端口能连」不等于「这个桥接是我的」**——归属校验才算。

### 2 进门

```powershell
node src/cli.js wait --profile <p> --scenario 已进图可玩
```

没有这张表就先记着：`playable` 比 `list_colonists` 更早、更稳（没进图时后者连 `colonists` 字段都没有）。

### 3 摆场景

用桥接动作类工具（debug action / 建造 / spawn / 选择 / 开面板…，**清单以 `node src/cli.js tools` 为准**）。
**每一个动作之后都要接一次第 5 阶段**。动作要给的参数（坐标、pawnId、目标格）先在 `tools` / `describe` 里看清楚。

### 4 推进时间

用 `step_game_ticks`（能穿 `forcePause`）；**不要**用 `play_for` 推时间——强制暂停下它可能静默跑 0 tick。
推完看返回值里的 `advancedTicks`：为 0 ⇒ 先去等「无强制暂停窗口」，而不是加大时长。

### 5 等判据

```powershell
node src/cli.js wait --profile <p> --scenario <场景名>            # 首选
node src/cli.js wait --profile <p> --probe <工具名> --condition-file c.json   # 表里没有时
node src/cli.js wait --profile <p> --source process --condition-file dead.json # 等进程没了
node src/cli.js wait --profile <p> --source event --condition-file cnt.json    # 等事件出现
```

读退出码，不要读文本：

| 退出码 | 含义 | 你该做什么 |
| --- | --- | --- |
| `0` | 命中 | 继续 |
| `2` | 超时没等到 | 看 stderr 的 `missingPath`：**字段一直没出现** ⇒ 前置没做（多半没进图）；**值不匹配** ⇒ 判据写错了 |
| `1` | 参数错 / 工具名不存在 / 桥接不可用 / 条件本身写错 | 修命令或修环境，**不要**重试等待 |

### 6 取证与断言

截图 / `cli call` 回读 / `runs/live/<p>.ndjson` 事件，落 `runs/`。
断言 = 把证据与期望写成一句可判真假的话 + 给出证据路径。**写不出可判真假的断言 ⇒ 需求还没说清，回去问用户。**

## 原子清单（缺什么、去哪加）

| 层 | 是什么 | 加一个要动 | 现在 |
| --- | --- | --- | --- |
| 条件算子 | 一个值 vs 一个期望值 | `src/condition.js` 一个 `case` + 文档一行 | 16 叶子 + `all/any/not` + `allItems/anyItem` |
| 采样来源 | 怎么取样/聚合 | `src/wait-sources.js` 一个 sampler | bridge / event / process / bridge-ready |
| 场景登记 | 场景 → 探针 + 参数 + 条件 | **只加一条数据**（`src/conditions.json`），带参数用 `$占位` + `--arg` | 16 条 |
| 游戏内工具 | 改/读状态的动作 | mod 侧加 | `cli tools` 为准 |

**算子的边界**：算子只做单值比较；窗口（`--window-ms`）、计数（`result.counts.<kind>`）、派生量在采样层算好。
`all/any/not` 已布尔完备 ⇒ 复杂测试应当**树更深**，不是算子更多。

**怎么查现有原子**（三条命令，别靠记忆）：

| 想查 | 命令 / 文件 |
| --- | --- |
| 已登记的场景 | `node src/cli.js wait --list`（含证据等级） |
| 游戏内可用的工具 | `node src/cli.js tools`（可加关键词）；单个参数用 `describe <工具名>` |
| 算子与四类来源的快照字段 | [docs/cli-wait-用法-20261024.md](cli-wait-用法-20261024.md) 的算子表与「四类来源」表 |

## 停手规则（最重要的一节）

遇到下面任一情况，**停下来说明并等用户**，不要硬编：

1. 需求里有一个"等"写不成「探针 + 一次单值比较」——例如要等"某封信被处理掉"但没有能按信件查状态的探针。
2. 动作需要运行期参数（坐标 / `pawnId` / 存档名）而登记表表达不了（当前用 `$占位` + `--arg`，但还没有真实条目验证过）。
3. 需求依赖**用户的主观判断**（"看起来对不对"）——那要截图交给人，不要把它伪装成断言。
4. 需要 `--force` 强杀全机进程、或需要动用户正在玩的那一局。

报缺原子的模板：

```
【缺原子】想要：<写下你想要的判据>
- 现在做不到的原因：<探针缺失 / 字段无据 / 需要聚合但采样层没有 / 算子不够>
- 我试过：<命令 + 返回值里的关键字段>
- 需要补：<一个只读探针 / 一个字段 / 一个采样参数 / 一个算子>
- 补上之后能登记成：<场景名> = <探针> + <条件 JSON 形状>
```

判据：**能写成「探针 + 一次单值比较」的，属于补数据；写不成单值比较的，才属于补算子/补采样层。**

## 反例集（这些是错的，复习用）

| 错误写法 | 为什么错 | 正确做法 |
| --- | --- | --- |
| 动作后 `Start-Sleep 2` | 赌时长；快则白等，慢则假失败 | 等一个可观测判据 |
| 拿 `success: true` 当断言 | 调用成功 ≠ 状态变了 | 回读状态 / 截图 |
| 上来就等 `result.colonists` | 没进图时字段根本不存在，白等满超时 | 先等 `playable` |
| 用 `play_for` 推时间 | `forcePause` 下静默 0 tick | `step_game_ticks` + 看 `advancedTicks` |
| 用手写 `runs/game-process.*.json` 造假桥测工具 | 别的会话会把它当真实例，4 次调用打进假桥（真发生过） | 用进程内假对象；不许造记录文件 |
| 多实例时不看归属就发命令 | 可能打进别人的局，而返回看着正常 | 先看 `status` 的 `bridgeResolution` |
| 按 `Player.log` 的偏移/ERROR 计数做断言 | 1.7 的日志全机共用、后启动者整份重写 | 走桥接探针或用 `runs/live/<p>.ndjson` |
| 把长 JSON 贴进对话汇报 | 吃上下文、没法复查 | 落 `runs/`，只给路径 |

## 交付格式

- 证据在 `runs/<日期>-<主题>/`
- 报告写 `docs/` 或 `runs/` 下的 md：**做了什么 → 期望 → 实际 → 结论 → 证据路径 → 未验证项**
- 每条结论标 `【实测】`（真跑过并贴输出）/`【未验证】`
