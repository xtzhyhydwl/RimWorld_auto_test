# 组合 skill 试跑：拿三个真实需求走一遍（2026-10-24）

> 目的：**检验草案好不好用**，而不是检验工具能不能跑。方法：取三个真实需求，严格按
> [组合skill-草案-20261024.md](组合skill-草案-20261024.md) 的六阶段 + 停手规则走一遍，
> 记录**卡在哪一步、缺什么原子、skill 正文哪里没写清**。全程不跑游戏（本轮禁止起停）。
> 口径：`【代码】`= 读源码 / 文档；`【实测·历史】`= 引用仓库里已有的真机记录；`【缺口】`= 现在做不到。

## 案例 1：「验证拒绝来信后小人真的离场了」

（对应 RHAH 票 0008，仓库里已有真机记录）

| 步骤 | 按 skill 应该做什么 | 实际能不能做 |
| --- | --- | --- |
| 摆场景 | 用 debug action 摆出「被困房间 + 拜访者 + 拒绝信」，再用 `click_ui_target` 点拒绝 | 【实测·历史】文档里做过，但**每一步动作的具体工具名与参数要现场 `cli tools` 核对** |
| 等判据① | 「拒绝已生效」 | 【缺口】没有按 `letterId` 查信件状态的只读探针；历史记录里的 `openChoices` / `armedChoiceId` 是**存档里读到的**，不是桥接探针 |
| 等判据② | 「小人离场」 | 【缺口】`list_colonists[].spawned` 字段存在【代码】，但「列表里消失」与 `spawned=false` 用现有算子分不清（前者=路径取不到，后者=字段为假） |
| 取证 | 截图 + 回读 | 可做 |
| 结论 | —— | **按 skill 必须停手**：报「缺 1 个信件状态探针 + 需要能区分『不在列表』与『spawned=false』」。这与当时人工踩出来的结论一致 ⇒ **skill 的停手规则有效**。 |

## 案例 2：「验证工作面板打开后能下 bill」

| 步骤 | 按 skill 应该做什么 | 实际能不能做 |
| --- | --- | --- |
| 进门 | `wait --scenario 已进图可玩` | ✅ 已登记、已真机验过 |
| 动作 | `open_main_tab {mainTabId}` → 等「工作面板已打开」 | ✅ 已登记、已真机验过（动作→闭环样板） |
| 动作 | 选中工作台（`click_cell`/`click_ui_target`）→ 等「选中的是目标建筑」 | ⚠️ 已登记但 `verifiedLevel=field-verified`（条件没跑过）；且「目标建筑」用的是 `contains "Building_"`，**没断言是哪一个建筑** |
| 动作 | 下 bill | ⚠️ 工具名与参数要 `describe` 核对 |
| 等判据 | 「bill 真的挂上了」 | 【缺口】没有「列出某建筑的 bill」的探针 |
| 结论 | —— | **前半段可执行、后半段必须停手**：缺「bill 列表」探针。⇒ skill 需要明确「一个需求可以只测一半吗」——目前正文没写，**这是正文的缺陷**。 |

## 案例 3：「验证饥饿机制 3 天后生效」

| 步骤 | 按 skill 应该做什么 | 实际能不能做 |
| --- | --- | --- |
| 推进 | `step_game_ticks` 推到 3 天的 tick | ⚠️ 3 天 ≈ 18 万 tick；`step_game_ticks` 单次上限与耗时**未知**，可能要分段推 + 每段等 `advancedTicks` |
| 等判据 | 「某个 hediff / 需求值到了」 | 【缺口】探针全名无据（历史上只有 `foodprobe/forbidden_stats` 这类专用探针的思路） |
| 结论 | —— | **必须停手**：缺「读 pawn 需求/hediff」的探针。另外「推 18 万 tick」这件事本身需要新的组合方式（分段推 + 段间等），skill 只说「用 `step_game_ticks`」，**不足以指导**。 |

## 试跑结论：正文要补三节

1. **从需求到判据的拆解四问**（最大的缺口）。三个案例都卡在同一处：需求说的是**人话结果**
   （"离场了"、"bill 挂上了"、"机制生效了"），skill 却直接从"字段"开始讲。
   建议补四问：
   - 这个结果**改动了什么可观测的东西**？（物体存在？字段值？UI 元素？事件？）
   - 它**在什么范围内**可观测？（本图 / 该 pawn / 该建筑 / 全局）
   - 有没有**更早、更便宜**的等价判据？（先等 `playable` 再等业务字段）
   - 如果只能靠人眼看，那就**不该**写成断言（转人工截图）。
2. **「需求只能测一半」怎么处理**。案例 2 前半段完全可测。正文应写：**分段交付**——
   能测的先测并给出证据，做不到的那一段按缺原子模板报，**不许**用"截图看起来对"糊过去。
3. **长推进（数万 tick）怎么等**。补：分段推 + 每段等 `advancedTicks` 落地 + 段间检查是否被窗口/暂停掐住；
   单次上限要现场测，不要假设。
