## §1 核心原则（把用户意图精确化）

### 1.1 时间不是完成信号，只是护栏

- **反模式的定义**：发起动作后 `sleep(固定时长)`，并把"睡醒了"当作"完成了"。
- **为什么它不是充分条件**：动作在第 1 分钟就失败，剩下 4 分钟纯浪费；动作要 6 分钟，脚本会在一件**还没发生的事**上超时。
- **为什么它不是必要条件**：本仓库的最佳实践恰好证明了这点——`scripts\verify-s5-peaceful.mjs:190-210` 推进游戏天数，**不信任 `play_for` 的时长**，而是累计 `advancedTicks`，并以 `stalls`（连续 0 推进次数）而不是时间判停。同一段代码在 `AUDIT.md:279` 被标为"全仓最佳范式"。
- **合法用法（护栏）**：时间只允许出现在三个位置——① **上界**（`timeoutMs`，防止永远不动）② **采样间隔**（`pollIntervalMs`，本身是采样语义）③ **重试退避**。`AUDIT.md:250-285` 已经把 154 个真实等待点分成 45 个合法护栏 / 0 个反模式 / 109 个可疑，本设计的目标就是把那 109 个可疑（`tmp\audit-test\FINAL-suspects.txt`，38 个文件）逐个消灭。

> 施工口径：**新增的任何 `setTimeout`/`sleep` 都必须能回答"它在防什么"**。答"防完成不了" = 护栏，可以；答"等它做完" = 反模式，拒绝。

### 1.2 超时的语义：它是**观察的补集**，是一个分支，不是控制流

定义：设测试声明自己关心的信号集合为 `W`（watch set），一次等待的全过程产生观测序列 `s₀, s₁, …, sₙ`。**超时**的含义精确地是：

> 在 `[t₀, t₀+timeoutMs]` 内，**`W` 中没有任何一条路径发生过变化**（或发生了变化但均不匹配任何已声明的预期分支）。

因此：

- 超时是**可观测事实**（"我看了 73 次，`state.mapCount` 一直是 0"），**不是猜测**。
- 桥接已经把这件事做成了结构化证据：`attempts` / `elapsedMs` / `blockingReason` / `probeFailureCount` / `lastProbeError`（`runs\food-recon\dumps\start_debug_game_ready_mapData_.json:85-94`：`attempts:73, elapsedMs:3944, probeFailureCount:0`）。`attempts` 把"我是在轮询，不是在死等"变成了**可审计事实**（`AUDIT.md:138`）。
- **超时是一个分支**：它和"预期分支"、"意外分支"平级，走同样的处理入口（§5.1），而不是靠 `throw` 直接逃出测试。
- 超时**必须能自证没被提前放弃**：证据包里必须留下 `attempts` 与时间跨度（§5.3）。

同时注意 `probeFailureCount` / `lastProbeError` 的存在说明桥接**区分"条件未满足"与"探针自己坏了"**（`AUDIT.md:211`）。统一层必须保留这个区分：探针抛错 ≠ 条件没满足。

### 1.3 相关性必须**显式声明**——这是机制成立的前提

测试如果不先声明"我关心哪些信号"，只可能退化成两种坏形态：

| 退化形态 | 表现 | 本仓库实例 |
| --- | --- | --- |
| 对一切反应（脆弱） | 任何无关变化都触发判定 | 无直接实例，但 `record-play.mjs:334-375` 的周期性采样器形态最接近 |
| 对一切不反应（固定等待） | 干脆不看，睡够就往下走 | 109 处可疑等待（`AUDIT.md:287-331`） |

所以 **"声明关注范围"（watch set）是本机制能成立的前提**，不是可选优化：

- 声明了 `W` 之后，"无关变化"有了定义：**采样 diff 中落在 `W` 之外的路径**。
- 无关变化**不是被扔掉的**：它们要计数、要进证据包（§5.2），因为"我以为是无关的，其实是相关的"正是最难查的 bug。
- `W` 是**测试用例的一部分**，要写进用例、进报告、可被 review。它同时是"这个测试到底在测什么"的可执行定义。

### 1.4 不确定性只允许出现在两个位置，**绝不允许出现在判定里**

允许：

1. **护栏取值**（`timeoutMs=300_000` 这种"总得有个上限"）；
2. **抽样/重试策略**（间隔、退避、采样密度）。

**不允许**：判定本身。判定必须是确定性函数：

```
relevant(paths, W)      → 集合运算，纯函数
matches(sample, expect) → 布尔表达式，纯函数
decide(diff, branches)  → 按优先级取第一个匹配，纯函数
```

### 1.5 明确禁止"AI 判断变化性质"

用户已明确：AI 的 tool "很多时候也只是一段 markdown 文本，它本身不可信"。因此：

- **不设计**"把 diff 丢给模型，让模型说这是预期内还是预期外"。
- 变化性质的判定只能来自：① 显式的期望表达式；② 操作登记表里登记的"可观测后置条件"（§3）；③ 条件词汇表里的命名条件（§2.1）。
- 这条纪律的代价是"新场景要手写条件"，收益是**判定可复现、可 review、可离线单测**。这个交易必须做。

## §2 三层结构（设计骨架）

```
┌─────────────────────────────────────────────────────────┐
│ ③ 相关性层  本测试声明关心的信号集合 W + 过滤器           │
│    解决：哪些变化算"我的事"；无关变化如何被忽略并留痕      │
├─────────────────────────────────────────────────────────┤
│ ② 分支层    预期分支 / 意外分支 / 超时分支（三者平级）      │
│    解决：变化发生（或始终不发生）之后走哪条路              │
├─────────────────────────────────────────────────────────┤
│ ① 条件层    wait_until(条件)   时间只作护栏               │
│    解决：把"等待"变成"轮询一个可证伪的条件"               │
└─────────────────────────────────────────────────────────┘
```

### 2.1 ① 条件层：`wait_until(条件)`

**解决什么问题**：把"睡够时长"替换为"反复观测一个条件，直到它成立或护栏到期"。它自己不判断相关性，也不决定失败后怎么办——那是②③层的事。

**接口形态**（设计稿；§4.4 给出统一层的完整签名）：

  timeoutMs: 300_000,                                  // 护栏：唯一的时间语义
  intervalMs: 50,
  onPoll: (s, ctx) => ctx.log && ctx.log(`  尝试 ${ctx.attempts}`),
  inject: { now, sleep },                              // 可注入 → 可离线单测
});

### 2.2 ② 分支层：预期 / 意外 / 超时

**解决什么问题**：等待结束只有一个理由吗？不是。至少要区分四种停止，并且每种都走**声明好的**处理路径（不是 `throw`）：

| 分支 | 触发 | 处理 |
| --- | --- | --- |
| **预期分支** | 匹配了某条已声明的期望 | 继续测试；把 `attempts`/`elapsedMs` 记入证据 |
| **意外分支** | 出现了已声明的"反预期"信号（例：`programState` 从 `MapInitializing` **退回** `Entry`） | **立刻停**，不等护栏到期；带证据包走失败路径 |
| **超时分支** | 护栏到期，`W` 内无任何匹配 | 记录"观察的补集"（还观察到了什么、`attempts` 多少），按用例声明的策略处理（失败 / 降级 / 标 inconclusive） |
| **探针故障** | `probe` 自身抛错（对应桥接的 `probeFailureCount`/`lastProbeError`） | **与超时严格区分**：这是"我们瞎了"，不是"它没发生" |

**接口形态**：

```js
await waitForChange(probe, {
  what: '开局殖民地',
  watch: SIGNALS.scene,                       // ③
  branches: [                                  // ② 按优先级排列
    { name: 'map-ready',  when: d => d.mapDataReady.to === true,     action: 'continue' },
    { name: 'rolled-back',when: d => d.programState.to === 'Entry',  action: 'unexpected',
      why: '启动第一分钟就失败了 —— 此时不该继续等剩下 4 分钟' },   // ← 用户口述的正是这条
    { name: 'never-started', on: 'timeout', action: 'fail',
      detail: ctx => `尝试 ${ctx.attempts} 次，mapCount 始终 ${ctx.last.mapCount}` },
  ],
  timeoutMs: 300_000,
});
```

**"提前失败"必须是一等公民**（`AUDIT.md:580` 指出：方式 1/2/3 **都不会提前失败**，条件永不成立时一定耗满超时）。目前全仓只有 `src\launcher.js:301-306` 做到了（进程死亡 → 立即抛）。设计上它必须进统一层，作为 `failFast`。

### 2.3 ③ 相关性层：声明集合 + 过滤器

**解决什么问题**：观测是全面的（`get_bridge_status` 一次给你 18 个 `state` 字段 + 顶层十几个），但**只有一部分与本测试有关**。相关性层负责：从采样 diff 中切出 `relevant` 与 `ignored` 两份，并让"忽略"这件事**有据可查**。

**接口形态**：

```js
/** 信号集合：按"关心面"分组（字段路径，点号表示层级，[] 表示数组逐元素） */
export const SIGNALS = {
  scene:   ['state.programState', 'state.inEntryScene', 'state.hasCurrentGame',
            'state.mapCount', 'state.currentMapReady', 'state.playable', 'state.longEventPending'],
  pawn:    ['colonists[].pawnId', 'colonists[].position', 'colonists[].job',
            'colonists[].selected', 'colonists[].drafted', 'colonists[].dead'],
  ui:      ['targets.uiState.openMainTabId', 'targets.uiState.windowCount',
            'targets.uiState.floatMenuOpen', 'targets.uiState.topWindowType'],
  cell:    ['cell.things[].defName', 'cell.terrainDefName', 'cell.zone.id',
            'cell.designations[].defName'],
  letters: ['letters[].letterId', 'letters[].defName'],
  logs:    ['logs[].sequence', 'logs[].level'],
};

/** 过滤器：显式声明"这些即使变了也不算我的事"（必须写明理由） */
const FILTERS = {
  ignore: [
    { path: 'state.fadeOverlayAlpha', why: '淡入淡出动画，与用例语义无关（AUDIT.md:209 证明 playable 不看画面）' },
    { path: 'state.timeSpeed',        why: '除非用例在测时间控制' },
  ],
  // 噪声预算：无关变化超过阈值 → 报"声明可能不完整"，而不是静默
  noiseBudget: { maxIgnoredChanges: 200, onExceed: 'warn' },
};
```

**切分规则（纯函数）**：

```
diff  = 逐路径比较 s_{i-1} 与 s_i（数值/字符串/布尔/null，数组按稳定键匹配）
watch = 展平(W)
relevant = { p ∈ diff : p ∈ watch }
ignored  = { p ∈ diff : p ∉ watch 且 p ∉ FILTERS.ignore.path }
filtered = { p ∈ diff : p ∈ FILTERS.ignore.path }
```

`ignored` 与 `filtered` **都要进证据包**。区别：`filtered` 是"我事先声明了不看、并写了理由"；`ignored` 是"我没声明但也没关心"——**后者是潜在的设计漏洞信号**（用例声明不完整时会膨胀）。

⚠ **硬性纪律（2026-10-13 实测新增）：写 `watch` / 条件时必须核对字段的大小写风格。** 同一份状态在桥接里**有两套拼法**：

| 来源 | 风格 | 例 |
| --- | --- | --- |
| `get_ui_state`（顶层） | **camelCase** | `openMainTabId` / `windowsForcePause` / `floatMenuOpen` |
| `get_selection_semantics.uiState` | **PascalCase** | `OpenMainTabId` / `WindowsForcePause` / `FloatMenuOpen` |

**混用会静默取到 `undefined`，而且不报错** —— 这是本文记录的第 **3** 个「语义静默漂移」实例（前两个见 §0.3、§3.3 的 `rimworld/`↔`rimbridge/` 命名空间混用）。证据：`tmp\bridge-contracts\CONTRACTS.md` §4.1 末段。

**推论**：`watch` 里的每一条路径**必须来自真实返回的抄录**（§0.5 的教训），并且在离线单测里加一条"路径必须能在样本上解析出非 `undefined`"的断言 —— 这样拼错风格会在**离线阶段**就暴露，而不是在游戏里静默失败。

**具体例子（RimWorld 真实场景：生成一个东西并确认它出现）**

现状：

```js
// scripts\recon-food-A.mjs:84-88 —— 同一语义动作靠 120/150ms 顶替，全仓 12 种时长（AUDIT.md:378）

await sleep(120);

```

设计后：

```js

const seen = await waitForChange(
  () => call('rimworld/get_cell_info', { x, z }),
  {
    what: 'Pemmican 出现在 (x,z)',
    watch: SIGNALS.cell,                                    // ③ 只关心格子的 things/zone/designations
    branches: [
      { name: 'appeared', when: (d) => d['cell.things[].defName'].added.includes('Pemmican'),
        action: 'continue' },
      { name: 'spawned-then-lost', when: (d) =>
          d['cell.things[].defName'].removed.includes('Pemmican'), action: 'unexpected',
        why: '出现了又消失 —— 多半被堆叠/销毁逻辑吃掉，属预期外' },
      { name: 'timeout', on: 'timeout', action: 'fail',
        detail: (ctx) => `${ctx.attempts} 次未观测到；格内现有 ${ctx.last.cell.solidThingDefs}` },

```

### 2.4 三层如何合成（端到端走查：开局载入殖民地）

```
① 条件层  waitUntil(probe = get_bridge_status, satisfied = programState==='Playing' && currentMapReady)
② 分支层  branches = [ map-ready(continue) | rolled-back(unexpected) | never-started(timeout→fail) ]
③ 相关性层 watch = SIGNALS.scene；ignored/filtered 进证据
```

- **一次探针调用同时服务三层**：探针给出采样 → ③ 切分相关/无关 → ① 判条件 → ② 按匹配结果选分支。这就是"不要为每个测试写专属等待函数"的落地形态：**测试只声明三样东西（probe / watch / branches），等待原语是共用的**。
- 顺序上 ③ 先于 ①：**只有相关的变化才允许触发条件判定**。否则 `state.fadeOverlayAlpha` 每帧都在变，会假性"有变化"。

## §3 原子操作登记表（"操作定义必须清晰"）

### 3.1 表的格式

> **可组合性的前提**：每个原子操作必须有**明确的前置条件、明确的效果、可观测的后置条件**。只有后置条件可观测，高级操作才能由原子操作组合出来。没有后置条件的动作，调用方就**只能**用时间去顶替——`AUDIT.md:287-380` 的 109 处可疑等待全部是这个根因。

一台台账，一行一个操作，列固定为：

| 列 | 含义 | 填写规则 |
| --- | --- | --- |
| **操作名** | 桥接能力名或库级函数名 | 桥接能力用全名（含命名空间），库级用 `文件:函数` |
| **类别** | 读 / 同步 / 异步 / 等待 | 沿用审计的五分类（`AUDIT.md:40-51`）：(a) 读、(b) 同步动作、(c) 异步动作、(d) 等待原语 |
| **前置条件** | 调用前必须为真、且**可观测**的条件 | 必须写成"某个能力的某个字段等于什么"，不允许写"环境正常" |
| **效果** | 游戏状态发生什么变化 | 一句话；不确定的写"未确证" |
| **可观测后置条件** | **本表的核心列**。动作之后读**哪个能力的哪个字段**、期望是什么 | 必须给 `能力 + 字段路径 + 期望值`；没有就写 `缺`，并进 §3.3 待补 |
| **护栏超时** | 上界（不是预计值） | 写默认值 + 仓库实际用法（两者常不同，要写清） |
| **证据来源** | 追得到的证据 | 文件:行；引用 `runs\tools.json` 时**必须带快照日期**，并记住它是 `vanilla`/134 的**过期**快照（§0.4） |

**填写纪律（三条）**

1. **`可观测后置条件` 不许写"返回 success"**。`SKILL.md:36-37` 已把这条写成第一原则：*"`success: true` 只表示调用返回了，不保证游戏真的变了"*。**2026-10-13 实测更正把它升级为更强的一条**：`success:true` 不仅不保证"变了"，**甚至不保证"做的是你让它做的那件事"**（`close_main_tab` 的语义静默漂移，§0.3）——所以凡"不传必填参数会退化成另一种行为"的动作，登记表必须显式写出**退化后的语义**。
2. **反推字段必须标记**。因为没有一个能力声明过 `outputSchema` 字段（134/184 两次普查一致，§0.2），所有字段都是从 description / inputSchema / 真实快照反推的，登记时必须写 `（反推：<来源>）`。
3. **append-only**：与真值表同一纪律（`docs\共享单车-机制真值表.md:452-478`）。

### 3.2 已登记操作（24 个桥接能力 + 4 个库级组合操作 + 1 个库级工具 = **29 行**）

> **2026-10-13 实测更正**：本表所有形如「`runs\tools.json`（2026-10-03）」的证据引用都指**离线快照**；该快照已证明**会过期**（在线 184 vs 快照 134，§0.4）。**能力存在性、参数名、`inputSchema` 一律以在线清单为准**；快照只作为取证留痕。

| 用途 | 能不能 | 说明 |

3. **`stateBefore`/`stateAfter`/`effects` 框架（见 §3.3）是"语义层基线"**，比 `operation` 段更接近完成信号，但**仍需逐动作确认它真的包含你关心的那个字段**。

### 3.4 登记表怎么用（施工规则）

1. **写测试前先查表**。要用一个没有登记行的动作 → **先补登记行**（含后置条件），再写测试。这条是"越测越完善"的机制：表增长 = 能力增长。
2. **后置条件缺失的动作，禁止直接在测试里 `sleep` 顶替**。要么补后置条件，要么在用例里显式写 `KNOWN_GAP` 并在报告里标"本条依赖时间护栏，判据弱"。
3. **登记行是可执行的**：`可观测后置条件` 列的内容应当能直接翻译成 §2.1 的 `satisfied` 谓词（`能力 + 字段路径 + 期望值` → JS 表达式）。巡检脚本可以校验"测试里用到的能力是否都有登记行"。

### 4.2 取舍结论：**不新建平行机制**；Node 侧 `waitUntil` 做唯一原语，`rb.poll` 做桥接侧加速器

**为什么不新建**：桥接层**已经有** `rb.poll`（`runs\food-recon\dumps\lua_reference.json:321-347`：*"Invoke one capability repeatedly until the shared continue condition model matches or times out"*）＋ `readiness` 词表 ＋ 6 个等待原语。再叠一套"自己的轮询 DSL"就是第二套机制，与"越测越完善，不是越测越臃肿"直接冲突。

**为什么主原语必须落在 Node 侧**（三条理由，都能追到证据）：

1. **`outputSchema` 全空（§0.2）** → 条件必须建在"我们自己反推并登记过的字段路径"上。条件写在 Node 侧，字段路径的来源（登记表）与使用者（条件函数）就在同一个仓库、可 grep、可 review；写进 `rb.poll` 的 JSON 里则**断掉了这条追溯链**（改字段名不会报错，只会静默不匹配）。
2. **条件算子集**（2026-10-13 实测更正：**已确证，不再"未确证"**）。`AUDIT.md:613` 时只确证了 `all`/`path`/`equals`/`countEquals`/`allItems`/`in`；现已知**全集 = 15 个条件算子 + 21 个表达式算子**（§2.1.1），**足以表达 §2.3 那类条件**。但"判定留在 Node 侧"的结论**不变**，理由改成两条**长期**理由：① **离线可测性**（§4.2 理由 3）；② **追溯链**——把条件写在 JS 里，字段路径与登记表在同一个仓库可 grep；写进 `continueUntil` 的 JSON 里则断掉这条链（改字段名不报错，只会静默不匹配；对照 §2.1.1 的两套根上下文，混用正是这种静默失败）。
   **`rb.poll` 的正确用法**因此更明确：它不是"判定引擎"，是**减少往返的执行器**。
3. **离线可测试性**：`dropbisect.mjs:1498,2555` 的注释已经证明这条路的可行性——"注入 `read`/`now`/`sleep` 三个依赖即可离线单测，不用真等 120 秒、也不用启动游戏"。Node 侧原语天然可注入（`sleep` 是模块级依赖），而 `rb.poll` 只能**在线**验。**判定逻辑必须能离线测**，否则每次改条件都要开一次游戏（几十分钟）。
   - 反证：现在 5 种实现里**只有 5 号**可离线测，而它**恰恰是唯一一个区分三种停止原因的**——这不是巧合，可离线测的实现才会长出好语义。

**`rb.poll` 的正确定位（阶段 4 才启用）**：

- 用途 A：**一次调用内完成的 mutate-then-poll**（省掉 N 次 GABP 往返）。官方指引明写 *"Mutate first, then poll. Do not loop a mutating capability unless retries are part of the intended behavior."*（`lua_reference.json:609`）。
- 用途 B：**长跑循环里的桥接侧等待**，例如推进天数时等 `mapCount`（把等待的往返成本放到桥接侧）。
- 前置：**先确证条件算子全集**（§9 未确证 #1），并把确证结果写进登记表。
- 纪律：`rb.poll` 里用的每一个字段路径，**必须同时出现在登记表的"可观测后置条件"列里**。做不到就不许用。

**桥接自带的 6 个等待原语**：统一层**调用**它们，**不重写**。`readiness` 词表直接用（`AUDIT.md:213-221` 已论证它就是一套可复用的条件词汇表）。

## §5 分支与失败处理

### 5.1 三分支的接口形态

三层里的②层，落地成一个**声明式分支表**（不是 `if/else` 散落在测试里）：

```js
const BRANCH = {
  expected:   (name, when, { why, evidence }) => ({ name, when, action: 'continue', why, evidence }),
  unexpected: (name, when, { why, evidence }) => ({ name, when, action: 'unexpected', why, evidence }),
  timeout:    ({ detail, action = 'fail' })  => ({ name: 'timeout', on: 'timeout', action, detail }),
};
```

用法（开局殖民地）：

```js
await waitFor(() => call('rimbridge/get_bridge_status'), {
  what: '开局殖民地',
  watch: SIGNALS.scene,
  branches: [
    BRANCH.expected('map-ready',   d => d['state.currentMapReady'].to === true,
                    { why: '登记表：start_debug_game_ready 的 wait 段判据' }),
    BRANCH.unexpected('rolled-back', d => d['state.programState'].to === 'Entry',
                    { why: '启动失败，退回主菜单 —— 不该继续等' }),
    BRANCH.timeout({ detail: ctx => `尝试 ${ctx.attempts} 次；mapCount=${ctx.last.state.mapCount}；blockingReason=${ctx.last.blockingReason ?? 'n/a'}` }),
  ],
  timeoutMs: 300_000,
});
```

**纪律**：

- `action: 'unexpected'` 的分支**优先级高于 `timeout`**，且必须能**提前中断**（否则"第 1 分钟失败"仍然会耗满护栏）。
- 每个 `why` 都必须是**可追的证据**（登记表行号 / 审计行号 / 实测快照），不许写"经验上会这样"。
- 超时分支的 `detail` **必须来自 ctx**（`attempts`/`last`），不许写死文案。

### 5.2 "无关变化"如何被忽略（信号过滤的具体设计）

1. **声明集合**（`watch`）：见 §2.3 的 `SIGNALS`。
2. **显式过滤器**（`filters.ignore`）：每条必须带 `why`。
3. **未声明但发生了变化** → `ignored`，计数进证据；超过 `noiseBudget` 报 `warn`（"你的声明可能不完整"）。
4. **判定顺序**：`relevant` 为空 → **本次轮询不产生任何分支判定**（这就是"忽略"的实现，不是"看不见"）。
5. **`ignored` 的用途**：报告里给一节"本次运行观察到的无关变化 Top-N"。这比"事后看日志找线索"强——它把"我以为是无关的"变成可复查的清单。
6. **路径必须能解析（2026-10-13 新增的硬性检查）**：每条 `watch` 路径在**样本上必须解析出非 `undefined` 的值**；解析失败 = **用例错误**，立即失败并报出"这条路径在你的样本里不存在（可能是大小写风格写错，见 §2.3）"。理由：大小写风格混用（`openMainTabId` vs `OpenMainTabId`）会**静默**变成"这个信号从未变化"，从而让判定退化成固定等待——这正是本设计要根除的形态。

> 反例（现状）：`recon-food-B7.mjs:79` 之后直接 `get_ui_layout` 抠文本、正则匹配 `/growth|rice|harvest/`（`AUDIT.md:371-380`）。这是**既没有声明集合、也没有过滤器**的形态：它不区分"这一格变了"和"另一格变了"，也不区分"选中变了"和"文字渲染变了"。后果是**得出看似成功的错误结论**（`% grown` 看起来没变，其实是读到了上一格）。

#### 闸 1b —— 参数名校验（**待做**，2026-10-13 新增）

**为什么必须"客户端侧 + 静态"**：因为桥接**不强制** `additionalProperties:false`（§0.3 实测），失败模式是**语义静默漂移**（无报错、无异常、`success:true` 但做的是另一件事）。运行时**没有任何可捕获的信号**，所以校验只能在**发请求之前**做。

**具体设计（施工稿）**

1. **数据来源（权威）**：**当次会话在线取到的 `inputSchema`**。
   - 取法一：`client.listTools()` 已返回每个工具的 `inputSchema`（`src\cli.js:145-158` 的 `dump-tools` 就是这么导出的）——**首选**，因为 1a 已经在同一次调用里拿到了它，零额外往返。
   - 取法二：`node src/cli.js describe <工具名>`（`src\cli.js:160-174`）——**单工具、调试用**，不做批量路径。
   - **不读 `runs\tools.json` 当权威**（§0.4）。
2. **新鲜度问题的解法（本设计的取舍）**：**会话内缓存 + 强制一次性权威快照**。
   - 每条测试运行在开局取一次 `listTools()`，得到 `Map<name, inputSchema>` 并在**进程内缓存**；同一进程内不再刷新（避免每条调用一次往返，也避免中途不一致）。
   - 缓存是**进程级、当次会话级**的，不落盘、跨运行不复用——**这就是"新鲜度"的解法：不追求跨运行的新鲜，只追求"与本次会话一致"**。
   - 落盘只作为**取证留痕**（供事后复核"你当时看到的 schema 是什么"），不作为下次运行的数据源。
   - 若某次运行取不到在线清单 → 按 1a 同款策略：**跳过 1b 并 warn**，并在证据里标 `schemaUnavailable:true`。
3. **校验规则（按严重度）**：

   | 规则 | 判定 | 依据 |
   | --- | --- | --- |
   | 传入的键不在 `inputSchema.properties` 里 | **硬失败**（并给最近的候选键，编辑距离） | §0.3：未声明参数被静默忽略 → 语义漂移 |
   | 键名大小写不一致（如 `MainTabId`） | **硬失败**，候选里报"正确大小写是 `mainTabId`" | §0.3 实测 A7 |
   | 必填（`required[]`）缺失 | **硬失败** | §0.3 实测 `open_main_tab({tabId})` → `"A RimWorld main tab id is required."` |
   | 必填存在但值为空串 | **硬失败**（提示"空串等同于没传"） | §0.3 实测 C4：`mainTabId:""` → 退化成无条件关闭 |
   | `inputSchema` 为 `{}` / 无 `properties`（工具没声明契约） | **不校验，不发警告**，证据里记 `unverifiable:true` | 例：`rimworld/start_debug_game` 的 `inputSchema` 就是 `{}`——那是工具没声明，不是调用方的错 |
4. **落点**：`callChecked(client, name, args, {schema, …})`（§4.4）。`assertToolNameExists()`（1a）之后、`callTool` 之前。
5. **离线巡检（升级已有的那条）**：现有计划里的"扫全仓 `call('字面量')`"脚本，**加上"扫参数名字面量 vs 快照 schema 的键集"**。但**其结果只作为"待复核清单"，不作为 CI 门禁**——因为快照可能少 50 个工具、`inputSchema` 也可能变，门禁会产生**假失败**。门禁只认**在线 schema**（运行时校验）。
6. **验收**：至少有一个**回归用例**覆盖 §0.3 的七种输入（`mainTabId` 正确 / `tabId` / `{}` / `bogusParam` / 错大小写 / 空串 / 不匹配的值），**前六种在客户端就被拒绝**，不再发到桥上。

#### 闸 2 —— 禁止无记录的 `catch`

- 规则：**不允许出现 `catch(() => {})` / `.catch(()=>{})`**。允许两种写法：
  - `callChecked(..., {onError:'raise'})`（默认）；
  - `callChecked(..., {onError:'record'})` → 错误进 `evidence.suppressed[]`，且**在报告里单独列一张"我主动忽略的错误"表**。
- 巡检：正则扫 `catch\(\(\)\s*=>\s*\{\s*\}\)|catch\(\(\)\s*=>\s*null\)`，命中即失败。现状数量可观（例：`verify-5-actions.mjs` 里 8 处 `wait_for_long_event_idle` 全带 `.catch(()=>{})`，`AUDIT.md:493`），因此**先做巡检脚本、再逐步改**，不要一次性改 100+ 处。
- **降级也不许静默**：故意吞超时的模式（`AUDIT.md:416` 记录 14 处 `start_debug_game_ready(...).catch(e => log(e.message))`）是**合法**的（有记录），要保留并明确写成 `{onError:'record'}`，与静默的 `catch(()=>{})` 区分开。

**闸 3 —— "等过了"必须有回执**

- 统一层每次等待都产出回执（`stopReason`/`attempts`/`waitedMs`），并且**必须落进报告**。判据：报告里出现"等待"字样却没有 `attempts` 的行 = 违规。
- 桥接已经把这件事做成结构化了（`attempts:73`、`elapsedMs:3944`），但**只有 `smoke.js:176` 用了 `blockingReason`，全仓无一处消费 `attempts`**（`AUDIT.md:488`）。所以闸 3 的一半工作是**消费已有的证据字段**。**现已实测的 `attempts` 来源有 4 处**（2026-10-13）：
  1. 6 个等待原语的顶层 `attempts` / `elapsedMs` / `probeFailureCount` / `lastProbeError`；
  2. `play_for` 的 `attempts` / `probeFailureCount` / `lastProbeError`（实测 `durationMs:200, pollIntervalMs:25 → attempts:8`）——**桥接把"我是在轮询"也返给了调用方**；
  3. **`run_script` / `run_lua` 的 `script.report.steps[].stepReport.attempts`** —— **`attempts` 是 `stepReport` 的一等字段**（`CONTRACTS.md` §5.4，形状 `{index, id, call, success, attempts, result, error}`）。这是**桥接侧脚本的天然回执落点**：只要用 `continueUntil`，每一步的轮询次数自动进报告；
  4. 每个返回的 `operation` 段（§3.2.7）提供 `DurationMs` 与 `OperationId`，作为"操作层"回执。
- **与 §1.2 同源**：`attempts` 把"我在轮询，不是在死等"变成**可审计事实**；闸 3 要求**任何"等过了"的结论都必须带上它**。
- ⚠ **未确证**：`attempts` 的确切语义（是否含首次立即探测）仍未定论（§9#10）。因此**报告里要同时记 `attempts` 与 `waitedMs`**，不要只记一个。

## §10 术语表（施工时的共同语言）

| 术语 | 定义 |
| --- | --- |
| **护栏（guard rail）** | 时间在等待中唯一的合法角色：上界 / 采样间隔 / 退避。护栏到期**不表示失败**，它表示"该走超时分支了" |
| **关注集 `W`（watch set）** | 用例声明的、与本次测试相关的字段路径集合。相关性判定的唯一依据 |
| **相关变化 / 无关变化** | 采样 diff 中路径 ∈ `W` / ∉ `W`。无关变化不丢弃，进 `ignored` |
| **可观测后置条件** | 动作之后可以**读**出来、用来判断动作真的发生了的 `能力 + 字段路径 + 期望值`。没有它，调用方只能用时间顶替 |
| **停止原因 `stopReason`** | `needle`（命中）/ `settle`（命中且静默期结束）/ `timeout`（观察的补集）/ `unexpected`（命中反预期信号）/ `fatal`（探针或环境坏了）。来自 `dropbisect.mjs:1553,1557,1560` 的三态扩展 |
| **静默失效** | 调用失败（名字错/参数错/被 catch 吞）但脚本以为成功。实锤：`verify-5-actions.mjs:201` |
| **语义静默漂移（semantic silent drift）**（2026-10-13 新增） | **服务端认为成功、客户端也收到 `success:true`，但执行的是另一件事**。它**没有报错可记录、没有异常可捕获**，所以**不能靠运行时发现，只能靠客户端静态校验**。已记录的 3 个实例：① `close_main_tab({tabId})` → 退化为"无条件关闭当前任意 tab"（§0.3）；② `rimworld/` ↔ `rimbridge/` 命名空间混用（3 个实例，§3.3）；③ `continueUntil` 与 `if/while/assert` 的**根上下文混用**、以及 `get_ui_state`（camelCase）与 `get_selection_semantics.uiState`（PascalCase）的**大小写风格混用**（§2.1.1、§2.3） |
| **根上下文（root context）**（2026-10-13 新增） | 桥接条件里"当前根"是什么。**两套**：`continueUntil` → 最新调用步引用（路径以 `result.` 开头）；`if`/`while`/`assert` → 只有脚本变量（路径以 `vars.` 开头）。混用 → 静默取不到值 |
| **操作层完成判据 vs 语义层后置条件**（2026-10-13 新增） | 前者 = `operation` 段（§3.2.7，14 字段：`Status`/`Success`/`Error`/`Warnings`/`DurationMs`），回答"桥接跑完了吗"；后者 = 业务字段（`drafted`/`openMainTabId`/`cell.things[]`），回答"游戏真的变成我要的样子了吗"。**先看后者，再看前者** |
| **探针（probe）** | 一次无副作用的观测调用。可以是 GABP 能力，也可以是读文件/查端口/看进程 |
| **回执** | 每次等待产出的 `stopReason + attempts + waitedMs + relevant/ignored`。没有回执的"等过了"不成立 |
