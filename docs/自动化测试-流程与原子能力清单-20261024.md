# 自动化测试：流程、原子能力、组合规则（2026-10-24）

> 用途：给「怎么把自然语言测试需求翻译成一次可执行的测试」提供**事实底稿**。
> 本文不含模块划分结论（那要用户先看流程再定），只写：**流程有哪几步 → 每步能用什么原子 → 组合时必须守什么规则 → 缺原子时怎么报**。
> 口径：`【实测】`= 真机跑过；`【代码】`= 读源码；`【未验】`= 没验。

## 0. 一句话

测试 = **动作**（改游戏状态）+ **等待**（等到某个可观测条件）+ **取证**（截图/回读/事件）+ **断言**（把证据与期望比）。
本仓库已经把「等待」收敛成一条命令（`cli wait`，四类来源、一套条件 JSON），剩下的是**怎么把它们串起来**——
那部分现在是**靠人/代理临场编**，没有成文的组合规则，也没有可被检索的「原子清单」。这就是缺口。

## 1. 一次测试的六个阶段

| # | 阶段 | 要达成什么 | 可用的原子 | 失败怎么读 |
| --- | --- | --- | --- | --- |
| 1 | 起实例 | 隔离的 RimWorld 在跑、桥接可用 | `cli start`（自带等待）/ 保活 job / `wait --source bridge-ready` | 桥接没出现 = exit 1 且消息带日志尾巴；**不要**当成超时 |
| 2 | 进门 | 进图、能下操作 | `wait --scenario 已进图可玩`（`result.state.playable`） | 字段一直取不到 = 还没进图，不是条件写错 |
| 3 | 摆场景 | 把要测的局面摆出来 | 桥接动作类工具（debug action / 建造 / spawn / 选择 / 打开面板…，**清单以 `cli tools` 为准**） | 动作只给 `success:true` 不算数，必须回读 |
| 4 | 推进 | 让时间/事件走下去 | `step_game_ticks`（能穿 forcePause）【实测】；`play_for` 在 forcePause 下可能静默 0 tick | `advancedTicks` 为 0 ⇒ 先查「无强制暂停窗口」 |
| 5 | 等判据 | 等某个可观测条件成立 | `cli wait`（四类来源 + 16 算子）/ `cli live --until` | exit 2 = 条件没成立；`missingPath` = 字段没出现（多半还没到那一步） |
| 6 | 取证 | 留下可复查的证据 | 截图工具 / `cli call` 回读 / `runs/live/*.ndjson` 事件 / `cli call` 的 JSON | 证据要落在 `runs/`，报告里给路径 |

**阶段 3/4 的每一步之后都必须接一次阶段 5**（动作→闭环）。固定 `Start-Sleep` 一律视为不合格。

## 2. 现有原子能力（四层，各自「加一个」的成本）

| 层 | 是什么 | 住哪 | 加一个要动 | 现在有多少 |
| --- | --- | --- | --- | --- |
| **条件算子** | 单值 vs 期望值的一次比较 | `src/condition.js` | 一个 `case` + 文档一行 + 离线矩阵几例（**不改循环、不改采样**） | 16 叶子 + `all/any/not` + `allItems/anyItem`【代码】 |
| **采样来源** | 怎么取一次样、怎么聚合 | `src/wait-sources.js` | 一个 sampler + `buildSampler` 一个分支 | 4 类：bridge / event / process / bridge-ready【实测】 |
| **场景登记** | 场景 → 探针 + 参数 + 条件 | `src/conditions.json` | 加一条数据（**零代码**）；带参数用 `$占位` + `--arg` | 16 条（4 条真机 wait 验过）【实测】 |
| **游戏内工具** | 真正改状态/读状态的动作 | mod 侧（`mods/`），本仓库用 `cli tools` 列 | mod 侧加工具 | 184 个【实测·上一轮】 |

**边界（用户 2026-10-24 定的原则）**：算子只做「一个值 vs 一个期望值」；
窗口 / 计数 / 派生量一律在采样层算好（`--window-ms`、`result.counts.<kind>`、`result.eventTexts[i].x`）。
`all/any/not` + 两个量词已布尔完备 ⇒ 更复杂的测试应当**树更深**，而不是算子更多。

**完备性现状**：不是所有需求都能表达。已知三类缺口【未验/缺口】：
1. 带运行期参数的动作/探针 — 已支持 `$占位`（`--arg`），但登记表里还没有一条真实用到它的场景；
2. 「至少 N 个」这类计数 — 靠采样层给 `counts` 绕过，没有 `countGreaterThanOrEqual`；
3. 正则 / 集合关系 — 故意不做（`contains` 够用就不加）。

## 3. 组合规则（agent 必须守的，按优先级）

1. **动作→闭环**：任何改状态的动作之后，等一个**可观测判据**再往下走；判据写不出来 ⇒ 这个场景不可测，先补原子。
2. **先查表再猜字段**：`wait --list` → 有场景就用 `--scenario`；没有才去 `cli call` 实测字段名，然后**回填一条登记**。
3. **先便宜后贵**：`hasCurrentGame` → `playable` → 具体业务字段；别一上来等一个要进图才有的字段（会白等）。
4. **多实例先归属**：`status` 的 `bridgeResolution.ok` 为假就**不发命令**（工具已内置这道闸，别绕）。
5. **失败三分**：exit 1 参数/环境错（改命令或先修环境）；exit 2 条件没成立（改判据或延预算）；`missingPath` 字段没出现（多半是前置没做）。
6. **证据落盘**：`runs/<日期>-<主题>/`，报告里只给路径 + 结论；**不许**把长 JSON 贴进对话。
7. **资源纪律**：只开轻 profile、`Fast` 上限、独立 profile、`--force` 只在用户明确要求时用。

## 4. 缺原子怎么反馈（给「常驻需求会话」用的模板）

```
【缺原子】想要：等「某封信被处理掉」之后再断言
- 现在做不到的原因：探针工具全名无据（只有短名 list_letters）
- 我试过：cli call rimworld/list_letters → 返回里没有 letterId 字段
- 需要补：一个能按 letterId 查信件状态的只读探针（或让 list_letters 返回 letterId）
- 补上之后能登记成：「信件已处理」= 探针 + condition
```

判据：**能写成「探针 + 一次单值比较」的，属于补数据（登记表）；写不成单值比较的，才属于补算子/补采样源。**

## 5. 建议的「组合 skill」大纲（草案，等用户切模块后再定稿）

一个 skill 的价值在于：让**没见过这套工具**的代理，看一遍就能把一个自然语言需求变成可执行的测试，
并且**知道什么时候该停下来说「这个原子没有」**。建议分五节：

1. **什么时候用**（触发词：测一下这个 mod / 验证这个行为 / 跑一遍游戏测试）
2. **六阶段流程**（本文 §1，每阶段给一条最小命令 + 失败怎么读）
3. **原子清单与扩展点**（本文 §2：四层各自「加一个」要动什么、去哪加）
4. **组合规则**（本文 §3，写成可勾选自检清单）
5. **什么时候停手**（本文 §4：缺原子的判定与反馈模板；以及「不许用 sleep 代替等待」「不许把 success:true 当证据」）

**待用户定的**：模块线怎么切（上面的「原子四层」是一种切法；也可能按「一个测试用例的生命周期」切），
以及这个 skill 是**并入** `rimworld-auto-test`，还是**单开**一个（例如 `rimworld-test-design`）。
