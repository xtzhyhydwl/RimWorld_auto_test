# 蓝图模板系统（Build Templates）设计

> 来源：用户 2026-10-03 提出的方向。**这一节是接口设计，需要用户确认后才实现。**
>
> 用户原话：
> 「我可以去手动的建造一些样板房……然后我们只需要**找一种方法把它编码编下来**……
> **不一定是要百分百还原，只要物块对得上就可以**。比如说床它可以是别的类型的床，
> 墙壁它可以是别的类型的墙壁，然后光源也可以是别的光源。
> 但是它的一些**基本要素**要有。……它的可能性是很多的。
> 我不希望它是一个**很随机**的东西，反而如果我们有一些样板，
> 那么需要建造的时候**直接抄**就可以。甚至之后可以去**学**。」
>
> 「之后……有那种类型的阵地是**逐步的发展逐步的扩大**……
> 在**空间容量、发展潜力和基地防御能力之间有一个渐进成长**的过程。
> 如果说之后我们的代理能够逐渐的把这样的基地构筑起来，那我觉得他基本上在建筑这个层面就毕业了。
> 要达到这个效果的良好的基础，就是我们要有一个**固定的样式，能够把样板存储起来**。」

---

## 一、这个方向为什么比"程序化生成户型"好

现在 `BuildSitePlanner` 生成的是**我猜的**户型（13×13 + 四边中心各一门 + 3 床 + 1 火把）。
样本化之后：

| | 程序化生成（现在） | 样板库（提议） |
| --- | --- | --- |
| 户型来源 | AI 猜的 | **用户手造的现实设计** |
| 质量 | 未知，可能很蠢 | 久经考验 |
| 可复现 | 是（有固定规则） | **更强**（逐格确定） |
| 可审查 | 要看代码 | **直接看样板文件** |
| 支持"逐步扩张" | ❌ 得自己发明 | ✅ 样板库可以做成有序的 |

**关键判断：建筑这类东西，"抄一个已知能用的设计"远胜于"现场生成一个可能很蠢的设计"。**

## 二、编码设计（核心）

### 2.1 三条设计原则

1. **相对网格 + 角色槽位**，不是绝对坐标
   → 样板可以放到地图任何位置
2. **按"角色"匹配，不按具体 Def 匹配**（用户明确要求）
   → 床槽可以放 `Bed` / `DoubleBed` / 其他 mod 的床；光源槽可以放 `TorchLamp` / `StandingLamp`
3. **人可以读、可以手改**（JSON，不是二进制）
   → 便于审查、便于以后"学"

### 2.2 文件格式（草案）

```jsonc
{
  "id": "basic-bedroom-13x13",
  "name": "基本卧室 13×13",
  "origin": "user",                  // user = 用户手造并导出；builtin = 仓库自带
  "size": { "w": 13, "h": 13 },
  "tags": ["bedroom", "starter"],     // 用途标签：bedroom/workshop/storage/defense...

  // 关键：rotatable = 允许 mod 按地形旋转/镜像后再放
  "rotatable": true,
  "mirrorable": true,

  // 逐格的角色。用紧凑的"行字符串"表示，好处是人能一眼看出形状
  "rows": [
    "WWWWWWWWWWWWW",
    "W...B....B...W",     // W=墙 .=空地 D=门 B=床槽 L=光源槽
    "...",
    "WWWWWWWWWWWWW"
  ],

  // 角色 → 可接受的 Def 列表（按偏好排序）。
  // ★ 这是"不必百分百还原、只要物块对得上"的落点：
  //   匹配时按这个列表 + 当前库存挑一个可用的
  "roles": {
    "W": { "any": ["Wall"] },                          // 任何墙都行（含 mod 的墙）
    "D": { "any": ["Door"] },
    "B": { "any": ["Bed", "DoubleBed"] },              // ★ 别的床也行
    "L": { "any": ["TorchLamp", "StandingLamp", "Campfire"] }   // ★ 别的光源也行
  },

  // 可选：必须满足的条件（放之前校验）
  "requires": {
    "minAreaCells": 121,
    "needsRoofAfterBuild": true,
    "minClearance": 1            // 外围至少留 1 格空地
  },

  // 可选：建议的锚点（"门朝哪"之类的语义）
  "anchors": { "entrance": { "x": 6, "y": 12 } }
}
```

**为什么用"行字符串"而不是二维数组**：13×13 的行字符串在编辑器里**直接就能看出形状**，
可以手画、可以在 diff 里看懂 —— 而 `[[0,1,1,0...]]` 不行。这对"人可以审查样板"很重要。

### 2.3 角色匹配规则（"物块对得上就行"的具体含义）

```
放样板时，对每个非空地槽位：
  1. 取该角色的候选 Def 列表
  2. 依次尝试：有库存吗？ → 能放吗（CanPlaceBlueprintAt）？
  3. 用第一个通过的
  4. 全都不行 → 这个槽位留空，并记进报告（★ 不整个放弃）
```

**决策记录要能解释**：遥测里要能看出"这个床槽用了 `Bed`，因为 `DoubleBed` 没料"。

### 2.4 与现有代码的关系

| 现有 | 样板化之后 |
| --- | --- |
| `BuildSitePlanner` 生成户型 | **改成**：只负责**选址**（找一块放得下的平地）+ **把样板贴上去** |
| `ShelterDomain` 放墙/门/床/火把 | **改成**：遍历样板的槽位 → 按角色匹配 → 放蓝图 |
| `BuildSiteOptions.Size = 13` | 从**样板自己**读尺寸，不再硬编码 |

→ **`BuildSitePlanner` 的几何生成部分会被样板取代，选址部分保留**。
现有的 123 条离线测试里，"户型几何"那部分要改成"样板加载/旋转/角色匹配"的测试。

## 三、怎么"把样板编码下来"（导入路径）

用户说「我可以去**手动建造**一些样板房……然后我们只需要找一种方法把它编码编下来」。
所以**必须有从游戏里导出样板的路径**，否则用户得手写 JSON（不现实）。

### 路径 A：在游戏里导出（推荐）

```
1. 用户照平常那样在游戏里手动画蓝图（甚至直接建好）
2. 调一个工具：foodprobe/capture_template { x, z, w, h, name }
   它扫这块矩形，按格分类成角色（墙/门/床/光源/空地），
   反向生成上面的 JSON（含 roles 的"实际用了什么"）
3. 用户看 JSON、按需手改（比如把 Bed 改成 ["Bed","DoubleBed"] 表示"别的床也行"）
4. 存进 templates/ 目录，commit
```

**优点**：用户零学习成本（照常玩），编码由工具做。
**注意**：导出时只能看到"用户**实际**用了什么"，所以 `roles.any` 的初始值
就是那一个 Def；**"允许别的替代"这一步需要人拍板**（或者我们给个默认的宽松规则）。

### 路径 B：手写 JSON

适合小的、简单的样板（比如"一堵墙 + 一个门"）。作为备选。

### 路径 C（以后）：从既有基地"学"

用户提到「甚至之后可以去**学**」。那是**从已有殖民地反推样板库**，
属于更远的阶段，现在不做，但格式要能支持（因为 A 已经是"从游戏导出"了，方向一致）。

## 四、这为"逐步扩张的成熟阵地"留了什么路

用户描述的目标形态：**空间容量 / 发展潜力 / 防御能力 三者渐进成长**。

样板库天然支持这个，因为扩张可以表达成**有序的样板序列 + 前置条件**：

```jsonc
// 不是现在实现，只是说明格式能承载
{
  "id": "colony-growth-v1",
  "stages": [
    { "template": "starter-room-13x13",
      "when": { "colonists": 3 },
      "placeAt": "nearBaseCenter" },
    { "template": "second-bedroom-13x13",
      "when": { "colonists": 5 },
      "placeAt": "adjacentTo", "to": "starter-room-13x13" },
    { "template": "perimeter-wall-segment",
      "when": { "threat": "raid" },
      "placeAt": "outerRing" }
  ]
}
```

**关键点**：`template` 是**确定的样板**（不是现场生成），
`when` / `placeAt` 是策略（这部分可以以后让 LLM 来定，见设计文档 §三的"慢环"）。

→ 所以**样板系统是"建筑层面毕业"的地基**：把"造什么"固化下来，
让上层只需要决定"什么时候造、造在哪"。

## 五、需要用户确认的点

| # | 问题 | 备选 |
| --- | --- | --- |
| 1 | 样板格式用 **JSON + 行字符串** 吗？ | 还是别的（比如直接存截图+格坐标、或者游戏自己的 Blueprint 存档格式） |
| 2 | **导入方式**：先做"游戏内导出"（路径 A）还是先手写几个样板（路径 B）？ | A 更省你的事；B 更快能看到效果 |
| 3 | **角色匹配的宽松度**：默认就允许"任何墙/任何床/任何光源"，还是要你逐个确认？ | 宽松=更可能放下，但可能放得不伦不类 |
| 4 | 样板放在**仓库里（git 管理）**，还是放在游戏存档目录（你随时改）？ | 仓库能被审查、能进版本；存档目录更灵活 |
| 5 | S4 要不要**先按现在的程序化户型做完**，再换样板？还是**立刻转向样板**？ | 立刻转向能少走弯路；先做完能有个可用基线 |

**我的建议**：**立刻转向样板**（问题 5 选后者），因为
① 程序化户型本来就是我猜的，做完也要被替换；
② 样板系统本身不大（格式 + 匹配 + 导出/放置），而且**可离线测试**；
③ 它能直接吸收你已经造好的房，比我再猜几轮快得多。
