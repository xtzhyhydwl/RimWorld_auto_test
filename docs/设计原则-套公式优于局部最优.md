# 设计原则：**套公式 > 局部最优**（AI 代理玩环世界最需要注意的一点）

> 来源：用户 2026-10-03，在我连续几轮用"算法挑位置"之后：
>
> 「就现在我觉得你在生成一些东西的时候……我感觉还是**按样板来**吧，
>  我们下一步就先**录入样板**。你在生成一些东西的时候，喜欢用某种**神秘的算法**。
>  其实很多时候**这个游戏很简单**啊，就你算法的**最优**，有些时候它只是**局部最优**。
>
>  你长此以往，假如说老是用算法生成随机的规则，那有可能就是**建筑中间或者说区域中间
>  的空隙又没有被考虑**，那整体其实**不够紧凑**。但是假如说你所有的区域、所有的建筑
>  都是那种**四四方方**的，都是那种**四边形**，那实际上整个殖民地就很**规整**，
>  它**空间利用率也比较高**。
>
>  我觉得这可能是那个**AI 代理玩环世界最需要注意的一点**：有些时候 AI 就是要追求
>  **局部最优**，但是其实环世界这个游戏**只要套公式能玩好 90% 的情况**。」

---

## 一、这条原则解决的是什么

### 我的错误模式

我做的每一个"选址"，都是把它当成**一个独立的优化问题**去解：

| 对象 | 我的"算法" | 输出 |
| --- | --- | --- |
| 种植区 | 找最肥沃的连片 | 形状不规则 |
| 储藏区 | K-means 聚类（跟着散落资源走） | 不规则团块 |
| 住处 | 滑窗找离基地最近的可行矩形 | 矩形，但位置随机 |
| 丢弃区 | 边缘找 10×10 方框 | **矩形** ✅ |

### 为什么"不规则"是错的（用户给的推理链）

```
算法追求的"最优"  →  只是**局部最优**（对这一个对象最优）
                  →  形状不规则
                  →  **对象之间的空隙没被考虑**
                  →  整体不紧凑
                  →  空间利用率低
```

### 为什么"全是四边形"是对的

1. **四边形能无缝拼贴** —— 两个矩形并排，接缝是一条线，**零浪费**；
   两个不规则团块并排，中间必然有啃不掉的缝
2. **样板是人设计的** —— 它承载的是"人的经验"，而不是"算法能算出来的极值"
3. **✅ 实测支持**：`EdgeDumpPlanner`（用户当时说"直接靠边画个 10×10，不用管了"）
   是**唯一一个已经符合规范的实现**，而且它也是最简单的一个

## 二、原则本身

> ### **能用公式的地方，不要用算法。**
>
> ### **能用样板的地方，不要用生成。**
>
> ### **算法只在"没有现成公式"时才用。**

### 为什么这条对 AI 代理特别重要

用户说这是"**AI 代理玩环世界最需要注意的一点**"。我理解它的深层原因：

**AI 的本能是"优化"，而优化的默认产物是不规则。**

- 优化器会去迁就地形（肥沃度、资源分布），于是形状跟着地形变
- 而人类玩家**不在乎那点最优** —— 他先拉一个方框，然后在方框里妥协
- **代价对比**：为了多 5% 肥沃度而搞出不规则形状，损失的是**整个殖民地的空间效率**

### 判定方法（怎么知道自己又在"神秘算法"了）

如果一段选址逻辑需要**解释"为什么选这里"**（而不是"规矩就是这么定的"），
那它大概率就是"神秘算法"。对照：

| 说法 | 性质 |
| --- | --- |
| "靠地图边缘画一个 10×10" | ✅ 公式（不需要解释） |
| "找最肥沃的连片，同时兼顾离基地距离和形状紧凑度，用加权评分" | ❌ 神秘算法 |

## 三、具体到下一步：**先录入样板**

用户明确指示：
> 「我们**下一步就先录入样板**。」

所以接下来的动作顺序是：

1. **用户造样板**（卧室 / 仓库 / 厨房 …），形状**一律方形/矩形**
2. **我扫描录进 `templates/`**（工具已就绪且自测 10/10）
3. **把"摆放规范"也做成样板的一部分**：
   - 每个样板带 **tag**（bedroom / storage / kitchen）
   - 每个 tag 有**落位规则**（该贴在建筑区、该靠边、该在中心…）
   - 这些规则**也是数据**（可读、可改），不是我代码里的启发式

→ 这样"殖民地的样子"就完全由**样板 + 规则**决定，**没有算法生成的部分**。

## 四、对现有代码的处置

| 现有 | 处置 |
| --- | --- |
| `EdgeDumpPlanner`（边缘 10×10 方框） | ✅ **保留，作为范本** |
| `StockpilePlanner`（K-means 聚类） | ⚠ **降级**：不再用它定形状，最多用来回答"资源大概在哪" |
| `PlotPlanner`（找最肥沃连片） | ⚠ **改**：先按矩形找地面，再在矩形内看肥沃度（而不是让肥沃度决定形状） |
| `TemplatePlacer.FindBestSite`（滑窗找最近） | ⚠ **改**：改成"按 tag 的落位规则找位置" |
| `MaterialPlanner` / `BuildingRegistry` / `TemplateJson` | ✅ 都是确定性逻辑，保留 |

## 五、这条原则和之前几条的关系

| 原则 | 内容 |
| --- | --- |
| **开局清单 > 样板库 > 域**（可靠性递减） | 能用左边解决的，不要动右边 |
| **套公式 > 局部最优**（本文件） | 能用公式/样板的，不要用算法 |
| **摆放规范**（`docs/摆放规范-设计.md`） | 每种对象的落位规则 |

三条其实是一条：**把"需要判断"的地方压缩到最小，能用确定的东西就用确定的。**

★ 而这条的**证据已经出现过了**：`EdgeDumpPlanner` 是所有选址里
  **最符合规范、最稳定、也最简单**的一个 —— 而它恰好就是用户口述的那句
  "直接靠边画个 10 乘 10，不用管了"。
  **用户的公式一直比我的算法好。**
