> **侦察时间**：2026-10-03 16:34–16:50（Asia/Shanghai）

## 0. 一句话结论

| 块 | 结论 |
| --- | --- |
| **A 食物数据** | 全图 `get_cells_info` 扫描**完全够用且很快**（62 500 格 / **0.75–0.9 秒** / ~15 MB）。但**拿不到 nutrition、stackCount、ThingCategory、地图边界**。算 nutrition 必须靠**伴生 DLL**（或外挂营养表）。 |
| **B 种植** | **能**用桥接建出真 `Zone_Growing`（设计器 id 见下）；**能**在 FloatMenu 里改成 Rice；**生长进度可读**（inspect 文本 `"% grown"`）。**默认作物在 XML 里改不了**（游戏里 `PlantDefToGrow` 是代码默认，XML 搜不到）。 |

## A. 食物数据从哪来

### A1. `rimworld/get_game_info` 返回什么？——只有 4 个字段 【实测】

```json
// node src/cli.js call rimworld/get_game_info  （scripts/recon-food-game.mjs）
{"status":"game_loaded","ticksGame":1,"mapCount":1,"selectedPawns":[]}
```

**没有**地图范围、没有殖民者列表、没有资源汇总、没有任何食物信息。
顶层键只有 `status, ticksGame, mapCount, selectedPawns, operation`。

各来源对比 【实测】：

| 想要的数据 | 从哪读 | 实测结果 |
| --- | --- | --- |
| 地图尺寸 | **没有任何工具直接给** | 用 `jump_camera_to_cell` 二分探测（见 A2） |
| 相机视野 | `get_camera_state` → `viewRect` / `mapPosition` / `rootSize` / `zoomRange` | ✅ 有 |
| 殖民者 | `list_colonists` | ✅ 有 |
| 地图上的东西 | `get_cell_info` / `get_cells_info` | ✅ 有（但字段有限，见 A2） |
| 区域/库存汇总 | **无** | ❌ 没有等价工具 |
| 某个 Def 的数值（营养、分类） | **无** | ❌ 必须写 DLL（见 A5） |

**失败/不存在的路径，别再试**：
- `search_debug_actions` 查 `"nutrition"` 之类只能搜到 debug action 菜单，**不是 Def 数据库查询**。
- 134 个能力里**没有任何**按关键词检索 item Def / nutrition / ThingCategory 的工具
  （`rimbridge/list_capabilities` 全量筛过，见 `runs/food-recon/dumps/capabilities_full.json`）。

### A2. 地图上所有食物在哪读？——`get_cell_info` 的字段清单 【实测】

**先确认地图尺寸（无工具直接给，用二分探边界）**【实测】

```
jump_camera_to_cell(0,0)       → success:true  camera(2,2)
jump_camera_to_cell(248,248)   → success:true  camera(248,248)
jump_camera_to_cell(249,249)   → success:true  camera(248,248)     ← 相机夹到边界
jump_camera_to_cell(250,250)   → success:false camera(248,248)
```
二分结果：**x 上界 = 249，z 上界 = 249（含）→ 地图 250x250 = 62 500 格**。

**生成食物**【实测，`scripts/recon-food-A.mjs`】

`spawn_thing` 可以直接生成食物（**只传物品，不传 pawn**）：

```
spawn_thing { defName:'MealSimple',  x:146, z:135, stackCount:7 }
  → {"success":true,"thingId":"Thing_MealSimple11991","stackCount":7,"defName":"MealSimple"}
spawn_thing { defName:'Pemmican',    x:147, z:135, stackCount:7 }  → ok
spawn_thing { defName:'RawRice',     x:148, z:135, stackCount:7 }  → ok
spawn_thing { defName:'RawPotatoes', x:149, z:135, stackCount:7 }  → ok
```

（`Actions\Spawn thing...` 下共 **1387** 个叶子，其中食物系 def：`MealSimple` / `MealFine[_Meat|_Veg]` /
`MealLavish[_Meat|_Veg]` / `MealNutrientPaste` / `MealSurvivalPack` / `Pemmican` / `Kibble` / `Hay` /
`RawRice` / `RawPotatoes` / `RawCorn` / `RawBerries` / `RawFungus` / `RawAgave` / `RawHops` /
`RawToxipotato` / `InsectJelly` / `BabyFood` / `Chocolate` / `Ambrosia` / `Milk` / `Meat_*`(129 个) /
`Plant_*`(作物本体) —— 索引见 `scripts/recon-food-tree.mjs`。）

**`get_cell_info` 返回结构（完整字段，实测原样）**

```jsonc
// get_cell_info {x:146,z:135}  （格子里的 Simple meal x7）
{"x":146,"z":135,"terrainDefName":"Gravel","roofDefName":null,"fogged":false,"walkable":true,
 "thingCount":1,"designationCount":0,
 "blueprintBuildDefs":[],"frameBuildDefs":[],
 "solidThingDefs":["MealSimple"],          // 只有 defName 数组，没有数量
 "zone":null,"areaCount":0,"areas":[],
 "things":[
   {"defName":"MealSimple","label":"Simple meal x7","className":"Verse.ThingWithComps",
    "stuffDefName":null,"isBlueprint":false,"isBlueprintBuild":false,"blueprintBuildDefName":null,
    "isFrame":false,"frameBuildDefName":null,"hitPoints":50}
 ],
 "designations":[]}
```

**`things[i]` 的全部键**（实测 10 个）：
`defName, label, className, stuffDefName, isBlueprint, isBlueprintBuild, blueprintBuildDefName, isFrame, frameBuildDefName, hitPoints`

**没有 `stackCount`、没有 `nutrition`、没有 `ThingCategory`、没有 `thingId`、没有 world 坐标。**

**堆叠数量只能从 `label` 的尾巴解析**【实测】：
`"Simple meal x7"` / `"Rice x7"` / `"Potatoes x7"` / `"Pemmican x11"` —— 即 `<label> x<N>`。
（物品本体是有数量的：`spawn_thing` 的返回里**有** `stackCount`，但那是生成时的回执，之后读不到。）

两个**容易踩的坑**【实测，`scripts/recon-food-A2.mjs`】：

1. **同格放不同 def → 第二个会被挪到邻近空格，不会共格**。
   在 `(152,135)` 先放 `MealSimple x3` 再放 `Pemmican x11`，回读 `(152,135)` 只有 `Pemmican x11`，
   扫描 24x14 发现 `MealSimple x3` 跑到了 `(153,135)`。
   → **想造同格多堆只能靠同 def 合并**，或者接受它们分散。
2. **同 def 二次生成会合并进已有堆（截到堆叠上限）**。
   `(162,132)` 放 `RawRice x3` 再放 `RawRice x4` → 回读**单堆 `Rice x4`**（不是 x3+x4=7）。
   → 说明 `spawn_thing` 走的是「先尝试堆叠合并」，超出上限的部分才落到别处。
   **对测试摆场景有影响：别用「多次 spawn 同一格同 def」来精确控制数量。**

**「选中食物读 inspect」（想拿营养值）——两条路都失败**【实测】：

| 路径 | 结果 |
| --- | --- |
| `click_cell` 选中食物 → `get_selection_semantics` | `success:false`，**`ArgumentNullException: source`**，栈底 `RimBridgeServer.RimWorldSelectionSemantics.GetInspectTabTypes` —— **对非 Pawn 会崩** |
| 选中食物 → `get_ui_layout` 读 inspect 面板文字 | 只有 `Simple meal x7` / `Fresh (Refrigerated, spoils in 13 days)` / `Acceptable food for everyone` / `Deteriorating: Unroofed…` —— **没有 nutrition 数字** |

**同一 bug 也影响 zone**：选中 `Zone_Growing` → `get_selection_semantics` 同样 `ArgumentNullException`。
（`list_selected_gizmos` 对 zone **正常**，7 个 gizmo 都读到了。）

> ⚠ **注意区分**：Pawn 的 `get_selection_semantics` **完全正常**（inspectString 有值）；
> 崩溃只发生在 **非 Pawn 的选中对象**（thing / zone）上。
> 调用失败但**不会挂死桥接**，可以放心用 try/catch 兜。

### A3. `get_cells_info` 批量上限与耗时 —— 全图扫描现实吗？**【实测：现实】**

上限确认（`width * height ≤ 1024`）：

| 调用 | 实测 |
| --- | --- |
| `16x16 = 256` | **5 ms**，79 344 字节 |
| `32x32 = 1024` | **11 ms**，335 800 字节 |
| `64x16 = 1024` | **11 ms**，307 843 字节 |
| `33x33 = 1089` | `success:false`，`"Requested rectangle contains 1089 cells, which exceeds the limit of 1024."`（干净报错，**不挂**） |

**全图 250x250 = 62 500 格，用 32x32 批扫：**

| 轮次 | 调用次数 | 总耗时 | 数据量 | 平均/次 | 中位 | 最大 |
| --- | --- | --- | --- | --- | --- | --- |
| 第 1 次（`A3.json`） | 64 | **899 ms** | ~18.0 MB | 14 ms | 11 ms | 38 ms |
| 第 2 次（`final.json`） | 64 | **745 ms** | **14.5 MB** | 12 ms | — | — |

→ **结论：全图扫描是完全现实的。** 一轮「殖民地里所有食物」的完整刷新 **< 1 秒**，
如果 5 秒一次轮询，占用约 15–20% 的单线程调用预算（还要算 Node 侧 JSON 解析），**可接受**。

**不需要**靠 stockpile / allowed area 限定范围来提速 —— 那只是为了减小解析开销的优化手段，不是必需。
（真要优化：`stockpile zone` 只覆盖几十格，`get_cells_info` 一次就能扫完；但区域本身**不告诉你里面有什么**，
还是要扫格子。见 B6。）

### A4. nutrition / stackCount / ThingCategory 能不能读？——**都不能**【实测】

| 想要 | 桥接能给吗 | 证据 |
| --- | --- | --- |
| `stackCount` | ❌ 只能从 `label` 尾巴 `"x7"` 解析 | A2 的 `things[0]` 键清单里没有 |
| `nutrition` | ❌ 任何工具都不给 | 全图扫 + 选中 + UI 文字，三路都没有 |
| ThingCategory | ❌ 不给 | 同上 |
| Def 的静态属性（营养/分类/生长期） | ❌ 没有 Def 查询工具 | `list_capabilities` 全量 134 个，无一类是 DefDatabase 查询 |

**`rimbridge/run_lua` 不能当旁路用**【实测，`C4.json` + `lua_reference.json`】：

```
run_lua 'return Game'          → Lua global 'Game' cannot be used as a runtime value
run_lua 'return Find'          → Lua global 'Find' cannot be used as a runtime value
run_lua 'return DefDatabase'   → Lua global 'DefDatabase' cannot be used as a runtime value
run_lua 'return Find.CurrentMap' → Lua expression 'IndexExpression' is not supported
run_lua 'return ipairs'        → Lua global 'ipairs' cannot be used as a runtime value
```

它只是「**JSON 脚本运行器的一个 Lua 外观**」：只能 `rb.call` 已有能力、静态字段访问（`a.b.c`）、
静态下标（`names[1]`）、`for i = 1, n`、`if`、`local` 算术。
**明确不支持**：动态下标 `names[i]`、字符串拼接 `..`、`break`、`require`、元表、协程、
**direct CLR access**、任意全局赋值（原文见 `dumps/lua_reference.json` 的 `unsupported` 数组）。
→ **无法用它遍历事物列表做聚合，也无法读任何 Def。**

### A5. 结论：算「殖民地当前食物总量」的最省事数据路径 —— **推荐 + 理由**

**推荐（分两层，按精度需求选）**

**第 1 层 —— 不写 DLL，只用桥接（可以立刻做，今天就能跑）**

```
① get_cell_info 扫全图（64 次 get_cells_info，32x32/批，约 0.75–0.9 s，~15 MB）
② 每格 things[] 里筛 food defName（正则 ^(Meal|Pemmican|Raw|Kibble|Hay|Silage|Milk|Egg|InsectJelly|BabyFood|Chocolate|Ambrosia|Meat_)）
③ 从 label 尾巴 "x<N>" 解析数量 N
④ 数量 × 该 def 的 nutrition（例如 0.9 / 0.05 / 0.05 ...）→ 求和
```

- **优点**：零编译、零重启、立刻可用；能分辨「生食 / 熟食 / 饲料」，能定位到具体格子（对搬运/腐烂分析有用）。
- **缺点**：
  - 营养表（def → nutrition）**必须自己维护一份常量表**。从 XML 手抄 60+ 个 def 的 `nutrition` 是最脏的活。
  - 食物很多时**扫描输出 15 MB/次**，轮询成本不低。
  - **不能算「已在地图外/在别人背包里」的食物**（进食中、在动物胃里的看不到）。
  - **殖民者背包里的食物读不到**（`get_selected_pawn_inventory_state` 只对**当前选中的** pawn 有效，
    实测也没有「遍历所有殖民者背包」的工具）。

**第 2 层 —— 写 RimBridgeServer 伴生 DLL（推荐作为正式方案）**

按 `bridge/DSH.CEBridge/` 的现成范式加一个 `food/*` 工具组：

```csharp
[Tool("food/summary", Description = "殖民地食物总量：总 nutrition、按 pawn-day 计、按 def 分组")]
public object Summary() {
  // 用 ThingCategoryDefOf.Foods / FoodUtility 遍历 map.listerThings.AllThings
  // 直接读 thing.GetStatValue(StatDefOf.Nutrition) * stackCount
  // 顺带返回：腐烂中/冷藏中/被禁用的那部分
}
```

**理由（都基于实测）**：
1. **营养值根本读不到**（A4），而这是「食物总量」的定义本身。桥接层**永远**给不了，
   因为返回结构里就没有这个字段 —— 这是**能力缺失**，不是用法问题。
2. 遍历 `map.listerThings.AllThings` 是 **O(n_thing)** 而不是 **O(62 500 格)**，比扫格快得多且不受地图尺寸影响。
3. DLL 里可以顺手提供 `work/get_priorities` / `work/set_priority`（C 块同样缺能力，见 C13），
   **一次编译解决 A+C 两块**。
4. 唯一成本：改 DLL 要**停游戏 → 编译 → 重启（~12 秒）**；但写完后每次迭代都省。

**中间路线（如果暂时不想写 DLL）**【实测可行】：
用 `rimbridge/update_mod_settings` 之类不行（那只能改 mod 的 settings 字段）。
**可以**用「`run_lua` 调 `get_cells_info` + 静态下标写死的脚本」把 1024 格一次性搬回 Node 侧 ——
但既然 Node 侧本来就要解析，多此一举，**直接 Node 侧循环 64 次更简单**。

## B. 种植 / 生长

### B6. `rimworld/list_zones` 返回结构 【实测】

```
list_zones { includeEmpty:true }  →  {"success":true,"count":2,"zones":[…]}
```

单条 zone 的**全部字段**（实测 8 个）：

```jsonc
{
  "id": "Zone_1",                              // 稳定 id，供 set_zone_target / delete_zone 用
  "label": "Growing zone 1",                   // 完整显示名（带序号）
  "baseLabel": "Growing zone",                 // 不带序号的基名
  "inspectLabel": "Growing zone 1",            // inspect 面板标题
  "className": "RimWorld.Zone_Growing",        // ★ 用它区分 Zone_Growing / Zone_Stockpile
  "cellCount": 16,                             // 格子数
  "hidden": false,
  "position": { "x":19, "z":11 }               // ★ 不是左上角！是 zone 的"代表点"（实测放在 19,10–22,13 的 4x4，报的是 19,11）
}
```

**注意**：`list_zones` **不返回** zone 的格子列表，也**不返回**种植区当前作物 / 平均生长。
要格子就 `get_cells_info` 扫那个矩形，或用 `get_cell_info(x,z).zone` 反查（见 B7 实测）。

`includeHidden:false`（默认）会滤掉隐藏 zone；`includeEmpty:false`（默认）会滤掉 0 格 zone。
**做自动化时两个都传 `true`**，否则你建的 zone 可能"看不见"。

### B7. 画一块种植区 —— **真的能**建出 Zone_Growing 【实测】

**用到的 designatorId（原文，照抄）**：

```
Growing zone  → architect-designator:zone:highlight-designator-zoneadd-growing
Stockpile zone→ architect-designator:zone:highlight-designator-zoneaddstockpile-resources
```

（分类 id 用 `architect-category:zone` 或裸 `Zone` 都行，实测等价。）

**完整可用流程（实测成功的那一次）**

```jsonc
// 1) list_architect_categories → 找到 { categoryDefName:"Zone", id:"architect-category:zone" }
// 2) list_architect_designators { categoryId:"architect-category:zone" } → 18 个设计器
//    其中 index=5 的就是 Growing zone
// 3) dryRun 预演（可选，见下方"坑"）
// 4) 真做：
apply_architect_designator {
  designatorId: "architect-designator:zone:highlight-designator-zoneadd-growing",
  x: 19, z: 10, width: 4, height: 4, keepSelected: false
}
→ {"success":true,"requestedCellCount":16,"acceptedCellCount":16,"appliedCellCount":16,"rejectedCellCount":0}

// 5) 回读（★ 这才是证据）
list_zones { includeEmpty:true }
→ {"count":2,"zones":[
     {"id":"Zone_1","label":"Growing zone 1","className":"RimWorld.Zone_Growing","cellCount":16,"position":{"x":19,"z":11}},
     {"id":"Zone_0","label":"Stockpile zone 1","className":"RimWorld.Zone_Stockpile","cellCount":20,"position":{"x":15,"z":11}}]}

// 6) 逐格确认 zone 真的挂上去了
get_cells_info { x:19, z:10, width:4, height:4 }
→ 16 格全部 {"zone":"RimWorld.Zone_Growing","id":"Zone_1"}
```

**⚠ 三个实测踩到的坑（下面这几条能省你半小时）**

**坑 1：`dryRun` 会改游戏状态，进而污染下一次真做。**

我先对 growing designator 做了 `dryRun:true`（在 `(106,110)` 4x4，全被拒）→ 又对 **stockpile** 做
`dryRun:true` 且**真做**了 `(120,130)` → 之后再对 growing 做**真做** `(15,8)` 4x4，
返回 `acceptedCellCount:16 appliedCellCount:16 success:true`，
**但 `list_zones` 里出现的却是 `Zone_0 / RimWorld.Zone_Stockpile / cellCount:20`（20 = 4 + 16）**。
→ 我的 16 格被**加进了那个 stockpile zone**。

**教训**：`apply_architect_designator` 的 `keepSelected` 默认 `true`，
**设计器选择是全局状态**。要新建不同类型的 zone，中间必须先
`press_cancel`（或 `select_architect_designator` 重新选）清掉当前设计器。
`press_cancel` 实测**清不掉**设计器（`get_designator_state` 里 `hasSelection` 仍为 true）——
但**重新 `apply_architect_designator` 带新 id 会覆盖选择**，所以流程上就是「连着做两个不同类型的 zone 要小心」。

**坑 2：Growing zone 只接受有肥力的地块 —— 沙地（Sand）100% 被拒。**

单格 `dryRun` 对照（`scripts/recon-food-B3.mjs`）：

| 地形 | accepted | rejected | reason |
| --- | --- | --- | --- |
| `Gravel` | **1** | 0 | — |
| `Soil` | **1** | 0 | — |
| `Sand` | 0 | 1 | `"The designator rejected this cell."` |

全图地形分布（实测）：`Sand=34236  Gravel=4000  Marble_Rough=3460  Soil=2855  SoftSand=2564 …`
→ **本图 55% 是 Sand，可种地只有约 10%**。我的第一次尝试 `(106,110)` 4x4 全 Sand → 16 格全拒。

### B9. 生长进度怎么读？——**能读到 0~100%，但只有 inspect 文本**【实测】

**`get_cell_info` 里读不到生长**【实测】：在种植区里选一格，返回
```jsonc
{"defName":"Plant_Rice","label":"Rice plant","className":"RimWorld.Plant","hitPoints":85, …}
```
`things[0]` 的字段和食物一模一样（10 个键），**没有 growth / growthPercent / age**。
→ **`className:"RimWorld.Plant"` 是唯一提示它是植物。**

**正确的读法：选中 → 读 UI 文本**【实测】

选中**单株植物**时，inspect 面板给：
```
"85 / 85"                                              ← 生命值
"2% grown\r\nGrowth rate: 0% (resting, needs light level 51%)"
```
选中**整个种植区**时，给的是聚合数据（**信息量更大，推荐**）：
```
"Size: 16\r\nContains: 16 rice plants\r\nAverage plant age: 12 hours (11% grown)\r\n
 Oldest plant age: 14 hours (12% grown)\r\n
 Growing period: 30/60 days (6th of Aprimay - 6th of Septober)\r\nGrowing season here now."
```

| 想算的东西 | 能不能算 | 依据 |
| --- | --- | --- |
| 当前生长百分比 | ✅ 从 `"N% grown"` 正则抠 | 实测 |
| 平均/最老植株年龄 | ✅ 从 zone inspect 的 `Average plant age: X (Y% grown)` 抠 | 实测 |
| 生长速率 | ✅ 从 `"Growth rate: N%"` 抠（**但会随光照/夜晚在 0%~100% 之间跳**） | 实测 |
| 生长期窗口 | ✅ zone inspect 的 `Growing period: 30/60 days (…)` | 实测 |
| **未来 15 天每天预计产出** | ⚠️ **【推测】可以外推，但误差大** | 见下 |

**「15 天预计产出」的实测校准数据**（同一块 16 格水稻区，`scripts/recon-food-D3.mjs`）：

| 时刻 | 平均植株年龄 | `% grown` |
| --- | --- | --- |
| T0 | 12 hours | **11%** |
| T0 + 15000 tick | 19 hours | **11%** |
| T0 + 150000 tick（实推 60000） | 1 day 22 hours | **24%** |

→ 从 12 小时龄到 1 天 22 小时龄（+34 游戏小时），生长从 **11% → 24%**（+13 个百分点）。
**【推测】** 线性外推：约 **2.6 %/游戏小时**，成熟（100%）还要约 **5.8 游戏天**。
**但这个外推不可靠**，因为：
- 实测里 T0+15000 时生长百分比**没变**（11% → 11%），而 T0+150000 才涨到 24%
  —— 说明**晚上完全不生长**（`Growth rate: 0% (resting, needs light level 51%)`），
  白天才长。**净结果是「每天只有白天那几个小时在长」，线性外推必然偏乐观。**
- 实测单株采样还出现过 **15% → 2%** 的"倒退"，那是采到了**不同植株**（`spawn_thing` 出来的
  和 zone 自己播种出来的不是同一株），**不是真的退了**。
  → 采样必须**锁定同一格**，或者干脆读 zone 的 `Average plant age`。

**⚠ 一个重要的实现事实：`spawn_thing` 生成的植物不是"幼苗"**【实测】
`spawn_thing Plant_Rice` 后立刻读单株 → `"15% grown\r\nGrowth rate: 57%"`（已是 15%）。
→ **`spawn_thing` 生成植物会带一个初始生长度**，摆"刚种下"的场景时要注意。
反而 **zone 自动播种**出来的植株才是真正从 0% 开始（实测刀割干净后，zone 在几个游戏小时内
把 16 格全播上了 `Plant_Rice`）。

**怎么让 zone 自动播种（实测有效）**：
1. `apply_architect_designator` 用 `Cut plants`（`architect-designator:orders:highlight-designator-tutortagnotset-2`）
   覆盖整个 zone → `accepted 16 / applied 16`，回读 `designations: [{"defName":"CutPlant",…}]` ✅
2. `step_game_ticks` 推进（实测推 3000 tick 殖民者来不及割完，但**新播种发生了**：
   推了几万 tick 后 16 格全部是 `Plant_Rice`，`Average plant age: 12 hours`）
   → **zone 的自动播种（Sow）工作确实会跑，殖民者会去种。**

### C13. 结论：「自动调工作优先级」和「自动派活」分别需要什么？

| 需求 | 现成工具够不够 | 缺什么 |
| --- | --- | --- |
| **自动派活（狩猎 / 割除 / 砍树 / 收获 / 搬运 / 屠宰）** | ✅ **够了** | 全走 `apply_architect_designator` + `cell.designations` 回读，实测闭环 |
| **自动派活（建造/种植）** | ✅ **够了** | 种植区 = zone designator；播种 = zone 的 Sow 工作自动干 |
| **读某人做什么工作类型列表** | ⚠️ 勉强 | Work 标签页列头文字可读；defName 拿不到 |
| **读/写每个殖民者的工作优先级** | ❌ **必须写 DLL** | `Pawn.workSettings.GetPriority(WorkTypeDef)` / `SetPriority(...)` —— 桥接**零覆盖**，UI 只有悬停 tooltip 一次一行 |
| **读某人当前 Job** | ✅ 够了 | `list_colonists[].job`（实测 `"GotoWander"` / `"Wait_Wander"` / `null`） |
| **驱动某人做具体某件事** | ⚠️ 间接 | 只能靠「下设计ation → 让 AI 自己选人干」，**不能点名叫谁去** |
| **读 food need（饥饿度）** | ❌ | `list_colonists` 无此字段；要靠 `ITab_Pawn_Needs` 的 UI 文字或 DLL |

**推荐**：写一个 `DSH.FoodBridge` 伴生 DLL，一次覆盖 A 与 C13 的缺口：
```
food/summary            → 总 nutrition / pawn-day / 按 def 分组 / 生食熟食分开 / 腐烂中
food/scan_things        → 遍历 map.listerThings.AllThings（O(n) 而不是 O(62500)）
work/get_priorities     → 读 { pawnId } 的全部 WorkTypeDef 优先级
work/set_priorities     → 批量写优先级（可选先存快照、便于回滚）
work/available          → 列出该殖民者可做/不可做的 WorkTypeDef
need/food               → 每个殖民者的 food need（0~1），用于算「还能撑几天」
```
参考实现：`bridge/DSH.CEBridge/DSH.CEBridge.cs`（已部署在游戏 `BridgeTools/`），
编译脚本：`scripts/build-cebridge.mjs`（**编译前必须先停游戏**，DLL 被占用）。

## D. 时间推进与观测

### D14. `step_game_ticks` 能推多少 tick / 要多久？【实测】

**⚠ 最重要的一条：`step_game_ticks` 有一个工具级 `timeoutMs`，默认 `10000`（10 秒），
超了就返回 `status:"timedout"` 并**只推进了一部分**。
它**不是** GABP 请求超时，而是工具自己的墙钟预算 —— 必须显式传大值。**

实测（`scripts/recon-food-D2.mjs`，游戏 `ticksGame` 从 80000 起）：

| 请求 tick | 工具 `timeoutMs` | 实际 `advancedTicks` | `status` | 耗时 | 速率 |
| --- | --- | --- | --- | --- | --- |
| 15000 | **10000**（默认值没传） | **3515** | `timedout` | 10013 ms | 351 t/s |
| 15000 | **10000** | **4710** | `timedout` | 10008 ms | 471 t/s |
| 30000 | **10000** | **5576** | `timedout` | 10013 ms | 557 t/s |
| 2500 | 600000 | **2500** ✅ | `completed` | **6 379 ms** | 392 t/s |
| 15000 | 600000 | **15000** ✅ | `completed` | **26 113 ms** | 574 t/s |
| 15000 | 600000 | 8699 | `failed`（`endTicksGame` 正好 120000 = 2 游戏天边界） | 21 760 ms | 400 t/s |
| 150000 | 600000 | **60000** | `failed`（`120000 → 180000` = 1 游戏天） | **105 186 ms** | 570 t/s |

**合计**：86 199 tick / 159.4 秒 → **平均 541 tick/s**。

**回答题目给的两个具体数字：**

| 请求 | 实测秒数 | 备注 |
| --- | --- | --- |
| **2500 tick**（≈1 游戏小时） | **6.4 秒** | `status=completed`，精确 2500 |
| **15000 tick**（≈6 游戏小时） | **26.1 秒** | `status=completed`，精确 15000 |

**15 天（900 000 tick）能不能跑完？—— 能，约 28 分钟纯推进**【实测外推】

```
900000 tick ÷ 541 tick/s = 1664 s ≈ 27.7 分钟
```

**但必须分批**，因为：
- 单次要给 `timeoutMs` 足够大（实测 600 000 能撑住 60 000 tick / 105 秒）；

工具描述写的是「**Each requested tick is executed on a separate Unity update frame**」，
实测 `advancedFrames == advancedTicks`（15000 tick → 15000 帧），
541 tick/s ≈ **541 帧/秒**（1600x900 窗口，暂停状态，渲染 2D 地图）。
→ **【推测】** 想更快只能靠 `set_time_speed('Ultrafast')` + `play_for`
（`RIMBRIDGE-技巧手册` 记的是 ~4700 tick/s），但那是**真实时间跑、不确定**，不适合做回归断言。
