# 验证结果总报告

在 RimWorld 1.6.4871（原版 + 全 6 DLC + Harmony + RimBridgeServer 2.1.1 + 测试 mod）上，
对原版调试体系的各条分支做端到端实机验证。

**判据统一是「回读实际游戏状态」，不是看 `success`。**

| 阶段 | 内容 | 结果 |
| --- | --- | --- |
| 1 | Settings 开关的写入/回读/批量应用/恢复 | **8/9**（1 项是发现，不是缺陷） |
| 2 | Outputs（247 个诊断读取）的读取通道 | **通过** |
| 3 | 人物属性类 debug action + 回读验证 | **8/9**（1 项是断言方式问题） |
| 4 | **Hot reload Defs 热重载** | **10/10** |
| 5 | Actions 各分支（生成/事件/袭击/地图操作） | **12/15**（3 项是我脚本的 bug） |

原始报告在 `runs/verify-*/result.json`。

## 阶段 1：Settings（181 个开关）

**已验证**：
- `set_debug_setting(path, enabled)` 写入后 `get_debug_action` 回读**完全一致**（true/false 双向）
- 12 项配置档批量应用、逐项回读通过，耗时 0.4 秒
- 能完整恢复到原始状态

**关键发现：默认有一批随机源是开着的**

| 开关 | 默认 |
| --- | --- |
| `Enable Storyteller` | **开** |
| `Enable Random Mental States` | **开** |
| `Enable Random Diseases` | **开** |
| `Enable Damage` / `Enable Player Damage` | **开** |
| `Pause On Error` | 关 |

**关掉 Storyteller ≠ 完全确定。** 实测关掉后仍刷出了 `Disturbing vision` 信件 ——
那是 **Anomaly DLC 的方尖碑（monolith）事件**，属于独立系统，Settings 里**没有开关能关它**。
要彻底确定，得在 `ModsConfig` 里去掉 `ludeon.rimworld.anomaly`。

## 阶段 2：Outputs（247 个诊断读取）

**已验证的读取通道**（这点一开始不清楚）：

`execute_debug_action` 执行 `Outputs\*` **不通过桥接返回文本**，而是弹出一个
`LudeonTK.Window_DebugTable` 窗口。所以流程是：

```
执行 Outputs 动作 → get_ui_layout → 只取 Window_DebugTable 那个 surface 的元素 → close_window
```

实测读取规模：威胁点数 257 行、远程武器 588 行、任务权重 521 行、研究项目 436 行、生物群系 137 行。

⚠ 注意要**只取 DebugTable 那个界面**的元素，否则会把 inspect 面板的文字混进来。

## 阶段 3：人物属性动作

**全部执行成功**（`success=true`）：

| 动作 | 层级 | 叶子数 | 备注 |
| --- | --- | --- | --- |
| `Actions\Max Skill...\Shooting` | 两级 | 12 | |
| `Actions\Give Trait...\nudist (0)` | 两级 | 73 | 标签带等级后缀 `(0)` |
| `Actions\Set Backstory...\Childhood` | **三级** | 383 | 第二层是 Adulthood/Childhood |
| `Actions\Add Gene...\Xenogene` | **三级** | 232 | 第二层是 Xenogene/Endogene/Heritable |
| `Actions\Mental state...\Berserk` | 两级 | 47 | |
| `Actions\Apply damage...\Flame` | 两级 | 104 | |
| `Actions\Add Hediff...\Acid burn` | 两级 | 324 | 面板有变化，但文本匹配没命中 |

**最有价值的回读通道**：`get_selection_semantics` → `selectedObjects[].inspectString`。
实测执行 `Mental state → Berserk` 后，它从
`"Female, age 18 (1943) of New Arrivals / Wandering."`
变成
`"Female, age 18 (1943) of New Arrivals / Mental state: Berserk"`。

> 纠正一个我先前的错误结论：inspect 文本**不在** `inspectStrings`（那个一直是空的），
> 而在 `selectedObjects[].inspectString`。

**未解决**：`Add Hediff` 的效果确认方式。Health 面板内容确实变了（346 行 vs 基线 369 行），
但按文字搜 `acid burn` 没命中 —— 可能渲染成了非文本元素，或者需要展开具体部位。
**做健康相关的断言时不要只靠面板文字**，建议同时看 `inspectString` 和 `rimbridge/list_logs`。

## 阶段 4：Hot reload Defs（10/10）★ 本轮最有价值的成果

完整端到端验证：

```
1. 测试 mod（dsh.autotest）加载确认：enabled=true loadedInSession=true source=ModsFolder
2. 生成 DSH_AutoTestThing → 回读 label = "Dsh autotest thing v1"
3. 改磁盘 XML：v1 → v2
4. 执行 Actions\Hot reload Defs → 耗时 0.0 秒
5. 再生成 → 回读 label = "Dsh autotest thing v2"   ← 热重载真的生效
6. 再执行一次 → 仍然成功（幂等，不崩）
```

**意义**：改 Def XML 的迭代从「重启游戏（6 秒起）+ 开殖民地」降到**亚秒级**。
这是对 mod 开发最大的加速。

**配套基础设施**：

- **测试 mod 的部署**：RimWorld **只扫描游戏安装目录的 `Mods/`** 和工坊目录，
  不扫描隔离存档目录（实测 `activeCount` 不含放在存档目录里的 mod）。
  仓库用**目录联接（junction）**把 `游戏目录\Mods\DSH_AutoTest` 指向
  `profiles\vanilla\Mods\DSH_AutoTest`，于是改工作区就等于改游戏看到的文件，
  **后续不再需要工作区外写权限**。
- `scripts/modsconfig.mjs` 管理 mod 组合（`list` / `add` / `remove` / `set` / `baseline` / `copy-main`）。
  `copy-main` 能一键复刻主力配置的 mod 列表，用于兼容性测试。

**未验证**：`Actions\Loaded Files For Mod` 执行成功但窗口只显示主菜单文字 ——
它多半是先弹一个「选哪个 mod」的对话框，需要多一步。**没有打通**。

## 阶段 6（额外）：最终回归暴露的一个真实缺陷

用全新实例跑冒烟测试时，`step_game_ticks` **在刚开完调试殖民地后返回 `status=failed`、推进 0 个 tick**
（当时游戏 tick 只有 5）。

原因：`start_debug_game_ready(readiness=mapData)` 只保证**数据**就绪，地图仍在初始化。
此时推进会被拒绝。

**修复**（已实装进 `src/smoke.js`）：
1. 开完殖民地后改为等 `readiness=currentMap`
2. `step_game_ticks` 带最多 3 次重试，失败则再等一次地图就绪

**修复被真实故障验证**：再次跑冒烟测试时第 1 次仍然 failed，重试后
`游戏 tick 57 → 357（+300），completed`，整轮 9/9 通过。

印证了第一原则：**调用返回了不等于游戏真的变了，一定要回读断言**。

## 阶段 6：Character Editor 接入（UI 路线，10/10）

CE 是纯 UI mod，**网上没有任何 agent 接口或自动化先例**（子代理全站搜索确认）。
但它用的是标准 IMGUI，所以 UI 自动化可行。实测控件规律：

| 部位 | 定位方式 |
| --- | --- |
| 主面板 | `list_main_tabs` 里 `targetId = main-tab:HotkeyEditor`，`open_main_tab` 打开 |
| 标签页 | Bio/Inventory/Health/Needs/Social/Log/Info/Records —— **自带文字，直接按文字点** |
| 殖民者 | 左侧列表，名字 label 同行有一个隐形按钮 |
| **技能 ±** | 每个技能行右侧固定两个 `icon_button`：**x≈1550 是「−」，x≈1575 是「+」** |
| 窗口 | `window:N:CharacterEditor.CEditor+EditorUI`，约 217 元素 / 125 可点 |

**踩到的坑**：CE 把左栏（殖民者）、中栏（特故事/特质）、右栏（技能）排在同一批 y 上，
只按 y 分行会把三栏混在一起；而且同一行元素 y 并不相等（技能名 y=503、等级数字 y=506），
必须**同时按 x 限列 + 按 y 容差（±8px）取带**。

**实测结果**：`Shooting` 15 → 18（点 3 次「+」），并通过读回确认。
驱动实现在 `src/ce.js`。

**发现的一个坑**：刚打开 CE 立刻截图会拿到还没绘制完的帧（截图里看不到 CE 窗口）。
等约 1 秒再截就正常 —— 子代理调研里也提到同类现象（首帧截图带 HUD）。

## 阶段 7：自建 Character Editor 程序化接口（8/8）★

子代理对 CE 的 IL 分析指出：**CE 的数据层与 UI 层是分离的**
（`CEditor.StartEditor(pawn)` 只负责开窗，不碰数据），数据操作散在 42 个 `*Tool` 静态类里。
于是我们**自己写了一个 RimBridgeServer 伴生 DLL**（`bridge/DSH.CEBridge/`），
用反射直接调 CE 的内部 API，完全绕过 UI。

**先解决了子代理报的阻塞项**：它说本机没有 C# 编译器。实际是有的 ——
`C:\Program Files (x86)\Microsoft Visual Studio\2022\BuildTools\MSBuild\Current\Bin\Roslyn\csc.exe`。
配合仓库的无管道执行器（沙箱里 `execFileSync` 会 EPERM），编译链路打通，**不需要安装任何东西**。

**部署方式**：RimBridgeServer 只从游戏目录的 `BridgeTools/` 加载伴生 DLL，
所以用目录联接把它指回工作区（和前面对测试 mod 的做法一致），重新编译不需要授权。

**`ce/probe` 自检结果**（反射可行性确认）：

```
loaded: true,  assemblyVersion: 1.6.3.3
CEditor_API_isNull: false                      ← CE 单例可访问
SkillTool_public: true,  get: true,  set: true
PresetPawn_Param_count: 57                     ← P00_id, P01_pawnkinddef, P03_name, P04_ageticks, P20_skills...
dataToolCount: 42                              ← 全部数据工具类及可见性
```

**已实现的工具**：`ce/probe`（自检）、`ce/colonists`、`ce/get_skills`、`ce/set_skills`、`ce/get_traits`。

**揭示的 CE 原生技能格式**（自描述文本，很适合程序处理）：

```
Shooting|5|1|0|0:Melee|6|2|0|0:Construction|4|1|0|0:...
        ↑等级 ↑激情 ↑经验
```

**端到端验证**：

```
ce/colonists              → 3 个殖民者，带稳定 pawnId
ce/get_skills             → 读到 200 字符的完整技能串
ce/set_skills             → Shooting 5 → 8
ce/get_skills 回读        → 确认已变
ce/get_traits             → "NaturalMood|1"
CE 的 UI 面板交叉验证      → 面板里 Shooting 也显示 8   ← 反射路线与 UI 一致
```

**为什么两条路都做了**：UI 路线有硬天花板 —— 子代理的 IL 分析确认
`Verse.Widgets.HorizontalSlider` **不在 RimBridgeServer 的 patch 列表里**（CE 用了 14 处），
而 125 个原生工具里**没有任何文字输入工具**。所以改名字、改滑块类数值走 UI 走不通；
而反射路线不受这些限制。**UI 路线适合"看得见地操作"，反射路线适合"精确批量设置"。**

> ⚠ 反射路线的代价：全靠字符串匹配 CE 的内部类型名，**CE 升级后可能失效**。
> 所以第一个工具是 `ce/probe`，出问题先跑它。

## 本轮修掉的自身缺陷

| 缺陷 | 后果 | 修复 |
| --- | --- | --- |
| 请求超时设成 **15 分钟** | 一个调用挂住就静默卡死，用户完全看不出发生了什么 | 默认改成 **60 秒**，超时错误里明确提示"桥接已被挂住，建议重启" |
| `Prefs.xml` 写到 profile 根目录 | 应在 `Config/` 下，导致游戏一直用默认值（全屏 4K + 音乐开） | 修正路径 + 只强制关键项、保留用户设置 |
| `tasklist` 在沙箱下返回 Access denied | 被当成"没有进程"，误判游戏已退出 | 改用纯 Node 的 PID 存活检测 |
| 沙箱下管道子进程 `spawn EPERM` | launcher 完全跑不起来 | `src/proc.js` 改成输出重定向到文件 |
| 用 `blueprintBuildDefs` 判断建筑是否建成 | 上帝模式下建筑是瞬间建成的，查错字段导致误判"没生效" | 改查 `cell.things` |
| 靠"哪个分类里有匹配项"找建筑师设计器 | 匹配到了 "wall torch lamp" | 先按 `categoryDefName` 定位分类，再精确匹配 label |

## 结论：哪些能力可以放心用

**可以放心用**：
- Settings 全部 181 个开关（确定性、加速、可视化、日志）
- `Actions` 里的 Direct / PawnTarget / MapTarget 动作，只要超时给够
- `Outputs` 全部 247 项（走「执行 → 读 DebugTable → 关窗」）
- 人物属性类的全部动作（技能/特质/背景/基因/精神/伤害）
- 时间控制（`step_game_ticks` 精确、`play_for` 快速）
- 真实 UI 驱动（点控件、多层对话框）
- 截图与格子裁剪
- **Hot reload Defs**

**要小心的**：
- `create_allowed_area` —— 挂死桥接，**禁用**
- `spawn_thing` 生成 pawn —— 崩，改用 `Spawn Pawn...`
- `search_debug_actions` 用短语 —— 会挂，用单词
- Anomaly 方尖碑事件 —— 无法通过 Settings 关掉
- `Benchmark Performance` / `Battle Royale All PawnKinds` —— 未验证，风险高
- 一切可能长时间阻塞的主线程操作 —— 超时必须有限
