# 02 · 类别与来源

> **这份文档管什么**：22 个播报类别各自绑定**哪一个**通道、用**哪条** def 判定、**丢弃**哪些重复项、优先级与开发期默认值、模板键；以及产品默认值的定稿流程。
> **谁该读**：写 `SpeechCatalog.Bindings` 的人（照 §2.1 一行一行抄）；写 5 个 Hook 文件的人（照 §3 的匹配算法）；做产品默认值的人（照 §6）。
> **与其它文档的边界**：模块/类型/补丁点编号（①…⑧）在 `01-架构与模块.md`；模板正文与切分规则在 `03-文案与片段.md`；开关落到哪个 `Settings` 字段在 `05-设置界面.md`。
> **标注**：【实测】= 来自 `docs/取证-22类来源分布.md` 等静态取证（IL/XML，未在游戏里复验）；【推测】= 由 IL 推出；【待验证】= 需要进游戏探针（编号见 `06` §9）。

## 1. 规则（表是规则的实例，改归属先改规则）

| # | 规则 | 落地 |
|---|---|---|
| R1 | **一个事件只在一个通道绑定。**"事件"= 原版发出那条通知的那一刻 | 同一件事在别的通道再出现时按 §4.1 丢弃总表处理，**不比对、不合并、不做"事件身份"** |
| R2 | **分类优先级：`incident` > `letter` > `message`。** 由 incident 发起的类别只在 `incident` 判定（那里拿得到 `IncidentDef`、`raidStrategy`、`arrivalMode`、`parms.pawns`，分类最准） | `letter`/`message` 只接**不是 incident 发起**的事件；由 incident 发起的类别在 `letter`/`message` 的 def 一律进 §4 丢弃表 |
| R3 | **通道内按 def 名精确过滤**（可再加一级文案后缀）；不在白名单也不在丢弃表的落到该通道的 `Other*` 兜底 | 匹配实现只有一处：`SpeechCatalog.ForIncident` / `ForLetter` / `ForMessage` |
| R4 | **同一类别可以有多条绑定，但各条必须覆盖互斥的事件集合**（不同人群、不同阶段、不同 def）；同一件事只由一条绑定受理 | 表里同一类别的多行必须靠 `def 判定` 互斥；互斥性由 §2.1 的判定条件本身保证 |
| R5 | **绑定是一张表**：`类别 / 通道 / def 判定 / 排他丢弃项`。加一类 = 加一行；调归属 = 改一行 | 代码形态 = `SpeechCatalog.Bindings`（`SourceBinding[]`），加类不碰任何 `if` |

### 1.1 通道名（固定四个）

| 通道 | 补丁点（见 `01` §4） | 匹配键 | 兜底类 | 丢弃表 |
|---|---|---|---|---|
| `incident` | ③ `IncidentWorker.TryExecute` | `defName` + `category` + `raidStrategy` + `arrivalMode` | `OtherIncident` | 无（判定不中就兜底） |
| `letter` | ② `LetterStack.ReceiveLetter` | `LetterDef.defName` | `OtherLetter` | `Death` / `BabyBirth` / `ThreatBig` / `ThreatSmall` / `NegativeEvent` / `PositiveEvent` / `NeutralEvent` |
| `message` | ① `Messages.Message` | `MessageTypeDef.defName` +（可选）文案后缀 | `OtherMessage` | `ThreatBig` / `ThreatSmall` / `PawnDeath` |
| `自算` | ④⑤⑥⑦⑧ | 挂在语义方法上，无 def | 无 | 无 |

> 丢弃表里的 def 名都"已由别的通道覆盖同一事件"：`Death`/`PawnDeath` 归 ⑦；`ThreatBig`/`ThreatSmall` 归 ③④；`NegativeEvent` 信件归 ③；`PositiveEvent`/`NeutralEvent` 信件归 ③⑤。三张丢弃表是 `letter`/`message` 两个通道**唯一**的排他声明处。

### 2.2 绑定行的代码形态

```text
BindingKey     = DefName | Category | RaidStrategyPrefix | ArrivalModeContains | WorkerClass | DefNameContains
SourceBinding  { SpokenCategory Category, SpeechChannel Channel, BindingKey Kind, string Value, string TextSuffix }
Bindings = [
  new(ThreatSiege,          incident, RaidStrategyPrefix,  "Siege"),
  new(ThreatSiege,          incident, ArrivalModeContains, "Drop"),
  new(ThreatSiege,          incident, DefNameContains,     "MechCluster"),
  new(ThreatAnimalInsanity, incident, DefName,             "AnimalInsanityMass"),
  new(DiseaseOutbreak,      incident, WorkerClass,         "IncidentWorker_Disease"),
  new(ThreatRaid,           incident, Category,            "ThreatBig"),        // 类别级判定
  new(TraderArrival,        incident, DefName,             "TraderCaravanArrival"),
  new(Quests,               letter,   DefName,             "NewQuest"),
  new(BuildPlaceFailed,     message,  DefName,             "SilentInput"),
  new(Rotten,               message,  DefName,             "NegativeEvent", TextSuffix: <派生值>),
]
```

| `BindingKey` | 匹配语义（`Value` 与现场事实怎么比） | §2.1 里用它的行 |
|---|---|---|
| `DefName` | `defName == Value` | `ThreatAnimalInsanity`（逐个 def 一行）、`TraderArrival`、`Visitors`、`WeatherExtreme`、`EnvHazard`、`Quests`、`BuildPlaceFailed`、`Rotten` |
| `Category` | `categoryDefName == Value` | `ThreatRaid` |
| `RaidStrategyPrefix` | `raidStrategyDefName` 以 `Value` 开头 | `ThreatSiege` |
| `ArrivalModeContains` | `arrivalModeDefName` 含 `Value` | `ThreatSiege` |
| `DefNameContains` | `defName` 含 `Value` | `ThreatSiege`（`Siege` / `MechCluster` / `Cluster` 三条） |
| `WorkerClass` | `def.workerClass` 是 `Value` 类型或其子类 | `DiseaseOutbreak` |

- `TextSuffix` 只对 `message` 通道有效，用于把 `NegativeEvent` 这一宽 def 收窄到 `Rotten` 一条；它的值由 `MessageRottedAwayInStorage.Translate()` 派生（§3.3），表里不写死文案。
- 表顺序**不是**判定顺序：判定顺序由 §3.1–§3.3 的三个 `For*` 函数写死；表只是数据。
- `BuildMissingMaterials` 是 `自算`，没有 `SourceBinding` 行（它的条件是代码判据，见 `01` §5.3）。

| 改动 | 只改哪一处 | 谁跟着变 |
|---|---|---|
| 某类换通道 | §2.1 主表一行 + 对应丢弃总表一行 | `Bindings`；钩子代码不变（钩子只调 `For*`） |
| 某类新增 def 名 | §2.1 主表该行的 `def 判定` | `Bindings` 多一行 |
| 调优先级 | §5 元数据表的 `Priority` | `SpeechQueue` 行为跟着变，代码不变 |
| 调默认开关 | §5 元数据表的 `DefaultEnabled` | `SetDefaults` 行为跟着变，代码不变 |
| 新增一类播报 | `SpokenCategory` 一行 + `CategoryEntry` 一条 + `PhraseEntry` 两条 + `Bindings` 一行 + `CategorySlot` 一行 | `05` 的播报类型页自动多一行 |

## 3. 三个匹配函数（唯一实现处）

`SpeechCatalog` 只收字符串，不认识 `Verse` 类型；钩子负责把现场事实拆成字符串再交进来。

### 3.1 `ForIncident(string defName, string categoryDefName, string raidStrategyDefName, string arrivalModeDefName)`

```text
1. ThreatSiege：raidStrategy 前缀 Siege / arrivalMode 含 Drop / defName 含 Siege·MechCluster·Cluster
2. 具体白名单（按 DefName 精确）：
     AnimalInsanityMass · AnimalInsanitySingle · ManhunterPack        ⇒ ThreatAnimalInsanity
     TraderCaravanArrival · OrbitalTraderArrival                     ⇒ TraderArrival
     VisitorGroup                                                    ⇒ Visitors
     HeatWave · ColdSnap · VolcanicWinter                            ⇒ WeatherExtreme
     SolarFlare · Eclipse · ToxicFallout                             ⇒ EnvHazard
3. WorkerClass：def.workerClass 是 IncidentWorker_Disease 的子类      ⇒ DiseaseOutbreak
4. categoryDefName == "ThreatBig"                                    ⇒ ThreatRaid
5. 其余                                                              ⇒ OtherIncident
```

- 判定顺序固定为"特例（Siege）→ 具体白名单 → workerClass → 类别（ThreatBig）→ 兜底"：**具体判据一律排在宽判据之前**，否则 `AnimalInsanityMass`/`ManhunterPack` 这类 `category` 也可能属于 `ThreatBig` 的事件会被 `ThreatRaid` 抢走【`[待验证]`：`AnimalInsanityMass.category` 的实际取值，进游戏或读 XML 即可定】。
- 顺序即优先级，写在函数里，调用方不重排。
- `DiseaseOutbreak` 只由 `workerClass` 判（13 个 `Disease_*` 共享一个 worker【实测】），不在白名单里逐个列 def 名。

### 3.2 `ForLetter(string letterDefName)`

```text
1. letterDefName 在丢弃表 ⇒ return null（不播）
2. letterDefName == "NewQuest" ⇒ Quests
3. 其余 ⇒ OtherLetter
```

### 3.3 `ForMessage(string messageDefName, string text)`

```text
1. messageDefName 在丢弃表 ⇒ return null（不播）
2. messageDefName ∈ {SilentInput, RejectInput} ⇒ BuildPlaceFailed
3. messageDefName == "NegativeEvent" 且 text 以腐烂文案的静态后缀结尾 ⇒ Rotten
4. 其余 ⇒ OtherMessage
```

- 腐烂的文案后缀由 `MessageRottedAwayInStorage.Translate()` 按 `{`/`}` 切出静态尾部得到，**只有这一处使用文案匹配**（其余全部按 def 名）。语言包变化只会让这一条失效（退化成 `OtherMessage`，功能不丢）。

### 4.2 丢弃语义与核对

**丢弃 = 不产出 `Notice`**（不是产出后丢弃），所以 `Trace("1", …)` 里能看到"命中丢弃表"，由此可核对上表是否漏项【`[待验证]`：一局实测每类条数，见 P2】。

### 4.3 维护规则

| 场景 | 怎么做 |
|---|---|
| 某类改由别的通道判定 | 改 §2.1 一行；把原通道里该事件的 def 加进 §4.1 对应行；`Bindings` 跟着改一行 |
| 某通道新出现一个"同一事件的重复通知" | 把它加进 §4.1 对应行；在 §3.1–§3.3 的 `For*` 里它自动被丢弃（丢弃表是函数的第一个判断） |
| 丢弃表与兜底冲突 | 丢弃表优先：命中丢弃表的 def 不进 `Other*` 兜底 |
| 想放开某条丢弃 | 只删 §4.1 那一行；该 def 随后落到该通道的 `Other*`，或另加一条 `SourceBinding` 指向具体类别 |

## 6. 默认值定稿流程

产品默认值**不由设计者拍**（AI 无法评估体感），由一次真实游玩产出，落在 `CategoryEntry.DefaultEnabled` 一处。

| 步 | 做什么 | 判据 / 产物 |
|---|---|---|
| 1 | **开发期全开**：`SetDefaults` 按 `CategoryEntry.DefaultEnabled` 置 22 类开关（该列当前全 `true`），`TraceEnabled = false` | 进游戏后 22 个开关全部打勾 |
| 2 | 用户正常玩一局：至少覆盖一次袭击、一次疾病爆发、一次死亡、一次商队、一次天气 | 官方 `Player.log` 里 `[VD] 1` 记录可按类别计数 |
| 3 | 用户按体感**关掉吵的类别**（设置窗口改动即时写盘，无"应用"按钮） | 存盘的设置 XML 里 `enabled_<类别>` 为 `false` |
| 4 | **回读存盘设置**：`Config\Mod_<packageId>_<Settings类名>.xml` 里每个 `enabled_<Category>` 的布尔值 | 得到一张 22 行的 `类别 → 开/关` 表 |
| 5 | 把这张表抄进 `CategoryEntry.DefaultEnabled`（`02` §5 的最后一列） | `SetDefaults` 只读 `DefaultEnabled`，默认值与代码常量脱钩 |
| 6 | 复测：删掉设置 XML 后进游戏，开关初值 = §5 表里的值 | 一处改动生效，别处零改动 |

- **只改一处**：默认值只在 `CategoryEntry.DefaultEnabled` 定义；`SetDefaults` 是唯一读它的地方；UI 只显示 `Settings` 的当前值，不碰默认值。
- 回读只抄**类别开关**；数值项（音量 / 停顿 / 队列 / 库上限）的默认值留在 `05` 的字段总表里，不参与本流程。
