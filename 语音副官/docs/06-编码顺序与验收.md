## 9. 进游戏探针清单 P1–P10

> 每条的"结果会改什么"都指向**一处**：改数据表、改常量、或改一个模块的一个函数。

| 编号 | 验什么 | 为什么现在验不了 | 结果会改什么 |
|---|---|---|---|
| **P1** | 突发疾病时 ③ 被调**几次**：一条自带 `Count=N` 的 `Notice`，还是逐人 N 条 | 需要真实疾病事件；静态取证只能看到 `SendStandardLetter` 发一次信，看不到 `parms.pawns` 的粒度 | `BatchAggregator` 走哪条分支：若逐人 N 条，则 `DiseaseOutbreak` 的 `BatchKey` 与 `Count` 来源要改成"成员计数"（`02` §4.5 一行 + `03` §5.2 一格） |
| **P2** | 一局里 `Messages.Message` 的实际条数与分类分布：`OtherMessage` 占多少、腐烂文案后缀是否匹配上 | 801 个调用点 / 441 个类型，静态无法判定玩家真会看到哪些；腐烂文案要中文语言包实际串 | `OtherMessage` 的 `DefaultEnabled`（`02` §5）与腐烂的后缀常量（`02` §3.3 一处）；`默认值定稿流程`（`02` §6）的输入 |
| **P3** | 工作台缺料挂起是否产生**任何**提示 | 需要真造一个缺料工作台并观察 ITab / Alert / 消息 | `BillSuspended` 的去留：留则新增补丁点（超出 8 点），删则从 `SpokenCategory`/`Entries`/`Bindings` 各删一行 |
| **P4** | 设置窗口排版 / 中文渲染 / 开关重启后是否读回 | 从未进过游戏 | `05` 的控件布局与字号；若中文截断则只改 `RowWidgets` 的尺寸常量 |
| **P5** | TTS 端到端延迟、片段拼缝听感、`Speed` 与 `GapMs` 的实际手感；TTS 是否把 `35` 念成"三十五" | 需要真的听 | `GapMs` 默认值（`05` §4）、`NumericText` 开关（`03` §4.4 一处）、`MaxNamedInBatch` 默认值 |
| **P6** | Unity 能否直接吃 SiliconFlow 的 WAV（头长度是占位值） | 需要跑一次 Unity 解码 | `WavReader` 是否必须重算长度（`01` §5.4 一处）；若 Unity 直接能吃，`WavReader` 仍保留重算（对其它服务端更稳） |
| **P7** | 一场袭击里 ⑦ 被调**几次**：会不会一次刷十几条 | 需要真打一场 | `PawnDied` 的 `BatchKey` 策略（`02` §4.5）与 `QueueLimit` 默认值；必要时把 `PawnDied` 的聚合从"同 tick + 同派系"改成"同 tick"（`PawnHooks` 的 `BatchKey` 一行） |
| **P8** | ⑧ 算出的缺口数值与建造 UI 红字是否一致；自动重建/样板是否被正确排除 | 需要真放蓝图、真拆一栋建筑 | `BlueprintHooks` 的成本比较函数（`01` §5.3 一处）；若数值不一致，只需换 `CostListAdjusted` 的调用口径 |
| **P9** | 袭击期间 `MessageRaidersBeginningAssault` 与第一封信的**实际间隔** | 需要在真袭击里看两个通道的先后 | 报文现在整类丢弃（`message` 丢弃表里的 `ThreatBig`）；若实测它明显早于袭击信且值得留下，就把它从丢弃表移出、映射到 `ThreatRaid`（`02` §4 一行 + `02` §3.3 一处） |
| **P10** | `IncidentParms.silent` / `sendLetter` 在真实玩法里的置位频率；置位时 ③ 是否仍触发 | 静态只证明"信可被抑制、incident 照跑"，不知道实际多常见 | 我们绑 ③ 所以静默袭击仍会播；若实测 `silent` 常见且玩家不希望播，则给 `ThreatRaid` 加一个"静默不播"的判断（`IncidentHooks` 一处） |

## 12. 步骤依赖（顺序由判据咬合，逐步可验收）

```text
1 入口+骨架
   └─► 2 设置窗口 ──► 3 目录表+开关闸
                          └─► 4 钩子+日志 ──► 5 文案切分
                                                   └─► 6 合成+落库（第一次出声）
                                                            └─► 7 播放调度+聚合
                                                                     └─► 8 清理+预热+整句缓存
```

| 依赖 | 为什么不能提前 |
|---|---|
| 2 在 3 之前 | 3 的 `DefaultEnabled` 由 2 的开关行验证；没有开关行就无法确认默认值生效 |
| 4 在 5 之前 | 5 的输入是真实 `Notice`；先用日志确认"取到的事实"正确，再谈怎么念 |
| 5 在 6 之前 | 6 的作业单位是片段；没有片段就没有合成清单 |
| 6 在 7 之前 | 7 的队列里放的是 `PlayableUtterance`；不会出声时队列无从验证 |
| 8 在 7 之后 | 清理对象是播报产生的条目；预热与整句缓存都依赖播放链路 |
| 任意步都可以停下来独立验收 | 每步的判据只依赖前面步骤的产物（A/B/C 类判据都不需要听感） |

## 13. 探针记录格式（每跑完一条探针，把这张表填在 `STATUS.md`）

| 列 | 填什么 |
|---|---|
| 编号 | P1…P10 |
| 日期 / 存档 | 什么时候、哪个存档 |
| 观察值 | 实际数出来的条数 / 顺序 / 状态码 / 数值 |
| 与设计假设是否一致 | 一致 / 不一致（不一致必须写出差在哪） |
| 触发的改动 | 改了哪个文件哪一行、或"无需改动" |

- 只有"触发的改动"一栏指向具体文件行，才算探针闭环；否则照旧按 `02` 的假设继续。
