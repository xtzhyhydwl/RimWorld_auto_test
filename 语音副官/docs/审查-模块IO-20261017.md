## §1 判决

**不能直接拿去施工。** 契约框架（六栏式、`Notice` 拍平、`ClipAssembler` 独立）方向对，但主链有一处断边会让整套片段缓存白做（H1），有一处字段缺失让 `LibraryJanitor` 的等级表根本无法实现（H2），还有一处启动时机不成立——`DeputyGameComponent` 按草案的注册法根本进不了游戏（H3）。

差在四个层面：①主链与旁路的 3 条边没有承接者（H1/H8/H13）；②接口签名级信息不全，`SpeechLibrary`、`BatchAggregator`、`SegmentPlanner` 三个模块照抄写不出类型（§5）；③两份状态被两处同时持有（H4/H5/H20）；④与已定事项的可操作面冲突——`BatchWindowMs`/`SpeechStyle` 在 §3.8 宣布退役，但 UI 还在让用户拨（H14，实测 `Tab_Volume.cs` / `Tab_Voice.cs`），正好撞上 R2-04b"不进设置项"。

建议：先改 H1–H8，其余可边施工边收口。**H1–H4 不改就开工，返工面是整条音频链。**

## §5 三个最含糊、照它写不出接口签名的模块

1. **`BatchAggregator`（§2.13）** —— 没有方法名。输入栏写"两种形态都收"、触发栏写"每次 `Announcer.Tick`"，输出栏写"返回给 `Announcer.Tick()`"：是 `Receive(Notice)` + `Flush()` 两个方法，还是一个 `Tick()` 返回数组？合并批的"同一批"如何判定（`BatchKey` 来自 `Notice`，§3.1 说非空才进；§2.13 又说"① 一条已带名单的 `Notice`（`Names.Length > 1`）"）——**两条路由条件不一致**，写不出"进来还是不进"的前置判断。另外同 tick 内 `Category` 变了怎么切批也没写。
2. **`SegmentPlanner`（§2.14、§3.2、§5.2）** —— 三个输入类型（`Notice`/`BatchSummary`/`string`）一个输出，入口名在 §2.14 是 `Plan`、在 §3.2/§5.2 是 `PlanBatch`，第三个入口（`SpeakDirect` 的裸 `string`）**根本没有名字**，也没写它怎么切 `Segment`、`Kind` 给什么。`MaxNamedInBatch` 是"决定点不点名"还是"决定模板选哪条"也没说——两者的签名完全不同（`Utterance` 参数还是模板选择）。
3. **`SpeechLibrary`（§2.22）** —— 一栏里混了属性（`Usage`）、带 `out` 的读、以及**签名自相矛盾**的 `Put(text, isSentence, byte[])`：键要 `fingerprint + scope + text`，`scope` 要 `Kind`，可 `Put` 一个都没有（H2）；`TryRead` 命中还要刷新 `LastUsedTick`（副作用）；`Trim()` 出现在 janitor 的输入里却写在库那一侧（H5）；没有 `Contains`/`ListFiles`/`SaveIndex`（H7/H8/H13）。六个消费者各要一种能力，凑不出一组自洽签名。

> 次一档含糊：`ClipAssembler`（§2.16 把"跳过缺失片段"写成策略、`FromSentenceCache` 没定义何时为 `true` 的边界）、`WarmupScheduler`（"先查库"的入口不存在，H13）。这两个签得出来，但要先补一条边。

## §6 我认为草案漏了的东西（对照原设计）

1. **威胁到达即冲刷聚合批**（拼接设计 §3.5："窗口期内如果来了威胁类事件，立即 flush 当前 Batch 并优先播威胁"）。R2-04b 取消了窗口，这条规则没被替换，也没被声明作废；现在聚合批一律等 tick 末，威胁句与批内其他事件同 tick 出句后顺序由 `SpeechQueue` 决定，§2.13/§2.17 都没有承接。【推测：tick 末 ≈16 ms，听感损失很小，但这是规则消失，不是被替代】
2. **"殖民者加入殖民地 / 商人类型首次出现 ⇒ 立刻预合成片段"**（拼接设计 §4.4）。草案最快的名字预热路径是 `LibraryJanitor` 每 300 s 的 `RosterDelta`（§2.23/§2.24），新人入队后最多 5 分钟才有预热——与"预热从优化升为结构性必需"（拼接设计 §7）的目标相反。缺一条"入队即预热"的边。
3. **设置界面 §3 的"附加参数（JSON）"** 在 §3.9 只剩一个 `ExtraJson` 字段，没有 `Settings` 字段、没有 UI 行（实测代码也没有）——是"有类型无生产者"。
4. **设置界面 §2 的"分组可折叠"** 在草案 §2.27/§2.28 完全没提（实测当前 `Tab_SpokenCategories` 也不折叠）。
5. **设置界面 §4 的"预录音量"与"语速同时下发预录 pitch"**：R2/S5 已决定不引入预录，草案里没有一句"该字段退役"的交代（代码里也确实没有）。这类"原设计有、现已不需要"的项，草案只在 `BatchWindowMs`/`SpeechStyle` 两处做了，其他没做。
6. **`Trace` 编号与时间序的一致性**：§2.25 表里时间序第 4 是 `3.5`（组装）、第 5 是 `3`（入队），编号倒序。草案自己给了 `3a/3b` 的备选但没定——这是"拿去施工"会立刻变成两个实现分叉的小裂口。
7. **原设计 "22 类 × 产出者" 的账**（见 H21）：`BuildPlaceFailed`、`Rotten`、`Addiction`、`DiseaseSpread` 的产出点没有任何位置写明。
