# 22 类 · 来源绑定表（2026-10-17）

> 依据：`docs/取证-22类来源分布.md`（IL/XML 静态实测）。本文是"类别 → 唯一来源"的唯一真源，草案与实现都以它为准。
> 规则先于表：表是规则的实例，规则变了先改规则。

## 规则

1. **一个事件只在一个通道绑定。** "事件"= 原版发出那条通知的那一刻；同一件事在别的通道再出现时，按白名单**丢弃**，不比对、不合并。
2. **分类优先级：`incident` > `letter` > `message`。** 凡是"由 incident 发起"的类别，只在 incident 通道判定（那里拿得到 `IncidentDef` 与 `parms.target`，分类最准）；`letter`/`message` 只接**不是 incident 发起**的事件。
3. **通道内按 def 名 / 类别精确过滤**；不在白名单的落到 `Other*` 兜底。
4. **同一类别可以有多条绑定，但各条必须覆盖互斥的事件集合**（不同人群、不同阶段），不允许两条对同一件事先后各播一次。
5. 绑定数据是一张表：`类别 | 通道 | def 匹配 | 短语键`。加一类 = 加一行；调整归属 = 改一行。

## 由这张表带来的三个改动

1. **死亡补丁点回来了**：挂 `Pawn_HealthTracker.NotifyPlayerOfKilled`（一处），不再依赖 `letter`/`message` 两处分流。⇒ **补丁点 7 → 8**（见 `拷打-第2轮-已定` R2-15 需同步）。
2. **incident 成为主分类器**：9 个"两通道"类别里，7 个由 incident 判定后把 letter/message 的重复项按 def 丢弃。
3. **`letter` 通道的职责收窄**：只剩"非 incident 发起"的信件（死亡已移走），因此它不再需要按 `LetterDef` 猜类别之外的事。

## 待游戏确认（进 P 表）

- P9：袭击期间 `MessageRaidersBeginningAssault` 与第一封信的**实际间隔**——若它比信早，用户会先听到"正在进攻"再听到"袭击来了"，顺序要按实际调。
- P10：`IncidentParms.silent` 在真实玩法里的置位频率（静默袭击会让信不出现，但我们绑 incident 所以不受影响——需实测确认 incident 仍会触发）。
